# Aceso 药房采购与供应商收货入库闭环实施计划

更新时间：2026-08-07

状态：待评审（数据库集成测试已通过；浏览器/E2E 后置）

## 1. 背景、前置与目标

011 已完成福利院用药医嘱的药房接方和药房库存出库，012 已完成从已发药明细退回原仓库的可追溯退药
入库，013 定义了药房到护理站的申领、预留和双仓调拨。至此药房库存已有消耗、退回和内部转移的
去向，但仍没有一个受控来源来解释“药房库存为什么增加”。

库存模块已有 `materials`、`lots`、`stocks`、`stock_operations` 和 `stock_operation_details`：

- `lots` 已能记录 `batch_no`、生产日期、有效期、生产企业和供应商文本，但没有供应商主数据；
- `stocks` 支持包装单位数量、锁定量和总成本，且以仓库、物资、批次的部分唯一索引表达库存行；
- 通用 `confirmInbound` 以及 012 的 `confirmPackageInbound` 能写入库操作，但后者的来源语义固定为
  `PHARMACY_RETURN`，不能用于采购收货；
- Pharmacy 的 `V300` 仅包含发药、退药和申领表，没有采购订单或收货凭证。

014 的目标是完成药房面向供应商的最小供给闭环：

```text
药房建采购订单 → 药房审核订单 → 供应商送货
        → 药房按物资/批次/数量/实际成本验收
        → 一张 PHARMACY_PURCHASE_RECEIPT 库存 INBOUND 操作
        → 药房库存、成本、收货凭证和订单收货进度原子更新
```

本计划以“采购订单可分批收货”为最小业务能力。一次到货可为同一订单物资登记多个批次；分批是由
药房明确录入的到货事实，不是系统的自动多批次分配。

## 2. 范围与不包含项

### 2.1 必须实现

1. 药房可创建多明细采购订单，选择目标药房仓库、供应商名称和 `ACTIVE` 物资及订购包装数量；
2. 采购订单由服务端生成 ULID 和订单号，创建人、审核人、收货人及各时间均从认证身份和服务端时间
   得到，浏览器不能冒充操作人；
3. 订单经审核后不可修改物资、仓库、供应商或订购数量；可在零收货时取消，在有收货后可关闭未收余量；
4. 药房可对一张已审核或部分收货订单登记多次供应商到货；每次收货可为同一订单项录入一个或多个
   人工选择的批次、到货数量、生产日期、有效期、生产企业和实际单位成本；
5. 收货在一个数据库事务中校验订单余量、物资、批次事实和成本，必要时安全新建批次，写一张
   `INBOUND` 库存操作及全部操作明细，增加药房库存和总成本，持久化收货凭证与明细，并更新订单收货
   数量和状态；
6. 订单创建和每次收货均要求 `Idempotency-Key`。同一键、同一规范化请求返回原结果；同一键、不同
   请求返回 `409`；并发相同键不能以数据库唯一约束异常泄露为 `500`；
7. 提供创建、列表、详情、审核、取消、关闭余量和收货 API；列表响应、单条响应和错误响应符合项目
   统一约定，正确区分 `400`、`404`、`409`；
8. 在 Aceso 药房管理页提供采购订单、待审核、待收货和历史查询工作区；所有调用经
   `@pitchfork/shared/aceso`，页面不直接写 Inventory API；
9. 提供默认不访问数据库的单元/路由测试、编译和前端构建。迁移、并发、故障回滚和浏览器主线只在
   获授权的独立 `aceso_test` 中执行。

### 2.2 明确不在本期范围

- 供应商主数据、供应商联系人、资质、合同、询价、报价比较、请款、发票、应付账款、付款和财务记账；
- 预计价、合同价、税费、折扣、价格审批、收货差异财务处理或按供应商自动对账；本期仅在收货时记录
  实际入库单位成本；
- 自动补货、最低库存、库存预警、采购建议、自动下单、盘点、报损、召回和仓库主数据管理；
- `SPLIT` 拆零、单位换算、自动先进先出、自动批次分配，或由系统替用户补齐批次/有效期；
- 退药、发药、护理站申领、跨机构采购、跨产品 HTTP 调用、供应商退货、采购退货和反向出库；
- 电子签名、双人复核、角色权限重构、打印/PDF、条码扫描、附件上传或采购审批流配置；
- 对 011--013 的历史库存操作、药房单、批次或库存成本进行回填、重估、补建采购来源。

本期供应商是采购订单和批次中的不可变文本快照 `supplier_name`，不创建“供应商”表，也不把名称当作
未来主数据外键。需要供应商档案、编码和跨订单统计时另立计划迁移。

## 3. 领域规则、状态与数量语义

### 3.1 采购订单状态机

```text
DRAFT ──approve──> APPROVED ──receipt (部分)──> PARTIALLY_RECEIVED
  │                    │                                  │
  └──cancel───────────┴──────────────────────────────────> CANCELLED (仅零收货)
                       │                                  │
                       └──── receipt (全部) ──────────────> RECEIVED
                                                          │
                                     close remaining ────┘
                                                          ↓
                                                       CLOSED
```

- `DRAFT`：已创建、尚未审核；可以编辑或取消，不存在库存、收货或批次写入；
- `APPROVED`：药房已审核订单；订单业务字段冻结，可登记收货或在没有任何收货时取消；
- `PARTIALLY_RECEIVED`：至少一项已有成功收货，且仍有未收数量；只能继续收货或关闭剩余数量；
- `RECEIVED`：每个订单项的 `received_quantity` 均等于 `ordered_quantity`；是终态；
- `CLOSED`：已有部分收货但药房主动结束未收余量；已入库数量和收货凭证保持不变，是终态；
- `CANCELLED`：零收货订单被取消；没有收货凭证或库存操作，是终态。

规则：

- 只允许上述动作接口转换状态，通用更新接口不得把订单跳转为 `APPROVED`、`PARTIALLY_RECEIVED`、
  `RECEIVED`、`CLOSED` 或 `CANCELLED`；
- 审核、取消、关闭和收货均锁定订单和全部订单项。重复审核仅当已审核身份和请求语义完全相同时返回
  原结果；终态或不匹配的动作返回 `409`；
- `DRAFT` 的编辑请求必须完整替换订单业务字段和全部明细，并在一个事务中完成。`APPROVED` 后任何
  业务字段的编辑均返回 `409`，不允许以删除后重建覆盖审计；
- 每个订单项的 `ordered_quantity > 0`，`received_quantity >= 0`，且服务端始终保持
  `received_quantity <= ordered_quantity`；
- 每个收货明细的 `received_quantity > 0`，同一订单项历次收货总量不得超过订购量。超额到货不自动
  入库，返回 `409`；应先由业务另建或修订为新的采购订单；
- 一次收货至少包含一条明细；同一订单项可在同一收货凭证中出现多次，但每条必须是不同的人工录入
  批次组合。相同订单项和相同批号的重复行返回 `400`，防止前端重复提交导致语义模糊；
- 关闭需要非空原因，只终止剩余收货权利，不创建出/入库操作，不释放或改变已入库库存；
- 取消只能发生在 `DRAFT` 或无收货的 `APPROVED`。对有已确认收货的订单使用关闭，不能以取消掩盖
  已发生的库存事实。

### 3.2 物资、批次和成本

- 本期所有采购和收货明细固定 `unit = PACKAGE`；`SPLIT`、拆零数量和单位换算请求一律 `400`；
- 创建和收货均要求物资存在且 `status = ACTIVE`。已审核订单在收货前若物资已停用，收货返回 `409`
  且不写任何凭证或库存；
- 启用批次管控的物资，收货必须提交非空 `batch_no` 和晚于收货当天的 `expiry_date`；
  `production_date`、`manufacturer` 可为空。非批次物资必须不提交批号、日期或生产企业，最终
  `lot_id = null`；
- 对同一 `material_id + batch_no`，库存端口必须复用已有批次或在同一外层事务内创建新批次。若已有
  批次的生产日期、有效期、生产企业或供应商事实与本次到货矛盾，返回 `409`，不得覆盖旧批次字段或
  静默创建第二个同名批次；
- 客户端不能提交 `lot_id`、库存行 ID、库存操作 ID、库存操作明细 ID、库存锁定量、总成本、订单状态、
  已收数量或任何操作人。服务端仅接受批号事实、到货数量和实际 `unit_cost`；
- `unit_cost >= 0`，`total_cost = received_quantity * unit_cost` 由服务端以库存既有精度计算并持久化；
  免费赠品可使用零成本，负成本、客户端总金额或舍入差异请求返回 `400`；
- 成功收货只增加 `stocks.quantity` 和 `stocks.total_cost`，不改 `locked_quantity`。库存模块现有成本模型
  不在本期额外写入移动平均单价列；后续出库沿用其既有成本读取规则。

### 3.3 幂等、认证与并发

- `POST /purchase-orders` 和 `POST /purchase-orders/:id/receipts` 必须携带格式合法、非空且长度受限的
  `Idempotency-Key`；页面在一次未完成提交的重试中复用同一键；
- 创建订单的请求摘要至少规范化仓库、供应商名称和按稳定键排序后的物资/订购数量。收货摘要至少包含
  订单 ID、按订单项/批号/数量/日期/成本排序后的到货行；同键不同摘要返回 `409`；
- 先按幂等键查询不足以处理并发插入。唯一约束冲突后，服务必须在同一业务边界重新读取凭证，比较摘要，
  匹配时返回已持久化结果，不匹配时返回 `409`，不让 SQL 异常映射为 `500`；
- 收货事务按稳定顺序锁定订单、全部订单项、相关批次和目标库存。并发收货同一订单项时，第二个事务
  必须在锁后看到已收数量，不能超额；并发首次到货同一批次或同一库存行时，不得出现重复批次、重复
  库存行或丢失数量；
- 创建人、审核人、收货人、取消人、关闭人均来自认证 principal，时间均为服务端 `OffsetDateTime`。
  若当前 Aceso 挂载没有 principal，先沿既有认证链补齐，不可退回请求体 `operator` 自由文本。

## 4. 数据设计与迁移

在 Pharmacy lib 新增 `V303__create_purchase_receipt_tables.sql`。迁移仅使用 Pharmacy 的 `V300+` 号段，
不得触碰 Inventory 的 V200/V201、Healthcare 的 V500+ 或历史 V300--V302。014 新建独立表，不复用
`pharmacy_returns`、`pharmacy_requisitions` 的 `metadata` 来伪造采购事实。

### 4.1 `pharmacy_purchase_orders`

| 列 | 规则与用途 |
| --- | --- |
| `id` | 服务端生成的 26 位 ULID 主键 |
| `purchase_order_no` | 服务端生成的业务单号，唯一；客户端不传入 |
| `warehouse` | 目标药房库存仓库；订单期内不可为空，审核后不可变 |
| `supplier_name` | 供应商文本快照，必填；不是供应商主数据外键 |
| `status` | `DRAFT`、`APPROVED`、`PARTIALLY_RECEIVED`、`RECEIVED`、`CLOSED`、`CANCELLED` |
| `requester_id`、`approved_by`、`cancelled_by`、`closed_by` | 从认证 principal 保存的审计身份 |
| `approved_at`、`cancelled_at`、`closed_at`、`created_at`、`updated_at` | 服务端写入的审计时间 |
| `cancel_reason`、`close_reason` | 取消/关闭时必填的明确原因，不放进自由 JSONB |
| `idempotency_key`、`request_fingerprint` | 创建订单的幂等身份和规范化摘要 |

为非空 `idempotency_key` 建立局部唯一索引；建立 `(status, created_at DESC)`、`warehouse`、
`supplier_name` 查询索引。不要在迁移中推测、回填或关联任何既有药房单。

### 4.2 `pharmacy_purchase_order_items`

| 列 | 规则与用途 |
| --- | --- |
| `id`、`purchase_order_id` | ULID 主键与订单所属关系 |
| `material_id` | 采购物资 ID；跨模块弱关联，由服务端经库存端口验证 |
| `ordered_quantity` | 用户确认的包装订购数量，精度为 `NUMERIC(15,4)` 且大于零 |
| `received_quantity` | 服务端在确认收货事务内累计；初始零，不能小于零或大于订购量 |
| `unit` | 014 新记录恒为 `PACKAGE` |

同一采购订单不能重复 `material_id`，用服务校验和 `(purchase_order_id, material_id)` 唯一约束共同保证。
订单项不保存预计价、税费、折扣或客户端可写状态。

### 4.3 `pharmacy_purchase_receipts` 与明细

`pharmacy_purchase_receipts` 表示一次已确认的供应商到货；不设可绕过库存事务的“收货草稿”。它包含：

| 列 | 规则与用途 |
| --- | --- |
| `id`、`receipt_no` | 服务端生成 ULID 和唯一收货单号 |
| `purchase_order_id` | 所属采购订单，服务端从路径确定 |
| `warehouse`、`supplier_name` | 从已锁定订单复制的不可变快照 |
| `received_by`、`received_at`、`created_at` | 服务端审计事实 |
| `stock_operation_id` | 这一次收货创建的唯一 `INBOUND` 库存操作单 ID |
| `idempotency_key`、`request_fingerprint` | 本次收货的幂等身份和规范化摘要 |

`pharmacy_purchase_receipt_items` 表示本次实际到货的物资/批次/成本事实，至少包含：

| 列 | 规则与用途 |
| --- | --- |
| `id`、`receipt_id` | 收货明细 ULID 与所属收货凭证 |
| `purchase_order_item_id` | 精确关联采购订单项，禁止跨订单项 |
| `material_id` | 服务端从订单项复制，不能由客户端改写 |
| `lot_id` | 库存端口解析或创建后的批次 ID；非批次物资为 `NULL` |
| `received_quantity`、`unit` | 实际包装到货量和固定 `PACKAGE` 单位 |
| `unit_cost`、`total_cost` | 服务端确认的实际成本与计算金额 |
| `stock_operation_detail_id` | 对应此次 `INBOUND` 操作明细 ID，确认后必填 |

为收货表建立非空 `idempotency_key` 局部唯一索引、`purchase_order_id` 和 `(received_at DESC)` 索引；为
收货明细建立 `receipt_id`、`purchase_order_item_id` 和 `stock_operation_detail_id` 查询索引。对每张收货凭证
建立 `(receipt_id, purchase_order_item_id, lot_id)` 的批次组合唯一约束或等效服务校验，以防相同行重复。

`lots` 是 Inventory 的权威批次表。014 不在 Pharmacy 重复保存可被伪造的批号、日期、生产企业和供应商列；
这些由库存端口验证/创建并以 `lot_id` 可追溯。收货详情 API 需要展示批次文本时，由库存的只读查询能力
返回已解析批次摘要，不能让 Pharmacy 直接写 Inventory 表。

### 4.4 库存采购入库端口

不能把浏览器直接调用通用库存入库接口，也不能复用 012 的 `InventoryInboundPort`：两者无法同时保证
采购订单、收货凭证、库存操作和订单进度的同一外层事务，也会错误使用退药来源元数据。014 在 Pharmacy
定义专用内部端口，例如：

```text
PurchaseReceiptInventoryPort
└── confirmPackagePurchaseReceipt(client, command)
    → StockService 使用调用方 SqlConnection 完成批量采购入库
```

端口命令由已锁定的采购订单与收货明细构造，包含仓库、供应商快照、收货 ID/单号、订单 ID/单号、
认证收货人以及每条服务端生成的 receipt item ID、物资、批号事实、数量和实际成本。端口不接受浏览器
传来的库存 ID、批次 ID、库存操作 ID、锁定量或订单状态。

端口必须：

1. 按稳定键锁定/解析所有物资、批次和目标库存，验证物资仍为 `ACTIVE`、单位为 `PACKAGE`、数量与成本
   合法，并按本计划的批次规则创建或重读批次；
2. 使用现有部分唯一索引兼容的冲突处理安全创建或合并目标库存行，不采用“先 SELECT、没有再裸 INSERT”
   的竞争写法；
3. 只写**一张** `INBOUND`、`CONFIRMED` 的 `stock_operations`，每个收货明细写一条
   `stock_operation_details`，并返回每条 receipt item ID 对应的 `lot_id`、库存操作明细 ID、单位成本和
   总成本；
4. 对每个目标库存执行 `quantity += received_quantity` 与
   `total_cost += received_quantity * unit_cost`，不改变 `locked_quantity`；
5. 在库存操作 `metadata` 写入 `source = PHARMACY_PURCHASE_RECEIPT`、`purchase_order_id`、
   `purchase_order_no`、`purchase_receipt_id`、`receipt_no`、`supplier_name`、仓库和收货人；
6. 自身不启动事务，不吞掉任何失败，始终复用 Pharmacy 外层 `SqlConnection`。任一批次、库存、操作或
   明细写入失败时，外层事务必须回滚收货凭证、订单项收货量、订单状态以及全部库存变化。

`apps/aceso/Main.kt` 仅负责把 `StockService` 的同连接适配器注入 `PurchaseReceiptInventoryPort`。Pharmacy
不得直接依赖或写入 Inventory 的 jOOQ 表；Inventory 也不得直接写 Pharmacy 采购表。

## 5. API 契约

以下路径均位于 `/crate-api/pharmacy/v1`。列表一律返回：

```json
{ "records": [], "meta": { "total": 0 } }
```

单条响应直接返回对象，错误一律为：

```json
{ "error": "<message>" }
```

所有 ID 为 26 位 Crockford Base32 ULID。路径和 JSON 字段采用现有 API 的小写、snake_case 约定。

### 5.1 创建、编辑与查询采购订单

```text
POST /purchase-orders
PUT  /purchase-orders/:id
GET  /purchase-orders?warehouse=&supplier_name=&status=&limit=&offset=
GET  /purchase-orders/:id
```

`POST` 必须带 `Idempotency-Key`。创建与仅限 `DRAFT` 的编辑请求只允许：

```json
{
  "warehouse": "药房西药库",
  "supplier_name": "华康医药配送",
  "items": [
    { "material_id": "01J...", "ordered_quantity": 100 },
    { "material_id": "01J...", "ordered_quantity": 40 }
  ]
}
```

服务端规则：

- `warehouse`、`supplier_name`、非空 `items`、每项 `material_id` 和正 `ordered_quantity` 必填；去除首尾
  空白后的仓库和供应商名必须非空；
- 同一订单不得重复 `material_id`；所有物资必须存在并为 `ACTIVE`；
- 创建在一笔事务内生成订单和全部明细，初始 `DRAFT`、`received_quantity = 0`、`unit = PACKAGE`；任何
  明细无效时不得留下订单单头；
- 创建/编辑不接受 `lot_id`、批次、有效期、成本、库存、收货量、状态、单号、操作人、`metadata` 或
  任何库存操作关联字段；
- `PUT` 只允许 `DRAFT`，完整替换仓库、供应商和明细；`APPROVED` 以后返回 `409`；
- 查询不锁库存、不改变状态。详情必须返回订单审计字段、每项订购/已收/剩余量、已收货凭证摘要以及每条
  收货明细的批次摘要、成本、库存操作单和明细关联。

### 5.2 审核、取消与关闭

```text
PUT /purchase-orders/:id/approve
PUT /purchase-orders/:id/cancel
PUT /purchase-orders/:id/close
```

审核请求为空对象。取消与关闭请求为：

```json
{ "reason": "供应商无法继续供货" }
```

规则：

- `approve` 仅允许 `DRAFT`，锁定订单和全部订单项，写入审核人和审核时间后转为 `APPROVED`；
- `cancel` 仅允许 `DRAFT` 或零收货 `APPROVED`，理由必填，写取消审计后转为 `CANCELLED`；不创建库存
  操作；
- `close` 仅允许 `APPROVED` 或 `PARTIALLY_RECEIVED` 且仍有未收数量，理由必填，写关闭审计后转为
  `CLOSED`；不回滚任何已确认收货或库存；
- 请求体错误、缺少理由、未知字段或非法 ID 返回 `400`；订单不存在返回 `404`；非法状态、已有收货后
  取消、无剩余量关闭或并发冲突返回 `409`；
- 已完成的相同合法幂等动作可读取返回既有订单；不得重复写审计字段或改变库存；业务冲突和端口失败不得
  泄露 SQL、堆栈或内部异常信息。

### 5.3 供应商收货

```text
POST /purchase-orders/:id/receipts
GET  /purchase-receipts/:id
```

收货 `POST` 必须带 `Idempotency-Key`。请求只允许到货事实：

```json
{
  "items": [
    {
      "purchase_order_item_id": "01J...",
      "received_quantity": 60,
      "batch_no": "A240801",
      "production_date": "2026-04-01",
      "expiry_date": "2028-03-31",
      "manufacturer": "某制药厂",
      "unit_cost": 12.5
    },
    {
      "purchase_order_item_id": "01J...",
      "received_quantity": 40,
      "batch_no": "A240802",
      "production_date": "2026-05-01",
      "expiry_date": "2028-04-30",
      "manufacturer": "某制药厂",
      "unit_cost": 12.5
    }
  ]
}
```

收货规则：

- 仅允许订单状态为 `APPROVED` 或 `PARTIALLY_RECEIVED`；服务端锁订单和全部订单项，校验每条
  `purchase_order_item_id` 属于路径订单；
- 所有数量必须为正、成本非负；客户不得传 `supplier_name`、`warehouse`、`material_id`、`lot_id`、
  `total_cost`、`stock_operation_*`、状态或操作人；物资、仓库、供应商均从已锁定订单/订单项导出；
- 批次物资要求批号和未来有效期，非批次物资要求所有批次字段为 `null`/缺失；批次与现有事实冲突、
  物资停用、订单项不属于订单、超额收货、订单关闭/取消/完成均返回 `409`；
- 服务端生成收货单与收货明细 ID，调用一次专用批量采购入库端口；端口成功返回后写入每条 `lot_id`、
  `stock_operation_detail_id`、成本，累计订单项 `received_quantity`；
- 若所有订单项都已足额收货，订单置为 `RECEIVED`；否则置为 `PARTIALLY_RECEIVED`；响应 `201` 返回完整
  收货凭证和更新后的订单摘要；
- 同一幂等键、同一规范化收货请求返回原收货凭证 `200`；同键不同请求返回 `409`；同一键并发创建不重复
  增加库存、不重复创建 `INBOUND` 操作。

`GET /purchase-receipts/:id` 返回收货单、订单/仓库/供应商快照、收货人/时间、库存操作单 ID，以及每项
订单关联、物资、批次摘要、数量、单位成本、总成本和库存操作明细 ID。它不触发入库或状态改变。

## 6. 后端实施设计

### 6.1 模块职责和事务边界

```text
PurchaseOrderRoutes
    └── 认证身份 + 严格 JSON/HTTP 映射
        └── PurchaseOrderService（Pharmacy 外层事务）
            ├── 订单/订单项状态机、幂等、收货凭证、收货进度回写
            └── PurchaseReceiptInventoryPort（同一 SqlConnection）
                └── StockService 批次解析/创建、批量采购入库、库存操作和库存更新
```

- 新增 `PurchaseOrderService.kt`、`PurchaseOrderRoutes.kt` 和专用异常/请求校验，使用 Pharmacy 生成的
  jOOQ 表与既有 `DatabaseConfig.sql/tuple` 约定；不要复制 013 以前的“普通 CRUD 只改状态”路径；
- `create`、`updateDraft`、`approve`、`cancel`、`close` 和 `receive` 由 `pool.withTransaction` 开启唯一的
  Pharmacy 外层事务。只读列表与详情可使用 Pool；
- `receive` 先处理幂等重放，再锁订单及所有订单项，验证状态/余量，生成收货记录 ID，调用一次库存端口，
  回写所有明细关联和累计数量，最后更新订单状态；任一步失败均使 Future 失败并回滚；
- 库存端口测试桩必须断言收到的是外层事务 `SqlConnection` 而不是 Pool。端口 Future 失败不得被转换成
  成功响应或被吞掉后继续写收货单；
- `PharmacyRoutes.kt` 注册新路由和错误映射，Aceso `Main.kt` 注入端口。CORS 变更必须在 Aceso 共同配置处
  允许 `Idempotency-Key`，并使用真实浏览器预检回归覆盖；
- 将新迁移加入 Pharmacy `jooq-config.xml` 所在数据库生成流程。只有在获授权 `aceso_test` 成功应用 V303
  后运行 `:libs:pharmacy:generateJooq`，仅提交真实生成的 Pharmacy 表、记录和键/索引源；不提交
  `build/tmp` 渲染物。

### 6.2 路由与输入安全

- 路由层仅负责解析认证 principal、路径 ID、查询分页和白名单 JSON；服务层负责所有状态、数量、批次、
  幂等与库存业务判断；
- 采用既有认证失败语义。没有有效 Bearer principal 的写请求在进入服务前拒绝，不能让用户标识为空或
  来自请求体；
- 对创建、编辑和收货使用显式允许字段集合；拒绝未知字段，避免浏览器以额外成本、状态、ID 或
  `metadata` 悄悄扩大持久化面；
- 错误映射统一为 `400`（格式/字段/非正数量/非法成本）、`404`（订单、订单项或收货凭证不存在）、
  `409`（状态、余量、物资、批次、并发或幂等冲突）。未处理异常使用安全通用错误，绝不把 PostgreSQL
  唯一键、SQL 或堆栈返回给客户端。

### 6.3 库存端口实现约束

- 在 `PharmacyPorts.kt` 定义采购专用命令/结果和 `PurchaseReceiptInventoryPort`；在 `StockService` 定义
  对应的内部 `PurchaseReceiptCommand`，不要把采购字段塞进退药 `PackageInboundCommand.note`；
- 对同一批次的并发创建，先尝试受唯一约束保护的写入，再冲突重读并比对批次不变量；对于目标库存行，
  使用与部分唯一索引兼容的 upsert/冲突重读和再次锁定；
- 每次收货仅创建一张 `stock_operations`，不能循环调用已有的单项 `confirmPackageInbound` 形成多张散乱
  入库单；每条收货明细必须可稳定映射回一条库存操作明细；
- 库存操作元数据是可追溯辅助信息，不代替 Pharmacy 收货凭证和其明细外键。任何查询关联必须以
  `purchase_receipts.stock_operation_id`、`purchase_receipt_items.stock_operation_detail_id` 为主；
- 不新增跨 schema 外键。模块通过同进程端口和同一事务保持一致性，避免 Pharmacy/Inventory 的双向表依赖。

## 9. 验收口径

### 9.1 后端、数据与并发

- V303 只在 Pharmacy 号段新建采购/收货事实表、约束和索引，不改写历史 Pharmacy 或 Inventory 数据；
- 创建订单只接受仓库、供应商文本、`ACTIVE material_id` 和正订购量；订单和明细原子创建，同一物资不能
  重复；客户端状态、成本、库存、批次、收货量和操作人永不被持久化；
- 同一创建幂等键重试只得到一张订单，同键不同内容为 `409`；并发相同键不返回裸唯一键 `500`；
- 审核后订单字段被冻结；零收货订单能取消，有部分收货订单只能关闭余量；已入库收货绝不被取消或覆盖；
- 收货只允许已审核或部分收货订单，所有到货累计量不超过订单量；足额后为 `RECEIVED`，部分后为
  `PARTIALLY_RECEIVED`，关闭后不能再收货；
- 批次物资只能用有效的批号和未来有效期收货，非批次物资不生成批次；相同物资/批号并发首次到货不会
  产生重复批次或库存行，批次事实冲突不会被静默覆盖；
- 每次成功收货恰有一张 `INBOUND` 库存操作和每条到货对应的一条库存操作明细，操作元数据、收货头和
  收货明细均能追溯订单、供应商、仓库和收货人；
- 成功收货后目标库存数量增加、总成本增加、锁定量不变；收货明细的数量/成本和库存操作明细精确对应；
- 库存写入、批次创建、明细写入、余量校验、幂等竞争或状态竞争任一失败时，订单收货量、订单状态、
  收货凭证、批次、库存、库存操作和明细均不留下半成品；
- 错误响应按 `400`/`404`/`409` 映射且不泄露 SQL、堆栈或内部端口异常；空列表仍含 `records` 和 `meta.total`。

### 9.2 页面手测

1. 使用已认证药房账号选择药房仓库、供应商文本和两个 `ACTIVE` 物资，创建采购订单；确认详情为
   `DRAFT`，申请人和时间由服务端显示；
2. 审核订单后尝试编辑仓库、供应商和订购量，确认得到清晰冲突且页面未修改已审核订单；
3. 对第一订单为同一订单项录入两个不同批号的部分到货，检查批次物资要求有效期、页面显示本次与剩余
   数量，并在成功后显示 `PARTIALLY_RECEIVED`；
4. 检查收货详情包含供应商、仓库、收货人/时间、两个批次、实际成本、唯一库存入库操作和每项操作明细；
5. 再次收齐余量，检查订单变为 `RECEIVED`，库存数量/成本正确且重复点击确认不会重复入库；
6. 对另一张零收货订单取消；对第三张已部分收货订单填写原因关闭，确认没有额外库存操作且不再显示可收货；
7. 尝试超额收货、停用物资、过期/矛盾批次、已关闭订单和同一键不同收货，确认错误清晰并保留可编辑
   输入，数据没有部分改变；

## 10. 风险与控制

| 风险 | 影响 | 控制 |
| --- | --- | --- |
| 013 未修复即扩展库存流程 | 缺陷和事务语义交叉，无法定位责任 | 014 的实施门槛要求 013 修复、测试和评审完成 |
| 复用退药入库端口 | 收货被标记为退药，审计来源失真 | 新建 `PurchaseReceiptInventoryPort` 和 `PHARMACY_PURCHASE_RECEIPT` 元数据 |
| 浏览器直接写库存 | 可伪造成本、库存行或操作关联 | Shared API 只调用 Pharmacy，库存命令由锁定订单构造 |
| 未锁订单项即累计收货量 | 并发到货超额入库 | 事务锁订单和全部订单项，稳定排序并验证余量 |
| 同一批次/库存首次并发创建 | 唯一冲突、重复行或丢失数量 | 以唯一索引兼容的写入、冲突重读、事实比对和再次锁定 |
| 只读幂等键后裸插入 | 并发相同请求以 500 失败或重复库存 | 唯一约束冲突恢复、摘要对比和返回原凭证 |
| 允许收货后取消订单 | 已增加库存却丢失来源审计 | 零收货才可取消；部分收货使用只关闭余量的 `CLOSED` |
| 将批次事实只放 metadata | 无法可靠核验或审计 | Inventory `lots` 为权威，收货明细保存 `lot_id` 和库存明细关联 |
| 把预计/财务价格混入收货成本 | 形成错误财务口径 | 014 仅接受实际入库单位成本，不实现报价、税费或付款 |
| CORS 未允许幂等头 | UI 的 POST 预检失败 | 013 修复作为前置，014 保留浏览器预检回归项 |
