## 1. 背景与目标

QA 第 8 轮三条，**均为文案/体验，非功能缺陷**：

1. 🟡 **押金超退错误信息是英文**：`refund exceeds deposit balance: available 2500.00, requested 9999.0`。其他权限错误已中文化，这条漏了。
2. 🟡 **重复建饮食档案返回 500 而非 409**：同一长者已有启用档案，再建触发唯一约束 → `500 {"error":"internal error"}`。UI 的「新建」下拉已排除已建档长者，但接口层没兜住。
3. 🟡 **医嘱/诊断/病程的署名标签写死「医生」**：`nurse01` 在诊断弹窗里看到「医生（只读，服务端按当前登录用户署名）· 护理员一号（当前登录用户）」。接口已拦住代签，但文案误导。

目标：三条全部按「用户看得懂、状态码正确、有回归护栏」收口，并**补上导致第 2 条漏网的测试盲区**。

## 3. 设计决策

### D1 — 押金超退：服务端出中文，状态码保持 400，金额统一两位小数

- 文案逐字冻结：**`退押金额超出押金余额（可用 <balance>，本次申请 <amount>）`**，两个金额均按**两位小数**渲染（`setScale(2, RoundingMode.HALF_UP)`，与既有 `amount must have at most 2 decimal places` 的口径一致）。
- 在**服务端**改，不在前端映射：消息含计算出的金额，前端映射需要解析数字，易漂移；且服务端是唯一权威（同 043 对 403 的处理结论）。
- 状态码仍 `400`（业务规则校验，不是冲突），**不改成 409**：调用方传了一个超过余额的金额，是请求非法，不是资源状态冲突。

### D2 — 膳食建档冲突：先复现定性，再按分支修，并补 DB-free 护栏

**强制第一步（复现）**：在授权、可销毁的测试库上复现，从服务端日志取 `respondError` 打出的异常类名与 `sqlState`（日志已含）。据此走以下分支：

| 分支 | 现象 | 修法 |
| --- | --- | --- |
| A | 异常是**被包裹**的 `PgException`（cause 链里才是 23505） | 引入**共享判定助手**（见下），遍历 cause 链 |
| B | 异常是 `PgException` 但 `sqlState != "23505"`（如约束名/其它 code） | 助手同时按**约束名** `uq_dining_diet_profiles_active_patient` 兜底 |
| C | 异常就是 `PgException` 且 `sqlState == "23505"`（说明测试环境构建早于映射） | 记录证据，本分支**不改代码**；仅补 DB-free 护栏防回归 |

**共享判定助手（D2 的工程决策）**：把「唯一约束冲突判定」收敛为一个纯函数，放在 `libs/database`（dining/healthcare 均已依赖）：

```kotlin
/** 唯一约束冲突判定：遍历 cause 链匹配 sqlState=23505，或命中给定约束名。 */
fun isUniqueViolation(error: Throwable, constraintNames: Set<String> = emptySet()): Boolean
```

- **本轮采纳方**：`DietProfileService`（2 处）、`WeeklyMenuService`（2 处）、`RosterService`（既有 2 处 `DiningConflictException` 分支）。dining 四处同源，一次收口。
- **不改**：`HealthcareService`/`FeeItemService`/`BillService` 的既有判定（各自带业务特定约束名与文案），避免把本轮 diff 扩到 82K 的 `BillService`；记入 §6 残项（后续统一时再切助手）。
- **新增 DB-free 路由级测试**（关键，见 §5.4）：用 mockk `Pool` 让 INSERT 失败为 `PgException("23505")`，断言 HTTP **409** + 中文体；再补一条「cause 链包裹」用例，锁分支 A。

### D3 — 署名标签改中性

| 位置 | 改后 label |
| --- | --- |
| 医嘱（`id="order-doctor"`） | `开嘱人（只读，服务端按当前登录用户署名）` |
| 诊断（`id="diagnosis-physician"`） | `记录人（只读，服务端按当前登录用户署名）` |
| 病程（`id="note-physician"`） | `记录人（只读，服务端按当前登录用户署名）` |

- 「开嘱人」不带岗位（医生/护士皆可读），且比「医生」精确；诊断/病程用「记录人」与自己的字段名（`physician` 存的是署名主体）语义一致。
- 备选：三处统一 `操作人`（与药房 `OperatorPicker` 默认 label 一致）。**改法成本相同（三行）**，见 §10 备注。
- 只改 label，**不动** `allowDelegation={false}`、不动 `id`（自动化用例可能锚定 `id`）。

### D4 — 同类业务规则文案一并中文化（限「状态冲突」三条）

`DepositOffsetService.kt:170`、`PaymentService.kt:144`、`PaymentService.kt:149` 三条**状态竞态**消息同属收费链路、UI 挡不住、且会原样透出英文。本轮一并中文化：

| 原（英文） | 改后（中文，逐字冻结） |
| --- | --- |
| `encounter billing is already settled` | `本次入住的账单已结算，不能重复结算` |
| `encounter billing is settled, cannot pay` | `本次入住的账单已结算，无法继续缴费` |
| `bill status is not ${STATUS_PENDING}, cannot pay` | `账单当前状态不允许缴费（仅待缴费状态可缴）` |

- **不做**纯入参校验类英文消息（`amount is required` / `method must be one of: …` 等）——那些由 UI 前置校验挡住，属于 §6 残项的全量清扫范围。

### D5 — 不做全量英文业务文案清扫（本轮）

实测英文消息规模：healthcare 312、dining 41、pharmacy 79、nursing 59、inventories 50（`IllegalArgumentException("English…")` 计数）≈ **540 处**。全量清扫需按「是否可达用户」逐条分类，是大工程，另立项；本轮只做 §2.1 报告的 1 条 + D4 的 3 条。

## 4. 接口契约（冻结）

### 4.1 押金超退（`POST /healthcare/v1/encounters/:id/deposits/refunds`）

```text
超退 → 400 {"error":"退押金额超出押金余额（可用 2500.00，本次申请 9999.00）"}
未超 → 200/201（行为不变）
```

金额一律两位小数，`，` 为全角逗号、`（）` 为全角括号（与仓库既有中文文案口径一致）。

### 4.2 膳食建档冲突（`POST /dining/v1/diet-profiles`）

```text
同一长者已有「启用」档案 → 409 {"error":"该长者已有启用的饮食档案"}
重新启用撞部分唯一索引 → 409 {"error":"该长者已有启用的饮食档案"}   （PATCH /diet-profiles/:id/status）
其它失败 → 既有语义不变（400/404/500）
```

**403 优先级不变**：未授权的调用仍先 `403`（046/047 的门禁在业务逻辑之前），不得因本次改动变成 400/409。

### 4.3 收费链路状态冲突

| 端点 | 改后 409/400 文案 |
| --- | --- |
| `POST /healthcare/v1/encounters/:id/billing-settlement`（重复结算） | `本次入住的账单已结算，不能重复结算` |
| `POST /healthcare/v1/bills/:id/payments`（已结算） | `本次入住的账单已结算，无法继续缴费` |
| `POST /healthcare/v1/bills/:id/payments`（状态不符） | `账单当前状态不允许缴费（仅待缴费状态可缴）` |

### 4.4 前端署名标签

三处 `label` 按 D3；`OperatorPicker` 的只读分支渲染不变（`<display_name>（当前登录用户）`）。

## 5. 验收口径

1. **押金超退中文**：押金余额 2500.00 时退 9999.00 → `400`，`error` 逐字等于 `退押金额超出押金余额（可用 2500.00，本次申请 9999.00）`；无英文残留；库内 `deposit_records` 无新增（回读断言）。
2. **金额小数位**：余额 500 退 500.01 → `可用 500.00，本次申请 500.01`（两位）；余额为整数、申请为整数时也渲染两位（如 `可用 1000.00，本次申请 1000.00` 不会被触发，用 1000.01 验证）。
3. **未超退不回归**：恰好等于余额的退费仍成功（`amount == balance` 不是超退）。
4. **膳食重复建档 409（DB-free 护栏）**：mock 池让 INSERT 失败为 `PgException("23505")` → HTTP `409` + `{"error":"该长者已有启用的饮食档案"}`；**再补一条 cause 链包裹用例**（`VertxException(cause = PgException)`）→ 同 409。
5. **膳食重复建档 409（真库）**：授权环境同一长者二次建档 → `409` + 中文；`dining_diet_profiles` 只增 1 行；`PATCH …/status` 重新启用撞索引同样 409。
6. **权限优先**：无 `dining:manage` 的账号 → 仍 `403`（不是 409）；有码但无唯一冲突 → 进入业务逻辑。
7. **收费链路文案**：重复结算 / 已结算缴费 / 状态不符缴费三条各返回对应中文（真库或 mock 池，按可达性选其一并记录方法）。
8. **署名标签**：三处 label 不再出现「医生」；`nurse01` 视角下诊断弹窗显示「记录人（只读，服务端按当前登录用户署名）· 护理员一号（当前登录用户）」；提交体仍不含该字段、服务端仍拒绝代签（046 行为不变）。
9. **回归**：
   - `./gradlew :apps:aceso:test`、`:libs:dining:test`、`:libs:healthcare:test`、`:libs:database:test`
   - `pnpm --filter @pitchfork/aceso build`、`pnpm test:unit:aceso`
   - `DepositServiceTest` 的英文断言已同步为中文断言（否则测试失败即为漏改）。
10. **默认验证不访问数据库**：新增的膳食 409 用例必须是 DB-free（mockk Pool），否则等于没加护栏。
