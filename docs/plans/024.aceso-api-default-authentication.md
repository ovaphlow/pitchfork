### 背景：整站 API 默认无认证

调度者在 2026-09-29 核实（代码审计 + 对运行中实例的实测，双向一致）：

**实测（未携带任何凭证、无 cookie、无 Authorization 头）**：

| 探测 | 结果 |
|---|---|
| `GET /crate-api/healthcare/v1/patients` | **200**，返回真实长者数据 |
| `GET /crate-api/healthcare/v1/encounters` | **200**，返回真实入住数据 |
| `GET /crate-api/inventories/v1/materials` | **200**，返回物资数据 |
| `GET /crate-api/dining/v1/dishes`、`GET /crate-api/pharmacy/v1/dispenses` | **200** |
| `GET /crate-api/nursing/v1/timeline?encounter_id=x` | **400**（已进入业务校验，说明未经认证就执行了业务逻辑） |
| `GET /crate-api/healthcare/v1/payments/summary` | 401（少数确实挂了认证的） |
| `GET /crate-api/healthcare/v1/nonexistent-xyz` | 404（对照组：证明 401 确实意味着路由存在） |

**代码审计（按 `(verb, path)` 去重，排除 `/health`）**：

```text
Aceso(8422) 完全无认证路由：GET 88 条 + 写 67 条 = 155 条

healthcare   57 条（GET 44 / 写 13）
nursing      39 条（GET 17 / 写 22）   ← Assessment/Plan/ServicePeriod/Task/TaskExecution/VisitSchedule 全裸
pharmacy     22 条（GET 7  / 写 15）   ← Dispense/Requisition/Return 全裸
dining       27 条（GET 11 / 写 16）
inventories  10 条（GET 5  / 写 5）
```

**根因**：各模块的 `create(...)` 只注册了 `router.route().handler(BodyHandler.create())`，**没有任何 catch-all 认证中间件**；认证是**逐路由显式挂的**，而挂载只覆盖了部分写路由。`apps/aceso/Main.kt` 的 `apiRouter` / `mainRouter` 对 `/crate-api/*` 也没有兜底认证。逐路由挂载天然会漏——实测漏了 155 条。

**最危险的 67 条写接口**（不完全列举）：`PATCH /encounters/:id/death`、`PATCH /encounters/:id/discharge`（任何人可把长者标记为去世/办理离院）、`POST /patients`、`PUT /patients/:id`、`POST /encounters/:id/orders`、`/diagnoses`、`/progress-notes`、`/nursing-records`、药房发药全链路（`confirm`/`cancel`/`review`/`from-medical-order`）、膳食排餐（`rosters/generate`、`weekly-menus`）、库存 `POST /operations/inbound`、`MaterialRoutes` 的增删改。

另有 `DiningRoutes.create(...)` 接收了认证中间件参数却**从未使用**——说明"逐路由挂载"这个机制本身已经失效。

### 产品决策

1. **改为默认拒绝（fail closed）**：在应用编排层（`apps/aceso`）给 `/crate-api/*` 挂**总闸认证中间件**，未在白名单内的**一切方法与路径**都必须先通过 IdP 会话校验。**新路由默认受保护**，不再依赖逐路由挂载。
2. **白名单只放行三类**：① 各模块 `/health`；② Identity 代理子树（登录/会话本身，否则无法登录）；③ CORS 预检 `OPTIONS`。
3. **`/crate-api/shared/v1/*`（Nexus 代理）默认纳入认证**（fail closed）。若验证发现确有匿名依赖，再以**显式、带注释的例外**加入白名单——不允许默认敞开。
4. **保留既有逐路由认证**（纵深防御）：总闸生效后它们是冗余的，但不同 app 挂载同一 lib 时仍有价值；不删除、不改写。
5. **不改任何业务路由的实现、路径、响应形状**，不改各模块 `create(...)` 签名。
6. **回归护栏**：新增测试断言"未认证访问任意受保护路由 → 401"，且断言总闸中间件在模块子路由**之前**注册，防止未来有人在前面插入绕过路径。

## 目标与范围

### 必须实现

1. 在 `apps/aceso/Main.kt` 的 `apiRouter` 上，**在挂载任何模块子路由之前**注册总闸中间件：
   - `OPTIONS` 直接 `ctx.next()`（CORS 预检不能被拦）；
   - 路径命中白名单 → `ctx.next()`；
   - 其余 → 交给 `idpSessionAuthHandler(vertx, idpBaseUrl)`；未通过时不进入任何业务处理器。
2. 白名单以**单一常量/函数**表达并有注释说明放行理由，至少包含：`/<module>/v1/health`（按已挂载模块逐一列出或按 `*/v1/health` 匹配，二者择一并在代码注释里说明取舍）、Identity 代理子树。
3. 未认证时的响应形状与既有认证一致：`401` + `{"error":"authentication required"}`（复用既有 `idpSessionAuthHandler` 的行为，不另造错误结构）。
4. **回归测试**（非数据库）：
   - 对**每个已挂载模块**各取至少一条读路由与一条写路由，断言无凭证时返回 401；
   - 断言 `/health` 仍 200；
   - 断言 `OPTIONS` 预检不被拦（返回 CORS 头而非 401）；
   - 断言总闸在子路由之前注册（例如用一条"若被绕过就会命中业务处理器"的构造验证）。
5. **实测验证（对运行中实例）**：未认证探测矩阵——每个模块的读/写各一条必须 401，`/health` 必须 200，登录链路必须可用；并把矩阵命令与输出记入实施记录。
6. **浏览器验证（用户手测）**：登录后逐页走查主要页面（长者档案/入住管理/照护管理/药房/库存/膳食/养老收费/费用项目），确认会话 cookie 被接受、页面数据正常加载、401 不再误伤已登录用户。

### 明确不在本期范围

- 不改业务路由实现、路径、响应字段、状态码语义（除新增的 401 之外）。
- 不重构各模块的 `create(...)` 签名，不删除既有逐路由认证。
- 不引入 RBAC/权限点（"谁能看哪条"），本期只解决"必须登录"。
- 不改 `apps/trainova` 或其它 app；不在本次处理它们的同类暴露面（已知存在，另立计划）。
- 不做 CSRF、限流、审计日志、越权（IDOR）加固——这些是独立的后续计划。
- 不改前端（预期不需要；若走查发现前端有匿名调用，另行最小修复并在报告中记录）。

## 领域模型与业务规则

### 认证闸门的判定顺序

```text
1. method == OPTIONS                    → 放行（CORS 预检）
2. path 命中白名单                        → 放行（/health、Identity 代理）
3. 其余一切 /crate-api/*                  → 必须通过 IdP 会话校验，否则 401
```

要点：

1. **默认拒绝**：新增路由无需任何额外代码即受保护——这是本计划的核心价值，也是"逐路由挂载"漏掉 155 条的根治办法。
2. **闸门必须在模块子路由之前**：Vert.x 按注册顺序匹配，闸门注册在 `apiRouter.route("/<module>/v1/*").subRouter(...)` 之前才会先执行。这一点必须有测试固定。
3. **Identity 代理必须例外**：登录本身要通过它；放行的是代理路径，Identity 服务自己的认证/限流语义不变。
4. **不产生双重 401**：总闸拦下后不会进入既有逐路由认证；两者都通过时，第二个认证处理器应是幂等放行（既有实现已如此，验证时确认）。

## 验收口径

### 主线成功

1. 未携带任何凭证，对每个已挂载模块各取一条读路由与一条写路由（至少 healthcare/nursing/pharmacy/dining/inventories 各 2 条）发起请求：**全部 401**，响应体为 `{"error":"authentication required"}`。
2. `GET /crate-api/<module>/v1/health` 全部仍 **200**。
3. `OPTIONS` 预检请求不被拦（返回 CORS 响应头，非 401）。
4. 携带有效会话（浏览器登录后）：主要页面数据正常加载，无 401 误伤；读写操作与改动前一致。
5. 登录链路不受影响：未登录访问登录页、提交登录、获取当前会话均正常。

### 拒绝、边界与无副作用

- 未认证访问**任意**受保护路由均 401，且**不进入业务处理器**（不产生任何数据库写入；对写路由尤其重要）。
- 未认证请求不得返回任何业务数据（不再出现 `patients`/`encounters`/`materials` 等 200 数据响应）。
- 404 语义保持：不存在的路径仍 404（总闸放行到模块路由后由其返回 404，或总闸对未知路径也返回 401——**需在实现时明确并测试**；建议保持"先认证后 404"，避免用 401/404 差异探测路由是否存在）。
- 已认证但无权限的语义不变（本期不引入权限判定）。
- 既有非数据库测试全部保持通过（本计划只增加中间件与测试，不应改变任何既有用例结果）。
- 前端无改动（如必须改动，需在报告中说明原因与最小范围）。

## 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 白名单过宽 | 暴露面没有被真正关闭 | 白名单只有三类且逐条有注释理由；评审专门检查最小性；实测矩阵逐条验证。 |
| 闸门注册位置晚于子路由 | 中间件不生效，漏洞依旧 | 实现时显式放在挂载之前，并以测试断言注册顺序。 |
| Identity 被误拦 | 无法登录（整站不可用） | Identity 代理子树白名单；登录链路列入主线验收第 5 条。 |
| `/shared/v1/*`（Nexus）确有匿名依赖 | 相关页面报错 | 默认纳入认证；若验证发现依赖，按决策 3 以显式例外处理并记录理由。 |
| CORS 预检被拦 | 前端所有跨源请求失败 | `OPTIONS` 直接放行；列入验收第 3 条。 |
| 已登录用户被误伤 | 页面空白、体验回归 | 主闸只做"是否登录"判定，复用既有 IdP 会话处理器；浏览器走查覆盖主要页面。 |
| 401/404 差异被用于探测路由 | 信息泄露面 | 明确"先认证后 404"策略并测试（建议：未知路径未认证也返回 401）。 |
| 认为"已修完" | 掩盖残留面 | 本期只解决"必须登录"；RBAC、CSRF、限流、IDOR 明确列为后续独立计划。 |
| **每次请求多一跳 Identity 校验（性能）** | 页面上每个 API 调用都要向 IdP 发一次 `GET /crate-api/identity/v1/session`，列表页可能出现明显延迟 | 本次以**正确性优先**：先默认拒绝，性能问题如实记录。若实测延迟不可接受，另立计划引入**会话校验缓存**（带 TTL 与失效语义），不在本期自行加缓存——缓存会引入吊销延迟这一新的安全权衡，必须显式设计。 |
