# Aceso 护士医嘱核对与药房门禁 MVP 实施计划

更新时间：2026-08-07

状态：待实施

## 编号、背景与决策

本计划编号在现有 `009` 之后递增。它建立在 008 医嘱、护理任务和 011 药房接方/发药能力之上；不替代或重构这些既有能力。

当前行为是：活动养老入住的 `MEDICATION` 医嘱会创建护理任务，同时药房待接方列表直接读取活动医嘱，药房从医嘱创建发药单时也只校验入住、医嘱类型和临床状态。因此，护士尚未核对的医嘱也会进入药房。

产品决策如下：

1. 护士在护理模块核对医嘱后，药房才可见并可从该医嘱发药。
2. **不创建**“待发药记录”“领药/摆药申请单”或新的申请页面；护士核对结果直接保存在医嘱上。
3. `medical_orders.status` 继续只表达临床生命周期（既有 `ACTIVE`、`DISCONTINUED`、`COMPLETED`）；不得将其改写为物流或护理核对状态。
4. 药房已发生的发药事实继续只由既有 `pharmacy_dispenses` 及其明细保存；本计划不改变其审方、调配、确认、取消、退药、库存或数量计算语义。

本计划只定义“护士核对后开放药房”的最小闭环，不宣称完成床旁给药、签收、摆药周期、条码核对或完整 MAR（给药单）。

## 目标与范围

### 必须实现

1. 在活动养老入住的活动 `MEDICATION` 医嘱上提供护士核对动作；核对人从现有认证中间件写入的 `userId` 取得，不接受客户端伪造的核对人。
2. 医嘱新增 `nurse_checked_by` 与 `nurse_checked_at` 两项核对审计字段。未核对以两个字段均为 `NULL` 表示，已核对以两者都有值表示；不新增英文或中文业务状态枚举。
3. 新增 Healthcare API `PATCH /crate-api/healthcare/v1/orders/:id/nurse-check`。成功只更新该医嘱的核对审计字段和 `updated_at`，返回更新后的医嘱；不创建领药记录、护理任务、执行、发药单或库存操作。
4. 护理工作台新增“医嘱核对”区块：对选中的活动养老入住展示活动用药医嘱及其核对状态，护士确认后可一键核对，成功后刷新该入住的医嘱和护理数据。
5. 药房待接方查询只返回活动养老入住下**已核对**的活动用药医嘱；药房界面清楚显示核对人和核对时间。
6. 从医嘱创建发药单的事务锁读快照与业务校验也必须要求已核对，不能只依赖列表过滤绕过门禁。
7. 既有医嘱详情、列表和药房待接方响应增加 `nurse_checked_by`、`nurse_checked_at`，并在 `@pitchfork/shared/aceso` 中提供准确类型和请求方法。
8. 编写并执行本计划指定的非数据库后端测试、相关编译、前端构建和 diff 检查；数据库集成和浏览器 E2E 只在用户明确授权的独立测试环境执行。

### 明确不在本期范围

- 不新建 `待发药`、领药、摆药、药房申请、护理签收或给药记录表；不要求护士填写药品数量、仓库、批次或发药周期。
- 不改变 `medical_orders.status` 的既有取值、转移和停嘱收束逻辑；核对不是停嘱、完成、取消或实际给药。
- 不改变医嘱创建时生成的护理任务、频次生成、今日执行、执行完成、耗材消耗、护理记录或时间线逻辑。
- 不实现“撤销核对”或“再次核对”。当前医嘱没有编辑接口；后续如增加会影响药品、剂量、频次、途径或有效期的改嘱，必须另行设计使核对失效的规则。
- 不修改药房发药单的数量、库存校验、审方、调配、确认、取消、退药或重复发药规则；不实现按日/周多周期供药。
- 不实现护士签收、床旁给药、拒服/漏服/暂缓、双人核对、条码、批次效期、权限角色模型或操作审计平台。
- 不修改非 `ELDERLY_CARE` 的医嘱，且不将本功能推广到护理、饮食、治疗等非 `MEDICATION` 医嘱。
- 不迁移、回填或猜测历史医嘱的核对人和核对时间；历史医嘱默认未核对，只有护士主动核对后才对药房可见。

## 领域模型与业务规则

### 两个正交维度

医嘱的临床有效性与药房可见资格必须分开，判定如下：

```text
临床有效：encounter 为 ELDERLY_CARE 且 ACTIVE
          且 medical_order 为 MEDICATION 且 ACTIVE

药房可见/可发：临床有效
             且 nurse_checked_by 非空
             且 nurse_checked_at 非空
```

`status = ACTIVE` 仍然表示医嘱在临床上有效。护士核对只补充“已由护理端确认、药房可处理”的事实，不改变临床有效性；药房的既有 `dispense_status` 继续由真实发药单关联派生。这样既不需要待发药实体，也能避免把“医嘱有效”错误等同于“已发药”或“已给药”。

### 护士核对规则

1. 路由从 `RoutingContext` 的 `userId` 读取核对人；未取得认证主体时返回 `401`，请求体必须为空对象，包含任何未知字段返回 `400`。
2. 服务端在一个事务内锁定医嘱及其 encounter，再按顺序校验：医嘱存在、入住类型为 `ELDERLY_CARE`、入住为 `ACTIVE`、医嘱类型为 `MEDICATION`、医嘱临床状态为 `ACTIVE`、尚未核对。
3. 医嘱不存在返回 `404`；非养老入住或非用药医嘱返回 `400`；非活动入住、非活动医嘱或已核对返回 `409`。错误响应均为 `{ "error": "<message>" }`，不返回 SQL、堆栈或内部快照。
4. 校验通过后，写入 `nurse_checked_by = userId`、`nurse_checked_at = OffsetDateTime.now()` 和 `updated_at`。响应返回完整医嘱与这两个字段，HTTP `200`。
5. 已核对的医嘱不得被同一人或另一人重复覆盖；客户端刷新并展示原有核对事实。核对发生后若医嘱被既有流程停用，保留核对审计字段，但因医嘱不再活动而不再对药房可见。
6. 医嘱创建、护理任务创建、护理执行生成与医嘱停用不应因本功能产生额外写入；任何核对资格校验或更新失败均不改动医嘱、任务、发药单或库存。

### 药房门禁规则

1. `GET /crate-api/pharmacy/v1/dispenses/medication-orders` 在 Healthcare 侧读取时增加“已核对”条件；未核对医嘱既不计入总数，也不在页面出现。
2. `POST /crate-api/pharmacy/v1/dispenses/from-medical-order` 继续锁定医嘱，但受控快照必须携带核对字段，`DispenseService.validateOrderForDispensing` 要求两个字段均非空。直接构造请求、并发列表过期或绕过 UI 都不能从未核对医嘱发药。
3. 已创建且未取消的发药单仍按既有逻辑在待接方结果中附带 `dispense_id` / `dispense_status`；本计划不把“已核对”重置为未核对，也不改变取消后是否允许重建发药单的现有行为。
4. 核对审计字段必须通过 App 组合层的 Healthcare→Pharmacy 端口快照传递，Pharmacy 不直接查询 Healthcare 表，保持模块依赖方向不变。

## API 契约

### 新增护士核对接口

```text
PATCH /crate-api/healthcare/v1/orders/:id/nurse-check
Authorization: Bearer <JWT>
Content-Type: application/json
{}
```

请求不接受 `nurse_checked_by`、`nurse_checked_at`、`status`、`id`、`encounter_id`、`metadata` 或任何其他客户端字段。核对人必须从认证中间件的 `userId` 提取，Shared client 只发送空 JSON 对象，以复用既有 token、JSON 和 401 处理。

成功响应为 `200` 单条医嘱，新增字段示例：

```json
{
  "id": "01J...",
  "encounter_id": "01J...",
  "order_type": "MEDICATION",
  "status": "ACTIVE",
  "nurse_checked_by": "护理用户ID",
  "nurse_checked_at": "2026-08-07T10:15:00+08:00",
  "updated_at": "2026-08-07T10:15:00+08:00"
}
```

### 既有读取响应扩展

以下既有读取均在不破坏既有字段的前提下增加可空字段 `nurse_checked_by`、`nurse_checked_at`：

- `GET /crate-api/healthcare/v1/encounters/:id/orders`
- `GET /crate-api/healthcare/v1/orders/:id`
- `GET /crate-api/pharmacy/v1/dispenses/medication-orders`

前两个接口对未核对医嘱返回两个字段为 `null`。药房待接方因已过滤，只返回非空核对字段。列表继续使用 `{ "records": [...], "meta": { "total": N } }`，单条继续直接返回对象。

## 数据库与模块边界

### V507 迁移

在 Healthcare 库新增 `V507__add_medical_order_nurse_check.sql`，只修改 `healthcare.medical_orders`：

- `nurse_checked_by VARCHAR`，可空，存放认证主体 `userId`；
- `nurse_checked_at TIMESTAMPTZ`，可空；
- 对两列建立成对约束：两者必须同时为空或同时非空；
- 新增面向药房读取的局部索引，条件为 `order_type = 'MEDICATION' AND status = 'ACTIVE' AND nurse_checked_at IS NOT NULL`，索引列以现有按入住/创建时间的查询实际需要为准；
- 为两列增加中文语义注释，明确它们是护士核对审计信息。

不重用已有但语义含糊的 `medical_orders.nurse` 列，也不对历史数据回填。迁移版本符合 Healthcare 的 `V500+` 号段，并且不移动、修改或复制 `V500`–`V506`。

获得用户授权的可恢复 codegen 数据库后，开发运行 Healthcare 的 `generateJooq`，只提交迁移实际生成的 `MedicalOrders` 表与 record 源文件，以及必要的生成引用变化；不提交 `build/tmp` 或本地配置。未获授权时，计划保持“迁移和生成待执行”，不得连接共享开发库、业务库或生产库。

### 责任与依赖方向

- **Healthcare** 拥有医嘱表、核对资格、核对 API、列表/详情响应和锁读快照；迁移放在 `libs/healthcare`。
- **Pharmacy** 只消费受控的 `MedicationOrderSnapshot`，在待接方读取及发药事务校验中要求已核对；它不依赖 Healthcare Kotlin 服务，也不直接读 Healthcare 数据表。
- **Aceso App** 只负责把 Healthcare 的锁读快照映射为 Pharmacy 端口契约，新增字段必须显式映射，不能靠 `metadata` 或动态 JSON 透传。
- **Nursing UI** 只经 `@pitchfork/shared/aceso` 调用 Healthcare API；不直接请求 Healthcare 或 Pharmacy URL，不新增 Nursing 领域表、路由或后端依赖。

## 验收口径

### 主线成功

对一个活动 `ELDERLY_CARE` 入住创建活动 `MEDICATION` 医嘱后：

1. 护理工作台能看到该医嘱为“未核对”；药房待接方列表看不到它，直接调用从医嘱发药接口也被拒绝。
2. 有效 JWT 的护理用户在确认医嘱后调用核对接口，响应为 `200`，医嘱仍是 `ACTIVE`，且 `nurse_checked_by` 等于认证上下文 `userId`、`nurse_checked_at` 为带时区时间。
3. 刷新护理工作台与 Healthcare 医嘱列表后，核对人和时间一致；药房待接方列表出现该医嘱并显示相同信息。
4. 药房按既有流程创建、审方、调配和确认发药成功；新增功能不额外创建护理任务、执行、申请单或库存记录，发药单仍是唯一的发药事实。
5. 对已核对医嘱执行既有停嘱，医嘱仍保留核对审计字段但不再出现在药房待接方；既有任务收束和发药单历史语义不变。

### 拒绝、并发与无副作用

- 医嘱不存在返回 `404`；非养老入住或非 `MEDICATION` 医嘱返回 `400`。
- 缺少认证 `userId` 返回 `401`；请求体传入核对人、时间、状态、ID、metadata 或未知字段返回 `400`。
- 非活动入住、非活动医嘱、已经核对的医嘱返回 `409`；第二次操作不覆盖首次核对人/时间。
- 未核对医嘱必须同时在药房列表过滤和发药事务校验中被拒绝；只验证前端隐藏不算通过。
- 核对失败或冲突时，医嘱的临床 `status`、护理任务、护理执行、发药单、库存与退药数据均不变。
- 并发核对同一医嘱时，行锁保证至多一笔更新成功，另一笔返回 `409`，不会产生两套核对审计信息。
- 历史医嘱不因迁移自动对药房可见；没有护士主动核对的历史数据保持不可发药。

## 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 将核对写入 `status` | 临床有效性与药房物流混淆，停嘱/任务收束可能回归 | 保留既有临床状态机，仅新增可空审计字段和派生资格。 |
| 只过滤药房页面 | 直接调用发药 API 仍可绕过 | 待接方查询与 `createFromMedicalOrder` 的锁读校验都要求已核对。 |
| 客户端提交核对人 | 护理核对记录可伪造 | 路由只读取认证中间件的 `userId`，拒绝请求体中的核对字段。 |
| 历史医嘱自动放行 | 未经实际核对即发药 | 不回填，历史数据保留 `NULL`，默认不可见不可发药。 |
| 把护士核对扩大为给药闭环 | 影响库存、任务和临床操作，范围失控 | 明确只做药房前置门禁；签收、给药和 MAR 独立计划。 |
| 相关文件已有未提交改动 | 覆盖用户工作或错误合并 | 开发先交接当前 diff；仅加最小独立 hunks，重叠时协调，不 reset/revert。 |
| jOOQ 需要数据库 | 未授权连接造成数据风险或生成源不一致 | 仅使用用户授权的可恢复 codegen 数据库；未授权则记录为后置项。 |
