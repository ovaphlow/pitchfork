本计划完整吸收 007 中仍适用的领域规则、API 契约、事务边界与收束设计。若草案与当前代码冲突，以当前代码为准，具体调整如下：

## 目标与范围

### 必须实现

1. 激活养老入住的医嘱生命周期。仅 `ELDERLY_CARE` 且 `ACTIVE` 的 encounter 可开立、查询和终结医嘱；创建后正文、结构化明细、开嘱医生和生效时间不可编辑，更正采用“停嘱后新开”。
2. 提供用药与诊疗医嘱类型：`MEDICATION`、`THERAPY`、`EXAMINATION`、`LAB_TEST`。服务端以白名单校验 `order_details`，不接受客户端将任意 JSON、`metadata`、状态或任务标识写入医嘱。
3. 每条医嘱在同一事务内创建一条精确护理任务：`nursing_tasks.order_item_id = medical_orders.id`，并写同一 encounter 与其精确 service period。`MEDICATION` 派生 `MEDICATION` 任务，其他允许医嘱类型派生 `TREATMENT` 任务；任务通过既有频次机制生成 `nursing_task_executions`，医嘱详情仅只读汇总执行状态。
4. 扩展既有离院收束，并新增去世收束。两者均须在一个数据库事务中处理进行中的执行阻断、活动医嘱停嘱、活动关联任务取消和服务期完成；去世另将 encounter 与患者置为 `DECEASED`。
5. 提供 healthcare API、`@pitchfork/shared/aceso` 类型化客户端和 Aceso 医嘱 UI。医嘱页面可开立、筛选、查看执行汇总并办理停嘱/作废/完成；入住页面提供活动入住的医嘱入口与办理去世入口。
6. 为输入校验、状态机、精确关联、事务回滚、终局收束、无副作用、跨入住隔离和前端错误状态提供分层证据。

### 明确不在本期范围

- 不做药房发药、退药、申领、库存扣减或 `pharmacy_dispense_items.order_item_id/order_execution_id` 强关联；这些字段继续是弱关联预留。
- 不做电子签名、审批流、打印/PDF、通知、收费结算、跨机构传输、权限模型或角色化操作审计。
- 不修改 `NursingPage.tsx` 的任务创建、执行、时间线或统计交互；医嘱页不提供执行按钮。护理工作量统计（004）、逾期/统计扩展及其他护理分支仍延后。
- 不实现复评与照护计划修订（006 原定后续 007）、护理计划历史重算、死亡小结、死亡档案文书、遗嘱/遗产字段。
- 不编辑既有评估、计划、任务、执行、耗材、库存、护理记录、时间线或 006 的离院交接摘要；不回填历史医嘱。
- 不改变非 `ELDERLY_CARE` encounter 的创建、更新、转诊和离院语义；不开放 `POST /crate-api/nursing/v1/tasks` 手工创建 `MEDICATION`/`TREATMENT`。
- 不自动收束同一患者的其他活动入住。去世只检查并拒绝该患者其他活动 `ELDERLY_CARE` 入住（`encounter_type=ELDERLY_CARE` 且 `status=ACTIVE`）；其他 encounter 类型与非活动入住既不受影响也不阻断，不做隐式改变。

## 可验证的验收口径

### 领域、数据与事务

1. 对活动养老入住 `POST /crate-api/healthcare/v1/encounters/:id/orders` 返回 `201`，同一提交在 `healthcare.medical_orders` 写一条 `ACTIVE` 医嘱、在 `nursing.nursing_tasks` 写一条活动任务，且 `task.order_item_id = order.id`、`task.encounter_id = order.encounter_id`、`task.period_id` 是该 encounter 唯一关联周期。任一任务写入失败时二者均不存在。
2. 只接受 `MEDICATION`、`THERAPY`、`EXAMINATION`、`LAB_TEST`。`NURSING`、`DIET`、`VACCINE` 或其他类型为 `400`。`order_content`、`doctor`、`start_time` 必填，去首尾空白后医生最多 100 字符、正文最多 2,000 字符；`death_cause` 最多 500 字符。
3. `MEDICATION` 的 `order_details` 只允许 `drug_name`、`dose`、`unit`、`route`、`frequency_code`、`frequency_name`、`duration_days`、`remark`，其中 `drug_name` 必填；`THERAPY` 只允许 `treatment_item`、频次、时长和备注，其中 `treatment_item` 必填；`EXAMINATION`/`LAB_TEST` 只允许 `item_name`、`remark`，其中 `item_name` 必填。未知键、非对象明细、负数或非整数的 `duration_days` 均为 `400`。频次 code/name 若提供必须成对提供。
4. 任务起始日期为 `start_time` 的上海业务日期；有 `duration_days` 时结束日期为起始日加该时长的业务日，否则为空。可生成的频次经既有 `ensureExecutionsForDateRange` 产生执行；无频次或 `PRN`/`STAT` 不产生计划执行但保留任务。任务生成遵循当前“任务和 period 均为 `ACTIVE`”过滤，收束后不能再生成未来执行。
5. 医嘱只能从 `ACTIVE` 转至 `DISCONTINUED`、`CANCELLED` 或 `COMPLETED`。前两者同一事务把关联活动任务改为 `CANCELLED`，后者改为 `COMPLETED`；写入 `end_time`，既有执行不删除、不改写。终态再次转换为 `409`，非法目标为 `400`，不存在医嘱为 `404`。
6. 医嘱创建资格按顺序判定：不存在 encounter `404`；非养老 `400`；非活动 encounter、缺失精确周期或周期不是 `ACTIVE`/`SUSPENDED` 为 `409`。不得依据 patient_id 猜测 period。公共 Nursing 任务接口继续拒绝两类新增内部任务类型。
7. `GET /encounters/:id/orders` 返回 `{ "records": [...], "meta": { "total": N } }`，包括空列表；支持 `order_type`、`status`、`limit`、`offset`。`GET /orders/:id` 返回单对象和 `task_id`，并给出所有键均存在的只读 `execution_summary: { PENDING, IN_PROGRESS, COMPLETED, SKIPPED, CANCELLED }`；汇总只按该任务 ID 聚合，不按患者或日期猜测，列表和详情都不写入数据、不生成执行。
8. 离院成功时保持既有请求/响应形状，且在同一事务中：若有 `IN_PROGRESS` 执行则 `409` 并且医嘱、任务、周期、encounter 均不变；否则所有活动医嘱改 `DISCONTINUED`、活动关联任务改 `CANCELLED`、周期 `COMPLETED`、encounter `DISCHARGED`。终局业务时间写入医嘱 `end_time`，周期日期使用既有 `businessDate`。
9. `PATCH /encounters/:id/death` 仅接受活动养老入住。成功后同一事务中医嘱/任务/周期按第 8 项收束，encounter 为 `DECEASED` 且有 `death_date`/可选 `death_cause`，`discharge_date` 保持空，患者状态为 `DECEASED`。去世时间缺失或格式错误为 `400`；不存在为 `404`；非养老为 `400`；已离院/已去世、进行中执行、周期异常或该患者仍有其他活动 `ELDERLY_CARE` 入住均为 `409` 且无半收束。
10. 所有业务错误统一为 `{ "error": "<message>" }`，不返回 SQL/堆栈信息。ULID、`created_at`/`updated_at`、JSONB `metadata` 的既有约定不变；本功能不把可扩展医嘱明细转存到 `metadata`。
11. 本计划状态更新为“已完成”的唯一前提：第“测试清单”节授权的 PostgreSQL 集成测试与 Chromium 浏览器验收已在获授权的独立可清理 `aceso_test` 与用户管理的 Aceso UI/API 上实际执行且全部通过，并附实际命令、退出码、通过数、清理残差与失败产物证据；未获授权时测试报告必须显式标注未执行项，评审只能记录缺口与残余风险，不得以编译/构建通过代替或宣布完成。

### 前端

1. `/dashboard/orders` 只通过 `@pitchfork/shared/aceso` 选择活动入住、创建用药或诊疗医嘱、筛选列表、查看详情汇总并办理状态转换。请求期间对应按钮禁用，失败后保留表单输入并显示独立错误。
2. 医嘱详情只读展示 `execution_summary`，没有执行、库存、护理记录、编辑或删除入口；刷新后服务端状态和列表筛选保持一致。
3. 入住页仅对活动入住提供“医嘱”跳转和“办理去世”。去世成功后刷新活动清单；另有活动 `ELDERLY_CARE` 入住/进行中执行的 `409`、网络/校验失败可见且不丢失去世表单输入。已离院档案、交接摘要和既有离院动作保持原语义。
4. 桌面和窄屏下表单、列表、详情弹窗、状态操作与去世弹窗均可访问，长文本不重叠；表格在需要时横向滚动，控件尺寸不因动态状态改变而跳动。

## 小步实施步骤

1. **确认前置与边界。** 开发阅读本计划、根/后端/前端 `AGENTS.md`、005、006，并核对当前 `HealthcareService.dischargeEncounter`、`ServicePeriodService.closeElderlyCarePeriod`、`TaskService`、`TaskExecutionService.ensureExecutionsForDateRange`。确认 healthcare 已依赖 nursing，Aceso `Main.kt` 已挂载两个模块，因而仅增加库内连接绑定协作，不新增 HTTP 回调、跨产品依赖或后台任务。

2. **新增最小迁移并生成 jOOQ。**
   - 在 healthcare 新建 `V505__add_encounter_death_and_order_closure.sql`：给 `healthcare.encounters` 增加可空 `death_date TIMESTAMPTZ` 与 `death_cause TEXT`。不更改 `V500`--`V504`，不回填，不新增跨 schema 外键；现有 status/encounter_type 查询索引足以支撑本轮，不附带报表索引。
   - 在 nursing 新建 `V405__extend_task_type_for_medical_orders.sql`：仅替换 `nursing_tasks.task_type` CHECK，使其允许既有五类和 `MEDICATION`、`TREATMENT`。保持 `order_item_id` 无外键；不更改 `V400`--`V404`。
   - 仅在获得可恢复 codegen 数据库授权后运行相应 `generateJooq`，提交实际受影响的 Healthcare 生成源 `Encounters.java`、`EncountersRecord.java`。`MedicalOrders` 已存在，V405 不产生列变更；不提交 `build/tmp` 渲染物。后续新增查询必须导入生成表类。

3. **在 Nursing 增加连接绑定的内部任务协作。** 在 `TaskService` 增加只供 Healthcare 编排调用的方法，接收外层事务的 `SqlConnection` 和经校验的医嘱任务输入；只允许 `MEDICATION`/`TREATMENT` 且 `order_item_id` 非空，用 `NursingTasks` 生成插入。补同连接的任务终结方法：锁定并验证唯一 `order_item_id` 的任务，按医嘱目标更新为 `CANCELLED` 或 `COMPLETED`。保留公共 `TaskService.create` 和 `/nursing/v1/tasks` 的既有五类白名单，不能以公开接口绕过约束。

4. **实现 Healthcare 医嘱读取、创建和状态机。** 在新建 `MedicalOrderService.kt`（由 `HealthcareService` 持有）实现以下逻辑，并以 `HealthcareService` 的锁定、错误映射、`businessDate` 和 `Pool.withTransaction` 模式复用现有行为：
   - `createOrder(encounterId, body)` 在一个连接中锁定并验证 encounter/精确 period，验证第 4 节所列输入，插入 `MedicalOrders`，调用 Nursing 内部任务创建，返回包含 `task_id` 的医嘱；`order_details` 采用受控 JSONB，`metadata` 不接收客户端输入。
   - `listOrders` 和 `getOrder` 只读查询。详情用单次按 `task_id` 的聚合查询建立固定五键执行汇总；不能逐医嘱查询执行形成 N+1。
   - `updateOrderStatus` 在一个连接中锁定医嘱与关联任务，执行状态机和任务联动，再写 `end_time`；任务缺失、任务状态异常或任意写入冲突使整个事务回滚。
   - `HealthcareService` 只承担编排和现有 encounter/患者响应；将 `death_date`、`death_cause` 纳入 encounter 读取、列表和响应映射，避免写入后 API 丢字段。

5. **扩展终局编排而不改变 005/006 边界。**
   - 调整 `dischargeEncounter`：继续先锁 encounter，并复用精确 period 的收束/进行中执行检查；在同一外层事务内收束全部活动医嘱和任务，再完成既有 period 与 encounter 更新。任何失败回滚全部改动。非养老离院走当前路径，不访问医嘱表。
   - 新增 `deathEncounter`：锁 encounter 和精确 period，检查养老类型、活动状态、进行中执行及该患者其他活动 `ELDERLY_CARE` 入住（`encounter_type=ELDERLY_CARE` 且 `status=ACTIVE`）；通过后在同一事务依次收束医嘱任务、完成周期、写 encounter 去世信息、更新患者状态。以 `businessDate(death_time)` 写 period 结束日，重复或互斥终局返回 `409`。
   - 不改写/生成 `DISCHARGE_SUMMARY`，不调用执行生成、执行状态更新、库存出库、护理记录写入或时间线写入。

## 测试清单

### 非数据库单元测试（开发执行）

开发编写并运行不访问数据库的 JUnit/嵌入式路由测试，至少覆盖：

1. 医嘱类型、必填项、长度、日期、`order_details` 白名单、时长与客户端注入字段的 `400`；路由静态/具体路径不被泛型路径吞掉，所有错误为 `{error}`。
2. encounter/period 资格的 `404`、`400`、`409` 映射，精确 `encounter_id` 关联和公共任务路由继续拒绝 `MEDICATION`/`TREATMENT`。
3. 医嘱创建任务参数：任务类型、`order_item_id`、period、encounter、频次、上海业务起止日；失败回滚和读取无副作用。
4. 三条合法状态转移、终态重复、非法目标、关联任务缺失/异常的回滚，且不删除既有执行。
5. 执行汇总空计数、精确按 task ID 聚合、列表分页/过滤和无 N+1 的查询边界。
6. 离院与去世成功收束、`IN_PROGRESS` 阻断全不变、去世互斥、另有活动 `ELDERLY_CARE` 入住、非养老与终态错误；断言不调用执行生成、执行写入、库存、护理记录或归档。
7. Shared API 与 React 交互的类型检查由 Aceso build 覆盖；UI 错误保留输入、重复提交禁用和窄屏布局由浏览器测试覆盖。

### 获授权的 PostgreSQL 集成测试（测试执行）

仅在用户明确授权的、独立且可清理的 `aceso_test` 运行；绝不连接共享 `aceso`、业务库或生产库。测试角色新增 `MedicalOrderIntegrationTest` 和 `ElderlyDeathIntegrationTest`，fixture 至少包含：

- 活动养老入住与其唯一活动 service period，含 `MEDICATION` 与 `THERAPY` 医嘱、派生任务、跨日执行；
- 同一患者的另一终局/重新入住及另一患者入住，用于 encounter/period 隔离；
- 非养老、缺 period、已离院、已去世和存在 `IN_PROGRESS` 执行的路径；
- 去世的“同患者仍有其他活动 `ELDERLY_CARE` 入住”冲突路径，以及无关任务、执行、护理记录、交接摘要和库存诱饵数据。

必须断言：

1. 医嘱与任务各一行、精确弱关联、频次/日期正确；`ensureExecutionsForDateRange` 为可生成频次创建记录，终局后不再生成未来执行。
2. 停嘱/作废/完成的任务联动、既有执行保留和所有状态机拒绝路径；任务或医嘱写入失败时整笔事务无残留。
3. 离院/去世的所有行在同一事务收束；`IN_PROGRESS` 和患者另有活动 `ELDERLY_CARE` 入住时每个相关表均不变；去世字段、患者状态、互斥终局均正确。
4. 列表/详情严格按 encounter、period、task 隔离，执行汇总计数不泄漏诱饵数据；读取不产生任务、执行或库存写入。
5. fixture 使用 `mo-`/`ed-` 前缀，按执行、任务、医嘱、周期、encounter、患者的外键依赖顺序清理；前后做残差查询并报告为零。密码仅从授权秘密源注入，不写进计划、命令历史、日志或交付物。

## 风险

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 跨模块写入不共用连接，导致医嘱与任务半成功 | 病历和执行链断裂 | Healthcare 在一个 `Pool.withTransaction` 中将外层 `SqlConnection` 传给 Nursing 内部方法；集成测试覆盖任务失败全回滚。 |
| 离院/去世先完成周期后才发现医嘱任务错误 | 终局半收束或未来执行泄漏 | encounter 锁定、period/进行中检查、医嘱任务收束和终局更新处于同一事务；所有失败回滚。 |
| `order_item_id` 没有数据库外键 | 孤儿任务或错误关联 | 连接绑定创建和终结都锁定并验证唯一 order ID；服务读取和集成测试按 encounter/period/task 三重断言；本期不扩大为跨 schema 外键。 |
| 医嘱详情任意 JSON | 不受控数据、前端/报表不可预测 | 服务端白名单、类型/长度校验，不接受 metadata；测试未知键和注入字段。 |
| 007 的 `/orders` 与当前 `/dashboard/*` 路由不一致 | 导航和 E2E 指向错误页面 | 本文件固定 `/dashboard/orders`，以当前 `Sidebar`/Astro 页面结构实现。 |
| 现有 `ensureExecutionsForDateRange` 已使用字符串 jOOQ 查询 | 大范围重构会引入护理回归 | 仅验证它已覆盖活动医嘱任务；本轮新增查询全部用生成表类，除非测试证明必须修复其选择条件，不做存量重构。 |
| 终局与上海业务日期/UTC 读回不一致 | period 结束日和医嘱日期错误 | 所有由 `OffsetDateTime` 导出的业务日复用 Healthcare `businessDate`；集成测试含 `+08:00` 输入和 UTC 存取回归。 |
| 无授权数据库或服务环境 | 无法以编译代替真实收束验收 | 默认只运行非数据库命令；测试角色获授权前显式阻塞（`needs_input`）并附授权清单，缺授权则报告显式标注未执行，评审不得宣布完成。 |
| 006 已归档摘要被医嘱补写 | 破坏不可变归档语义 | 收束只更新医嘱和任务，不创建或编辑 `DISCHARGE_SUMMARY`；集成/E2E 设置并断言摘要诱饵不变。 |
