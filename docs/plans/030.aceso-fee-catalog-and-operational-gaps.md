## 3. 调度者裁决（用户不在场，按「推荐方式」执行并留档）

- **D1 护理等级枚举值 = 评估表单现有四值**：`低风险 / 中风险 / 高风险 / 无需干预`
  （与 `NursingPage.tsx:2504`、`FeeItemsPage.tsx:36` 一致）。不引入英文 code，遵循「业务枚举遵循既有中文值」。
- **D2 等级绑定落 `metadata.nursing_level`，不新增列。** 理由：新增列需要重新生成 jOOQ，
  而 `generateJooq` 只能对着**真实库**跑（`build.gradle.kts` 的 `doFirst` 强制 `PITCHFORK_DB_PASSWORD`，
  模板 URL 固定 `localhost:5432` 指向开发库——按仓库策略 agent 不得连接）。
  `metadata` 本就是本仓约定的扩展 JSONB 字段；服务端把它作为**结构化业务字段**读写并在 API 层拉平为顶层 `nursing_level`，
  名称仍只是描述文本。DB 兜底用部分唯一索引（不需要 jOOQ 生成）。
- **D3 无评估口径 = 「不计 + 显式告知 + 可手工补」**（三选一的裁决）：
  1. 护理费**不自动计**（保持既有金额语义不变，避免静默按默认等级计费产生错账）；
  2. `precheck.notices` 明确给出 `nursing_fee_not_billed_no_assessment`，前端显示中文口径与「请先补护理评估」的下一步；
  3. 保留 `POST /bills/:id/items` 手工加项作为补记通道（既有能力，不新增）。
  理由：默认等级计费会把机构未评估的责任转成账单金额，属不可回滚的财务错误；不计但不可见则是「页面不告诉用户」的原缺陷。
- **D4 床位主数据只做候选来源，不做强制外键。** `beds` 提供 `(department, ward)` 候选，
  入住表单用 `<datalist>`（自由文本 + 候选），保存路径与校验**完全不变**（029 的区间冲突校验继续生效）。
- **D5 逾期收口口径**：`POST /nursing/v1/executions/converge-overdue`，
  默认阈值 `min_overdue_minutes = 1440`（24h，与 `STALE_IN_PROGRESS_MINUTES` 同口径），
  目标状态 `SKIPPED`（漏执行），单次上限 200 条，幂等（第二次返回 `converged: 0`）。
  为支持「执行中→漏执行」，`VALID_STATUS_TRANSITIONS` 的 `IN_PROGRESS` 增加 `SKIPPED`
  （仅增加一条允许转移，不改既有语义；通用 `PATCH /:id/status` 因此也支持该转移，属有意的口径统一）。
- **D6 批量绑定口径**：单事务全成全败；`≤100` 条；`items[].order_id` 去重后必须非空；
  已绑定的单条返回 409（整体回滚），与单条补绑 `bindDrugMaterial` 同文案。
- **D7 医嘱正文字段只改** **UI 文案与提示**（含列表头、表单标签、校验文案、详情标签），
  API/DB 名 `order_content` 不动。
- **D8 `notices` 契约**：始终返回数组（无提示时 `[]`），元素形如
  `{"code": "...", "category": "护理费", "level": null}`；`code` 与中文文案的映射留在前端（沿用 `billingMessages.ts` 的既有口径）。

## 4. 冻结接口（跨角色契约，实施中不得单方面改动）

### 4.1 费用字典（W1，后端 Dev-A / 前端 Dev-E）

- `POST/PUT /crate-api/healthcare/v1/fee-items`：请求体新增可选键 `nursing_level`。
  - `category = 护理费`：必填，且 ∈ 四值枚举；缺失 → 400 `nursing_level is required for 护理费 fee item`；
    非法值 → 400 `nursing_level must be one of: 低风险, 中风险, 高风险, 无需干预`。
  - `category ≠ 护理费`：传入非空值 → 400 `nursing_level is only allowed for 护理费 fee item`；省略/`null` 合法。
  - 落库：`metadata.nursing_level`；`metadata` 其余键原样保留（服务端合并写）。
- 启用态唯一性：同一 `护理费` 等级**至多一条启用项**；违反 → **409**
  `another enabled 护理费 item already bound to level 低风险`（服务端在事务内检查 + DB 部分唯一索引兜底；
  索引名 `uq_fee_items_nursing_level_enabled`，捕获 23505 同样转 409）。
- 响应（列表/单条/创建/更新/状态流转）统一新增顶层 `nursing_level`：字符串或 `null`。
- `metadata` 里的 `nursing_level` 视为服务端字段：**不得**通过 `metadata` 直接写入（写白名单仍为原 6 键 + `nursing_level`）。
- DB（`V520__add_fee_item_level_indexes.sql`）：
  ```sql
  CREATE UNIQUE INDEX IF NOT EXISTS uq_fee_items_nursing_level_enabled
      ON healthcare.fee_items ((metadata->>'nursing_level'))
      WHERE category = '护理费' AND status = '启用';
  CREATE UNIQUE INDEX IF NOT EXISTS uq_fee_items_single_enabled_per_category
      ON healthcare.fee_items (category)
      WHERE status = '启用' AND category IN ('床位费', '伙食费');
  ```
- Seed（`V521__seed_demo_fee_items.sql`）：固定 26 位 ULID，`床位费 60.00 元/天`、
  `伙食费 15.00 元/餐次`、`护理费 低风险 30 / 中风险 50 / 高风险 80 / 无需干预 10`，全部 `启用`，
  `metadata` 带 `{"demo": true, "nursing_level": "<等级>"}`。
  **幂等且对既有数据安全**：每条都用 `INSERT ... SELECT ... WHERE NOT EXISTS (同分类/同等级已有启用项)`
  且以 `ON CONFLICT DO NOTHING` 兜底（不能只用 `ON CONFLICT (id) DO NOTHING`——
  V520 的部分唯一索引会让「同分类已有启用项但 id 不同」的插入报错并中断迁移）。
  V520 的两条索引在**存在冲突存量数据**的库上会直接创建失败（fail-closed，不静默改数据）；
  本计划依据的数据快照为 `fee_items` 0 条（见 R7/R8）。
  **更正（评审 P2-4）**：`uq_fee_items_single_enabled_per_category`（床位费/伙食费同分类至多一条启用项）
  是**新增约束**——base 的 `FeeItemService` 没有任何分类唯一性检查，只在计费时由
  `requireSingleEnabled` 报 400；升级后「新建第二条启用床位费」由「允许、计费时才 400」变为
  「建即 409」，且**在已有重复启用项的库上 V520 会让迁移失败、应用起不来**（评审已真库复现）。
  上线前须先做一次体检（见 R13）。

### 4.3 逾期执行收口（W5，后端 Dev-B / 前端 Dev-F）

- `POST /crate-api/nursing/v1/executions/converge-overdue`
  - 体：`{"encounter_id"?: string, "task_type"?: string, "min_overdue_minutes"?: int, "limit"?: int}`
    （白名单，未知键 → 400 `unsupported converge keys: ...`；`min_overdue_minutes` 默认 1440、最小 1；
    `limit` 默认 200、最大 200）。
  - 命中条件：`status ∈ {PENDING, IN_PROGRESS}` 且 `planned_time < now() - min_overdue_minutes`，
    可选 `encounter_id`/`task_type` 过滤；按 `planned_time ASC` 取前 `limit` 条。
  - 动作：逐条 `status = 'SKIPPED'`，`metadata.convergence = {"reason":"逾期未执行，批量标记漏执行","at":"<ISO>","min_overdue_minutes":<n>}`
    （与既有 `metadata` 合并，不覆盖其它键）；同事务提交；不加锁跨 encounter 的行集。
  - 响应：`{"converged": N, "ids": [...], "truncated": bool, "min_overdue_minutes": n}`；第二次调用 `converged: 0`。

### 4.4 待补绑清单 + 批量绑定（W6，后端 Dev-C / 前端 Dev-G）

- `GET /crate-api/healthcare/v1/orders/unbound-material?encounter_id=&search=&limit=&offset=`
  - 条件：`order_type='MEDICATION'`、`status='ACTIVE'`、`order_details->>'material_id' IS NULL`、
    入住为 `ELDERLY_CARE`；`search` 模糊匹配 `order_content` / `order_details->>'drug_name'` / 患者姓名 / 住院号。
  - 响应：`{records:[{id, encounter_id, encounter_no, patient_id, patient_name, order_content, drug_name,
    start_time, end_time, nurse_checked_at, created_at}], meta:{total}}`（`drug_name` 取自由文本，缺失为 null）。
- `POST /crate-api/healthcare/v1/orders/bind-material-batch`
  - 体：`{"items":[{"order_id": "...", "material_id": "..."}]}`；未知键/结构错 → 400；`items` 空 → 400
    `items must not be empty`；>100 → 400 `items must not exceed 100`；重复 `order_id` → 400。
  - 每项经 `DrugCatalogPort.findDrugMaterial` 解析（不存在 → 404；`status != 启用` / `category != 药品` → 400；
    端口未注入 → 503；**注意**：`category != 药品` / `status != ACTIVE` 在本批量路径按本计划取 **400**，

## 7. 残余风险（预期，实施后按实回填）

- **R1** `metadata.nursing_level` 是 JSONB 内的业务键，而不是列：DB 层只有部分唯一索引兜底，
  不能对非护理费行约束「不得携带等级」；该约束只在服务端。另：**没有 `nursing_level` 的历史/手写
  `护理费` 启用项不会按名称回退匹配**，账单生成会以 `no enabled fee item for nursing level X` 400 报错
  （费用项目页对这类行显示「未绑定（无法自动计费）」，改选等级即可修复；本轮数据快照 `fee_items` 为 0 条，无存量影响）。
  **补充（评审 P2-5）**：部分唯一索引**不约束 NULL**，因此两条「无等级」的启用护理费可以共存；
  服务端 `requireLevelAvailable` 在 `level == null` 时也直接放行。影响惰性（NULL 永不匹配槽位，
  不会被计费、也不会把 precheck 的 `satisfied` 计成多条），但「同等级唯一」这条兜底对 NULL 等级无效。
- **R2** `deriveBillingSlots` 返回类型变化会影响 `generate` 路径，需确保金额语义逐字不变（回归用例锁定）。
- **R3** 床位主数据不强制引用完整性：历史 `'001'` 与 `'01'` 仍可能被当成两张床，需人工订正。
- **R4** 逾期收口是人工动作，队列仍可能长期无人处理；无催办/通知（027 非目标）。
- **R5** 业务时区仍硬编码（后端 7 处 `Asia/Shanghai` + 前端 `+08:00`），跨时区部署仍会错。
- **R6** 本分支的写端点（POST/PUT/PATCH）依赖用户在主检出修复的 `BodyHandler` P0；
  二者叠加后才会在运行实例上生效。合并顺序：用户 P0 修复先在 `main`，本分支在其上叠加或反之皆可（文件不重叠）。
- **R7** seed 价格是演示值，机构须按实际合同价在「费用项目」页调整。
- **R8** 隔离测试库下 `:libs:healthcare:test` 有 **3 条既有失败**（`MedicalOrderIntegrationTest` 的
  `closeExpiredOrders真库…`），根因是 027 遗留用例把 `(boolean)::text` 期望成 `t`，而 PostgreSQL 返回
  `true`。已用 `main` @ 0f9822b 在同一隔离库流程下取得基线（base 570 tests / 3 failed；本分支
  622 tests / 3 failed，失败集合逐条相同）→ **非本计划引入**，须单独立项修断言。
- **R9** `:libs:nursing:test` 的真库门控用例**无法在模块自身 classpath 下通过**：既有用例会访问
  `healthcare.medical_orders` 等 healthcare 表，需要先用含 healthcare 段的 classpath 迁移同一库；
  仓库单命令入口（`scripts/aceso-test.sh`）只跑 healthcare 与 apps 两个任务，不覆盖 nursing 门控用例。
  属**既有测试基础设施缺口**（base 对照：同环境 base 230 tests / 24 failed，本分支 236 tests / 22 failed，
  失败类集合相同且更少）。本计划新增的 `TaskExecutionConvergeIntegrationTest` 只依赖 nursing 表，
  在上述流程下 **3/3 通过**。
- **R10（已按评审 P2-1 更正）** 真实失败模式不是「`ctx.body()` 为 null → NPE」——评审用独立 Vert.x
  探针证明 BodyHandler 挂载后 `ctx.body()` **永不为 null**；真正的 500 来自 `asJsonObject()` 对
  **非对象/畸形 JSON 请求体**抛 `DecodeException`。本计划新增的三条床位写路由与逾期收口路由
