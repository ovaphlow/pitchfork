# Aceso 离院/去世不再自动收束账单实施计划

更新时间：2026-09-28

状态：开发候选（整模块 512/0/57、前端构建 0 errors；待授权后置验证、评审与用户手测）

## 编号、背景与决策

本计划编号 023（020、021、022 已占用，按 `loop-lessons.md` 第 2 条取当前最大编号 +1）。

### 背景：一条没有流量的路

020 与 021 把「押金核销」与「未结余额显式减免」都做在了 `POST /encounters/:id/billing-settlement`（即养老收费页的「结算收束」）这条路上。但这条路的**可达性从未被验证**。核实结果：

1. `HealthcareService.dischargeEncounter`（养老入住分支，约 `HealthcareService.kt:240-249`）在离院事务内**无条件**调用 `billService.settleEncounter(connection, id, now, requireTerminalStatus = false, endDate = 离院日)`；`deathEncounter`（约 `:306`）同构。
2. 该调用把 `encounters.settled_at` 置位、并把该入住全部账单置 `已结算`。
3. 养老收费页「结算收束」的启用条件是 `（已离院 | 已去世） && !settled_at`。**因此对每一个正常离院的长者，这个按钮永远是禁用的。**
4. 结论：**押金核销（020）与减免门禁（021）在正常业务流程里一步都走不到**；唯一可达场景是历史遗留的「已离院但未收束」补结算。真实世界里，离院那一刻欠费仍被静默结转、押金仍没有机会抵扣。
5. 后端与界面**自相矛盾**：卡片文案明写「结算收束适用于已离院/去世的养老入住」，说明设计意图就是「先离院，再到收费页收束」——后端却在离院时抢先把这件事做完了。
6. 021 在 V519 注释中声明的不变量「`outstanding_amount > 0` 的账单必须带 `write_off_reason`」，在这条路径上也不成立（离院写入的是 `outstanding_amount > 0` + `write_off_reason = NULL`）。

### 产品决策（2026-09-28 用户确认，方案 A）

1. **离院/去世只标记事实与业务收尾，不再收束账单。** 离院继续完成：状态流转、离院/去世日期、离院诊断或去世原因、医嘱终止、护理周期关闭、交接摘要归档、唯一活动入住约束。**账单收尾统一由「结算收束」承担**，并强制核销与减免留痕。
2. **删除 `BillService.settleEncounter` 兼容入口，而不是把它留成一个没人调用的口子。** 已核实：它唯一的生产调用者就是上述两处，且**没有任何测试直接调用它**，因此删除不产生测试债。目标是让「静默结转」这条代码路径从仓库里消失。
3. **离院后、收束前是一段正常的可收费窗口。** 该窗口内允许生成账单、手工加项、缴费；现实现本来就只以 `settled_at` 作为冻结条件（`BillService` 的生成校验只查 `settled_at`/`admit_date`/账期重合，不查入住状态），本计划要求**以测试固定这一行为**，不得回退。
4. **不改变离院/去世本身的其余语义**，不把未结处理内联进离院表单（用户已否决），不把核销解绑为随时可用（用户已否决）。

## 目标与范围

### 必须实现

1. `HealthcareService.dischargeEncounter` 去掉 `billService.settleEncounter(...)` 调用，并保持其余步骤与执行顺序不变（医嘱终止 → 护理周期关闭 → 状态/日期/诊断写入）。
2. `HealthcareService.deathEncounter` 同样去掉该调用。
3. 删除 `BillService.settleEncounter`；删除后确认全仓（`libs/**`、`apps/**`）无任何引用残留，包括 KDoc 中的指向性描述要同步修正。
4. 离院/去世完成后：`encounters.settled_at` 保持 `NULL`；该入住账单的 `status`、`total_amount`、`outstanding_amount`、`write_off_reason` 与押金台账全部不变（新增断言固定）。
5. 离院后未收束窗口内，以下四个动作**均可用**：`POST /encounters/:id/bills`（生成账单，含区间外月份）、`POST /bills/:id/items`（手工加项）、`POST /bills/:id/payments`（缴费）、`POST /encounters/:id/billing-settlement`（结算收束）；收束之后四者按既有守卫一律 409。
6. 前端最小可达性补强：
   - 养老收费页「结算收束」卡片对「已离院/去世且未收束」的长者变为**可用**（这是本计划的目的，必然生效）；
   - 在入住管理页的离院/去世成功路径上给出下一步指引（例如成功提示中增加「请到『养老收费 → 结算收束』完成账单收尾」），避免新出现的"已离院未收束"状态无人收口；
   - 检查并修正任何暗示「离院即已结账」的文案（若有）。
7. 测试：调整 `BillingSettlementTest` 中两个以「离院/去世即收束」为前提的用例；新增 `DischargeBillingWindowTest`（离院不改账单、窗口内四项可用、收束后一律 409、去世路径同构）。

### 明确不在本期范围

- 不修改离院/去世的状态机、日期与原因语义、医嘱终止、护理周期关闭、交接摘要归档、唯一活动入住校验。
- 不修改 `settleEncounterBilling` 的三步路径（建最终账单 → 核销 → 未结判定 → 冻结）与减免门禁（021 已定），不改 `prepareSettlement`/`outstandingBills`/`freezeSettlement`/`previewSettlement` 的语义。
- 不做「离院表单内联处理未结」（含可选减免原因透传）。
- 不把押金核销解绑为对任意待缴费账单随时可用的独立动作。
- 不改 `BillingEngine` 的计价规则、账单状态枚举、费用项目字典。
- 不引入新的后台任务、报表或提醒机制（例如"已离院未收束"清单）；如需另立计划。

## 领域模型与业务规则

### 事件与职责重新划分

```text
离院/去世 = 业务事实与照护流程收尾（状态、日期、医嘱、护理周期、交接归档）
结算收束  = 账单流程收尾（区间最终账单 → 押金核销 → 未结判定与减免留痕 → 冻结）
两者解耦：离院不再隐含收束，收束是离院之后一次显式的、带门禁的操作。
```

### 冻结条件的唯一来源

账单层的冻结条件**始终只有** `encounters.settled_at`（由结算收束写入），与入住状态（`ACTIVE`/`DISCHARGED`/`DECEASED`/`TRANSFERRED`）无关。这样：

- 离院后未收束：可生成、可加项、可缴费；
- 收束后：一律 409，且不可逆。

### 与既有不变量的一致性

- V519 的「`outstanding_amount > 0` ⇒ `write_off_reason` 非空」在**所有**写入路径上成立：唯一写这两列的地方是 `freezeSettlement`，而它由带门禁的收束路径触发。
- `应缴 − 已缴 = 欠费 + 减免` 在离院后未收束期间同样成立（此时该入住的减免为 0，欠费非 0）。

## 验收口径

### 主线成功

1. 对一名在住养老长者办理离院（带离院日期、诊断）：响应 `status = DISCHARGED`、`settled_at` 仍为 `null`；该入住既有账单的 `status`/`total_amount`/`outstanding_amount`/`write_off_reason` 与押金台账**逐行未变**；离院过程中**没有**任何账单插入或账单状态更新。
2. 该长者的账单保留原状态（如 `待缴费`），并出现在全局欠费列表中（欠费口径把已离院未收束者也计入，这是正确行为）。
3. 在养老收费页选中该长者：「结算收束」卡片**可用**，预览返回 `settlement_period`/`final_bill_total`/`pending_balance`/`outstanding_total`/`deposit_balance`/`max_offset`/`requires_write_off`。
4. 离院后未收束期间：生成账单、手工加项、缴费均成功（各自 201/200），核销与收束前置条件不受入住状态影响。
5. 执行结算收束（带核销金额与减免原因）：生成区间最终账单、全部账单置 `已结算` 并写 `settled_at`/`outstanding_amount`/`write_off_reason`；押金余额按核销额减少并留下 `核销` 台账与 `押金` 缴费流水。
6. 收束后再试生成/加项/缴费/收束 → 一律 409，且无任何写入。
7. 去世路径与离院路径同构（`status = DECEASED`、`settled_at` 为 `null`、账单未变、收束后冻结）。

### 拒绝、边界与无副作用

- 离院/去世的其余既有断言全部保持：非养老入住 400、非 `ACTIVE` 409、日期/原因校验 400、医嘱终止与护理周期关闭、交接摘要归档、唯一活动入住约束。
- `BillService.settleEncounter` 删除后，全仓无引用残留（`libs/**`、`apps/**` 均需 grep 为零）。
- 离院失败（任一校验不通过）时事务整笔回滚：账单、押金、医嘱、护理周期、交接归档均不变。
- 未离院/未去世的入住执行收束仍 409（既有语义不变）。
- 已收束的入住离院/去世不产生二次写入（既有 409 语义不变）。
- 021 的门禁在离院后收束时**真实生效**：核销后仍有未结且无原因 → 409 且整笔回滚。
- 历史数据（在本次变更前已离院且已被自动收束的入住）保持原状：`settled_at` 非空、账单 `已结算`、`outstanding_amount = 0`，**不回填、不重算**。
