## 1. 背景与现状

037 打通了"配了角色真的会拦请求"，但只覆盖一条通道：

| 事实 | 现状 |
| --- | --- |
| 已接线的权限码 | 只有 `nursing:execute`，覆盖护理执行两条写路由 |
| 门禁实现位置 | `apps/aceso/.../SubjectPermissionGate.kt`（app 内私有），Trainova 不可复用 |
| 已接线清单 | `apps/aceso/.../DeclaredPermissions.kt` + 自省端点 `/crate-api/access/v1/permissions` |
| 可被误判为"已保护"的写路由 | 发药确认（`POST /pharmacy/v1/dispenses/:id/confirm`）、账单写操作、给药之外的护理写等仍只校验登录 |
| Trainova 侧 | 无角色消费；`apps/admin` 员工页仍指向已删除的 `/permission/v1/*` 与**全仓库不存在**的 `/users/v1/*` |

**本轮目的**：把门禁从"一个 app 的实现"变成"产品可复用的能力"，并按受控顺序扩大覆盖；同时把 Trainova 侧的角色管理接回同一套模型。

## 2. 设计决策（推荐口径，确认即冻结）

### D1 — 下沉到新 lib `libs:access`（**本轮暂缓，触发条件见下**）

- 内容：权限查询客户端、`requirePermission` 门禁、`DeclaredPermission` 登记表与自省路由工厂。
- 理由：门禁是跨产品的横切能力，但**不属于任何业务域**；放进 `libs:common` 会让平台库逐渐变成杂货铺，
  且 `common` 的职责（日志/基础类型）与 HTTP 授权无关。`libs:access` 不建表、不涉及迁移号段，新增成本可控。
- 自省端点路径保持不变：`GET /crate-api/access/v1/permissions`（迁到 lib 后由各 app 挂载，登记内容按 app 合并）。
- **2026-10-02 修订（用户：Aceso 之外的 app 都不管）**：下沉的唯一动机是"给第二个产品复用"，
  现在没有第二个消费者 —— 本轮**不做**，避免把已验证的实现搬一遍却无人受益。
  触发条件：Aceso 之外有产品要接角色消费时，先做 D1 再接线（届时 037 的 8 个门禁用例必须原样通过）。

### D2 — 覆盖顺序：一模块一提交，逐个放量（推荐）

1. 护理执行（037 已接，本轮只做迁移与回归）；
2. 发药确认 `POST /pharmacy/v1/dispenses/:id/confirm` → `pharmacy:dispense`；
3. 账单写操作（生成/加项/红冲/结算）→ `billing:write`；
4. 其余按"危险写操作优先"排期，读接口继续不接。

每个模块单独一个提交 + 单独验收，出问题只回滚一个模块。

### D3 — 把登记纪律变成测试（推荐）

- 约定：新增受保护路由必须与 `DECLARED_PERMISSIONS` 同提交更新，且复用同一个权限码常量。
- 落地：`DeclaredPermissionsTest` 由"对照常量"升级为**按模块断言**（护理 = `nursing:execute`；
  发药 = `pharmacy:dispense`；账单 = `billing:write`），漏登记即测试失败。
- 权限码格式继续固定为 `<域>:<动作>`，权威仍在 Nexus 目录，产品侧只声明"哪个路由用哪个码"。

### D4 — 本轮不引入资源级权限（推荐）

- 现在判定的是"动作级"（能不能做这类事），不区分"对哪一条数据"（例如仅本人负责的病区）。
- 触发条件：出现第一个"同一动作但按数据范围区分"的真实需求时再立项；届时需要的是资源归属数据模型，
  不是门禁改造，提前做只会得到没人用的字段。

### D5 — 放量协议：先有角色，再接线（**必须**）

门禁是 fail-closed：没有角色 ⇒ 403。因此每个模块接线前必须满足：

1. 目录里已存在承载该权限码的角色（如 `pharmacy.staff` + `pharmacy:dispense`）；
2. 至少一个真实账号已分配该角色（否则接线当刻全员 403）；
3. 前端对该模块的 403 有明确文案（见 §4 验收 4）；
4. 部署顺序：**建角色 → 分配 → 重启后端**；回滚时先摘角色再回滚代码。

### D6 — Trainova 侧接回同一套模型（**范围外**）

- `apps/admin` 员工页改为「IDP 主体 + Nexus 角色」：用户来自 `listIdentitySubjects`，
  角色与分配用 `listRoles` / `listSubjectRoles` / `replaceSubjectRoles`，部门继续用 Nexus `settings`。
- 前提：Trainova 后端需要像 Aceso 一样代理 `identity/v1` 与 `shared/v1`（当前只挂业务模块），
  或在应用侧直连 IDP/Nexus 端口（需评估 CORS 与 cookie 域）。**这是本计划最大的不确定项**，见 §8 裁定 3。
- 完成后删除 `ui-astro/packages/shared/src/index.ts` 中指向 `/permission/v1/*` 的 4 个函数
  （037 阶段 1 第 4 项遗留，因该页面被阻塞而未删）。
- **2026-10-02 修订（用户：Aceso 之外的 app 都不管）**：本节整体移出范围，`apps/admin` 冻结，
  4 个死函数保留；本计划只覆盖 Aceso 侧（D2 覆盖扩展 + §4 验收 4 的 403 文案）。

## 3. 接口契约

```text
GET /crate-api/access/v1/permissions      （自省端点，路径不变，登记内容按 app 合并）
  → 200 { "permission_codes": ["billing:write","nursing:execute","pharmacy:dispense"],
          "routes": [ { "method": "POST", "path": "/nursing/v1/executions/:id/administration",
                        "permission_code": "nursing:execute" }, ... ] }
```

不变式：037 已冻结的 Nexus `subject-permissions`、`subject-roles` 与 IDP `/identity/v1/roles` 契约不变；
门禁的 403/503 响应形状不变（`{"error":"forbidden","required_permission":...}` / `503` + `Retry-After`）。

## 4. 验收口径

1. **下沉无行为变化**：迁移到 `libs:access` 后，037 的 8 个门禁用例与自省用例全部原样通过（不改断言）。
2. **登记纪律可执行**：故意注释掉一条 `DECLARED_PERMISSIONS` 记录，`DeclaredPermissionsTest` 必须失败。
3. **逐模块生效**：每个新接线的模块都有"有角色 → 200 / 无角色 → 403 / 上游故障 → 503"三类用例。
4. **403 可读**：前端在无权限时展示"缺少 `xxx` 权限（该角色未分配或未生效）"，不显示堆栈，不静默失败。
5. **放量协议**：接线提交的说明里必须写明"角色是否已建、账号是否已分配"（§2 D5 四项）。
6. **Trainova**：员工页能列出 IDP 主体、分配 Nexus 角色、保存后回读一致；`/permission/v1/*` 的函数被删除。
7. **回归**：`:apps:aceso:test`、`:libs:nursing:test` 全绿；`pnpm --filter @pitchfork/aceso build` 0 error；
   Nexus `cargo test` 20 passed（不回归）。

### 2026-10-02 权限闸门在线双向验证（真实实例，未写业务数据）

| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 放行 | 有 `nursing.staff` 的会话打 `PATCH /nursing/v1/executions/<不存在>/status` | `404 execution not found`（闸门放行，业务逻辑执行；未落任何数据） |
| 放行 | 同一会话打 `POST /nursing/v1/executions/<不存在>/administration` | `400 result is required`（同上） |
| 拒绝 | 清空该会话主体的角色 → 等过 60s TTL → 重打同一写路由 | `403 {"error":"forbidden","required_permission":"nursing:execute"}` |
| 恢复 | 重新分配 `nursing.staff` → 等过 TTL → 重打 | 恢复为业务侧响应（非 403） |

结论：闸门真的在工作（放行/拒绝都可复现），403 的响应形状能被前端翻成"需要「nursing:execute」权限"；
60s 权限缓存按设计收敛。**测试期间的角色变更已全部还原**，最终 3 个主体都持 `nursing.staff`。
