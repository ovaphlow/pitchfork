## 1. 当前事实与问题

养老院入住已由 `POST /crate-api/healthcare/v1/elderly-admissions` 创建 `ELDERLY_CARE` 类型的 `healthcare.encounters`。但当前护理工作台在选中入住记录后，只以 `patient_id` 查询活动服务期并取第一条；不存在精确的入院记录与照护周期关系。

这导致同一长者存在多个活动服务期时，工作台、时间线和今日执行可能取到错误周期。新建周期时前端还固定写入 `COMMUNITY_CARE` 和当天日期，不能表达养老院入住，也不能保证与入住日期一致。离院操作仅把 encounter 改为 `DISCHARGED`；关联服务期保持活动，后续日期仍可能由任务生成逻辑创建执行记录。

现有 `nursing_service_periods` 的 `service_type` 已有稳定英文代码集合；本计划只复用 Healthcare 已有的 `ELDERLY_CARE`，不创造新的业务枚举代码。家庭上门、`nursing_visit_schedules`、签到、位置和服务时长不属于本计划。

## 2. 目标

1. 每次养老院入住都在同一数据库事务中创建唯一、可追溯的养老照护周期，周期开始日期与入住业务日期一致。
2. 护理工作台按 `encounter_id` 精确加载周期，绝不再按同一患者的“第一条活动周期”猜测关联。
3. 离院在同一数据库事务中将对应养老照护周期收束为 `COMPLETED`，从而阻止后续任务执行生成；既有评估、计划、任务、执行和记录保持可查询的历史事实。
4. 不自动终结执行中的工作，也不静默把其他类型的旧服务期绑定或关闭。

## 3. 范围

### 3.1 必须实现

- 在 `nursing_service_periods` 增加可空 `encounter_id`，并为 `ELDERLY_CARE` 服务期建立一对一关系。
- 入住创建成功时，在同一 `Pool.withTransaction` 中创建 `ELDERLY_CARE` 服务期；接口响应包含该周期。
- 为历史上已存在但尚未绑定周期的活动养老入住提供幂等补建接口；它只能创建新的、精确绑定的养老照护周期。
- 离院时锁定入住与关联周期，检查执行中任务后，在同一事务将入住设为 `DISCHARGED`、周期设为 `COMPLETED` 并写入相同业务结束日期。
- 服务期列表支持精确 `encounter_id` 过滤；`NursingPage` 用它加载所选入住记录。
- 入住页、护理工作台、Shared API 类型和错误状态反映周期已建立、需要补建或不能离院的情况。
- 覆盖事务原子性、重复提交、关联隔离、离院阻断、历史保留和不再生成未来执行的测试证据。

### 3.2 明确不在本期范围

- 不实现家庭护理上门排班、签到、轨迹、服务时长或 `nursing_visit_schedules` 的改造。
- 不自动创建入院评估、照护计划、任务、护理记录、耗材出库或执行记录；护理人员继续在既有工作台明确创建这些业务事实。
- 不批量推断、绑定或关闭既有 `HOME_CARE`、`COMMUNITY_CARE`、`HOSPICE` 周期。部署前存在的养老入住数据须由用户批准独立的对账/迁移方案处理。
- 不自动取消待执行、已逾期或执行中的历史记录；不篡改已完成、跳过、取消的执行记录。
- 不实现离院小结、长期档案导出、复评提醒、计划版本、质量评分、趋势报表、绩效或权限模型变更。
- 不改变非 `ELDERLY_CARE` encounter 的创建、更新、转诊或离院语义。

## 4. 领域规则与数据约束

### 4.1 精确归属

`nursing.nursing_service_periods.encounter_id` 表示养老照护周期对应的唯一养老入住记录。

- 只有 `service_type = ELDERLY_CARE` 的周期可以填写 `encounter_id`；此类型必须填写该字段。
- `encounter_id` 建立唯一部分索引，任何非空入住 ID 至多关联一个服务期。一次重新入住会生成新的 encounter，因此可以拥有新的服务期。
- 服务端验证 encounter 存在、类型为 `ELDERLY_CARE`，并且其 `patient_id` 与周期一致。依照既有 Nursing 跨 schema 关联惯例，本期使用服务层校验，不增加跨模块数据库外键。
- 通用 `POST /nursing/v1/periods/` 保持原有居家、社区和安宁类型；它不得接受 `ELDERLY_CARE` 或 `encounter_id`。养老周期只能由第 5 节专用流程创建。

### 4.2 入住建立周期

- `admit_date` 是周期唯一的开始日期来源；客户端不得为养老周期指定不同的 `start_date`。
- 创建患者、创建 `ELDERLY_CARE` encounter 和创建服务期必须使用同一个数据库连接与事务。任一步失败都回滚，不能出现“已入住但无周期”或“孤立周期”。
- 成功响应包含 `{ patient, encounter, nursing_period }`。`nursing_period.service_type` 必为 `ELDERLY_CARE`，`nursing_period.encounter_id` 必为返回的 encounter ID。
- 为重试和历史补建提供 `POST /crate-api/nursing/v1/periods/elderly-admission`，请求体仅为 `{ "encounter_id": "..." }`。同一活动入住重复调用返回既有周期，不能创建第二条；遇到已离院、非养老入住或患者不匹配返回 `409` 或 `400` 的项目统一错误形状。

### 4.3 离院收束

- 仅当关联养老周期状态为 `ACTIVE` 或 `SUSPENDED` 时，`PATCH /crate-api/healthcare/v1/encounters/:id/discharge` 才能完成其收束；周期最终写为 `COMPLETED`，`end_date` 取离院时间携带的业务日期。
- 如该周期存在 `IN_PROGRESS` 的执行记录，离院必须返回 `409`，且 encounter、服务期和执行记录均不变。护理人员先按既有流程完成或取消该执行，再办理离院。
- 已创建但非终态的待执行记录不在离院时修改；服务期终态使 `ensureExecutionsForDateRange` 不再为该周期生成新记录。今日工作台只展示活动服务期的执行，统计和时间线继续能够查询历史范围。
- 养老入住缺少精确绑定服务期时，离院返回可操作的 `409`，不得按患者 ID 猜测并关闭任意旧周期。上线前遗留数据必须先通过受控补建/对账处理。
- 同一入住重复离院沿用现有“already discharged”冲突语义；不得第二次改变周期结束日期或历史记录。

## 5. API 契约

### 5.1 入住响应扩展

```json
{
  "patient": { "id": "01..." },
  "encounter": {
    "id": "01...",
    "encounter_type": "ELDERLY_CARE",
    "status": "ACTIVE"
  },
  "nursing_period": {
    "id": "01...",
    "patient_id": "01...",
    "encounter_id": "01...",
    "service_type": "ELDERLY_CARE",
    "start_date": "2026-07-31",
    "end_date": null,
    "status": "ACTIVE"
  }
}
```

现有 `patient`、`encounter` 字段保持不变。Shared Aceso API 为 `ElderlyAdmission` 增加必填 `nursing_period`，并为 `NursingServicePeriod` 增加 `encounter_id: string | null`。

### 5.2 补建与精确查询

```http
POST /crate-api/nursing/v1/periods/elderly-admission
Content-Type: application/json

{ "encounter_id": "01..." }
```

- 首次成功返回 `201` 和单个周期；幂等重试返回 `200` 和同一周期。
- `GET /crate-api/nursing/v1/periods?encounter_id=01...&status=ACTIVE` 仍返回统一 `{ "records": [...], "meta": { "total": N } }` 列表形状；`patient_id` 与 `encounter_id` 同时存在时必须同时满足，不能任选其一。
- `encounter_id` 为空、非养老入住或入住不活动使用 `{ "error": "<message>" }` 返回 `400`；活动入住已经关联不同类型周期、周期状态异常或离院前缺少关联周期返回 `409`。

### 5.3 离院响应

`PATCH /crate-api/healthcare/v1/encounters/:id/discharge` 保持返回单个 encounter 对象，不将周期混入现有响应。前端在成功后各自刷新入住列表和所选护理数据；失败响应继续为 `{ "error": "<message>" }`。

## 6. 后端实施设计

### 6.1 迁移和 jOOQ

新增 Nursing 所有的 `V404__add_elderly_care_period_link.sql`：

1. 添加 nullable `encounter_id VARCHAR(32)`。
2. 修改服务类型检查以允许既有 `ELDERLY_CARE` 代码。
3. 添加约束：`ELDERLY_CARE` 与非空 `encounter_id` 成对出现，其他既有服务类型保留空关联。
4. 添加 `WHERE encounter_id IS NOT NULL` 的唯一索引，以及按 `encounter_id, status` 查询的索引；不为报表或患者列表附带无关索引。
5. 不回填既有数据，不引入跨 schema 外键，也不移动现有 `V400`–`V403`。

实现者在获授权的可恢复环境用本模块的 `jooq-config.xml` 生成并提交所需源文件；不得以共享开发库替代该步骤。

### 6.2 Nursing 所有的周期服务

在 Nursing 中将服务期的创建/关闭细节收敛为使用调用方传入 `SqlConnection` 的内部服务，确保它始终在外层事务内执行：

1. 创建方法只接受已验证的 `patientId`、`encounterId`、入住日期和统一 `now`，写入固定 `ELDERLY_CARE` 与 `ACTIVE`。
2. 通过唯一约束处理并发补建；冲突后锁定并读取同一关联周期，幂等返回，不按患者查找替代。
3. 关闭方法锁定关联周期，拒绝缺失/终态/不一致状态；查询并拒绝存在 `IN_PROGRESS` 执行的情况，再将状态和结束日期写为 `COMPLETED`。
4. `ServicePeriodService.list` 与 `ServicePeriodRoutes` 增加 `encounter_id` 精确过滤和校验。`NursingRoutes` 的 `/periods/elderly-admission` 静态路径必须在 `/:id` 动态路由前注册。
5. `ensureExecutionsForDateRange` 保持只为 `ACTIVE` 周期生成。核对今日执行查询也应用活动周期条件，不能让离院长者的历史待执行记录继续进入工作台；统计和时间线不按活动状态过滤历史数据。

### 6.3 Healthcare 入住与离院编排

Healthcare 继续拥有 encounter 状态。为避免医疗模块直接写 Nursing 表，在 Healthcare 对 Nursing 建立单向编译依赖，并调用其连接绑定服务；Nursing 不新增对 Healthcare Kotlin 库的反向依赖。

1. `admitElderly` 保持现有“已有患者或新患者二选一”和单一活动入住校验；在同一事务内先创建 encounter，再创建养老周期，最后组合响应。
2. `dischargeEncounter` 重构为单个事务：锁定 encounter，若它不是 `ELDERLY_CARE` 则保留原离院路径；若为养老入住则锁定并收束精确关联周期，最后更新 encounter。
3. 两个过程均在异常时回滚。不得用前端两次请求、后台异步任务、补偿队列或按患者 ID 的批量更新模拟事务。
4. 仅为本流程增加必要的 `409` 映射；其他 Healthcare 路由和非养老 encounter 的响应语义不变。

### 6.4 Shared API 与前端

1. 在 `@pitchfork/shared/aceso` 扩展上述类型，增加 `enrollElderlyAdmissionCarePeriod(encounter_id)`，并为 `listNursingServicePeriods` 增加 `encounter_id?`。所有调用仍经既有 `request`、token 和错误处理。
2. `AdmissionsPage` 成功办理入住后使用包含 `nursing_period` 的响应刷新列表；离院只调用原有离院 API，成功后刷新入住列表。页面不得自行创建第二个周期。
3. `NursingPage.loadResidentData` 必须使用所选 `selectedAdmission.id` 的 `encounter_id` 查询，禁止再以 `patient_id` 的第一条活动周期作为当前周期。
4. 若是历史活动入住且服务期缺失，工作台显示“建立养老照护周期”的受控恢复动作，调用幂等补建 API；不得回退创建 `COMMUNITY_CARE` 或允许手工填写开始日期。失败保留上次成功数据并显示独立错误。
5. 周期已关闭的入住不应出现在活动入住工作台；历史仅由既有时间线/记录查询呈现。本期不新增离院详情页或自动跳转。

## 7. 测试与验收

### 7.1 实现者：单元和嵌入式 HTTP 测试

新增或扩展 Nursing/Healthcare 的非数据库测试，至少覆盖：

1. `ELDERLY_CARE` 服务期输入只能走专用创建路径，开始日期从入住日期派生。
2. `encounter_id` 的精确列表条件不会匹配同患者另一入住或另一活动周期。
3. 补建首次为 `201`、重复调用为 `200`，并发唯一冲突读取既有记录。
4. 静态 `/periods/elderly-admission` 不会被 `/:id` 路由吞掉；无效/非养老/已离院请求返回预期 `400` 或 `409`。
5. 存在 `IN_PROGRESS` 执行时离院为 `409`，任何表均未改变；不存在时离院关闭服务期并保留历史执行。
6. 非养老 encounter 离院保持原行为，重复离院仍冲突。

### 7.2 独立验证者：PostgreSQL 集成测试

独立验证者新增 `ElderlyCareLifecycleIntegrationTest.kt`，仅在获准的 `aceso_test` 运行。fixture 至少包含两个入住周期、同一长者的重新入住、另一个长者、一个活动养老周期、一个旧式未绑定周期、历史完成记录、未来待执行记录和一个执行中记录。

断言：

1. 新入住创建 encounter 与精确绑定周期，服务类型、开始日期、患者和唯一关系正确。
2. 同一长者重新入住创建新的 encounter/period；按 `encounter_id` 查询互不泄漏。
3. 重复补建不产生第二周期；非活动或非养老 encounter 不可补建。
4. 正常离院后 encounter 为 `DISCHARGED`、周期为 `COMPLETED`、结束日期正确，历史评估/任务/记录和已存在执行数不变，日期范围生成不再新增记录。
5. 存在执行中记录时离院失败且事务全部回滚。

### 13.2 阻断项

1. **P1：集成测试没有验证 Healthcare 离院事务。** `ElderlyCareLifecycleIntegrationTest` 的正常离院和执行中阻断用例直接调用 `ServicePeriodService.closeElderlyCarePeriod(pool, ...)`，没有调用 `HealthcareService.dischargeEncounter` 或 Healthcare HTTP 路由。因此没有证据证明成功时 encounter 同步为 `DISCHARGED`、失败时 encounter 与周期在同一事务中保持不变；正常离院用例也没有对该 encounter 做最终状态断言。测试通过不能替代计划第 7.2 节的跨模块原子性验收。
2. **P1：历史集成断言存在空验证。** 正常离院测试为新周期创建后只检查全局 fixture 执行数量，并查询该周期原本不存在的 `PENDING` 记录，没有调用 `ensureExecutionsForDateRange`，也没有给被关闭周期建立历史记录/未来任务后验证“历史保留且未来不新增”。`@AfterAll` 才统一清理，且 cleanup 异常被吞掉，不符合“每个测试后按子表到父表清理”的交接要求。
3. **P1：SUSPENDED 周期会被 Aceso 工作台误判为缺失。** `NursingPage.loadResidentData` 按所选 `encounter_id` 查询时额外固定 `status: "ACTIVE"`；计划明确允许 `ACTIVE` 与 `SUSPENDED` 周期离院。SUSPENDED 周期因此显示“尚未建立养老照护周期”，恢复请求又会返回既有周期，工作台无法正常展示或操作该周期。
4. **P1：Playwright 验收包即使具备 Chromium 也不能作为当前功能证据。** “历史未绑定”用例先通过正常入住流程创建（该流程已经自动创建周期），再以 `if (recoverButton.isVisible())` 包住全部断言，周期已存在时会无条件通过；“执行中任务”用例只进入护理工作台，没有创建任务或 `IN_PROGRESS` 执行记录，却断言离院返回 `409`；测试还没有清理 `pw-` fixture。另有工作台页面没有 `服务类型`/`关联入住` 文本，而 Page Object 直接查找这些标签。该包需补齐受控 fixture、真实前置数据、失败断言和清理后才能复验。

### 13.3 非阻断但必须闭环项

- **P2：并发补建返回码不稳定。** `createElderlyCarePeriod` 在唯一冲突后锁读既有周期，但 `enrollElderlyAdmission` 无论插入成功还是冲突都包装为 `Pair(true, ...)`；并发第二请求可能错误返回 `201`，违反重复/并发补建应返回既有周期和 `200` 的契约。应增加并发测试并修正 created 标记。
- **P2：关闭周期缺少跨模块患者一致性校验。** 关闭逻辑按 `encounter_id` 锁周期，却没有核对周期 `patient_id` 与被锁定 encounter 的 `patient_id`；在无跨 schema 外键的设计下，异常或历史错误数据可能被错误收束。创建路径的服务层校验和关闭路径的校验需要分别有证据。
- **P2：数据库测试的清理证据不完整。** 集成测试使用固定前缀是正确方向，但统一 `@AfterAll`、best-effort 且静默吞异常的清理不能证明每个测试都隔离且最终无残留；应将清理置于每个测试生命周期并对残留/失败显式失败。
