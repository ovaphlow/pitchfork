### 现状与问题

养老收费（`/dashboard/billing`）与押金管理（`/dashboard/deposits`）已有完整页面，账单生成、手工加项、缴费、欠费、结算收束的后端能力也已在库，但整条链路在真实环境一步都走不通：

1. **费用项目字典没有任何维护入口。** 后端 `POST/PUT/DELETE/PATCH /crate-api/healthcare/v1/fee-items` 与 `@pitchfork/shared/aceso` 的 `createFeeItem` / `updateFeeItem` / `deleteFeeItem` / `updateFeeItemStatus` 全部已实现，但侧边栏「系统设置」只有 用户/部门/仓库/物资/角色，全站没有 `/dashboard/fee-items` 页面；这些写函数是死代码。唯一触点只是账单页「手工加项」弹窗里的只读下拉。
2. **新库 `fee_items` 恒为空。** `V514__add_fee_items.sql` 只建表和索引，不写种子数据，也没有任何 fixture。`GET /fee-items` 必然返回 `{"records":[],"meta":{"total":0}}`。
3. **生成账单因此必然失败。** `BillService.computeAutoItems` 要求「床位费」恰有一条启用项、「护理费」按护理评估结果等级逐级各一条启用项（按**名称**匹配）、账期内有餐次时「伙食费」恰有一条启用项。字典为空时任何账期都无法生成账单。
4. **失败提示是后端英文原文。** `respondFailure` 直接回传 `error.message`，Shared client 原样抛出，页面 `errorMessage()` 原样渲染，界面出现 `no enabled fee item for category 床位费`：中英混杂、未指明该去哪里配置。
5. **押金核销完全不存在。** 全库 `核销` 出现 0 次。押金只有 登记/退押，`V513` 与 `DepositService` 明确写着「结算收束不自动冲抵押金」，缴费/欠费/汇总口径也只统计 `payments`。用户预期的「用押金抵扣欠费再离院」没有任何入口。

### 产品决策

0. **定位前提（2026-09-28 用户确认）：费用相关功能用于「标记数据状态与业务流程收束」，不做真实的付款/收款操作。** 「缴费」「退押」「核销」都是状态标记与流程收束动作，不是收银动作：不接支付通道、不做资金对账、不追现金流。因此验收口径以「状态可追溯、状态转换无歧义、流程能收口」为准，而不是以资金到账为准；金额字段是标记载荷，不承担资金核算职责。这条前提直接影响后续计划的优先级：**「状态没被标记出来」比「钱没收回来」更严重**。
1. **开放既有能力，不新建后端字典 API。** 新增「费用项目」维护页调用既有 CRUD；后端契约保持不变。
2. **不预置种子数据。** 单价是机构自定数据，写入占位价会让自动计费生成错误账单。以「空态引导 + 生成账单前置校验」替代种子数据。
3. **后端错误文案保持不变，在前端做收费域中文化。** 后端消息是既有约定（`{"error":"<message>"}`、英文句式内嵌中文枚举），且被 `FeeItemServiceTest`、`BillServiceTest`、`PaymentServiceTest`、`BillingSettlementTest`、`DepositServiceTest` 的 `contains(fragment)` 断言锁定。本期不改后端文案，改为在 Aceso 前端新增收费域错误映射，把已知失败条件翻成可操作中文，并顺手补上「去哪配」的入口。
4. **押金核销本期纳入，定位为「结算收束时的手工核销」。** 由操作员在结算收束确认前填写核销金额，核销与冻结在**同一个事务**内完成；不做自动冲抵，不做独立于结算的核销入口（在住期间用押金抵扣另立计划）。
5. **核销复用既有两张台账，不新建表、不新增列。** 核销写入 `payments`（`method = 押金`，账单余额因此递减）与 `deposit_records`（`type = 核销`，押金余额因此递减），账单关联写入两侧 `metadata`；唯一 DDL 变更是把 `payments.method` 的 CHECK 扩到含「押金」。
6. **核销不改变结算收束的既有语义。** 区间最终账单仍创建即 `已结算`；未被核销的欠费仍随冻结收束，但界面必须在收束前明示「核销后仍欠费 ¥X，将随收束冻结、不可再收」。

## 领域模型与业务规则

### 两个台账与核销

```text
押金余额 = Σ押金登记 − Σ退押 − Σ核销
账单余额 = 账单合计 − Σ缴费（含 method = 押金 的核销缴费）
欠费     = Σ(待缴费 且 余额 > 0 的账单余额)
```

核销是**押金余额与账单余额同减**的内部结转，不产生现金流入，不改变账单合计。核销写入的 `payments` 行计入「已缴」，因此既有恒等式 `应缴 − 已缴 = 欠费` 继续成立（该处的「已缴」含义是「已收妥，含押金抵扣」）。

### 核销规则（服务端强制）

1. 核销只能由结算收束路径触发；`POST /bills/:id/payments` 的缴费方式白名单**不放行**「押金」，客户端无法伪造核销。
2. 核销在结算事务内、冻结之前执行，与 `settleEncounter` 同连接同事务；任一环节失败整笔回滚，押金台账、缴费流水、账单状态、`settled_at` 全部不变。
3. 分配目标：该 encounter 全部 `待缴费` 且余额 > 0 的账单，按 `period_start` 升序、同账期按 `id` 升序逐笔分配；单笔分配额 = min(剩余核销额, 该账单余额)。
4. 上限 = min(押金余额, 目标账单余额合计)。请求金额超过上限 → 400，不部分执行。
5. 每笔分配写入一行 `payments`（`bill_id`、金额、`method = 押金`、`operator = 认证主体`、`metadata = { "deposit_offset": true, "encounter_id": ... }`）与一行 `deposit_records`（`encounter_id`、`type = 核销`、金额、`operator`、`metadata = { "bill_id": ..., "payment_id": ..., "period_start": ..., "period_end": ... }`）。
6. 账单余额归零 → 同一事务内状态 `待缴费` → `已结清`；未归零保持 `待缴费`，随后被收束冻结为 `已结算`（既有行为）。
7. 核销金额必须 > 0、至多两位小数、不超过 `9999999999.99`；省略或 0 表示不核销。
8. 目标账单余额合计为 0 或押金余额为 0 而请求核销 > 0 → 400。
9. 并发：结算事务内既有 `SELECT ... FOR UPDATE` 锁定 encounter 行，核销在同一事务内进行；同一 encounter 并发两次结算至多一次成功，另一次 409，不产生重复核销。

### 核销资格

| 条件 | 结果 |
|---|---|
| 非养老入住 / 无 `admit_date` / 无离院（去世）日期 | 400 |
| 在住（非 DISCHARGED/DECEASED） | 409 |
| 已收束（`encounters.settled_at` 非空） | 409 |
| 核销金额 ≤ 0、超 2 位小数、越界 | 400 |
| 核销金额 > min(押金余额, 欠费合计) | 400 |
| 无欠费 / 押金余额为 0 且请求核销 > 0 | 400 |
| 请求体含未知字段 | 400 |
| 未认证 | 401 |

### 费用项目规则（既有，维护页必须如实遵守）

1. 分类固定 6 值：床位费/护理费/伙食费/个性化服务费/押金/其他；状态 启用/停用。
2. `PUT` 全量替换分类/名称/单价/备注/扩展，**不改状态**；状态只能走 `PATCH /:id/status`。
3. 账单明细是快照（`bill_items.item_code/item_name/unit_price`，与 `fee_items` 无外键），改价/停用/删除字典项不影响已生成账单。
4. 自动计费只消费 床位费/护理费/伙食费；`个性化服务费`/`押金`/`其他` 仅作为手工加项可选来源，维护页需说明这一点，避免用户误以为给「押金」配了单价就能自动抵扣。
5. 护理费按名称精确匹配护理评估的 `result_level`；同名多条启用项会使生成账单报「多个启用项」。维护页对护理费提供同名重复的即时提示（前端校验 + 后端 400 双层）。

## API 契约

### 结算收束接口（扩展，向后兼容）

```text
POST /crate-api/healthcare/v1/encounters/:id/billing-settlement
Authorization: Bearer <JWT>
Content-Type: application/json

{ "deposit_offset": 3000.00 }     // 可省略或为 {}；省略即不核销
```

- 请求体可省略或为空对象（既有调用方行为不变）；非空时只允许 `deposit_offset` 一个字段，其他字段一律 400（`operator`、`bill_id`、`amount` 等客户端不得提交）。
- `deposit_offset` 必须是数字、> 0、至多两位小数、≤ `9999999999.99`。
- 成功仍返回 `201` 与收束后的 encounter（既有响应形状），核销结果通过 `payments`/`deposit_records` 台账体现。
- 失败沿用既有 `400`/`401`/`404`/`409` 与 `{ "error": "<message>" }`。

### 既有接口的读取语义变化

- `GET /crate-api/healthcare/v1/encounters/:id/deposits`：`meta.balance` 现按新口径（减去核销）计算；`records` 可能出现 `type = 核销` 的行，其 `metadata` 带 `bill_id`/`payment_id`。
- `GET /crate-api/healthcare/v1/payments/arrears`、`GET /crate-api/healthcare/v1/payments/summary`：核销产生的 `payments` 行计入「已缴」，恒等式不变；响应字段不变。
- `POST /crate-api/healthcare/v1/bills/:id/payments`：`method = 押金` 仍为 400，不因 CHECK 放宽而放行。

### 费用项目接口

不新增、不修改路由；维护页复用既有 `GET/POST/PUT/DELETE /fee-items` 与 `PATCH /fee-items/:id/status`。

## 数据库与模块边界

### V518 迁移

在 Healthcare 库新增 `V518__add_deposit_offset.sql`，只做一件事：

- 放开 `payments.method` 的 CHECK，使其允许 `押金`，其余 5 个方式不变：先 `DROP CONSTRAINT payments_method_check`，再以同一名字重建，`NOT VALID` 不适用（表内既有数据全部满足新约束）；同步更新 `payments.method` 的中文列注释，说明「押金」只由结算核销写入。
- **不新增列、不新增表**，因此核销账单关联写入 `metadata`，不需要为 `deposit_records` 增加 `bill_id`。
- 迁移版本符合 Healthcare 的 `V500+` 号段，不移动、修改或复制 `V500`–`V517`。

获得用户授权的可恢复 codegen 数据库后，开发运行 `PITCHFORK_DB_PASSWORD=... ./gradlew :libs:healthcare:generateJooq`，只提交 CHECK 文本实际变化的生成源（预期为 `tables/Payments.java` 的 `getChecks()` 与列注释），不提交 `build/tmp` 或本地配置。

> **未授权时的降级口径（必须显式记录）**：本次 DDL 只改 CHECK 约束、不增删列，运行期 SQL 不依赖 jOOQ 生成的 CHECK 元数据，因此**未重新生成 jOOQ 不阻塞实现与测试**。此时 `tables/Payments.java` 的 `getChecks()` 与列注释相对 V518 为陈旧快照，计划状态保持「jOOQ 重生成待执行」，不得手写或假称已生成。

### 责任与依赖方向

- **Healthcare** 拥有费用项目字典、账单、缴费、押金与结算收束，V518 迁移放在 `libs/healthcare`；核销逻辑属于 Healthcare 内部，不引入新模块。
- **Healthcare 内部**：`DepositOffsetService`（新增）拥有核销分配与双台账写入；`DepositService` 拥有押金余额口径；`PaymentService` 拥有缴费/欠费/汇总口径与「客户端可提交的缴费方式」白名单；`BillService` 的结算收束逻辑本期不改；`HealthcareService` 只做跨服务的同事务编排。
- **Aceso App** 只负责注入既有认证中间件，不改路由挂载方式。
- **Aceso UI** 只经 `@pitchfork/shared/aceso` 调用 Healthcare API；不直接拼 URL，不新增领域表或后端依赖。

5. **固定缴费方式边界。** `PaymentService` 增加 `METHOD_DEPOSIT = "押金"` 常量与「账单缴费记录方式」集合，用于读取与展示；`methods`（客户端可提交白名单）保持 5 值不放行「押金」，并在注释写明核销是唯一写入路径。缴费、欠费、汇总的聚合口径与恒等式注释同步说明核销行计入已缴。

6. **接入结算编排。** `HealthcareService` 持有 `DepositOffsetService`，`settleEncounterBilling(id)` 扩展为 `settleEncounterBilling(id, depositOffset, operator)`：在同一 `pool.withTransaction` 内先执行核销（>0 时），再调用既有 `billService.settleEncounter(...)`；保持既有 400/409 语义与返回形状。

7. **暴露路由可选请求体。** `HealthcareRoutes` 的 `POST /encounters/:id/billing-settlement` 从 `body(ctx)` 读取并做字段白名单（只允许 `deposit_offset`）+ 数值校验，认证主体从 `userId(ctx)` 取得并传入服务；其余路由不动。

## 验收口径

### 主线成功

在授权隔离库 + 浏览器环境下：

1. 全新数据库进入 系统设置 → 费用项目：列表为空，空态说明自动计费至少需要「床位费 ×1、护理费 ×每等级 ×1、伙食费 ×1」并提供新增入口。
2. 新增并启用 床位费 1 条、护理费 1 条（名称与某长者的护理评估结果等级一致）、伙食费 1 条后，回到养老收费页对该长者生成某月账单成功，明细含床位费 × 在院天数、护理费 × 该等级分段天数、伙食费 × 折合餐次，金额为 ROUND_HALF_UP 到分。
3. 字典缺项时，账单页在打开生成账单对话框前即提示缺少哪一类（护理费按该入住已有等级逐级提示）并给出「去配置」入口；即使绕过前端，接口返回的失败也以中文可操作文案呈现，界面不再出现英文原文。
4. 登记押金 5000 元，生成 3 张 `待缴费` 账单合计欠费 3000 元；对该已离院入住执行结算收束并核销 3000 元后：押金余额 2000 元、3 张账单全部 `已结清`、欠费合计 0、押金台账出现 3 条 `核销` 记录、缴费流水出现 3 条 `method = 押金` 记录且逐笔对应账单。
5. 核销后仍有欠费时，收束确认弹窗在提交前明确显示该剩余金额将随收束冻结；收束完成后该 encounter 全部账单为 `已结算`，`settled_at` 非空。

### 拒绝、并发与无副作用

- 核销金额 ≤ 0、超 2 位小数、越界，或 > min(押金余额, 欠费合计) → 400，且不写入任何缴费/押金记录、不改账单状态。
- 无欠费、押金余额为 0，或目标账单余额合计为 0 而请求核销 > 0 → 400。
- 在住入住、已收束 encounter → 409；核销与收束同事务回滚，押金台账与账单状态不变。
- 请求体含 `operator`、`bill_id`、`amount` 或任何未知字段 → 400；`operator` 恒取认证主体，客户端无法伪造。
- 缺认证 `userId` → 401。
- 通过 `POST /bills/:id/payments` 提交 `method = 押金` → 400；核销只能由结算收束路径产生。
- 收束后任何生成账单、手工加项、缴费、再次核销 → 409。
- 并发两次结算同一 encounter：至多一次成功，另一次 409，且不产生重复核销或重复缴费行。
- 停用或删除费用项目不影响已生成账单的明细快照与合计。
- 费用项目维护页的校验与后端一致：非法分类、超长名称、非正单价、超 2 位小数、超上限、非法状态值均被拒并给出中文提示。
- 未改动后端错误文案与 `{"error": "<message>"}` 响应形状；`FeeItemService`、`BillService`、`PaymentService`、`BillingSettlementTest`、`DepositServiceTest` 的既有断言全部保持通过。

## 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 核销写入绕过缴费白名单 | 客户端可伪造押金抵扣 | `PaymentService.methods` 保持 5 值；核销只能由结算路径写入，DB CHECK 放宽只为服务端写入服务。 |
| 核销与收束不在同一事务 | 收束失败但押金已被扣减 | 核销与 `settleEncounter` 共用同一 `pool.withTransaction`，任一失败整笔回滚。 |
| 押金余额口径漏算核销 | 余额虚高，退押可超付 | `balanceOf` 计入「核销」减项，并补 `DepositServiceTest` 余额与退押上限用例。 |
| 恒等式 `应缴 − 已缴 = 欠费` 被打破 | 汇总页数字对不上 | 核销行写入 `payments` 而非旁路台账，聚合口径不变，仅注释说明「已缴」含押金抵扣。 |
| 未重新生成 jOOQ | 生成源与 V518 的 CHECK 文本不一致 | 只改 CHECK 不增删列，运行期不依赖该元数据；授权后立即重生成，未授权时显式记录为待执行项。 |
| 把「押金」当成自动计费分类 | 用户误以为配单价即可自动抵扣 | 维护页明确标注只有 床位费/护理费/伙食费 参与自动计费；核销只在结算收束时手工发生。 |
| 结算后仍有欠费被默认遗忘 | 财务口径争议 | 收束确认弹窗在提交前显示「核销后仍欠费 ¥X 将随收束冻结、不可再收」；本计划不改冻结语义，只把事实说清。 |
| 前端错误映射掩盖真实原因 | 排障困难 | 已知条件给中文可操作文案，未映射错误显示中文兜底并附原始信息为次要小字；后端文案与响应形状不变。 |
| 相关文件已有未提交改动 | 覆盖用户工作或错误合并 | 开发先交接当前 `git status` 与 diff；只追加最小独立 hunks，重叠处协调，不 reset/revert/checkout。 |
| 数据库与 codegen 需授权 | 越权连接造成数据风险 | 默认验证全部不连库；集成/E2E 与 `generateJooq` 仅在用户明确授权的可销毁环境执行。 |
| 范围蔓延到在住核销/自动冲抵 | 结算语义与对账口径被动摇 | 本计划只做结算时手工核销；在住抵扣、自动冲抵、红冲与撤销收束明确列为后续独立计划。 |
