# Aceso 院内护理异常事件与交班闭环 MVP 实施计划

更新时间：2026-08-12

状态：待实施

## 1. 决策、目标与边界

本计划补齐养老院每天、每班都必须运行的两条安全主线：院内异常事件的上报与处置追溯，以及交班人向接班人交付重点风险和未完成事项。

它不以此前尚未完成的复评、护士医嘱核对、药房发药、退药、调拨、采购或库存单位切换为前置条件。实现只能复用已稳定存在的养老入住、精确照护周期、护理任务/执行、护理记录、护理时间线与离院收束边界；不得借本计划补做上述功能。

养老入住与照护周期计划已将“院内护理异常事件与交班闭环”列为养老主线的后续能力。当前护理工作台能够记录日常护理、执行、时间线和医嘱核对，但没有一套可按入住和周期追溯的异常事件、处置过程或双向确认的班次交接事实。本计划不把自由文本护理记录冒充为可审计的异常或交班流程。

### 1.1 必须实现

1. 对精确关联的活动 `ELDERLY_CARE` 入住上报院内护理异常事件，完整记录发生时间、类别、严重程度、说明和认证主体。
2. 为异常事件追加即时处置、通知/联系事实、观察结果和关闭说明；任何已写入的事实不得被静默覆盖或删除。
3. 为照护单元和业务日期创建班次交接单。交班单冻结创建时的只读重点事项快照，并允许交班人补充文字事项。
4. 接班人通过认证主体确认接收交班；交班人、接班人、时间和原始内容均可追溯。
5. 在现有护理时间线显示异常事件和交班摘要，且可进入只读详情；时间线读取绝不产生新事件、交班、任务、执行、库存或护理记录。
6. 在现有 `NursingPage.tsx` 中提供异常事件和交班工作区。所有前端请求只能经 `@pitchfork/shared/aceso`，不直接 `fetch`。
7. 实现字段白名单、精确 `encounter_id + period_id` 归属校验、认证主体审计、锁定/幂等保护、分页和统一错误响应。
8. 完成本计划指定的非数据库测试、编译、前端构建和差异检查；真实 PostgreSQL 与浏览器验收只在获授权的隔离环境执行。

### 1.2 明确不在本期范围

- 不实现床旁给药、给药单（MAR）、拒服/漏服/暂缓、双人核对、条码、药房库存、发药、退药或药品批次追踪。
- 不实现自动风险评分、自动停嘱、自动修改护理任务/执行、自动生成新照护计划或自动调用医生。
- 不实现排班、人员主数据、消息通知、短信/电话/微信实际发送、家属门户、电子签名、影像附件、打印/PDF、导出或跨机构上报。
- 不建立独立的床位、照护单元或护理班次主数据。交班只能使用既有入住可验证的照护单元信息；若当前数据没有可验证的单元字段，开发必须在实现前回报并单列最小主数据计划，不能接受客户端自由文本绕过。
- 不改写既有护理记录、评估、计划、任务、任务执行、医嘱、库存、药房单或已冻结的离院交接摘要；历史离院摘要不因本计划自动重算或补写。
- 不为非 `ELDERLY_CARE` 入住、居家服务或跨患者/跨入住数据提供该流程。

## 2. 业务主线与规则

### 2.1 异常事件

异常事件是已经发生或被发现的客观护理安全事实，不是任务执行备注、医嘱状态或库存操作。首版类别为中文业务值：`跌倒/坠床`、`走失`、`压疮`、`误吸/噎食`、`用药差错`、`感染暴露`、`其他`；严重程度为 `一般`、`较重`、`严重`。不得为该领域自行加入英文业务 code。

创建事件时服务端必须：

1. 锁定路径中的 encounter，验证其存在、类型为 `ELDERLY_CARE` 且状态为 `ACTIVE`。
2. 锁定该 encounter 的唯一精确护理周期，验证周期的 `encounter_id`、患者归属和活动状态；不得按 `patient_id` 推测周期。
3. 验证 `occurred_at` 不在未来，且其上海业务日期不早于周期开始日；客户端不能提交 `id`、`period_id`、`reporter`、状态、审计时间或任意 `metadata`。
4. 从认证上下文取得上报人；在同一事务中写入事件与第一条“已上报”审计事实。任一写入失败则两者均回滚。

事件初始状态固定为 `已上报`。处置记录只能追加，允许把事件推进为 `处理中`，关闭必须填写关闭说明，状态转为 `已关闭`。关闭后不能重开、编辑或删除；发现新的风险时必须新建事件。路由和服务端都必须拒绝以“编辑”替换历史文本、处置人或发生时间。

不允许在离院或去世后的周期新建事件。为了保存离院前事件的最终行政处置，既有事件可以在周期终态后追加一次关闭记录，但必须仍精确归属于该事件、发生时间不得被改写，且不能创建任何新任务、计划、医嘱或库存操作。该例外不适用于新建事件或新建交班。

“通知”只记录已采取的联系方式、对象、时间和结果，不调用任何外部消息系统，也不把“已联系”当作临床处置完成。

### 2.2 班次交接

交班单以“照护单元 + 上海业务日期 + 班次”为一个事实单元。首版班次为中文业务值 `早班`、`中班`、`夜班`。服务端从当前活动养老入住的既有照护单元字段验证交班单范围；客户端不提交或覆盖照护单元、交班人和接班人。

创建交班单时，服务端在一个只读快照查询中收集该照护单元下的：

- 本班尚未完成或进行中的护理执行；
- 尚未关闭的异常事件及其最新处置摘要；
- 本业务日新增的护理记录；
- 活动养老入住的基础识别信息和精确 `encounter_id`、`period_id`。

快照被保存为结构化交班事项，不在前端临时拼接，也不在读取时重新计算并覆盖原交班内容。每个自动事项都保留来源类型、来源 ID、入住 ID、周期 ID、摘要和快照时间；手工事项可附在同一交班单中。快照只是交接时的事实，不会改变源任务、事件或护理记录的状态。

同一“照护单元、业务日期、班次”永久只能有一张交班单。创建请求需要 `Idempotency-Key`：同键同内容返回原交班单，同键不同内容返回 `409`；不同键的并发创建由范围唯一约束与锁读保证至多产生一张。接班操作只允许一次，接班人由认证上下文写入；重复接班或尝试覆盖接班人返回 `409`。已接收交班单不可编辑，补充内容只能追加为新事项，并保留补充人和时间。

创建交班只允许当前活动养老入住范围。周期终态后的交班单只读，不能新建、接收或补充。系统不因未关闭异常事件阻止离院；本期也不把异常事件补入既有离院摘要，后续如有合规需求须单列快照版本演进计划。

### 2.3 无副作用和边界

- 异常事件和交班写入不得调用 `ensureExecutionsForDateRange`，不得生成或改变任务执行。
- 不改变医嘱临床状态、护士核对字段、药房发药单、库存结存或库存流水。
- 不复用 `healthcare.medical_records` 的 `NURSING_RECORD` 作为事件或交班权威数据；必要的展示链接由时间线读取新增 Nursing 事实表完成。
- 时间线、列表、详情和交班快照读取不得触发事件创建、状态变更、通知、任务生成或数据清理。
- 任何 API 错误统一为 `{ "error": "<message>" }`，不返回 SQL、堆栈、未过滤的审计数据或其他入住内容。

## 3. 数据、模块与 API 契约

### 3.1 Nursing 数据归属

新增迁移归 Nursing lib 所有。实施开始时，开发必须先核对 `libs/nursing` 的实际 Flyway 历史和已分配的计划迁移，选择连续且不会要求 `outOfOrder` 的 `V4xx` 版本；不得因为本计划独立而跳过或抢占已分配的版本号。

迁移新增四张事实表：

| 表 | 目的 | 核心约束 |
|---|---|---|
| `nursing_incidents` | 异常事件主事实 | ULID 主键；`encounter_id`、`period_id`、类别、严重程度、状态、发生时间、上报人；按周期/发生时间和未关闭状态建立最小索引。 |
| `nursing_incident_actions` | 处置、通知、观察、关闭的追加事实 | ULID 主键；`incident_id` 外键；动作中文类型、正文、认证主体、发生时间；禁止更新/删除入口。 |
| `nursing_shift_handovers` | 班次交班头 | ULID 主键；照护单元快照、业务日期、班次、交班人/时间、接班人/时间、幂等键/摘要；`照护单元 + 业务日期 + 班次` 建立范围唯一约束。 |
| `nursing_shift_handover_items` | 自动快照与人工/补充事项 | ULID 主键；`handover_id` 外键；精确 encounter/period、来源引用、事项正文、创建人/时间；不能从客户端伪造来源关联。 |

`encounter_id` 保持跨 schema 的弱关联，Healthcare 在进入 Nursing 写入前完成 encounter 资格校验；Nursing 不依赖 Healthcare Kotlin lib 或直接读取 Healthcare 表。交班快照收集与照护单元活动入住校验由 Healthcare 侧通过连接绑定端口完成，使用生成表类 `ENCOUNTERS`/`PATIENTS`/`MEDICAL_RECORDS`/`NURSING_SERVICE_PERIODS`；`ShiftHandoverService` 只读写 Nursing 事实表，不直读 Healthcare 表。重要查询使用实际生成的 jOOQ 表类；不以 `DSL.table` 或字符串字段替代新表类。只有获得可恢复 codegen 数据库的明确授权后，才运行 `generateJooq` 并提交实际生成源。

### 3.2 聚合服务与公开接口

Healthcare 负责验证养老入住资格、认证上下文和公开聚合接口；Nursing 负责同连接的事件/交班读写、锁定和时间线映射。Aceso App 只做已有的模块挂载与依赖注入，不创建模块之间的 HTTP 回调。

新增 API 路径如下，所有列表都返回 `{ "records": [], "meta": { "total": 0 } }`：

```text
POST /crate-api/healthcare/v1/encounters/:id/nursing-incidents
GET  /crate-api/healthcare/v1/encounters/:id/nursing-incidents?status=&date_from=&date_to=&limit=&offset=
GET  /crate-api/healthcare/v1/encounters/:id/nursing-incidents/:incidentId
POST /crate-api/healthcare/v1/encounters/:id/nursing-incidents/:incidentId/actions
POST /crate-api/healthcare/v1/encounters/:id/nursing-incidents/:incidentId/close

POST /crate-api/healthcare/v1/nursing-shift-handovers
GET  /crate-api/healthcare/v1/nursing-shift-handovers?care_unit=&business_date=&shift=&limit=&offset=
GET  /crate-api/healthcare/v1/nursing-shift-handovers/:id
POST /crate-api/healthcare/v1/nursing-shift-handovers/:id/receive
POST /crate-api/healthcare/v1/nursing-shift-handovers/:id/items
```

`POST /encounters/:id/nursing-incidents` 只接受 `incident_type`、`severity`、`occurred_at`、`description` 和可选 `initial_action`。`POST /actions` 只接受动作类别、正文、可选通知对象和通知结果。`POST /close` 只接受关闭说明。所有 actor、状态、事件/周期/入住 ID、时间戳、来源 ID、幂等存储字段和 `metadata` 均由服务端推导或拒绝。

创建交班只接受必填 `encounter_id`（锚定入住）、上海业务日期、班次、可选手工事项和 `Idempotency-Key`；锚定入住须为活动 `ELDERLY_CARE`、`department` 非空可验证，快照覆盖整个照护单元（非仅锚定入住），照护单元由服务端验证并确定。接班请求只能是空对象，接班人来自 JWT 主体。补充事项只接受正文，不允许客户端指定另一个入住、周期、来源事实或创建人。

错误顺序保持一致：对象不存在为 `404`；非养老、字段格式/白名单错误为 `400`；非活动入住、周期不一致、状态冲突、重复创建、重复接班、已终态限制或并发竞争为 `409`；认证主体缺失为 `401`。

### 3.3 时间线与页面

扩展 `NursingTimelineService`，在既有按 `period_id + encounter_id` 的批量读取、内存合并、排序、分页基础上加入异常事件和交班来源。新增时间线来源须沿用既有技术枚举和 UI 显示模式；对外业务类别、严重程度和状态仍为本计划约定的中文值。禁止按每个时间线事件再单独查询详情形成 N+1。

`NursingPage.tsx` 增加两个局部工作区：

```text
护理工作台
├── 异常事件
│   ├── 当前入住的事件列表、状态、严重程度和发生时间
│   ├── 上报、追加处置/通知、关闭和只读审计详情
│   └── 时间线跳转
└── 班次交接
    ├── 当前照护单元/班次的已冻结事项
    ├── 手工补充事项和接班确认
    └── 历史交班只读详情
```

提交期间禁用对应命令，失败时保留输入和当前入住上下文；异常类别、严重程度、班次使用选择控件，不能以自由文本伪造业务值。窄屏下长描述、处置正文、交班事项和错误信息不得重叠，列表可横向滚动。页面不显示未授权入住的数据，也不将完整异常详情塞入时间线摘要。

## 4. 实施步骤

1. **核对基线与单元字段。** 阅读根、后端和前端 `AGENTS.md`，核对现有养老入住的照护单元来源、`NursingTimelineService`、`HealthcareRoutes`、`NursingPage`、认证中间件、任务执行查询和本计划的 Flyway 版本。若没有可验证单元来源，停止在设计阶段并单列最小主数据方案。
2. **新增 Nursing 迁移与生成源。** 只新建本计划的四张表、中文业务值约束、外键和最小查询/并发索引；不修改历史迁移或跨 schema 建外键。获授权后生成且只提交实际 jOOQ 变化。
3. **实现 Nursing 连接绑定服务。** 新建事件与交班服务，提供同连接的资格后写入、锁定、追加、关闭、创建/接收/补充交班和只读查询方法；确保状态与唯一竞争在事务中收束。
4. **实现 Healthcare 编排与路由。** 在一个外层事务中锁定 encounter 和精确 period，执行资格判断后调用 Nursing 服务；路由只解析受控请求、分页和认证主体，静态路径置于泛型 `/:id` 前。
5. **扩展时间线、Shared API 与工作台。** 更新时间线批量读取与事件映射，随后增加 Shared 类型/函数和护理工作台两个工作区；不得直接请求模块 URL。
6. **编写默认测试并交付候选。** 覆盖输入、状态、并发、精确隔离、时间线无副作用与前端失败状态，记录实际命令、退出码、jOOQ 状态和未运行项。
7. **在授权环境进行隔离验证。** 测试角色只在可清理的 `aceso_test` 执行迁移、真实事务和 Chromium 主线；缺陷按最小复现回传，开发仅修复本计划范围，评审在证据闭环后更新最终状态。

## 5. 验收口径

### 5.1 主线成功

1. 护理员为活动养老入住上报“跌倒/坠床”事件，得到 `201`；事件精确关联当前 encounter 与 period，且上报人来自认证主体。
2. 护理员追加即时处置和家属联系结果，事件转为“处理中”；首次上报内容、处置人和时间仍可读取。
3. 护理员填写关闭说明并关闭事件；重复关闭、编辑旧处置或覆盖操作者均返回 `409`，数据库历史不变。
4. 交班人创建当前照护单元的交班单，交班事项同时包含未完成执行、未关闭事件和手工重点事项；创建本身不改变这些来源记录。
5. 接班人接收交班后，交班人、接班人、时间和冻结事项一致；重复接班不覆盖首次接班事实。
6. 护理时间线按选中 encounter 和 period 同时显示事件/交班摘要，详情严格隔离，读取没有新增数据库行或改变任务、执行、医嘱、库存。

### 5.2 拒绝、并发与边界

- 非养老、已离院、已去世、缺失/不一致周期、另一患者或另一入住的数据必须按 `400`/`404`/`409` 拒绝，不能跨入住写入或读取。
- 未来发生时间、未知字段、伪造 actor/status/period/encounter/source/metadata、空关闭说明、非法中文业务值和缺少认证主体均被拒绝。
- 同一事件的并发关闭至多成功一次；同一照护单元、业务日期和班次的并发交班创建至多保留一张交班单；相同幂等键重试不产生第二张。
- 终态周期不能新建事件或交班；对离院前既有事件的允许关闭不改变发生时间、入住、周期或任何临床/库存数据。
- 创建、追加、关闭、接班、列表、详情和时间线均不得创建/修改护理任务、执行、护理记录、医嘱、药房单、库存操作或离院摘要。
