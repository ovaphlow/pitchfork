## 1. 决策与规模控制

路线图的下一阶段是“护理员工作量和计划完成率统计”。本计划只实现其中风险最低、无需新增数据模型的第一小步：让护理员在既有“今日执行”工作台中看见并筛选逾期执行记录。

本计划刻意限制为一个既有列表接口的扩展和一个工作台交互闭环：不新建页面、不新增表、不产生定时任务。计划实现前预计只修改 Nursing 执行服务/路由、Shared API 类型、`NursingPage.tsx` 与相邻测试。

## 2. 目标

1. 护理员能一眼看到所选日期、周期和执行人范围内的逾期执行数量。
2. 护理员能点击“逾期 N 项”只查看逾期记录，并清晰知道每项已逾期多久。
3. 逾期是只读派生状态，不改变 `PENDING`、`IN_PROGRESS` 等既有状态机，也不影响完成、跳过、取消和耗材扣减流程。
4. 列表分页、既有状态筛选和耗材摘要查询保持原行为，且不会新增 N+1 查询。

## 3. 范围

### 3.1 必须实现

- 扩展既有 `GET /crate-api/nursing/v1/executions/today`：支持 `overdue=true` 查询参数，并在响应 `meta` 中返回 `overdue_total`。
- 今日执行每条记录增加 `is_overdue` 与 `overdue_minutes` 两个只读字段。
- 在现有 `NursingPage.tsx` 的“今日执行”区域显示可点击的“逾期 N 项”筛选；启用时只显示逾期记录，且可一键恢复全部记录。
- 逾期记录显示明显但不干扰操作的中文标签，例如“已逾期 35 分钟”或“已逾期 2 小时 10 分钟”。
- 为逾期判定、筛选条件、分页 `meta` 和前端构建提供验证证据。

### 3.2 明确不在本期范围

- 不实现护理员个人工作量、跨日/周/月报表、计划完成率、排行榜、图表或独立仪表盘。
- 不修改或自动升级执行状态，不自动跳过、取消、通知、催办或发送消息。
- 不实现家庭照护上门签到、轨迹、服务时长、SLA 配置或告警规则管理。
- 不新增数据库表、Flyway 迁移、jOOQ codegen 或新的权限模型。
- 不更改既有 `/today` 日期区间和时区策略；本计划只在现有查询结果的时间基准上判定是否逾期。

## 4. 领域规则

### 4.1 逾期定义

一次执行在同一服务端参考时间 `now` 下满足以下全部条件时为逾期：

```text
status ∈ { PENDING, IN_PROGRESS }
AND planned_time < now
```

- `COMPLETED`、`SKIPPED`、`CANCELLED` 永不显示为逾期，即使实际完成晚于计划时间。
- `planned_time == now` 不算逾期；比较采用严格小于。
- `overdue_minutes = floor(Duration.between(planned_time, now).toMinutes())`；非逾期记录返回 `null`。
- 同一次响应的所有 `is_overdue`、`overdue_minutes` 和 `meta.overdue_total` 必须使用服务端在查询开始时获取的同一个 `now`，避免边界时刻前后不一致。

### 4.2 筛选和分页

`overdue=true` 只能返回逾期记录，并可与 `date`、`period_id`、`executor` 组合使用。

- `overdue=true` 与 `status=COMPLETED|SKIPPED|CANCELLED` 同时传入时返回 `400`，避免“逾期终态”这种无意义组合。
- `overdue=true` 与 `status=PENDING|IN_PROGRESS` 可组合使用。
- 未传 `overdue` 或传 `false` 时保留现有列表语义，但每条记录仍返回逾期派生字段。
- 现有 `meta.total` 表示当前全部筛选条件（包括 `overdue`）后的总数。
- 新增 `meta.overdue_total` 表示相同日期、周期、执行人范围内的全部逾期数，**忽略** `status` 和 `overdue` 本身，以便工作台上的逾期按钮在状态切换时保持稳定。
- 记录继续按 `planned_time ASC` 排序；逾期筛选下最早逾期的任务自然排在最前。

## 5. API 契约

### 5.1 扩展今日执行查询

```http
GET /crate-api/nursing/v1/executions/today?date=2026-07-30&period_id=01...&executor=01...&status=IN_PROGRESS&overdue=true&limit=50&offset=0
```

响应保持统一分页形状：

```json
{
  "records": [
    {
      "id": "01...",
      "status": "IN_PROGRESS",
      "planned_time": "2026-07-30T09:00:00+08:00",
      "is_overdue": true,
      "overdue_minutes": 95
    }
  ],
  "meta": {
    "total": 1,
    "overdue_total": 3
  }
}
```

`is_overdue` 始终返回布尔值；`overdue_minutes` 仅在 `is_overdue = true` 时为非负整数，否则为 `null`。不得使用中文状态值替代既有英文 API 状态码。

### 5.2 错误响应

- `overdue` 不是 `true` 或 `false` 时返回 `400`：`{ "error": "overdue must be true or false" }`。
- `overdue=true` 与终态 `status` 同时传入时返回 `400`：`{ "error": "overdue cannot be combined with terminal status" }`。
- 其他日期、分页和认证错误继续遵循既有 Nursing 路由约定。

## 6. 实施设计

### 6.1 后端：`TaskExecutionService`

1. 为 `todayExecutions` 增加 `overdue: Boolean?` 参数，并在方法入口固定 `now`。
2. 用一个可测试的纯函数（或等价内部 helper）计算单条记录的逾期字段；不要在循环内重复调用 `OffsetDateTime.now()`。
3. 为 `overdue=true` 向现有 SQL 条件添加：`status IN ('PENDING', 'IN_PROGRESS') AND planned_time < :now`。
4. 用独立聚合查询计算 `overdue_total`：复用日期、周期、执行人条件，但忽略 `status` 与 `overdue` 筛选；不得先加载全部列表再在内存计数。
5. 将派生字段写入 `executionWithSummaryJson` 的 JSON；保留既有耗材摘要批量加载流程，不能为逾期字段产生额外逐行查询。

### 6.2 后端：`TaskExecutionRoutes`

1. 严格解析可选 `overdue` 参数；缺省为 `null`，显式 `false` 为 `false`。
2. 在调用服务前校验它与 `status` 的组合，按第 5.2 节返回 `400`。
3. `/today` 的静态路由继续在 `/:id` 前注册；不新增新的动态路由。

### 6.3 Shared API 与前端

1. 在 `@pitchfork/shared/aceso` 的 `NursingTodayExecution` 中加入 `is_overdue`、`overdue_minutes`；为今日列表分页响应补充 `meta.overdue_total`。
2. `listNursingTodayExecutions` 增加 `overdue?: boolean` 参数，继续使用既有 `request` 和 query helper。
3. 在 `NursingPage.tsx` 新增局部 `todayOverdueOnly` 状态；点击逾期按钮时设置该状态、清空互斥的终态筛选，并按原日期、周期、执行人刷新列表。
4. 逾期为零时按钮可见但不可触发空筛选，文案为“无逾期”；加载失败沿用现有今日执行错误区域。
5. 每个逾期行在状态列附近显示 `Badge`；使用分钟/小时中文格式化 helper，移动宽度下允许换行，不截断“逾期”与时长。
6. 完成、跳过、取消成功后，沿用既有 `loadTodayExecutions` 刷新路径，使逾期数和行标签立即重新计算。

## 7. 测试与验收

### 7.1 后端测试

至少覆盖：

1. `PENDING`、`IN_PROGRESS` 且计划时间早于 `now` 时为逾期；相等或晚于 `now` 时不逾期。
2. 三种终态即使计划时间已过也不逾期，且 `overdue_minutes = null`。
