## 1. 背景、目标与排期关系

现有 Inventory 以 `materials.package_unit`、`materials.split_unit` 和 `split_ratio` 表达物资单位，
`stocks.quantity`、`stocks.locked_quantity` 与 `stock_operation_details.quantity` 均以包装数量记账。
护理耗材的 `SPLIT` 输入会先换算为包装数量；Pharmacy 的发药、退药、申领调拨和采购收货则全部固定为
`PACKAGE`。这使“2 盒又 5 粒”、按毫升消耗、部分退回、盘点差异、批次成本和包装规格变更需要依赖
小数包装数量，不能成为长期账实一致性的基础。

[ADR-001：库存以最小可发放／可消耗单位记账](../decisions/ADR-001-inventory-base-unit-of-measure.md)
已提出目标模型：库存事实以物资定义的基础单位记账；采购、入库、展示和盘点可以使用包装单位输入，
但必须保存换算快照。本计划把该 ADR 落为一个可审计、可回滚、兼容历史 API 的独立交付。

本计划按用户优先级**不等待，也不代替** 013、014 的缺陷修复、数据库验收或浏览器验收：

- 013、014 的未完成工作及其验收证据仍各自归属原计划；015 不修改其状态、不吸收其缺陷，也不以其
  默认构建结果作为本计划通过证据；
- 015 只以已存在的 Inventory V200/V201、Nursing V400--V406 和当前已挂载的 API 为基线。013/014
  候选代码若继续使用 `StockService` 的包装单位端口，015 在过渡期保留该端口，由 Inventory 内部做
  明确的包装到基础单位换算；
- 不在 015 修改 Pharmacy 的 V300--V303 表或采购、发药、申领、退药的状态机。后续对其领域明细增加
  基础数量镜像，须在相应 Pharmacy 计划中单独审查和验收；本计划以关联的库存操作明细为该等动作的
  基础数量权威记录；
- 015 的代码落地须在独立分支或明确的合并顺序中进行。若 013/014 候选改动与 `StockService`、
  Shared API 或 `PharmacyPage.tsx` 冲突，合并解决和原计划复验归还给 013/014，不作为 015 的附带修复。

目标闭环如下：

```text
物资定义基础单位和精度 + 包装规格/换算率
    -> 操作员按包装或基础单位录入
    -> 服务端精确换算、校验并固化输入/换算快照
    -> 库存结存、可用量、锁定量、批次与成本按基础数量记账
    -> API/UI 同时展示基础数量和可读包装换算
```

本计划完成后，后续“盘点、差异调整与报损”可以以同一基础数量账本实现；供应商主数据、采购退货、
自动补货等仍应各立计划，不能混入本期。

1. 将每个物资的基础单位、基础数量精度和包装规格显式建模；一个物资只能有一个有效基础单位，

## 4. 领域规则与数量语义

### 4.1 基础单位和包装规格

- `base_unit` 是一项物资最小且合法的发放/消耗单位，例如“片、粒、支、瓶、毫升、双、枚”；它不是
  任意可无限切分的物理单位。每项物资恰好一个有效 `base_unit`；
- `base_quantity_scale` 是该基础单位允许的小数位，范围 `0..6`。片、粒、支、瓶、双、枚默认 `0`；
  仅经业务确认的液体或可分割物资允许大于零。所有基础数量以 `NUMERIC(20,6)` 保存；
- 一个包装规格由 `input_unit`、`base_ratio` 和状态组成，`base_ratio > 0` 表示一个输入单位等于多少
  基础单位。基础单位本身也有一条固定 `base_ratio = 1` 的有效规格；
- 每个物资最多一个 `is_default = true` 的活动包装规格，作为旧 `PACKAGE` 端口与过渡 API 的默认映射。
  非默认活动规格可以用于受控的新 API；已停用规格可读、不可再录入；
- 一旦该物资有库存结存、已确认库存操作或护理耗材关联，不能修改 `base_unit`、`base_quantity_scale`，
  也不能修改/删除已被引用的规格或其换算率。包装变更只能新增规格并停用旧规格；
- 输入数量乘以 `base_ratio` 后必须正数且符合该物资 `base_quantity_scale`。不精确或超出精度的换算返回
  `400`；库存不足、物资停用、批次无效、规格非活动、库存迁移阻断或并发状态变化返回 `409`。

### 4.2 成本、批次、锁定和不可变流水

- `stocks.base_quantity`、`stocks.locked_base_quantity` 和可用量均以基础单位计算；任何时刻必须满足
  `base_quantity >= locked_base_quantity >= 0`；
- `stock_operation_details.base_quantity`、`base_unit`、`input_quantity`、`input_unit`、
  `unit_spec_id`、`conversion_ratio`、`input_unit_cost`、`base_unit_cost` 和 `total_cost` 都是确认流水的
  不可变快照。不得从当前物资配置倒推历史换算；
- `total_cost` 是该输入行的总成本。`base_unit_cost` 只用于计算/展示，采用 `NUMERIC(24,8)`；金额累计和
  事务核对以 `total_cost` 为准，金额在写入前按约定成本精度明确量化，不能因显示格式悄悄改变账面值；
- 批次、有效期、物资启用状态、可用量和锁定量均按基础数量校验。一个操作的多个输入行可对应相同
  物资/批次，但每条输入行都保留自己的规格和成本快照；
- 任何入库、出库、护理耗材消耗、退回、锁定或释放只能追加新的操作/关联事实或更新当前结存，不能修改
  既有 `CONFIRMED` 操作明细。未来的盘点、更正与报损也必须遵从这条规则；
- 同连接 Pharmacy 包装端口在过渡期只接受当前默认包装规格的正数量和输入单位成本。它们内部转换为
  基础数量；没有默认规格、规格已停用或转换不精确时返回业务错误，绝不回退为小数包装扣减。

### 4.3 历史迁移与阻断状态

历史数据处理按以下确定顺序执行：

1. `split_unit` 非空且 `split_ratio > 0` 的物资：基础单位为 `split_unit`，默认包装规格为
   `package_unit -> split_ratio`；
2. 没有拆零定义的物资：基础单位为 `package_unit`，默认规格比率为 `1`；
3. 对历史 `PACKAGE` 明细，输入快照为原 `quantity` 和当时的包装规格，基础数量为
   `quantity * base_ratio`；对历史 `SPLIT` 明细，输入快照为 `split_quantity` 与基础单位，
   基础数量等于该输入数量；
4. `SPLIT` 明细缺少有效 `split_quantity`、物资缺失可用单位、比率无效、数量不符合确认精度，或库存
   结存无法与可回放明细一致时，写入可查询的迁移异常记录并将相应物资标为 `MIGRATION_BLOCKED`；
5. `MIGRATION_BLOCKED` 物资及其库存仍可按旧字段只读查询，但不得新建/确认任何库存、药房或护理库存
   写入。业务确认后必须通过受控的独立修复脚本生成新的调整事实并留下审计证据；不得直接 UPDATE
   历史数量、操作或成本。

迁移成功不等同于账实验收。测试必须复算“每个库存行基础数量/锁定量与历史操作之和”的受控 fixture，
并将历史异常、修复原因和结果记录在本计划验收材料中。

## 5. 数据设计与 Flyway

### 5.1 Inventory V202

在 `libs/inventories/src/main/resources/db/migration/` 新增
`V202__add_base_unit_and_packaging_specs.sql`。它是 Inventory 所有权内的下一迁移：不得改写 V200/V201，
不得复制到 Pharmacy 或 Nursing，不启用全局 Flyway `outOfOrder`。

V202 以新增列、约束、索引和确定性回填组成；所有历史列保留，未解决行保留为只读历史。

| 对象 | 新增内容与规则 |
| --- | --- |
| `materials` | `base_unit`、`base_quantity_scale`、`unit_model_status`（`LEGACY`、`ACTIVE`、`MIGRATION_BLOCKED`）和 `updated_at`。先允许迁移阶段为空，安全回填后只允许 `ACTIVE` 物资使用非空基础单位/精度。旧 `package_unit`、`split_unit`、`split_ratio` 保留为历史兼容来源，不再作为新写入的权威模型。 |
| `material_unit_specs` | 新表：ULID `id`、`material_id`、`input_unit`、`base_ratio NUMERIC(20,6)`、`is_base_unit`、`is_default`、`status`（`ACTIVE`、`RETIRED`）、创建/停用审计字段。约束一个物资最多一条基础规格、最多一个活动默认规格；`base_ratio > 0`。对已引用规格禁止物理删除。 |
| `stocks` | 新增 `base_quantity NUMERIC(20,6)`、`locked_base_quantity NUMERIC(20,6)` 和 `unit_model_status`。新写入以两项基础数量为权威；旧数量列只保留给过渡投影与历史比对。增加 `base_quantity >= locked_base_quantity >= 0` 的约束及可用库存查询索引。 |
| `stock_operation_details` | 新增 `unit_spec_id`、`input_quantity NUMERIC(20,6)`、`input_unit`、`conversion_ratio NUMERIC(20,6)`、`base_quantity NUMERIC(20,6)`、`base_unit`、`input_unit_cost NUMERIC(24,8)` 和 `base_unit_cost NUMERIC(24,8)`；保留既有 `quantity`、`unit`、`split_quantity`、`unit_cost`、`total_cost` 供历史读取。确认后这些新字段不得为空；历史异常行允许为空并由异常表关联。 |
| `inventory_unit_migration_issues` | 新表：ULID、对象类型/ID、`material_id`、原因码、脱敏详情、`status`（`OPEN`、`RESOLVED`、`WAIVED`）、发现/解决审计字段。它记录无法自动换算的历史事实，不替代库存调整单。 |

迁移中将相关金额列扩展为 `NUMERIC(24,8)`，不得降低精度或截断历史值。所有新增 ID 使用 26 位 Crockford
Base32 ULID；时间字段为 `TIMESTAMPTZ` / `OffsetDateTime`；受控扩展信息才可写入 JSONB `metadata`，关键
计量、成本和状态字段不得藏在 JSONB。

## 6. 后端实施设计

### 6.1 统一转换与库存写入

在 Inventory 新建 `UnitConversionService`（或同等内聚服务），它是唯一允许把录入数量转换为基础数量的
入口。它负责加载/锁定物资和 `material_unit_specs`、校验状态和精度、生成不可变快照，并返回
`base_quantity`、`base_unit`、`conversion_ratio`、`input_unit_cost`、`base_unit_cost` 与 `total_cost`。

`StockService`、`InventoryConsumptionService` 和新/旧内部端口复用这一服务：

```text
客户端/内部端口输入（规格 ID + 输入数量 + 输入单位成本）
    -> UnitConversionService（物资、规格、精度、状态）
    -> BaseQuantityCommand（仅服务端构造）
    -> StockService（锁库存、写操作/明细、更新基础余额与成本）
    -> source-specific fact（护理耗材关联等）
```

实现要求：

1. 所有金额和数量从 Vert.x JSON 的原始十进制文本构造 `BigDecimal`；禁止先取 `Double` 再转
   `BigDecimal`。换算使用精确乘法并以 `UNNECESSARY` 验证基础精度；
2. 同一库存操作按 `warehouse`、`material_id`、`lot_id`、`unit_spec_id` 稳定排序锁定物资、批次、库存行
   与规格。库存查询、可用量校验、锁定/释放、出入库和成本累加全程使用同一基础数量；
3. 外层事务仍由 Nursing/Pharmacy 调用方拥有。转换或库存端口不得从 `Pool` 另起事务；任一步失败必须
   回滚库存、操作、明细和调用方领域事实；
4. 现有 `confirmPackageOutbound`、`confirmPackageInbound`、申领预留/释放/调拨和采购收货包装端口保留
   签名，在内部显式解析该物资当前默认规格。它们不允许把客户端选择的包装比率传入；
5. `InventoryConsumptionService` 的旧 `PACKAGE` / `SPLIT` 输入映射到默认包装规格/基础规格，并停止
   使用 `split_quantity / split_ratio` 向上取整包装的算法。新输入改为规格 ID 与输入数量；旧输入仅作为
   过渡兼容，任何无法精确转换都返回 `400`；
6. `listAvailableStocks`、仓库列表和所有库存读模型以 `base_quantity > locked_base_quantity` 筛选，
   并携带当前默认规格的只读投影。不得在查询时根据已变更的物资字段重写历史操作快照；
7. `MaterialService.update` 不能再自由修改单位字段。对有任何库存/操作/耗材引用的物资，变更基础单位、
   精度、规格比率或删除规格一律 `409`；只允许新增规格、停用未使用规格、以及不影响计量事实的常规
   物资字段更新。

### 6.2 路由和错误映射

路径保留 `/crate-api/inventories/v1`。列表响应恒为：

```json
{ "records": [], "meta": { "total": 0 } }
```

单条成功响应直接返回对象，错误一律为：

```json
{ "error": "<message>" }
```

新增或调整以下契约：

| 路径 | 行为 |
| --- | --- |
| `GET /materials/:id/unit-specs` | 返回物资基础单位、精度、迁移状态和全部活动/已停用规格；只读。 |
| `PUT /materials/:id/unit-model` | 仅在无计量事实或经批准的迁移状态下创建首次基础单位模型；请求不接受库存、成本、历史操作或状态伪造字段。 |
| `POST /materials/:id/unit-specs` | 新增一条包装规格。只接受输入单位、正换算率和是否默认；服务端决定 ULID、审计字段和基础单位规格。 |
| `POST /materials/:id/unit-specs/:specId/retire` | 停用未被要求作为现有默认规格的包装规格；已引用规格保留历史可读，不允许删除。 |
| `GET /stocks` | 在保留既有字段的同时新增 `base_unit`、`base_quantity`、`locked_base_quantity`、`available_base_quantity`、`base_unit_cost`、默认规格摘要和 `unit_model_status`。`MIGRATION_BLOCKED` 不进入可用库存列表。 |
| `POST /operations/inbound` | 新契约的每个明细提交 `material_id`、可选 `lot_id`、`unit_spec_id`、`input_quantity` 与 `input_unit_cost`；服务端换算、建操作与库存。旧 `quantity`/`unit_cost` 形式只在过渡窗口映射默认包装规格并记录弃用日志，不能在新页面使用。 |
| Nursing 执行耗材接口 | 新输入为 `stock_id`、`unit_spec_id`、`input_quantity`；响应在保留历史字段的同时返回基础数量和输入快照。 |

字段缺失、未知字段、空/非法 ULID、非正数量、非正换算率、违反精度、客户端传基础数量/换算率/库存成本
或不支持的旧字段组合返回 `400`。物资/规格/批次/库存不存在返回 `404`。物资未启用、规格已停用、
迁移阻断、基础单位不可变、库存不足、锁定竞争或状态冲突返回 `409`。不得向客户端泄露 SQL、堆栈、
数据库约束名或内部端口异常。

## 7. Shared API 与页面设计

在 `@pitchfork/shared/aceso` 新增 `InventoryUnitModel`、`InventoryUnitSpec`、`BaseQuantitySnapshot`、
`InventoryMaterial`、扩展后的 `InventoryStockAvailability` 与 Nursing 耗材类型，以及相应的读取、创建、
停用和入库函数。所有请求复用既有 `request`、Bearer token、JSON 处理与 `401` 清理；Aceso 组件不能
自行拼接 `/crate-api` 或绕过共享客户端 `fetch`。

在 Aceso 新增 `/dashboard/inventory` 及“库存计量”导航入口。页面是操作性工作区，而非营销页或嵌套卡片
集合，包含以下稳定区域：

```text
库存计量
├── 物资与基础单位
│   ├── 物资、基础单位、精度、迁移状态
│   └── 新建/查看单位模型
├── 包装规格
│   ├── 输入单位、换算为基础单位、默认/已停用状态
│   └── 新增规格、停用未引用规格
└── 库存查看
    ├── 仓库、物资、批次
    ├── 基础结存/锁定/可用量、成本
    └── 当前默认包装下的只读可读展示
```

页面要求：

- 基础单位、精度和包装换算使用表单字段、数字输入与选择器；删除/停用、保存和提交才使用有文字的命令
  按钮。使用项目现有 UI 组件、全局主题和 lucide 图标；不为“帮助说明”增加占位性营销文字；
- 新物资的基础单位和首个规格须在同一受控表单中完成。已有计量事实的基础单位/精度/比率显示为只读，
  变更尝试展示服务端冲突；
- 规格列表和库存列表保持固定列宽与横向滚动，避免长单位名、六位小数、批次号、错误文本与状态标签在
  窄屏重叠；数量/成本列使用等宽数字并明确标注其单位；
- 手工入库表单只允许选择活动 `unit_spec_id` 并输入输入数量/输入单位成本，客户端不计算和提交基础
  数量或换算率；提交期间禁用同一命令，失败保留输入，成功仅刷新相关物资、规格和库存查询；
- Legacy/迁移阻断物资只显示状态和只读历史摘要，不能出现可写入、可调库存或“自动修复”命令；
- 不在本页面加入盘点、损耗、退货、供应商、采购、发药、护理站调拨、自动补货或财务界面。

## 10. 风险与控制

| 风险 | 影响 | 控制 |
| --- | --- | --- |
| ADR 未确认即编码 | 基础单位与临床规则错误，后续迁移不可逆 | 以第 3.1 节为实施硬门槛；未确认只维护计划。 |
| 历史拆零数量/比率不完整 | 伪造余额、成本或审计链 | 仅安全回填；异常记录并阻断写入，使用新的调整事实处理。 |
| 双写包装/基础数量漂移 | 可用量、成本和并发校验不一致 | 新写入以基础数量唯一权威；旧数量仅只读兼容投影，统一转换器集中处理。 |
| JavaScript/`Double` 精度损失 | 液体、单位成本和累计金额产生尾差 | 服务器从十进制文本建 `BigDecimal`，固定 `NUMERIC` 精度并拒绝不可精确换算。 |
| 规格改动重解释历史 | 历史回放与审计失真 | 操作明细保存快照；有引用的基础定义和规格不可修改/删除。 |
| 与 013/014 候选改动交叉 | 合并冲突掩盖原计划缺陷 | 保留包装端口签名；分支隔离；冲突回传原计划，不混合验收。 |
| 仅在单元测试验证 | 无法证明 Flyway、锁序、回填与数据库事务 | 获授权后必须在 `aceso_test` 跑迁移/并发/回滚/浏览器验收。 |
| 以计划名夹带盘点/采购/退货 | 范围膨胀并改变库存来源语义 | 第 3.3 节排除；后续功能另建编号计划。 |
