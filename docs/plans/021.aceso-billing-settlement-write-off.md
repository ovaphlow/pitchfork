# Aceso 结算收束未结余额显式标记实施计划

更新时间：2026-09-28

状态：实施中（V519 迁移与 jOOQ 重生成已完成；后端主体与小程序前端进行中）

## 编号、背景与决策

本计划编号 021（020 已占用，按 `loop-lessons.md` 第 2 条取当前最大编号 +1）。

本计划**建立在 020 之上**，不替代 020：020 修的是「字典配不了、账单生不出来、报错看不懂」，本计划修的是「账单生出来之后，流程收束时状态没有被标记出来」。

### 定位前提（继承 020 产品决策 0）

费用相关功能用于**标记数据状态与业务流程收束**，不做真实的付款/收款操作。据此，**「状态没被标记出来」比「钱没收回来」更严重**。本计划处理的正是前者。

### 现状与问题

`BillService.settleAndFreeze` / `freezeAndReturn` 在结算收束时把该 encounter 的**全部账单无条件置 `已结算`**：

1. 余额仍 > 0 的 `待缴费` 账单也被直接置 `已结算`。收束后 `欠费 = Σ(待缴费 且 余额>0)` 恒为 0，**未结余额在数据上消失**。
2. `bills` 上没有任何字段区分「收束时已收妥/已核销」与「收束时未结、被放弃」。同一条 `status = 已结算` 表达两种完全不同的业务事实，状态机出现歧义。
3. 没有任何减免/放弃记录，也没有原因，事后无法追溯某笔欠费是被押金覆盖还是被放弃。
4. 020 加入的押金核销只覆盖「押金余额能盖住的部分」；盖不住的部分仍然无声消失。
5. 区间最终账单由 `generateFinalBill` **创建即 `已结算`**，因此它在结构上不可能被押金核销，也无法在收束前被处置 —— 最终账期的费用事实上是一张只写不结的陈述单。

### 产品决策

1. **不新增账单状态枚举值**。`bills.status` 保持 `待缴费 / 已结清 / 已结算`，不改既有状态机语义，避免动一批已锁定的测试与前端状态映射。
2. **用「收束快照 + 显式减免确认」补上标记**：在 `bills` 上记录收束时刻的未结余额快照与减免原因，让「已收妥」与「被放弃」在数据上可区分。
3. **不允许静默转换**：收束时若存在未结余额，必须由操作员**显式确认减免并填写原因**，否则整个收束被拒绝（409）。放弃一笔应收是一项业务决定，必须留痕。
4. **减免只是状态标记**，不产生任何收款/退款/冲销流水，不改变账单合计。
5. **区间最终账单改为先建后判**：最终账单先以 `待缴费` 建立，再走「押金核销 → 未结判定 → 冻结」的同一套流程。这同时修掉「最终账期不能被核销」的结构性缺陷（**修订 020 中「区间最终账单创建即 `已结算`」的既有口径**，020 的该条「不在本期范围」由此计划接手）。
6. **可预览**：收束前必须能查到「会发生什么」——最终账单金额、押金余额、最大可核销额、核销后仍未结需要减免的金额。否则操作员无法在提交前做出减免决定。

## 目标与范围

### 必须实现

1. **V519 迁移**：`healthcare.bills` 增加两列 —— `outstanding_amount NUMERIC(12,2) NOT NULL DEFAULT 0`（收束时刻的未结余额快照；`0` 表示收束时已收妥/已核销）、`write_off_reason VARCHAR`（减免原因，仅当快照 > 0 时写入）。附中文列注释。
2. **收束流程重排**（`BillService.settleEncounter` 内部拆步，对外契约不变部分保持兼容）：
   - 既有资格校验（非养老 400 / 未离院去世 409 / 已收束 409 / 缺日期 400）**顺序与错误码不变**；
   - 生成区间最终账单时状态改为 `待缴费`（不再是创建即 `已结算`，也不再在创建时写 `settled_at`）；
   - 在最终账单存在之后执行押金核销（020 的 `DepositOffsetService.offsetArrears`），使最终账期同样可被核销；
   - 计算该 encounter 全部 `待缴费` 账单的未结余额合计 `outstanding`；
   - `outstanding > 0` 且未提供 `write_off_reason` → `ConflictException("unsettled bills require explicit write-off: outstanding $outstanding")`（409），整笔回滚，不产生任何写入；
   - 通过后冻结：全部账单置 `已结算` 并写 `settled_at`；每张账单写入 `outstanding_amount` 快照（= 该账单 `合计 − Σ缴费`，下限 0），`outstanding > 0` 的写入 `write_off_reason`；`encounters.settled_at` 照旧。
   - 无可用计费项时仍生成 0 元封口账单，其 `outstanding_amount = 0`。


## 领域模型与业务规则

### 收束的新语义

```text
收束 = 生成最终账期账单 → 用押金核销未结 → 判定剩余未结 → 显式减免留痕 → 冻结
```

冻结后每张账单携带两个新事实：

```text
outstanding_amount = 收束时刻该账单的未结余额（total_amount − Σ缴费，下限 0）
write_off_reason   = 该未结余额被放弃的原因（仅 outstanding_amount > 0 时非空）
```

「已结清」与「已核销」账单的 `outstanding_amount` 恒为 0；`outstanding_amount > 0` 的账单必须带原因。这样同一 `status = 已结算` 不再掩盖两种事实。

### 口径关系（三者互不重叠）

```text
应缴 = Σ账单合计
已缴 = Σ缴费金额（含 020 的 method = 押金 核销行）
欠费 = Σ(待缴费 且 余额 > 0 的账单余额)          // 收束后恒为 0
减免 = Σ(已结算账单的 outstanding_amount)         // 收束时被放弃的部分，新增口径
```

**严格恒等式（2026-09-28 勘误，开发复核后由计划确认）**：

```text
应缴 − 已缴 = 欠费 + 减免
```

推导：`应缴 − 已缴 = Σ(账单合计 − 该账单累计缴费)`，逐项拆开即「待缴费账单的余额（＝欠费）」加上「已结算账单的未结快照（＝减免）」；已结清账单那一项恒为 0。

> 本计划初稿把该恒等式写成 `应缴 − 已缴 = 欠费`，并声称「收束前后均成立」——**这是错的**：只要存在被减免的金额，等式右边就必须加上减免项。开发在实现时按严格关系断言并上报，计划据此勘误。前端汇总区文案与 KDoc 必须同步为 `应缴 − 已缴 = 欠费 + 收束减免（减免为 0 时即旧式）`，否则用户会以为账不平。

### 收束规则（服务端强制）

1. 资格校验顺序与错误码完全沿用既有实现，不因本计划改变（非养老 400 → 非终态 409 → 已收束 409 → 缺入住日 400 → 缺离院/去世日 400）。
2. 最终账单以 `待缴费` 建立；区间起止算法（`BillingEngine.settlementInterval`）与「与既有账单账期完全一致时不重复生成」的判定不变。
3. 押金核销在最终账单建立之后、冻结之前执行；核销上限 = `min(押金余额, 全部待缴费账单未结合计)`（含最终账单）。
4. `outstanding > 0` 且 `write_off_reason` 为空 → 409 且整笔回滚（已有的一切核销写入、最终账单、`settled_at` 全部撤销）。
5. 提供原因时，全部 `outstanding > 0` 的账单写入同一条原因（trim 后的原文）。
6. 冻结后不再允许生成账单/加项/缴费/核销（既有守卫不变）；`outstanding_amount` 与 `write_off_reason` 冻结后不可再改。
7. 预览接口必须与收束实际算法**同源**（共用同一个「计算最终区间 + 计算未结」的内部实现），不允许预览与执行各算一套。

### 兼容与回归边界

- `{}` 空体且**无未结余额**的收束：结果与 020 后逐字段一致（除新增的两个字段为 `0` / `null`）。
- `{}` 空体且**有未结余额**的收束：由「静默成功」变为「409 拒绝」——这是本计划刻意的行为变更，必须在测试与发布说明中显式列出，不得当作回归缺陷处理。
- 既有 `BillingSettlementTest` 中在存在未结账单的前提下断言收束成功的用例，必须改为携带原因或改为断言 409，并在测试注释中说明变更依据。

## API 契约

### 收束接口（扩展）

```text
POST /crate-api/healthcare/v1/encounters/:id/billing-settlement
Authorization: Bearer <JWT>
Content-Type: application/json

{ "deposit_offset": 3000.00, "write_off_reason": "离院结算，家属书面确认不再追收" }
```

- 两个键均可省略；其他键 400（`unsupported settlement keys: ...`）。
- `deposit_offset` 校验沿用 020（数字、> 0、≤2 位小数、≤ `9999999999.99`；缺省/0 = 不核销）。
- `write_off_reason`：必须是字符串，trim 后非空且 ≤500 字符；非字符串 400。
- 成功 `201`，返回收束后的 encounter（形状不变）。
- 409 文案：`unsettled bills require explicit write-off: outstanding <金额>`。

### 预览接口（新增，需认证）

```text
GET /crate-api/healthcare/v1/encounters/:id/billing-settlement/preview
Authorization: Bearer <JWT>
```

```json
{
  "settlement_period": { "start": "2026-09-01", "end": "2026-09-28" },
  "final_bill_total": 1234.00,
  "pending_balance": 2000.00,
  "outstanding_total": 3234.00,
  "deposit_balance": 5000.00,
  "max_offset": 3234.00,
  "requires_write_off": true
}
```

- `settlement_period` 为 `null` 时表示不生成最终账单（区间起 > 区间止或已存在同账期账单）。
- 非养老入住 400、已收束 409、encounter 不存在 404；**无写操作**。
- 未认证 401（挂 `billAuthHandler`）。

### 既有读取扩展

- `GET /encounters/:id/bills`、`GET /bills/:id`：账单对象新增 `outstanding_amount`、`write_off_reason`；其余字段不变。
- `GET /payments/summary`：新增 `write_off_amount`；`due_amount`/`paid_amount`/`arrears_amount` 口径不变。

## 验收口径

### 主线成功

1. 一名已离院长者存在 2 张 `待缴费` 账单（未结合计 2000 元），押金余额 5000 元。调用预览：`pending_balance = 2000`、`final_bill_total` 为最终账期金额、`outstanding_total = 两者之和`、`max_offset = min(5000, outstanding_total)`、`requires_write_off = true`。重复调用预览不产生任何写入。
2. 不带 `write_off_reason` 收束 → 409，错误含 `unsettled bills require explicit write-off`；库中零残留：两张账单仍为 `待缴费`、无最终账单、无缴费/押金记录、`encounters.settled_at` 仍为空。
3. 带核销 + 原因收束 → 201：最终账单已生成、押金按上限核销、全部账单 `已结算`、每张账单的 `outstanding_amount` 等于其收束时刻未结余额、`outstanding_amount > 0` 的账单带 `write_off_reason`。
4. 汇总：`欠费` 为 0，`write_off_amount` 等于全部被放弃金额之和，且严格关系 `应缴 − 已缴 = 欠费 + 减免` 成立；账单列表对 `已结算 且 outstanding_amount > 0` 的行显示「收束时未结」与原因，汇总区第四块 tile 显示减免合计并写明三者关系。
5. 全部账单在收束时已收妥（含押金足够核销全部未结）时，`{}` 空体收束成功，所有 `outstanding_amount = 0`、无 `write_off_reason`。

### 拒绝、并发与无副作用

- 非养老入住 400；未离院/去世 409；已收束 409；缺入住日/离院日 400 —— 顺序与文案与既有实现一致。
- 请求体含未知键 400；`write_off_reason` 非字符串或超 500 字符 400；核销金额非法沿用 020 的 400。
- 409 路径整笔回滚：押金台账、缴费流水、账单状态、最终账单、`settled_at` 全部不变。
- 并发两次收束：至多一次成功，另一次 409，且不产生重复最终账单、重复核销或重复减免记录。
- 收束后任何生成/加项/缴费/核销仍 409；`outstanding_amount` 与 `write_off_reason` 不可再改。
- 预览接口未认证 401；对同一 encounter 反复调用不改变任何一行数据。
- 历史 `已结算` 账单的 `outstanding_amount` 保持 0，不因迁移或本计划被回填猜测。
- 020 的既有断言（核销上限、双台账写入、`method = 押金` 不可经缴费接口提交）全部保持通过。

## 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 行为变更被当作回归 | 既有 E2E/集成用例断言"有未结也能收束成功"而失败 | 计划显式列出该变更；相关用例按「改为带原因或改断言 409」处理，并在测试注释写明依据。 |
| 最终账单改 `待缴费` 影响既有语义 | 冻结前它出现在欠费列表与待缴费账单中 | 收束在同一事务内完成建单→核销→冻结，事务外不可见中间态；预览接口负责让中间态可预期。 |
| 预览与执行各算一套 | 预览数字与实际结果不一致，操作员据此做错减免决定 | 强制共用同一内部实现，并以测试断言两者同源。 |
| 减免变成"一键放弃" | 未结余额被无脑放弃，失去标记意义 | 必须填写原因（服务端强制 ≤500 非空），列表与详情展示原因；不做审批流属刻意取舍。 |
| V519 两列被生产代码引用 | 未重生成 jOOQ 则编译失败 | 把 jOOQ 重生成标为硬依赖；未授权时计划状态保持「不可交付」，不降级。 |
| 历史账单不可考 | 既有 `已结算` 账单未结事实无法还原 | 不回填、不猜测，`outstanding_amount` 保持 0，并在计划与发布说明中记录该残余。 |
| 与 020 改动重叠 | 覆盖用户或 020 的未提交改动 | 开工前记录 `git status` 与 diff，只追加最小独立 hunks，重叠处协调，不 reset/revert。 |
