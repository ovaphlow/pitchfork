## 1. 当前事实与问题

005 已使养老入住的 `healthcare.encounters` 与 `nursing.nursing_service_periods` 一一精确关联，并在办理离院时于同一事务将 encounter 设为 `DISCHARGED`、将关联周期设为 `COMPLETED`。评估、计划、任务、执行、耗材关联和 `NURSING_RECORD` 已作为历史事实保留；时间线可以按周期和入住记录查询它们。

但当前离院成功后只有 encounter 的离院日期、离院诊断和周期终态。入住管理页只列出活动入住，护理时间线面向日常操作，不能在不逐页拼接历史数据的情况下提供一份稳定、可追溯的离院交接材料。若只在前端实时拼装，后续护理记录更正或数据变动会使同一次离院的交接内容随之变化；若通过离院流程批量修改原始护理记录，则会破坏既有历史事实和 001 的更正语义。

Healthcare 已有 `medical_records` 文书载体及既有 `DISCHARGE_SUMMARY` 类型，包含 `content`、`content_blocks`、`metadata`、`record_date` 和责任人字段。Nursing 已拥有本领域评估、计划/措施、任务和执行数据；Healthcare 已拥有患者、入住与护理记录。现有依赖方向允许 Healthcare 单向调用 Nursing，本计划必须保持该方向，不能让 Nursing Kotlin 库依赖 Healthcare Kotlin 库。

## 2. 目标

1. 对每个已离院的养老入住创建至多一份不可变的“养老照护离院交接摘要”，把明确关联周期的护理事实封存为版本化快照。
2. 快照只读取精确的 `encounter_id` 与 `period_id` 数据，不混入同一长者的其他入住、其他服务期、其他医疗文书或库存流水。
3. 首次归档、重复提交和并发提交具有明确且可验证的语义；任一读取、校验或写入失败均不产生半成品文书。
4. 在入住管理的已离院档案中以只读方式查看或生成摘要；不在护理工作台、离院接口或前端组件中实现第二套数据拼装和直接 `fetch`。
5. 保留原始护理记录及其更正、评估、计划、任务和执行的既有写入、时间线和查询语义；归档不触发任务生成、状态变更、库存扣减或数据清理。

## 3. 范围

### 3.1 必须实现

- 在 Healthcare 的 `medical_records` 中以既有 `record_type = DISCHARGE_SUMMARY` 存储一份养老离院交接摘要，并以结构化 `content_blocks` 保存版本化快照。
- 新增仅面向养老入住的获取与创建接口；创建只允许在精确关联周期已经 `COMPLETED`、入住已经 `DISCHARGED` 后进行。
- 以数据库部分唯一索引和同一事务内的锁定读取共同保证每个养老照护周期只有一份归档；相同重试返回既有文书，不同内容的重试返回冲突。
- 从 Nursing 以连接绑定、批量且只读的方式汇总评估、计划/措施、任务和执行；Healthcare 在同一归档事务中补充患者、入住和 `NURSING_RECORD` 快照并写入文书。

- 覆盖资格校验、精确隔离、快照内容、幂等/并发、原始数据无副作用、后续更正不改写既有快照、HTTP 错误形状及窄屏 UI 的测试证据。

### 3.2 明确不在本期范围

- 不在 `PATCH /crate-api/healthcare/v1/encounters/:id/discharge` 中自动生成摘要，不把办理离院与人工确认/归档混为一次提交。
- 不编辑、删除、迁移、标记终态或补写任何既有评估、计划、任务、执行、耗材关联、护理记录或护理时间线事件。
- 不实现离院后继续写护理记录的权限规则、摘要补充件、摘要再生成、撤销归档、版本修订、电子签名、审批、打印/PDF、导出、消息通知、收费结算或跨机构传输。
- 不复制身份证号、医保号、完整住址、患者通用 `metadata`、库存成本/流水、其他 encounter 的诊断或任何非本周期 `medical_records` 到摘要中。
- 不新增通用出院小结、非 `ELDERLY_CARE` encounter 的归档能力，不调整居家上门排班、复评/计划版本、异常事件或权限模型。

## 4. 领域规则与数据边界

### 4.1 归档资格

归档对象始终由路径中的 `encounter_id` 唯一确定。服务端必须在同一数据库事务中按以下顺序锁定并验证：

1. 锁定 Healthcare encounter；不存在返回 `404`，类型不是 `ELDERLY_CARE` 返回 `400`。
2. encounter 必须为 `DISCHARGED`，且必须有 `discharge_date`；活动、转出或其他非离院状态返回 `409`，提示先完成既有离院流程。
3. 锁定 `nursing_service_periods.encounter_id = encounter.id` 的唯一关联周期；缺失、患者不一致、服务类型不为 `ELDERLY_CARE`、状态不是 `COMPLETED` 或 `end_date` 不等于 encounter 的离院业务日期，均返回 `409`。
4. 只使用该周期 ID 查询 Nursing 数据，并对护理记录同时限制 `encounter_id` 与 `metadata.period_id`。任何“按 patient_id 取第一条周期”或通过同长者其他入住兜底的实现均不允许。

005 保留的离院后 `PENDING`、`SKIPPED`、`CANCELLED` 与 `COMPLETED` 执行都是历史事实，必须如实快照，不得在归档时取消、完成或过滤它们。`IN_PROGRESS` 本应被 005 阻止离院；若归档查询仍发现它，只能作为完整快照中的执行状态展示，归档本身不承担修复职责。

### 4.2 不可变文书与幂等

首个成功归档创建一条 `medical_records` 记录，固定字段如下：

| 字段 | 规则 |
|---|---|
| `record_type` | 固定为既有 `DISCHARGE_SUMMARY`，不新增第二个业务文书类型。 |
| `title` | 固定为“养老照护离院交接摘要”。 |
| `encounter_id` | 固定为路径中的养老入住 ID。 |
| `record_date` | 固定取 encounter 的 `discharge_date` 对应业务日期，不取生成时的今天。 |
| `physician` | 取请求中必填、去空白后的 `author`；它表示归档交接人，不伪造为系统或其他临床人员。 |
| `content` | 请求中可选、去首尾空白后的 `handover_note`；空值保持 `null`。 |
| `content_blocks` | 存放单个版本化交接快照块，而不是由客户端传入的任意内容。 |
| `metadata` | 至少含内部归档标记、`period_id`、`snapshot_version: 1`、`generated_at` 与来源计数；不得存放客户端任意 `metadata`。 |

请求中的 `author` 必填且最多 100 个字符；`handover_note` 可选且最多 2,000 个字符。创建后不提供更新、删除、重新生成或覆盖接口。现有护理记录更正接口只接受 `NURSING_RECORD`，仍须拒绝该 `DISCHARGE_SUMMARY`。

同一归档请求的判定以规范化后的 `author` 与 `handover_note` 为准：首次成功返回 `201`；后续完全相同的重试返回 `200` 和原文书；已存在文书但作者或备注不同返回 `409`，不能静默覆盖。数据库唯一约束是并发最后防线；唯一竞争后必须锁定并读取既有文书再做同样比较，不能向客户端泄漏数据库约束文本。

快照在首次成功事务的读取结果上冻结。此后合法的护理记录更正、患者资料变更或历史查询不会改变快照，也不产生新版本；本计划应在摘要 UI 中显示“归档时间”和“归档后源记录更正不会自动同步”的说明。

### 4.3 快照内容与最小必要数据

`content_blocks[0]` 使用稳定的 `snapshot_version = 1` 与结构化 `snapshot`，API 映射为明确类型而不是让前端解析自由文本。快照必须包含：

- **长者最小照护资料**：`id`、姓名、性别、出生日期、紧急联系人、过敏史和既往史摘要；不包含第 3.2 节列出的身份、地址、保险和通用扩展字段。
- **入住与周期事实**：住院号、照护单元、房间/床位、入住与离院时间、入/离院诊断、责任照护人员、周期 ID、服务类型、开始/结束日期、协调人和终态。
- **护理评估**：该周期全部评估的类型、日期、评估人、分数、结论、详情和备注，按评估日期和创建时间升序。
- **照护计划**：该周期全部计划及其措施，保留目标、状态、起止日期、创建人、措施频次/时长/备注与状态；计划和措施均按稳定时间与 ID 排序。
- **任务与执行**：该周期全部任务及其状态、频次、起止日期；执行的计划/实际时间、执行人、状态和备注，并提供各执行状态计数。执行只通过任务的 `period_id` 关联，不能按患者或日期范围猜测。
- **护理记录**：同时属于该 encounter 与该 period 的原始 `NURSING_RECORD` 及其更正记录，包含记录 ID、种类、标题、正文、记录时间、记录人和更正关联；按业务记录时间、创建时间和 ID 稳定排序。

每类数据只执行固定数量的批量查询并在内存组装；不得为每份计划、措施、任务、执行或记录逐行再次查询。快照查询只读，不调用 `ensureExecutionsForDateRange`、状态流转、库存服务或任何外部 HTTP 服务。Healthcare 负责 Healthcare 表的读取和文书写入；Nursing 负责 Nursing 表的批量读取。两者都必须使用外层 `Pool.withTransaction` 传入的同一 `SqlConnection`，以免产生跨连接的半成品归档。

## 5. API 契约

### 5.1 获取既有摘要

```http
GET /crate-api/healthcare/v1/elderly-admissions/:id/discharge-handover
```

符合归档资格且已有文书时返回 `200` 与单个对象；不存在既有摘要返回 `404`。对于非养老入住、未离院或周期不一致，先按第 4.1 节返回 `400` 或 `409`，不能把状态错误伪装成“尚未生成”。响应示例：

```json
{
  "id": "01...",
  "record_type": "DISCHARGE_SUMMARY",
  "title": "养老照护离院交接摘要",
  "encounter_id": "01...",
  "period_id": "01...",
  "record_date": "2026-07-31",
  "author": "王护理师",
  "handover_note": "已向家属说明居家照护注意事项。",
  "generated_at": "2026-07-31T10:15:00+08:00",
  "snapshot_version": 1,
  "snapshot": {
    "patient": { "id": "01...", "name": "张三" },
    "encounter": { "id": "01...", "encounter_no": "A20260731001", "status": "DISCHARGED" },
    "care_period": { "id": "01...", "service_type": "ELDERLY_CARE", "status": "COMPLETED" },
    "assessments": [],
    "plans": [],
    "tasks": [],
    "execution_summary": { "PENDING": 0, "IN_PROGRESS": 0, "COMPLETED": 0, "SKIPPED": 0, "CANCELLED": 0 },
    "nursing_records": []
  }
}
```

数组为空时必须返回空数组，状态计数必须返回零，不能省略字段或以 `null` 替代。`snapshot` 是已保存的快照，不是请求时重新聚合的实时视图。

### 5.2 创建或幂等读取

```http
POST /crate-api/healthcare/v1/elderly-admissions/:id/discharge-handover
Content-Type: application/json

{
  "author": "王护理师",
  "handover_note": "已向家属说明居家照护注意事项。"
}
```

- 首次成功返回 `201` 与第 5.1 节对象；服务端构造全部快照字段，客户端不得提交 `snapshot`、`period_id`、`record_date`、`metadata` 或文书类型。
- 相同规范化输入的重试返回 `200` 与同一 `id`；不同输入的重试返回 `{ "error": "..." }` 与 `409`。
- `author` 缺失/空白、字段类型错误或长度超限返回 `400`；不存在 encounter 返回 `404`；资格、精确关联或幂等内容冲突返回 `409`（类型错误保留 `400`）。
- 所有失败响应保持 `{ "error": "<message>" }`，不返回快照正文、数据库错误或任何未脱敏的 SQL。

## 6. 后端实施设计

### 6.1 Healthcare 迁移与 jOOQ

新增 Healthcare 所有的 `V504__add_elderly_discharge_handover_archive.sql`：

1. 在 `healthcare.medical_records` 为 `record_type = 'DISCHARGE_SUMMARY'` 且 metadata 中标记为本养老归档的记录，建立按 `period_id` 的部分唯一索引；它必须阻止同一精确照护周期产生第二份摘要。
2. 为按 `encounter_id` 获取同类摘要建立最小的部分查询索引；复用 V503 已有的 `(record_type, encounter_id, record_date DESC)` 索引时不得重复创建等价索引。
3. 不新增表、列、跨 schema 外键、全局 Flyway `outOfOrder`，不修改 `V500`–`V503`，不回填历史离院数据。

在获授权、可恢复的 codegen 环境执行 Healthcare 的 jOOQ 生成并提交受影响的生成源（如 `Indexes.java`）；不得以 `DSL.table`/字符串字段替代已有 `MedicalRecords` 表类，也不得把本地生成配置提交到仓库。

### 6.2 Nursing 的只读快照服务

在 Nursing 增加一个仅供 Healthcare 调用、接受外层 `SqlConnection` 的内部交接快照服务。它先通过已有关联服务期能力锁定并返回已完成的 `ELDERLY_CARE` period，再以固定数量的批量查询读取护理评估、计划及措施、任务及执行，并生成第 4.3 节的 Nursing 部分 JSON。

- 该服务不得注册 `/crate-api/nursing/*` 新公开路由，也不得直接写 Healthcare 表或依赖 Healthcare Kotlin 库。
- `ServicePeriodService` 如需暴露连接绑定的“锁定并验证已完成关联周期”方法，只能复用 005 的精确 `encounter_id` 关系；不得开放按患者猜测或改变通用服务期创建/关闭路径。
- 计划/措施、任务/执行必须分别批量读取并按 ID 组装，避免 N+1；关联字段为空、异常状态或来自其他 period 的行不得进入快照。
- 服务只读且不对执行、库存或时间线调用产生副作用。任何源表查询失败都使外层归档事务失败。

### 6.3 Healthcare 归档编排与路由

`HealthcareService` 新增获取和创建养老离院交接摘要的领域方法，Healthcare 继续拥有 `medical_records` 的写入。创建方法应：

1. 使用 `Pool.withTransaction`，先锁定 encounter，再按与 005 一致的顺序锁定/验证关联 period，避免与既有离院收束流程反向加锁。
2. 在写入前锁定并读取既有本计划摘要；存在时执行第 4.2 节的幂等比较后直接返回，不重新读取或重组快照。
3. 不存在时从 Nursing 读取只读快照，并用同一连接批量读取 Healthcare 所有的患者、入住和精确关联护理记录数据，组装 `content_blocks` 与受控 `metadata`。
4. 写入单个 `DISCHARGE_SUMMARY` 后读取/映射该行返回。唯一索引冲突时重新锁读既有行并按输入比较；任何异常使整个事务回滚，不能留下只含 metadata 或空 `content_blocks` 的记录。
5. 获取方法只读取已保存文书并严格验证标记、record type、period ID 与路径 encounter ID；不得为 GET 触发创建、重组或更正。

`HealthcareRoutes` 注册精确的 `GET`、`POST /elderly-admissions/:id/discharge-handover`，保持 `elderly-admissions` 静态资源路由清晰地位于泛型 encounter 路由之前。复用现有 `IllegalArgumentException`、`HealthcareNotFoundException` 与 `ConflictException` 的 `{ "error": "..." }` 映射；只为本计划新增必要的 `409` 分支，不能改变通用入住、离院或护理记录接口的既有语义。

### 6.4 Shared API 与前端

在 `@pitchfork/shared/aceso` 增加明确的 snake_case TypeScript 类型：`ElderlyDischargeHandover`、版本 1 的 `ElderlyDischargeHandoverSnapshot`、评估/计划/任务/执行/记录子项及创建输入。新增：

```text
getElderlyDischargeHandover(encounterId)
createElderlyDischargeHandover(encounterId, { author, handover_note? })
```

两者必须复用既有 `request`、Bearer token、JSON 解析和 `401` 处理；组件内不得自行 `fetch` 或维护第二套 API 基址。现有 `Encounter`、养老入住创建与离院响应保持不变。

`AdmissionsPage` 在保留“当前活动入住”工作流的前提下增加“已离院档案”视图：

1. 只在该视图请求 `listElderlyAdmissions({ status: "DISCHARGED" })`，显示住院号、长者、入住/离院日期和只读摘要入口；不把已离院人员重新放入活动护理工作台。
2. 用户点击某一行时先单次 GET 摘要；成功则在只读弹窗按稳定区块展示基础资料、入住/周期、评估、计划/措施、任务/执行统计、护理记录与归档备注。不得为列表的每一行预读摘要，避免 N+1 请求。
3. 仅当该次 GET 明确为 `404` 时，展示该行的“生成交接摘要”表单；表单只允许填写交接人和可选交接备注。提交期间禁用重复操作，成功后以服务端返回的不可变对象替换表单；`409`、网络失败或校验失败时保留用户输入并显示独立错误。
4. 弹窗不显示编辑、删除、重新生成或下载按钮；显示归档日期、快照版本及“后续源记录更正不会自动同步此摘要”的只读提示。窄屏内容采用纵向区块和可横向滚动的表格，不截断护理记录正文或操作按钮。

### 12.3 P1 阻断项

1. **集成测试引用不存在的表，整个套件无法启动。** `ElderlyDischargeHandoverIntegrationTest.kt` 的 fixture/清理/残差 SQL 均操作 `healthcare.nursing_records`，但该表不存在：NURSING_RECORD 实际存于 `healthcare.medical_records`（`record_type='NURSING_RECORD'` 加 `metadata.period_id/record_kind/corrects_record_id`，见 V500/V503 与 `HealthcareService.loadHandoverNursingRecords`），迁移全集与 jOOQ 生成代码均无此表。`@BeforeEach` 的清理第二条语句即报 relation does not exist，9 个用例全部无法运行。
2. **Playwright 套件同样引用不存在的表且用例逻辑与 DOM 不符。** `cleanupDatabase`/残差查询引用 `healthcare.nursing_records`，`beforeAll` 即失败。另存在确定性错误：`getByRole("dialog")`/`getByRole("tab")`/`getByRole("form")` 与当前 Modal（无 `role="dialog"`）、视图切换按钮（普通 button）及未命名 form 不匹配；Modal 不处理 Escape 键；"查看只读摘要"用例对尚未生成摘要的入住断言只读内容（实际 404 后显示生成表单，且断言文本 `归档测试长者…` 与真实患者名 `pw-dha-…` 不符）；"更正不影响快照"用例调用 `/nursing-records` 缺少服务端必填的 `period_id`（必然 400）。
3. **fixture 清理不能删除服务端生成的摘要，用例互相串扰。** 服务端写出的 `medical_records.id` 是 ULID，不匹配 `dha-`/`pw-dha-` 前缀，清理与残差检查均漏计；先建摘要的用例会使后续 `DELETE encounters` 因 `medical_records.encounter_id REFERENCES encounters(id)` 外键失败，且"首次归档断言 201"与"相同请求重试断言 200"彼此依赖测试执行顺序。`GET 无既有摘要返回 404` 的 `200 || 404` 断言是空验证。
4. **计划 7.2 明确要求的并发与部分资格用例缺失。** 两套测试均无"并发相同请求"（唯一索引竞争、同 ID 200）场景；缺周期、周期未完成、日期不一致的集成拒绝用例未实现（仅单元覆盖）；"快照不含库存流水/其他医疗文书/另一入住诱饵数据"的隔离断言没有对应 fixture 数据。
5. **UI 失败态违反"保留用户输入"契约。** `AdmissionsPage` 在生成失败（409/网络/校验）时用纯错误面板替换生成表单；输入虽保留在 state 中但不可编辑，关闭重开即清空，不满足 6.4.3/7.3.3"保留用户输入并显示独立错误"，且 e2e 无对应用例。

### 12.4 P2 非阻断但必须闭环项

- Nursing 快照服务使用 `DSL.table(DSL.name(...))` 与字符串字段访问 Nursing 表，Nursing 已有 jOOQ 生成表类，不符合 `service-vertx-kotlin/AGENTS.md`"使用生成 jOOQ 表"的约定，丢失列名类型检查。
- `isUniqueViolation` 依赖错误消息字符串匹配（`duplicate key`/约束名），建议按 SQLState 23505 或错误码判定。
- 护理记录排序按 `record_date` 加 `created_at`，计划要求按业务记录时间（`metadata.record_time`）排序，存在轻微偏差。
- 快照隔离用例未在活动重入住/另一长者周期下放置评估、计划、任务、记录等诱饵数据，也未断言库存流水与无关文书不进入快照。
- `handover_note` 为数字等错误类型时被静默忽略而非 400；集成测试项数交付记录（8）与实际（9）不符。
- e2e"重复点击不重复请求"未验证提交期间按钮禁用，"刷新后仍显示同一快照"未覆盖；窄屏用例仅验证关闭按钮可点，未验证文字不重叠。
