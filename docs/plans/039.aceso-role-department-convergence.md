# Aceso 039 — 角色/部门归一到 Nexus 与 IDP 控制面角色下线

- 创建时间：2026-10-02
- 状态：**计划编制完成，待产品/调度者确认**（第 11 节 4 项新裁定；确认即采纳推荐口径）
- 基线：`fix/035-child-health @ 2efa5d7`（工作区含 035 / 036 / 037 / 038 未提交改动）
- 上游：018（Nexus 角色目录）、036（用户 ↔ 角色分配）、037（角色体系收敛与消费）、038（权限平台化）
- 范围：`service-idp-go`（控制面角色下线）、`service-nexus-shared`（部门升格 + 用户 ↔ 部门）、
  `ui-astro`（aceso + packages/shared）。Kotlin 默认不改（Aceso 已有 `/identity/v1/*`、`/shared/v1/*` 代理）。

## 1. 背景与目标

项目处于开发阶段、尚未上线，当前目标是清掉阻塞业务流程的问题。用户 2026-10-02 裁定：

1. **IDP 控制面角色采用 B 方案**：IDP 只保留「平台管理员」这一个不依赖 Nexus 的根权限，
   角色与部门的目录、分配、消费全部归 Nexus。
2. **部门与病区是两个概念，分开处理**：部门用独立表管理；床位/入住/申领里的
   `department`（照护单元/病区）保持现状，不在本计划内改动。
3. **用户 ↔ 部门采用一人一主部门**（`UNIQUE(subject_id)`）。

目标：消除「两套互不相通的角色体系」的语义与可见分裂；补齐用户 ↔ 部门关系；
让部门从「没人消费的目录」变成用户归属的真实数据。

## 3. 设计决策（确认即冻结）

### D1 — Nexus 是角色与部门的唯一权威

- 产品角色目录：Nexus `roles`（018，已有）。
- 用户 ↔ 角色：Nexus `subject_roles`（036，已有）。
- 部门目录：Nexus `departments`（本计划升格，见 D3）。
- 用户 ↔ 部门：Nexus `subject_departments`（本计划新增，见 D4）。
- IDP 不再持有任何产品语义的角色或部门数据。

### D2 — IDP 只保留「平台管理员」根权限（B 方案）

- `identity_subjects` 新增 `is_platform_admin INTEGER NOT NULL DEFAULT 0 CHECK(IN (0,1))`。
- 删除 `identity_roles`、`identity_subject_roles` 两张表及其全部查询/端点/测试。
- `HasRole(subjectID, "identity.admin")` → `IsPlatformAdmin(subjectID)`。
- 管理台准入（`requireAdministrator` / `requireAdministratorPage` / dashboard）改判 `is_platform_admin`。
- **授予入口**：`PATCH /identity/v1/subjects/{id}` 接受 `{"platform_admin": true|false}`，仅平台管理员可调用；
  关闭时沿用「最后一个启用的平台管理员不可关闭」保护（409，复用 `ErrLastAdministrator`）；IDP HTML 管理台加对应开关。
- **引导兜底**：`EnsureBootstrap` 创建首个主体时置 `is_platform_admin=1`；若已有主体但库内没有任何平台管理员，
  按 `IDENTITYD_BOOTSTRAP_IDENTIFIER` 命中主体提升（幂等，仅在该库无管理员时触发），避免出现「无人能进管理台」。
- **为什么不能把根权限也交给 Nexus**：Nexus 每个受保护请求都要回调 IDP 会话；若 IDP 管理台准入再依赖 Nexus，
  会形成循环依赖且 Nexus 故障会锁死管理台。这条约束与是否上线无关。

### D3 — 部门升格为 Nexus 独立表

- 新增 `departments(id, code, name, description, parent_code, sort_order, created_at, updated_at)`，`code` 唯一。
- 理由：部门要成为被外键引用的实体，且需要层级、成员数、排序；继续挂在通用 KV `settings` 的
  `category+code+payload JSON` 上会让外键语义含糊、字段不断塞进 JSON。`roles` 已是独立表，部门对称化。
- 迁移把 `settings` 中 `category='department'` 的行**复制**进 `departments`（不删除原行），
  避免直接影响仍在引用 `/settings?category=department` 的冻结应用（Trainova 侧 `apps/auth`、`apps/admin`）。
  原行清理单独立项，见 D7。
- Aceso 侧一律改走 `/crate-api/shared/v1/departments`。

### D4 — 用户 ↔ 部门：一人一主部门

- `subject_departments(id, subject_id UNIQUE, department_id FK→departments(id) ON DELETE RESTRICT,
  granted_by_subject_id, created_at, updated_at)`。
- 写入语义与 036 `subject_roles` 一致：`PUT /subject-departments/subjects/{subject_id}` 全量替换单值，
  `{"department_id": null}` 表示清空。
- 多部门/主次部门不在本轮；出现真实需求再引入 `is_primary` 或去掉唯一约束。

### D5 — 消费点：用户页与部门页

- 用户页新增「部门」列 + 「设置部门」弹窗；部门页新增「成员数」列。
- 部门目录从「没有任何消费者」变为「有归属关系与可见消费」。
- **不做**按部门的数据范围/资源级权限（038 D4 已冻结为「出现真实需求再立项」）。
- 部门删除受 `ON DELETE RESTRICT` 保护：仍有成员时返回 409 与可读文案。

### D6 — 病区/照护单元保持现状，显式隔离

- `beds.department`、`encounters.department`、`pharmacy_requisitions.department` 继续是自由文本，
  与 `departments`（组织科室）**无外键、无联动**。
- 在 `DepartmentsPage` 文案与模块文档中写明二者区别，避免后续把病区填进部门目录。
- 业务侧自由文本收敛到部门 code 单独立项（影响现网数据，非当前阻塞项）。

### D7 — 端点的列表形状

- 新端点 `GET /departments` 与 `GET /subject-departments` 遵循根 `AGENTS.md` 契约：`{ "records": [...], "meta": { "total": N } }`。
- 既有 Nexus `/roles`、`/subject-roles` 的裸数组偏差本轮不动（Aceso 前端消费契约已由 037/038 冻结，
  改形状会制造额外回归面），列为后续清理项。

### D8 — 迁移号段

- IDP（SQLite + 自研迁移，`db/migrations/000001` 起）：新增 `000011_platform_admin.sql`。
  编号跳过 `000010`：开发库的 `schema_migrations` 可能残留其它分支用过的 `000010`
  （迁移器只按版本号判重），撞号会被静默跳过。
- Nexus（SQLite + sqlx migrate，`migrations/0001` 起）：新增 `0004_departments.sql`、`0005_subject_departments.sql`。
- 与 Kotlin 侧 Flyway 号段无关，不触碰 `V1–V699` 任何文件。

## 5. 接口契约（冻结）

```text
GET /crate-api/shared/v1/departments                （Nexus，需会话）
  → 200 { "records": [ { "id": "<ULID>", "code": "nursing", "name": "护理部",
                         "description": "", "parent_code": "", "sort_order": 0,
                         "member_count": 3, "created_at": "...", "updated_at": "..." } ],
          "meta": { "total": 1 } }
POST   /crate-api/shared/v1/departments             body { code, name, description?, parent_code?, sort_order? } → 201
PUT    /crate-api/shared/v1/departments/{id}        同上 → 200
DELETE /crate-api/shared/v1/departments/{id}        → 204；仍有成员 → 409；code 冲突 → 409；非法 id → 404

GET /crate-api/shared/v1/subject-departments?subject_ids=<ulid,ulid>   （Nexus，需会话）
  → 200 { "records": [ { "id", "subject_id", "department_id", "department_code",
                         "department_name", "granted_by_subject_id", "created_at", "updated_at" } ],
          "meta": { "total": N } }
  → 400 subject_ids 含非法 ULID
PUT /crate-api/shared/v1/subject-departments/subjects/{subject_id}
     body { "department_id": "<ulid>" | null }      → 200 全量替换后的记录数组（空数组表示已清空）
  → 400 subject_id 非 ULID / department_id 不在目录；401 无会话

PATCH /crate-api/identity/v1/subjects/{subject_id}  （IDP）
     body { "platform_admin": true|false }          → 200 主体
  → 400 与 status/temporary_password 混用；403 非平台管理员；403 last-administrator 关闭最后一个启用的平台管理员
  （不变式：既有的 status=禁用、temporary_password 两个分支行为不变；删除 GET /identity/v1/roles）
```

不变式：018/036 的 `roles`、`subject-roles` 与 037 的 `subject-permissions` 契约不变；
`identity/v1/subjects` 响应中 `roles: string[]` 由 `platform_admin: boolean` 取代。

## 6. 验收口径

1. **IDP 单根权限**：库中无 `identity_roles`/`identity_subject_roles`；`identity.admin` 不再是角色码；
   管理台准入只由 `is_platform_admin` 决定；`GET /identity/v1/roles` 路由不存在。
2. **不锁死**：关闭最后一个启用的平台管理员返回 403 `last-administrator` 且不落数据；引导兜底能让空管理员库恢复可管理。
3. **部门独立**：`departments` 表存在且含从 settings 复制的行；settings 中原行仍在（未破坏冻结应用）。
4. **用户 ↔ 部门**：给主体设置部门后 `GET /subject-departments?subject_ids=` 回读一致；
   传 `department_id: null` 可清空；未知部门 400；非法 ULID 400。
5. **删除保护**：删除仍有成员的部门返回 409；清空成员后可删除。
6. **病区隔离**：床位/入住/申领的 `department` 仍为自由文本，行为与改前一致（回归用例）。
7. **UI**：用户页显示部门并可编辑；部门页显示成员数；角色页只剩 Nexus 产品角色，平台管理员在用户页以只读徽标呈现。
8. **回归**：`:apps:aceso:test`、`cargo test`、`go test ./...`、`pnpm --filter @pitchfork/aceso build` 全绿；
   `rg "identity_roles|identity_subject_roles|identity.audit.read"` 仅命中历史计划文档。

## 7. 范围与明确不做

- 不做按部门的数据范围/资源级权限（038 D4）。
- 不改床位/入住/申领的自由文本 `department`，不建它与 `departments` 的外键。
- 不做多部门、主次部门、部门负责人、部门排序拖拽（只保留 `sort_order` 字段）。
- 不删除 settings 中的 department 旧行（D3），不改冻结的 `apps/auth` / `apps/admin`。
- 不改 Nexus `/roles`、`/subject-roles` 的裸数组响应（D7）。
- 不启停用户管理的服务（8420 / 8422 / 4324 / 5432）；不连接共享/业务/生产库。
