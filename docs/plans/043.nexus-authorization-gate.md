## 1. 背景与目标

QA 第 6 轮三条：

1. 🟠 **基础数据完全没有权限校验** —— `nurse01` 能打开 部门 / 角色 / 物资 / 床位 四个页，并成功创建了一个部门（`QA-AUTHZ`，已清理）；只有身份服务的「用户」页被拦住。
2. 🟠 **权限不足的提示会误导** —— 业务账号打开「用户」页：显示英文 `not authorized`，同时列表是"共 0 条 / 暂无用户"，「添加用户」按钮还在；会被读成"系统里没有用户"。
3. 🟡 **药房「护士核对」列显示 ULID 而不是护士姓名** —— 同类问题在病程记录/配餐名单出现过，没清干净。

本计划负责 1 与 2（**授权边界 + 错误语义**）；第 3 条按裁定单独立项 **044**（主体姓名解析 / 非管理员可读的业务人员目录），与 042 §7 残项合并处理。

目标：

- 把**授权权威**落到 Nexus（Aceso 侧加门禁挡不住直连 `8421`）；
- 堵住**自授角色提权链**，并给基础数据写加门禁；
- 让"权限不足"在 UI 上是一个**可读、可照做、不与空态混淆**的状态。

## 3. 设计决策

### D1 — 授权权威在 Nexus，Aceso 不再单独判定

门禁实现在 `service-nexus-shared`：直连 `8421` 与经 Aceso 代理两条路径都被拦（§2.4）。Aceso 侧**不新增**平行判定，避免两套逻辑漂移。

### D2 — 门禁 = 平台管理员 bypass + 权限码双轨

判定：`platform_admin == true` **或** 主体权限码集合包含所需码。

- 平台管理员是**引导者**：没有它，权限码的第一次授予无处发生（鸡生蛋）。
- 因此**不需要 040 §9.1 那种放量协议**：接线当刻平台管理员仍可操作，不会出现"全员 403"。
- `platform_admin` 取自 042 的 `/session` 新字段（§2.1 已实测 dev 库中 `admin`/`ovaphlow`/`fortestonly` 三个主体 `is_platform_admin = 1`）。

### D3 — 两个权限码（产品声明，Nexus 只校验格式）

| 权限码 | 门禁对象 |
| --- | --- |
| `access:manage` | `roles` 写、`subject_roles` 写、`subject_departments` 写（账号与授权管理） |
| `base_data:manage` | `departments` 写（组织主数据；后续物资/床位/费用项/仓库并入时沿用此码） |

`subject_departments` 归 `access:manage` 的理由：它是"人员归属"而非目录本身（§11 待裁定 2）。

格式校验沿用 040 D2 的 `^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$`（`roles/mod.rs` 的 `validate_permission_code`），两个码天然合规。

### D4 — 403 形状统一

Nexus 新增 `ApiError::ForbiddenPermission { required_permission }`，响应体在既有 Problem Details 上**新增一个可选字段**：

```json
{ "type": "/crate-api/shared/v1/problems/permission-required",
  "title": "Forbidden", "status": 403,
  "detail": "permission required: access:manage",
  "required_permission": "access:manage" }
```

与 Aceso 门禁的 `{"error":"forbidden","required_permission":…}` 形状**不同但字段同名**——`problem-message.ts` 的 `ApiProblem` 是两者的超集（`error?`/`detail?`/`title?`/`required_permission?`），已能同时消费，无需改动前端映射逻辑。

### D5 — 越权读收紧：`/subject-permissions` 只允许查自己

`subject_id != 当前主体` 且非平台管理员且无 `access:manage` → `403`。理由：Aceso 的权限闸门**只会用当前主体**调用它（`SubjectPermissionGate` 传的就是会话主体），所以收紧不会回归任何既有消费方。

### D6 — 空态与错误态互斥

- 共享 `Table` 新增可选 `error?: string`：非空时渲染单一错误态，**不**渲染空态文案。
- 本轮接入 5 个页面：`UsersPage`（403 是**预期**状态）+ `DepartmentsPage` / `RolesPage` / `MaterialsPage` / `BedsPage`（写操作 403 后的反馈）。
- `UsersPage` 额外做**前置判定**：用 042 的 `/session.platform_admin` 决定是否渲染「添加用户」与列表；非平台管理员直接渲染"仅平台管理员可管理用户"，不发那次注定 403 的请求。
- `problem-message.ts` 补兜底：403 **无** `required_permission` → 中文"权限不足：该操作需要管理员权限，请联系平台管理员。"（不再透出英文 `not authorized`）。

### D7 — 门禁只挂在写路由上，读路由保持开放

读路由（`GET /roles`、`GET /departments`、`GET /subject-roles`、`GET /subject-departments`）不加门禁：

- 目录内容（角色名、权限码、部门名）是产品元数据，且 `UsersPage`/`RolesPage` 的渲染依赖它；
- 收紧读会让现有页面出现新的 403 面，超出"只堵提权链 + 基础数据写"的裁定范围。

实现上**必须保证"新增的写路由默认受保护"**：`MethodRouter::layer`（axum 0.8 支持）只作用于写方法，不做 router 拆分；若实现者选择拆 `write_router()`，须在模块内保证同一不变式。

### D8 — 不做：全量业务写路由接线、前端通用权限感知、Nexus 权限缓存

- 208 条写路由按域接线需分轮放量，另立项（§6）。
- 前端权限感知（按钮置灰/菜单过滤）040 D5 已裁定不做；本轮只做"403 可读 + 无权限态"。
- Nexus 侧**不引入权限缓存**：`subject_roles ⨝ roles` 是本地 SQLite 的索引查询，缓存只会带来"撤权滞后"的语义负担（Aceso 侧的 60s 缓存是跨进程 HTTP 才需要）。

## 4. 接口契约（冻结）

### 4.1 门禁矩阵

| 方法 + 路径 | 现状 | 改后 |
| --- | --- | --- |
| `POST /crate-api/shared/v1/roles` | 仅需登录 | `access:manage` 或平台管理员 |
| `PUT /crate-api/shared/v1/roles/{id}` | 仅需登录 | 同上 |
| `DELETE /crate-api/shared/v1/roles/{id}` | 仅需登录 | 同上 |
| `PUT /crate-api/shared/v1/subject-roles/subjects/{subject_id}` | 仅需登录 | 同上 |
| `PUT /crate-api/shared/v1/subject-departments/subjects/{subject_id}` | 仅需登录 | 同上 |
| `POST /crate-api/shared/v1/departments` | 仅需登录 | `base_data:manage` 或平台管理员 |
| `PUT /crate-api/shared/v1/departments/{id}` | 仅需登录 | 同上 |
| `DELETE /crate-api/shared/v1/departments/{id}` | 仅需登录 | 同上 |
| `GET /shared/v1/subject-permissions?subject_id=…` | 任意主体可查任意主体 | 仅本人；或平台管理员 / `access:manage` |
| 其余读路由（`GET roles/departments/subject-roles/subject-departments`） | 仅需登录 | **不变** |
| `settings` / `messages` / `files` / `interactions` 写路由 | 仅需登录 | **本轮不变**（§6 残项） |

### 4.2 判定契约

```text
allow  ⇔ platform_admin == true
       ∨ required_permission ∈ 该主体角色目录里的 permission_codes
deny   → 403 { required_permission: <code> }   （形状见 D4）
未认证 → 401（沿用 require_identity，行为不变）
依赖不可用（IDP 会话校验失败）→ 现有降级路径（不新增形状）
```

### 4.3 权限目录声明（Aceso 侧）

- `PERMISSION_CATALOG` 新增两条：`access:manage`（"账号与授权管理（角色、用户↔角色、用户↔部门）"）、`base_data:manage`（"基础数据管理（部门等组织主数据）"）。
- `PermissionCatalogEntry` 新增 `enforced_by: "aceso" | "nexus"`；`wired` 语义改为"已被任一层接线"。
- `DeclaredPermissionsTest` 的既有断言 `assertEquals(listOf(NURSING_EXECUTE_PERMISSION), codes.toList())` 必须同步调整：`DECLARED_PERMISSIONS`（Aceso 路由）保持只有护理执行码，Nexus 侧由新的常量表 `NEXUS_ENFORCED_PERMISSIONS` 承载，断言改为"每个 `wired: true` 的目录条目必须出现在两张表之一"。
- 自省端点 `GET /access/v1/permissions` 的既有字段形状不变（040 §3 冻结），只新增 `catalog[].enforced_by`。

## 5. 验收口径

1. **提权链被堵**：`nurse01`（非管理员、无 `access:manage`）→ `POST /shared/v1/roles`、`PUT /shared/v1/subject-roles/subjects/{自己}` 均 `403` 且带 `required_permission: "access:manage"`；库内角色与分配不变（回读断言）。
2. **基础数据写被堵**：`nurse01` → `POST/PUT/DELETE /shared/v1/departments` 均 `403` + `required_permission: "base_data:manage"`；`GET /departments` 仍 200。
3. **引导者仍可操作**：平台管理员（`admin`）在**没有任何 `access:manage` 持有者**的前提下，能创建角色、分配角色、建/改/删部门（不需要放量协议）。
4. **委派成立**：平台管理员把带 `access:manage` 的角色分配给某业务账号后，该账号可管理角色/分配，但**仍不能**写 `departments`（缺 `base_data:manage`）→ 证明两个码相互独立。
5. **直连绕过被封**：上述 1–3 项的判定在**直连 `8421`**（不经 Aceso）时结果一致。
6. **越权读收紧**：`nurse01` 查他人 `subject_id` 的权限 → `403`；查自己 → `200`。
7. **403 可读**：业务账号打开「用户」页 → 页面渲染"仅平台管理员可管理用户"，**无**「添加用户」按钮、**无**"共 0 条/暂无用户"；`problem-message.ts` 对无 `required_permission` 的 403 输出中文。
8. **空态不混淆**：5 个接入页在 `pageError` 存在时不渲染空态文案。
9. **回归**：`cargo test --offline`（Nexus，需沙箱外：测试桩要 bind）、`./gradlew :apps:aceso:test`、`pnpm --filter @pitchfork/aceso build`、`pnpm test:unit:aceso` 全绿；`GET /access/v1/permissions` 形状与既有消费方（角色页）兼容。

## 11. 裁定记录（2026-10-03 调度者裁定：按建议）

1. **门禁码形态：双轨** —— 放行条件 `平台管理员 ∨ 拥有所需权限码`；新增两个可委派码 `access:manage`（角色 / 用户↔角色 / 用户↔部门）与 `base_data:manage`（部门目录）。
   - 理由：单轨会逼着把"部门维护"与 IDP 根权限（改用户、改密码、改角色）绑死；双轨的额外代价仅 3 处小改（目录两条 + `enforced_by` 字段 + 一处测试断言）。
   - 必须知晓的语义：`access:manage` 持有者可以给自己分配任意角色（角色管理员的固有权力），授予它 = 授予完全授权管理员；双轨的意义是"不必为了管部门而交出 IDP 根权限"。
   - 两码默认无人持有 → 首日行为等同单轨，**不需要放量协议**。
2. **`subject-departments`（用户↔部门）归 `access:manage`** —— "设置某人的主部门"是改人（账号管理），与改目录（`base_data:manage`）分离，权限最小化；"组织管理员"能维护部门目录但动不了人员归属。

后续若要把"部门维护"委派给业务角色：平台管理员在角色管理页勾选 `base_data:manage` 建角色 → 分配给该账号即可（目录已声明，无需再改代码）。
