## 1. 背景与根因

数据事实：一条 `planned_time = 2026-08-08 09:00` 的待执行用药任务，
接口已正确返回 `is_overdue: true`、`overdue_minutes: 73332`（≥51 天）。
但「照护管理 → 今日执行」在 2026-09-28 显示「待执行 0 / 无逾期 / 逾期 0」。

根因（代码位置为 `main` 上的事实）：

1. **逾期只看当天，跨日逾期不汇总。**
   `TaskExecutionService.todayExecutions`（`libs/nursing/.../TaskExecutionService.kt:1079-1119`）
   无论是否 `overdue=true`，都把 `planned_time` 限制在 `[dayStart, dayEnd)`；
   `meta.overdue_total` 也用同一日期窗口（`:1105-1119`）。
   因此 51 天前的逾期执行既不进列表，也不进计数，`overdue_total` 恒为 0，
   前端「逾期 N 项」入口退化成「无逾期」静态文字
   （`ui-astro/apps/aceso/src/components/NursingPage.tsx:1639-1652`）。
2. **两个模块口径不一致。**
   康复活动页有可点的「只看逾期」（`ActivitiesPage.tsx:787`），照护管理页在计数为 0 时
   只剩不可点的「无逾期」；且两页的「逾期」都只覆盖当天，实际都无法暴露跨日逾期。
3. **医嘱状态不收敛。**
   `medical_orders` 只有手动 `PATCH /healthcare/v1/orders/:id/status`
   （`MedicalOrderService.kt:507-549`），没有任何到期判定或收束：
   `end_time = 2026-08-09` 的 `ACTIVE` 医嘱 50 天后仍显示「进行中」
   （`OrdersPage.tsx:153` 把 `ACTIVE` 映射为「进行中」）。
4. **长挂 `IN_PROGRESS` 的执行没有任何提醒。**
   执行记录只有 `is_overdue` / `overdue_minutes`，没有「开始多久还没结束」的派生字段，
   `2026-08-07` 开始、一直 `IN_PROGRESS` 的执行在界面上与刚刚开始的执行无法区分。

### 1.1 调度者裁决（用户 2026-09-29 选择）

- **收敛口径 = 只读派生 + 显式一键收束。**
  不引入定时任务（代码库当前没有任何 `setPeriodic`/`setTimer` 调度基础设施），
  不改 GET 语义产生写副作用，不伪造护理记录；由列表上的「已到期」派生标签把人引到
  幂等的显式收束动作。
- **长挂执行的处置 = 只提醒不自动改。**
  超过阈值仍 `IN_PROGRESS` 的执行只做派生标记与界面提醒，由护理员人工处理，
  系统绝不自动改写为 `COMPLETED`/`SKIPPED`。

## 3. 领域规则

### 3.1 逾期（沿用 003 定义，新增跨日口径）

一次执行在服务端参考时间 `now` 下为逾期，当且仅当：

```text
status ∈ { PENDING, IN_PROGRESS } AND planned_time < now
```

- `planned_time == now` 不算逾期（严格小于）。
- `COMPLETED/SKIPPED/CANCELLED` 永不显示为逾期。
- 跨日逾期队列**不施加任何日期窗口**；同一次响应的所有派生字段与聚合使用同一个 `now`。
- 逾期是只读派生状态，不参与状态机，不影响完成/跳过/取消与耗材扣减。

### 3.2 长挂执行（新增）

```text
in_progress_minutes = status == "IN_PROGRESS" && actual_time != null
                      ? max(0, floor(Duration.between(actual_time, now).toMinutes())) : null
is_stale            = in_progress_minutes != null && in_progress_minutes >= 1440
```

- `actual_time` 的写入语义见 `TaskExecutionService.kt:351`（首次进入 `IN_PROGRESS` 时写入）。
- `is_stale` 只是提醒，不触发任何写入。
- 阈值常量 `STALE_IN_PROGRESS_MINUTES = 1440` 定义在 `TaskExecutionService` 伴生对象上，
  便于测试与后续调整。

### 3.3 医嘱到期（新增）

```text
is_expired      = status == "ACTIVE" && end_time != null && end_time < now
expired_minutes = is_expired ? floor(Duration.between(end_time, now).toMinutes()) : null
```

- `end_time == now` 不算到期；`end_time = null`（长期无明确终点）永不到期。
- `DISCONTINUED/CANCELLED/COMPLETED` 永不到期。
- 到期是只读派生状态，不自动改写 `status`；只有显式收束动作才写库。

### 3.4 收束（新增，显式、幂等）

候选医嘱：`status = 'ACTIVE' AND end_time IS NOT NULL AND end_time < now`
（可再按 `encounter_id` 限定）。对每条候选：

1. 在同一事务内 `SELECT ... FOR UPDATE` 锁住医嘱行（与 `updateOrderStatus` 的加锁顺序一致，
   避免与手动停嘱/作废并发冲突）。
2. 结束其关联护理任务（`taskService.terminateOrderTask(conn, orderId, "COMPLETED")`）；
   任务缺失或已非 `ACTIVE` 时**不阻断收束**，只把异常写入 `warnings`，
   因为必须保证候选不会被永久卡住（否则每次调用都返回同一批未收束医嘱）。
3. 更新医嘱：`status = 'COMPLETED'`、`updated_at = now`，
   `metadata = COALESCE(metadata,'{}') || {"convergence":{"reason":"EXPIRED","at":<now>,"end_time":<原 end_time>}}`；
   **`end_time` 保持原值**（临床终点不被"收束时刻"覆盖）。
4. **绝不写 `nursing_task_executions`。** 未执行的执行记录保持原状态，
   继续出现在逾期队列里作为提醒（与 §1.1 的「只提醒不自动改」一致）。

为什么必须结束护理任务：`ensureExecutionsForDateRange` 只为 `ACTIVE` 任务派生新执行，
若只关医嘱不关任务，系统会继续为已结束的医嘱生成新的待执行记录，逾期队列只增不减。

## 4. Shared API 契约（前端/后端并行开发的冻结接口）

### 4.1 执行记录新增派生字段（列表响应 `/today`、`/overdue`）

```json
{
  "is_overdue": true,
  "overdue_minutes": 73332,
  "in_progress_minutes": null,
  "is_stale": false
}
```

`in_progress_minutes` 始终返回（非 `IN_PROGRESS` 或 `actual_time` 为空时为 `null`）；
`is_stale` 始终返回布尔值。

**口径边界（2026-09-29 第 2 轮裁决，回应评审 P2-3）**：这四个派生字段的**契约保证范围是
`/today` 与 `/overdue` 两个列表响应**（后端由 `executionWithSummaryJson` 统一构造）；
单条记录响应（`GET /executions/:id` 等既有 `toJson` 路径）**维持 003 以来的既有形状**，
不新增派生字段。本条是计划措辞收敛，不是待实现缺口。

### 4.2 `GET /crate-api/nursing/v1/executions/today`（响应扩展，行为不变）

```json
{
  "records": [ ... ],
  "meta": {
    "total": 8,
    "overdue_total": 0,
    "overdue_total_all": 3,
    "status_totals": {
      "PENDING": 0, "IN_PROGRESS": 1, "COMPLETED": 7, "SKIPPED": 0, "CANCELLED": 0
    }
  }
}
```

- `total`：既有语义（当前全部筛选条件后的总数），不变。
- `overdue_total`：既有语义（当天 + 周期 + 执行人 + 任务类型范围内的逾期数），不变。
- `overdue_total_all`：**忽略日期**，仅保留周期/执行人/任务类型范围与参与条件后的逾期总数。
- `status_totals`：日期 + 参与条件 + 周期 + 执行人 + 任务类型范围内各状态计数，
  **忽略 `status` 与 `overdue` 筛选**；五个键恒在，无记录为 0。
- 出参必须是整数（`Long` → `JsonObject`），不得返回 `null`。

### 4.3 `GET /crate-api/nursing/v1/executions/overdue`（新增）

```http
GET /crate-api/nursing/v1/executions/overdue?period_id=01...&executor=01...&task_type=REHABILITATION&limit=200&offset=0
```

- 条件：逾期定义（§3.1） + 与 `/today` 相同的参与条件
  （`taskParticipationCondition`） + 可选 `period_id`/`executor`/`task_type`。
- **不接受日期语义**：传入 `date` 时忽略该参数（不报错），行为不受影响；队列天然跨日。
- 排序 `planned_time ASC`（最早逾期在前）；`limit` 默认 50，服务端收敛到 1..200；`offset` 默认 0。
- 不调用 `ensureExecutionsForDate`（不产生任何写副作用）。
- 响应：

```json
{ "records": [ ... ], "meta": { "total": 3 } }
```

- 每条记录与 `/today` 同形（含 `is_overdue`、`overdue_minutes`、`in_progress_minutes`、
  `is_stale`、`patient_name`、`consumption_summary`）。
- 路由必须注册在 `/:id` 之前（参照 `/today` 的既有做法）。

### 4.4 医嘱新增派生字段（`listOrders`/`getOrder`/`createOrder`/`updateOrderStatus` 共用 `orderJson`）

```json
{ "status": "ACTIVE", "end_time": "2026-08-09T09:00+08:00", "is_expired": true, "expired_minutes": 72000 }
```

### 4.5 `POST /crate-api/healthcare/v1/orders/close-expired`（新增）

请求体可为空，或仅含 `encounter_id`：

```json
{ "encounter_id": "01..." }
```

- 未知字段 → `400 { "error": "unknown field: <name>" }`。
- `encounter_id` 非空但入住不存在 → `404 { "error": "encounter not found: <id>" }`。
- 成功（含无候选）：

```json
{
  "closed": 2,
  "order_ids": ["01...", "01..."],
  "warnings": [ { "order_id": "01...", "reason": "order has no linked task" } ],
  "closed_at": "2026-09-29T12:00:00+08:00"
}
```

- 幂等：第二次调用 `closed = 0`、`order_ids = []`。
- 路由注册在 `GET /orders/:id` 之前（与 `/orders/pending-nurse-check` 相邻的静态路径区）。

### 6.2 逐条断言（评审必须逐项核对）

1. `/executions/overdue` 在**无日期窗口**下能返回 51 天前的 `PENDING` 执行，

### R4 残余风险

1. **加锁顺序死锁隐患 —— 部分成立（开发自报成立）**：`closeExpiredOrders` 为 Encounter→Order（`MedicalOrderService.kt:598`→`:607-611`），`nurseCheckOrder` 为 Order→Encounter（`:642`→`:655`）→ 同一入住同一条医嘱并发时构成 ABBA 环。PostgreSQL 会检出死锁并中止一方（`40P01`→路由 500），不会静默丢数据或半写（单事务回滚）。`updateOrderStatus`（`:545`→`:558` `terminateOrderTask`）与收束同为 Order→Task，无环；`terminateOrderTask` 内部锁 `nursing_tasks`（`TaskService.kt:263-269`），收束在锁完全部候选后才逐条加 Task 锁，亦无环。

3. **`expiredOrderCount` 可见性 —— 成立**（见 P2-1）。
4. **真库未验证项 —— 成立**：§6.3 全部未执行（无授权隔离库、未连库、未起容器/服务、未跑 Playwright）。因此以下只能待 §6.3：`/overdue` 对 51 天前 PENDING 的真实返回与分页 total、`overdue_total_all`/`status_totals` 的真实数值、`is_stale`/`is_expired` 对真实 TIMESTAMPTZ 行的取值、`close-expired` 的事务/`FOR UPDATE`/幂等/`metadata` 合并的真库行为。
