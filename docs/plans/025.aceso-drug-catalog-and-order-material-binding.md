# Aceso 药品目录主数据与医嘱-物资绑定实施计划（025）

更新时间：2026-09-29

状态：待实施（演示候选）——§7.1 开发默认验证、§7.2 六条隔离库断言与 §4.5 fail-closed **已由评审验收通过**；**§7.3 用户主线手测未做、E2E 无运行证据**，按 §8 门槛不得置为「已完成」

## 1. 背景与根因

用户实测报告（2026-09-29，截图 `创建发药单` 弹窗）：

- 医生开立的 `MEDICATION` 医嘱只有自由文本 `order_details.drug_name`（实测值 `降压药A`），
  与 `inventories.materials` 没有任何关联字段；
- `GET /crate-api/inventories/v1/materials` 在实测库只有 1 条 `纱布`（类别为耗材）；
- 药房「创建发药单」的「药品物资」下拉只列 **当前仓库中有可用库存** 的物资
  （`listInventoryStocks`），因此只有 `纱布`；
- 结论：该用药医嘱无法发药、库存永远扣不动。

根因：**缺少药品目录主数据，且医嘱与库存物资之间没有绑定关系**。
医生可以开立药房里不存在的药，药房只能在一份与医嘱无关的库存清单里凭人脑选物资。
011 明确把「药品目录维护」列为不在范围，本计划补上这一环。

## 2. 目标与范围

### 2.1 必须实现

1. **药品目录即物资主数据**：药品 = `materials` 中 `category = '药品'` 的记录，
   不新建 `drug_catalog`/`drugs` 第二套主表；目录的可维护入口复用既有
   `库存计量 → 物资`（`MaterialsPage`，类别已含「药品」）。
2. **医嘱绑定物资**：`MEDICATION` 医嘱的 `order_details` 新增
   `material_id`、`material_code`、`material_name` 三个字段（JSONB，无需新列）。
3. **医生端只能从目录开药**：`POST /crate-api/healthcare/v1/encounters/:id/orders`
   的 `MEDICATION` 医嘱强制要求 `material_id`；服务端校验该物资存在、
   `status = ACTIVE`、`category = '药品'`；`drug_name` 由服务端取目录物资名写入。
4. **药房端按绑定发药**：`POST /crate-api/pharmacy/v1/dispenses/from-medical-order`
   校验请求的 `material_id` 与医嘱绑定一致，不一致返回 409；
   `GET /crate-api/pharmacy/v1/dispenses/medication-orders`
   返回绑定字段供前端预选。
5. **历史自由文本医嘱可补绑**：对没有 `material_id` 的存量医嘱，允许药房在创建发药单时
   一次性补绑目录药品；补绑写入 `medical_orders.order_details` 并留痕
   `material_bound_by` / `material_bound_at`，与发药单同事务提交或回滚。
6. **前端闭环**：医生开药表单的「药名」从文本输入改为药品目录选择器；
   药房发药弹窗按医嘱绑定物资预选并过滤库存；药品在所选仓库无可用库存时给出
   可执行的缺货提示，而不是静默空下拉。
7. **最小演示药品集**：迁移预置 2 条演示药品（含 `降压药A`），幂等、可辨识、可删除，
   使存量医嘱与现场手测能直接走通闭环。

### 2.2 明确不在本期范围

- 不新建药品目录表、药品分类树、剂型/规格字典、医保编码或药品说明书；
- 不实现处方（prescription）模型，不把一条医嘱拆成多条药品明细
  （`medical_order_items` 仍不在本期）；
- 不实现诊断-药品适应症校验、配伍禁忌、抗菌药物分级、麻醉药品管控、皮试标记；
- 不实现药品库存不足时自动补货、自动生成采购申请或跨仓库自动调拨；
- 不改变医嘱状态机、护理任务生成、护士核对门禁与发药事务的既有语义；
- 不引入新的库存主键或包装换算模型（延续 015/016 单一基础单位契约）；
- 不修改 Nexus 仓库（`settings`）配置，不在迁移里伪造仓库或库存事实。

## 3. 领域与数据设计

### 3.1 药品目录

- 判定：`materials.category = '药品' AND materials.status = 'ACTIVE'`；
- `materials.code` 是药品目录编码（已 `UNIQUE`），医生端与药房端都以 `material_id` 为稳定键；
- 演示药品的 `code` 一律以 `DEMO-DRUG-` 前缀标识，避免与真实主数据混淆；
- 演示药品 `enable_batch_control = false`（无批次），理由与代价见 §6；
- 药品目录的增删改仍走既有物资接口，本计划不新增目录维护端点。

### 3.2 医嘱明细字段（JSONB，无新列）

`MEDICATION` 医嘱 `order_details` 的明细白名单新增：

| 字段 | 写入方 | 说明 |
|---|---|---|
| `material_id` | 客户端提交，服务端校验 | 目录物资 ID（ULID），仅 `MEDICATION` |
| `material_code` | 服务端覆写 | 目录物资 `code` 快照 |
| `material_name` | 服务端覆写 | 目录物资 `name` 快照 |
| `material_bound_by` | 服务端写入，仅补绑路径 | 补绑操作人 |
| `material_bound_at` | 服务端写入，仅补绑路径 | 补绑时间（ISO-8601） |

既有字段 `drug_name`、`dose`、`unit`、`route`、`frequency_code`、`frequency_name`、
`duration_days`、`remark` 语义不变；`drug_name` 由服务端取目录物资 `name` 写入，
不再接受客户端任意文本。

### 3.3 依赖方向与端口

沿用 011/014 的「库内定义端口 + `apps/aceso/Main.kt` 注入适配器」范式，
**不新增跨产品库依赖，不让 pharmacy 依赖 healthcare，不让 healthcare 依赖 inventories**：

- `libs/healthcare`：新增 `DrugCatalogPort`（读目录药品，同连接）。
  由 `Main.kt` 用 `MaterialService` 适配。
- `libs/healthcare`：`MedicalOrderService` 新增同连接写方法
  `bindDrugMaterial(client, medicalOrderId, materialId, materialCode, materialName, operator)`，
  经 `HealthcareService` 透出。
- `libs/pharmacy`：`PharmacyPorts.kt` 新增 `DrugCatalogPort`（校验目录药品，同连接）、
  `MedicalOrderReader` 新增 `bindDrugMaterial(...)`。
- 所有端口方法必须复用外层事务连接，禁止内部 `pool.withTransaction`。

## 4. Shared API 契约（前后端并行开发的冻结接口）

### 4.1 物资列表（复用，无改动）

`GET /crate-api/inventories/v1/materials?category=药品&status=ACTIVE&limit=200`

现有 `MaterialRoutes` 已支持 `category`/`status` 过滤，Shared 客户端
`listInventoryMaterials({ category, status, limit })` 已支持，前端零改动即可用。

### 4.2 创建医嘱（行为变更）

`POST /crate-api/healthcare/v1/encounters/:id/orders`

`MEDICATION` 请求体 `order_details`：

```json
{
  "material_id": "01J...",
  "drug_name": "降压药A",
  "dose": "1",
  "unit": "片",
  "route": "口服",
  "frequency_code": "QD",
  "frequency_name": "每日一次"
}
```

服务端行为：

- `material_id` 缺失或空白 → `400`（`material_id is required for MEDICATION order`）；
- 物资不存在 → `404`；`category != '药品'` 或 `status != 'ACTIVE'` → `409`；
- `drug_name` 缺省时服务端写入目录物资名；显式提供且与目录物资名不一致 → `400`
  （`drug_name must match catalog material name`），避免前端与目录静默漂移；
- 服务端覆写 `material_code` / `material_name`，忽略客户端同名入参；
- 其余医嘱类型（`THERAPY`/`EXAMINATION`/`LAB_TEST`）不受影响。

### 4.3 药房待接方列表（响应扩展）

`GET /crate-api/pharmacy/v1/dispenses/medication-orders`

每条记录新增 `material_id`、`material_code`、`material_name`，历史医嘱为 `null`。
不新增必填字段，旧前端不会因此失败。

### 4.4 创建发药单（行为变更）

`POST /crate-api/pharmacy/v1/dispenses/from-medical-order`

请求不变：`medical_order_id`、`warehouse`、`material_id`、`lot_id?`、`dispensed_quantity`。

服务端在既有事务内、锁定医嘱之后新增校验（顺序固定）：

1. 医嘱 `order_details.material_id` 存在且与请求 `material_id` 不一致 → `409`
   （`material_id does not match the prescribed drug`）；
2. 医嘱 `order_details.material_id` 不存在（存量自由文本医嘱）→ 用 `DrugCatalogPort`
   校验请求 `material_id` 为 `ACTIVE` 药品；校验通过后经
   `MedicalOrderReader.bindDrugMaterial(...)` 回填
   `material_id`/`material_code`/`material_name`/`material_bound_by`/`material_bound_at`；
3. 补绑失败、药品非目录、与绑定不一致时，发药单、库存出库与医嘱更新全部回滚。

### 4.5 调度者裁决：端口缺失必须 fail-closed，操作人必须可追责

为使 20+ 处既有测试调用点（`HealthcareRoutes.create(vertx, pool)`、`HealthcareService(pool)`
等，属测试角色文件范围）保持可编译，新增端口参数采用「追加在末尾 + 默认值」。
**代价必须由 fail-closed 兜住**，否则等于「端口漏注入 → 医生又能开目录外的药」，
根因原样复活：

1. `MedicalOrderService.createOrder`：`MEDICATION` 且 `drugCatalogPort == null` → 失败，
   响应 `503`，文案写明「药品目录端口未配置」。**不得**跳过校验后成功返回。
2. `DispenseService`：补绑路径需要端口而其为 `null` → 失败 `503`；
   **不得**静默跳过补绑，也不得降级为「只校验不补绑」。
3. `MedicalOrderReader.bindDrugMaterial` 的接口默认实现返回失败（fail-closed）。
4. `material_bound_by` 取认证上下文 `ctx.get<String>("userId")`
   （`Main.kt:546` 注入；与 `RequisitionRoutes.kt:98`、`PurchaseOrderRoutes.kt` 同范式）。
   **仅在补绑路径**上要求身份；`userId == null` → `401`，与既有两处路由响应形状一致。
   **不得写入 `material_bound_by: null`**——那会产生无法追责的审计记录。
   `material_bound_by` 与 `material_bound_at` 成对写入。
5. 生产组装点 `apps/aceso/Main.kt` 必须实际注入两个 `DrugCatalogPort` 适配器；
   评审须逐条核对该 fail-closed 分支，不能只看构建是否通过。

## 6. 迁移 V204：最小演示药品集

`libs/inventories/src/main/resources/db/migration/V204__seed_demo_drug_materials.sql`

- 号段归属 inventories（V200+），取 `V204`（`V203` 已占用，`V202` 历史缺号不复用）；
- 幂等：`INSERT ... ON CONFLICT (code) DO NOTHING`；
- 预置 2 条（`id` 用固定 26 位 Crockford Base32 ULID 常量，保证可重复执行且可引用）：

| code | name | category | spec | base_unit | quantity_scale | enable_batch_control | status |
|---|---|---|---|---|---|---|---|
| `DEMO-DRUG-001` | `降压药A` | `药品` | `10mg/片` | `片` | 0 | false | ACTIVE |
| `DEMO-DRUG-002` | `阿莫西林胶囊` | `药品` | `0.25g/粒` | `粒` | 0 | false | ACTIVE |

- **已知代价（必须在迁移注释中写明）**：`enable_batch_control = false` 意味着演示药品
  无批次/效期管控，且既有库存事实后不可再改为 `true`。演示药品仅用于走通链路；
  真实药品应通过物资页以 `enable_batch_control = true` 新建。
- **不预置库存**：仓库（`药库`）来自 Nexus `settings`，其 `code` 由环境决定，
  迁移无法安全伪造仓库或库存事实。演示药品的入库由用户在
  `库存计量 → 手工入库` 中完成（见 §7.3）。
- 迁移不得删除或修改任何既有物资。

### 7.2 集成验收（测试角色，隔离库，单命令入口）

```bash
cd service-vertx-kotlin && ./scripts/aceso-test.sh
```

必须覆盖：

1. 目录药品可被 `GET /inventories/v1/materials?category=药品&status=ACTIVE` 检索到；
2. `MEDICATION` 医嘱缺 `material_id` → 400；非药品物资（如 `纱布`）作 `material_id` → 409；
   不存在物资 → 404；合法目录药品 → 201 且 `order_details.material_name` 等于目录名；
3. 药房待接方列表返回 `material_id`/`material_code`/`material_name`；
4. 请求 `material_id` 与医嘱绑定不一致 → 409，且无发药单、无库存操作、医嘱未被改动；
5. 存量无绑定医嘱补绑成功：同事务写入绑定字段与 `material_bound_by`/`material_bound_at`，
   发药确认后库存扣减且 `stock_operation_detail_id` 回写；
6. 补绑路径失败（如请求 `material_id` 指向耗材）→ 409，医嘱 `order_details` 保持原样。

### 7.3 用户手测主线

1. `库存计量 → 物资`：确认「药品」类别下已出现 `降压药A`（`DEMO-DRUG-001`）；
   → 真实药品请在此新建并勾选批次管控。
2. `库存计量 → 手工入库`：仓库选 `药库`，物资选 `降压药A`，数量 `100`，成本 `0.5`，提交。
3. `医生诊疗`：新建 `MEDICATION` 医嘱，「药名」下拉选择 `降压药A`（不再手工输入），
   剂量 `1`、单位 `片`、频次 `每日一次`，提交。
4. `医嘱核对`：护士核对通过。
5. `药房管理 → 待接方用药医嘱` → `创建发药单`：药品物资应已按医嘱预选为 `降压药A`，
   数量 `1`，提交 → 审方 → 开始调配 → 发药确认。
6. 断言：药房单为 `DISPENSED`，`库存计量` 中 `药库/降压药A` 可用量由 `100` 变为 `99`。
7. 反向用例：对 `降压药A` 医嘱在弹窗中选 `纱布`（若仍可选）应被服务端拒绝；
   对无库存药品应看到明确的缺货提示而非空下拉。
