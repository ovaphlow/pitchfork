# Aceso 生成账单前置校验下沉与欠费按入住过滤实施计划

更新时间：2026-09-28

状态：开发候选（后端与前端均已交付：整模块 504/0/57、前端构建 0 errors；待授权后置验证、评审与用户手测）

## 编号、背景与决策

本计划编号 022（020、021 已占用，按 `loop-lessons.md` 第 2 条取当前最大编号 +1）。

本计划是 020 的收尾补强：020 的步骤 10 为了"在点生成账单之前就告诉用户缺什么"，**在前端复刻了服务端的计价前置判定**。这种做法能立即改善体验，但把服务端语义复制到了客户端，是明确的维护负债。

### 现状与问题

1. **前端复刻了护理等级取级规则。** `BillingPage.tsx` 为了判断"这个账期需不需要某个护理等级的护理费项目"，按 `BillingEngine.nursingSegments` 的规则在客户端重新实现了一遍：按评估日分组、同日取 `created_at` 最新、账期前最后一次评估决定首段等级、账期内每个变更点各成一段，再取等级集合。服务端一旦调整取级规则（同日并列的取舍、账期边界、停用评估、跨月裁剪等），前端会**静默误判**：要么错误禁用按钮挡住合法操作，要么放行后在提交时才报错。
2. **核销上限用的欠费合计取自全局欠费列表的前若干条。** 020 的结算核销 UI 用 `listArrears({ limit: 50 })`（全院长者账期倒序）过滤出本入住的欠费行求和，得到"欠费合计"与"核销上限"。若该入住的欠费行不在前 50 条内，上限会被**低估**：方向偏保守（不会触发后端 400），但会挡住合法的核销金额，且"核销后仍欠费 ¥X"的展示数值偏小。
3. 两处都是同一个病根：**服务端语义在客户端被猜测**。020 已经修掉了"字典配不了"和"报错看不懂"，本计划修掉"能不能生成要靠前端猜"。

### 产品决策

1. **判定归服务端，文案归前端。** 新增的前置校验接口只返回**结构化数据**（缺哪个分类、哪个护理等级、启用条数、是否满足），不返回中文句子；中文提示继续由 `billingMessages.ts` 与页面渲染负责。这样后端不引入中文业务文案，前端也不需要理解计价规则的细节。
2. **同源实现，禁止两套算法。** 前置校验与实际生成必须基于**同一份**"本账期需要哪些费用项目槽位"的推导实现；不允许校验走一套、生成走另一套。
3. **纯读取能力扩展，不引入迁移。** 本计划只新增一个只读端点与一个可选查询参数，**不新增数据库列、不新增表、不需要 jOOQ 重生成、不需要数据库授权**，因此不受 021 的授权阻塞影响，可独立交付。
4. **向后兼容。** `GET /payments/arrears` 不带 `encounter_id` 时行为与现在逐字段一致；`GET /encounters/:id/bills` 的生成契约完全不变。

## 目标与范围

### 必须实现

1. **`GET /crate-api/healthcare/v1/payments/arrears` 增加可选 `encounter_id` 过滤**：传入时只返回该入住的欠费账单，`records` 与 `meta.total` 同源过滤（不能只过滤数据而让 `total` 仍是全局数）。已挂 `paymentAuthHandler`，认证要求不变。
   > **与 021 的关系（2026-09-28 计划补充）**：021 的预览接口会返回 `pending_balance` / `outstanding_total` / `max_offset`，届时前端结算核销的数值来源将从"客户端过滤欠费列表"切换为"服务端预览"。因此本项的定位是：**先修掉当前的低估问题**（021 落地前它是唯一来源），并在 021 落地后作为按入住查询欠费的**正确 API 能力**保留（欠费列表页仍可选择性使用），不作为死代码清理对象。若 021 先落地，本项可只做后端参数与测试、前端不再改这一处。
2. **新增只读前置校验接口**（挂 `billAuthHandler`）：
   ```text
   GET /crate-api/healthcare/v1/encounters/:id/bills/precheck?month=YYYY-MM
   ```
   响应为结构化数据，包含：账期裁剪后的 `period_start`/`period_end`、`can_generate`、机器可读的 `blocked_by`、以及 `requirements` 列表（每个槽位含 `category`、`level`（护理费才有）、`required`、`enabled_count`、`satisfied`）。
3. **抽取同源推导实现**：把「本账期需要哪些费用项目槽位」从 `BillService.computeAutoItems` 内部抽出为可复用实现（需要护理评估分段与就餐折合餐次两个既有输入），供 precheck 与 `computeAutoItems` 共用。`computeAutoItems` 的计价结果、校验顺序与错误文案**保持不变**。
4. **前端停止复刻**：`BillingPage.tsx` 删除客户端护理取级实现，改为在账期变化时调用 precheck（防抖，避免每次输入都打接口），据返回的 `requirements`/`blocked_by` 渲染既有的中文缺项提示与按钮 `disabled`；`billingMessages.ts` 只新增 `blocked_by` 枚举 → 中文的映射，不再承载计价规则。
5. **前端欠费合计改为按入住过滤**：核销上限的"欠费合计"改用 `listArrears({ encounter_id, limit })`；「核销后仍欠费 ¥X」随之精确。
6. **Shared API**：`listArrears` 支持 `encounter_id`；新增 `precheckBillGeneration(encounterId, month)` 与对应响应类型。
7. 编写并执行本计划指定的非数据库后端测试、相关编译与前端构建；数据库集成与浏览器 E2E 只在用户明确授权的独立环境执行。

### 明确不在本期范围

- 不新增数据库列/表/迁移，不做 jOOQ 重生成。
- 不修改自动计价的任何规则（床位 = 在院天数、护理 = 等级分段天数、伙食 = 折合餐次、ROUND_HALF_UP 到分）与错误文案。
- 不修改生成账单、手工加项、缴费、收束的接口契约与请求参数。
- 不把中文业务文案搬到后端；不引入错误码体系。
- 不处理 021 的收束未结标记、不处理费用项目唯一约束、不处理读写端点认证一致性。
- 不改结算核销的后端算法与上限规则（只让前端拿到准确的欠费合计）。

## API 契约

### 欠费列表（扩展）

```text
GET /crate-api/healthcare/v1/payments/arrears?encounter_id=<ULID>&limit=50&offset=0
Authorization: Bearer <JWT>
```

- `encounter_id` 可选；省略时行为与现在完全一致。
- 传入不存在或非法的 `encounter_id`：不返回 404（它只是一个过滤条件），返回空列表 `records: []` 且 `meta.total: 0`。
- 过滤后 `records` 与 `meta.total` 必须一致。

### 生成账单前置校验（新增）

```text
GET /crate-api/healthcare/v1/encounters/:id/bills/precheck?month=2026-09
Authorization: Bearer <JWT>
```

```json
{
  "month": "2026-09",
  "period_start": "2026-09-01",
  "period_end": "2026-09-30",
  "can_generate": false,
  "blocked_by": "missing_fee_items",
  "requirements": [
    { "category": "床位费", "level": null,     "required": true, "enabled_count": 1, "satisfied": true },
    { "category": "护理费", "level": "高风险", "required": true, "enabled_count": 0, "satisfied": false },
    { "category": "伙食费", "level": null,     "required": true, "enabled_count": 0, "satisfied": false }
  ]
}
```

- `satisfied` = `enabled_count == 1`（0 条与多条都不满足），由服务端判定，前端不重算。
- `required` = 该槽位在**本账期**是否真的会被用到（例如账期内无就餐记录时伙食费 `required = false`）。
- `blocked_by` 枚举（机器可读，前端映射中文）：
  - `null` —— 可生成；
  - `missing_fee_items` —— 有 `required` 且 `!satisfied` 的槽位；
  - `already_exists` —— 该账期已存在账单（与生成时的重复判定同源）；
  - `not_overlapping` —— 账期与该入住在院区间无重合；
  - `no_admit_date` —— 缺少入住日期；
  - `settled` —— 该入住已完成结算收束；
  - `not_elderly_admission` —— 非养老入住。
- 校验：`month` 必填且为 `YYYY-MM`，非法 → 400（沿用 `month must be in YYYY-MM format`）；encounter 不存在 → 404；未认证 → 401。
- **纯读**：可反复调用，不产生任何写入。`blocked_by` 的判定顺序须与真实生成时的校验顺序一致，避免"precheck 说能生成、生成却报另一个错"。

## 领域模型与业务规则

### 槽位推导（唯一实现）

```text
槽位 = [床位费]
     + [护理费(level) for 账期内每个生效等级]
     + ([伙食费] if 账期内就餐折合餐次 > 0)
```

生效等级的取法与 `BillingEngine.nursingSegments` 完全一致（同日多份评估取 `created_at` 最新；账期前最后一次评估决定首段；账期内每个变更点各成一段）。`computeAutoItems` 与 precheck 必须共用这一次推导结果，禁止各算一套。

### 一致性要求

1. `precheck.can_generate == true` 时，随后以同一 `month` 调用生成接口必须成功（在无并发变化的前提下），不得出现"校验通过但生成 400 缺字典项"。
2. `precheck.can_generate == false` 时，`blocked_by` 必须解释真实原因；`missing_fee_items` 必须至少给出一个 `required` 且 `!satisfied` 的槽位。
3. precheck 不得因字典缺项而返回 4xx（缺字典是**被查询的业务状态**，不是请求错误）。

## 数据库与模块边界

- **不涉及任何数据库变更。** 本计划不需要迁移、不需要 jOOQ 重生成、不需要数据库授权。
- **Healthcare** 拥有槽位推导、precheck 与欠费过滤；改动落在 `BillService`、`PaymentService`、`HealthcareRoutes`。
- **Aceso UI** 只经 `@pitchfork/shared/aceso` 调用；删除客户端复刻逻辑后，`BillingPage.tsx` 不再包含任何计价规则。

## 验收口径

### 主线成功

1. 某入住 3 张 `待缴费` 账单分散在全局欠费列表第 60 条之后；`GET /payments/arrears?encounter_id=<该入住>` 返回 3 条且 `meta.total = 3`；不带该参数时返回结果与改动前一致。
2. 字典齐全且账期合法时，precheck 返回 `can_generate = true`、`blocked_by = null`，`requirements` 中每个 `required` 槽位 `enabled_count = 1`；随后生成账单成功。
3. 停用唯一一条「床位费」后，precheck 返回 200、`can_generate = false`、`blocked_by = "missing_fee_items"`，且 `requirements` 中「床位费」为 `enabled_count = 0`、`satisfied = false`；界面直接显示"缺少启用的「床位费」…请到「系统设置 → 费用项目」新增并启用"，生成按钮禁用。
4. 存在两条启用「床位费」时，该槽位 `enabled_count = 2`、`satisfied = false`，提示"存在多条启用的费用项目"。
5. 账期内无就餐记录时，「伙食费」`required = false`；即使没有启用伙食费项，`can_generate` 仍为 `true`。
6. 护理费按**本账期真正生效的等级**判定：历史评估已被新等级取代时，不要求旧等级的同名护理费项目，界面也不误禁用。
7. 已收束入住的 precheck 返回 `blocked_by = "settled"`；账期与在院区间无重合返回 `not_overlapping`；非养老入住返回 `not_elderly_admission`。

### 拒绝、一致性与无副作用

- `month` 缺失或非 `YYYY-MM` → 400；encounter 不存在 → 404；未认证 → 401。
- precheck 反复调用不产生任何写入（账单、明细、缴费、押金台账、`settled_at` 均不变）。
- `precheck.can_generate == true` 与随后生成成功一致；`false` 时 `blocked_by` 能解释真实原因，不出现"校验通过但生成报缺字典项"。
- 字典缺项时 precheck 返回 200，不返回 4xx。
- 不带 `encounter_id` 的欠费查询行为与改动前逐字段一致；带过滤时 `records` 与 `meta.total` 同源。
- 020 的既有断言（核销上限、双台账写入、`method = 押金` 不可经缴费接口提交）与既有 `BillServiceTest` 计价断言全部保持通过。
- 自动计费的金额与明细构成不因本计划发生任何变化。
