# Aceso 药房申领与护理站补货调拨闭环实施计划

更新时间：2026-08-06

状态：开发候选版本（评审阻断项与 P2 已修复并交付，默认验证通过，待测试复验/评审确认与隔离库/浏览器验收）

## 1. 背景、前置与目标

011 已完成福利院用药医嘱的药房接方与药房仓库出库闭环，012 已完成从已发药明细退回原仓库的
可追溯退库闭环。011 明确将“申领、护理站调拨”留作后续工作；本计划接续该边界，完成护理站或
科室从药房仓库申领药品、耗材并转入自身库存的最小闭环。

`V300__create_pharmacy_tables.sql` 已预留 `pharmacy_requisitions` 和
`pharmacy_requisition_items`。当前的 `RequisitionService`/`RequisitionRoutes` 只是基础 CRUD：
它接受客户端单号和明细，审批/发放未锁库存、未写库存操作、未创建目标仓库存货，且用 `400` 表达
状态冲突。因此它是 013 的待替换基线，不得在其上继续叠加“只改状态”的实现。

本计划的目标是让一次已确认调拨满足下列不可分割的事实：

```text
护理站建单 → 药房审核并预留批次库存 → 药房确认调拨
       → 药房仓库 OUTBOUND + 护理站仓库 INBOUND
       → 双向库存操作明细可追溯 → 申领单 DISPENSED
```

前置能力和边界：

- 002 已建立物资、批次、库存结存、`locked_quantity`、库存操作及明细模型；
- 011 的 `InventoryOutboundPort` 和 012 的 `InventoryInboundPort` 均要求复用 Pharmacy 外层事务
  连接，但现有单向端口分别固定写入 `PHARMACY_DISPENSE`、`PHARMACY_RETURN` 元数据，不能不加
  改造地用于双仓调拨；
- 本计划只覆盖 Aceso 内同一机构的药房仓库到护理站库存仓库；`warehouse` 是现有库存账的仓库标识，
  `department` 是护理站/科室业务名称，二者不假设存在新的仓库主数据；
- 所有 HTTP 路径以 `/crate-api/pharmacy/v1` 为前缀，前端只能通过 `@pitchfork/shared/aceso` 调用。

## 2. 范围与不包含项

### 2.1 必须实现

1. 护理站可创建一张包含多项物资的申领单，选择药房源仓库、目标护理站仓库和科室/护理站名称；
2. 创建时仅接受服务端允许的 `material_id` 与正的申领数量；服务端生成 ULID 和申领单号，不接受
   客户端传入成本、批次、库存行、库存操作、实际发放量或状态；
3. 创建和审批均校验物资为 `ACTIVE`，且本期所有新申领明细只支持 `PACKAGE`；
4. 药房在审批时逐项填写批准数量并选择实际批次，锁定源库存、校验物资/批次/效期/可用量，且把
   批准数量预留到 `stocks.locked_quantity`；
5. 确认调拨时必须在一个数据库事务内锁定申领单、申领明细及全部涉及库存，写一张药房出库操作和
   一张护理站入库操作、每项各一条操作明细，更新两侧库存和申领明细的双向关联，最后置单据为
   `DISPENSED`；
6. 取消草稿或已审批但未调拨的单据；对已审批单据，取消必须在同一事务释放此前预留的
   `locked_quantity`，且不得产生库存操作；
7. 提供创建、列表、详情、审批、确认调拨、取消 API，统一列表/单条/错误响应，正确区分 `400`、
   `404` 与 `409`；
8. 在 Aceso 药房管理页提供“护理站申领”入口，包括护理站建单、药房审核批次和数量、确认调拨、
   历史查询及错误展示；
9. 提供非数据库单元/路由测试、默认编译与前端构建；仅在授权的可销毁 `aceso_test` 中进行迁移、
   真实事务和浏览器验收。

### 2.2 明确不在本期范围

- 采购、供应商、采购入库、自动补货、盘点、库存预警和库存仓库主数据管理；
- `SPLIT` 拆零、单位换算、自动先进先出、自动多批次拆分、批次替代建议；
- 退费、收费、患者用药医嘱、退药流程或改写 011/012 的既有语义；
- 跨机构、跨产品调拨，或护理站之间的反向调拨；
- 新的角色权限系统、电子签名、双人复核、打印/PDF，以及按护理任务自动生成申领单；
- 对 V300 历史申领记录猜测目标仓库、批次、成本或双向库存操作关联。

本期刻意采用“一项申领明细只对应一个实际批次”的最小模型。审批时若单一有效批次无法覆盖该项
数量，药房只能减少该项批准量；不得在没有独立批次分配子表的情况下静默拆为多个批次。多批次自动
拆分须另立计划评估 `requisition_item_allocations`，不能借 `metadata` 伪造事实关联。

## 3. 领域规则、状态与数量语义

### 3.1 申领单与状态机

```text
DRAFT ──approve──> APPROVED ──dispense──> DISPENSED
  │                    │
  └─────cancel─────────┴────cancel───────> CANCELLED
```

- `DRAFT`：护理站已提交物资和期望数量，尚未发生库存预留；
- `APPROVED`：药房已确定每项批准数量和批次，且已在药房源库存的 `locked_quantity` 中完成等额预留；
- `DISPENSED`：所有正批准明细已在同一事务完成药房出库与护理站入库，库存和双向明细关联均已写入；
- `CANCELLED`：草稿直接取消，或已审批单据已原子释放预留后取消；没有库存出/入库操作。

规则：

- 只允许上述动作路线，不能用通用状态更新接口跳到 `APPROVED`、`DISPENSED` 或 `CANCELLED`；
- 同一张单在 `APPROVED` 后不得编辑源仓库、目标仓库、科室、申领明细、批准数量或批次；带有不同
  内容的修改请求返回 `409`；
- `DISPENSED` 和 `CANCELLED` 是终态。对已完成确认调拨的重复请求返回原已完成结果，不再写库存；
  对其他终态动作返回 `409`；
- 一个审批请求必须覆盖这张单的全部明细，明细 ID 不得重复、不得跨单；每项
  `0 <= approved_quantity <= requested_quantity`，至少一项必须大于零；
- 只允许在审批阶段做部分批准。确认调拨不接受客户端 `dispensed_quantity`，服务端把每项正的
  `approved_quantity` 原样写入 `dispensed_quantity`，以免已审批数量被前端偷偷改写；
- 每项正批准数量必须对应一个 `lot_id`；批次管控物资必须选有效且归属该物资的批次，非批次物资
  必须为 `lot_id = null`；
- 源仓库与目标仓库均不能为空且必须不同。`department` 作为护理站业务标签必须非空；没有仓库主数据
  的情况下只做格式、非空和不相等校验，不虚构“有效仓库”目录。

### 3.2 预留而非只读库存检查

只在审批时读取可用库存会导致两个并发审批都看到相同余额、各自批准成功，最终超额。013 因此把
审批定义为库存预留事务，而不是展示性检查：

```text
APPROVED：source.quantity 不变；source.locked_quantity += approved_quantity
DISPENSED：source.quantity -= approved_quantity；source.locked_quantity -= approved_quantity
CANCELLED：source.quantity 不变；source.locked_quantity -= approved_quantity
```

审批、确认和取消均在同一连接事务内按确定顺序锁定申领单、明细和库存。审批以后若物资被停用、
批次过期或预留被异常破坏，确认调拨必须失败并保持 `APPROVED` 与既有预留；药房随后只能取消释放
预留并新建一张申领单，不能绕开状态机改写审批明细。

### 3.3 操作人、时间和幂等身份

- 创建人、审批人、调拨确认人和取消人必须来自已认证请求的服务端解析身份；不接受客户端自由文本
  冒充操作人。路由使用既有 `RoutingContext` principal / `userId` 约定；若 Aceso 挂载层尚未向该
  路由提供认证 principal，开发必须先补齐既有认证挂载，而不是退回请求体 `operator` 字段；
- 创建时间、审批时间、确认时间、取消时间和 `updated_at` 均由服务端写入 `OffsetDateTime`；
- `POST /requisitions` 要求 `Idempotency-Key` 请求头。服务端持久化该键与规范化请求摘要；同一键、
  同一请求返回原单据，同一键、不同请求返回 `409`；
- `PUT` 动作以单据行锁和状态为幂等边界：已 `DISPENSED` 的同一确认返回已完成结果，已
  `CANCELLED` 的同一取消返回已取消结果。已 `APPROVED` 的审批只有在身份和完整批准集合完全相同
  时才返回原结果，其余请求返回 `409`。

## 4. 数据设计与迁移

在 Pharmacy lib 新增 `V302__add_requisition_transfer_traceability.sql`。迁移只使用 Pharmacy 的
`V300+` 号段，不移动 Trainova 基线或 Inventory 的 `V200/V201`。历史 V300 记录可能没有真实库存
调拨事实，新增列保持可空；新服务只接受并写入完整的 013 字段，不对历史记录回填或伪造关联。

### 4.1 `pharmacy_requisitions`

保留既有 `warehouse` 列，明确它是**药房源仓库**，避免无必要的列重命名和历史数据风险。新增：

| 列 | 规则与用途 |
|---|---|
| `destination_warehouse` | 护理站实际目标库存仓库；历史可空，013 新单必填且不同于源仓库 |
| `requester_id` | 从认证 principal 得到的创建人身份；不得由客户端传入 |
| `approved_by`、`approved_at` | 审批操作人和服务端时间 |
| `dispensed_by` | 确认调拨操作人；既有 `dispensed_at` 保留为确认时间 |
| `cancelled_by`、`cancelled_at`、`cancel_reason` | 取消的审计事实；取消原因必填且不写自由 JSONB |
| `idempotency_key`、`request_fingerprint` | 创建请求幂等身份及规范化内容摘要；键在非空时唯一 |
| `updated_at` | 每次合法状态转换由服务端更新 |

为 `idempotency_key` 建立局部唯一索引，为 `(status, created_at DESC)`、`destination_warehouse` 建立
查询索引。申领单号由服务端生成，使用既有业务前缀与 26 位 ULID；不再接受客户端
`requisition_no`，避免客户端重试把唯一冲突当作幂等实现。

### 4.2 `pharmacy_requisition_items`

新增以下专门字段，不能用 `metadata` 代替：

| 列 | 规则与用途 |
|---|---|
| `unit` | 013 新记录固定 `PACKAGE`；历史记录可为 `NULL`，不猜测历史拆零语义 |
| `lot_id` | 已审批并实际调拨的单一批次；批次物资必填、非批次物资为空 |
| `outbound_stock_operation_detail_id` | 药房源仓库 `OUTBOUND` 操作明细 ID |
| `inbound_stock_operation_detail_id` | 护理站目标仓库 `INBOUND` 操作明细 ID |

旧的 `stock_operation_detail_id` 不再作为 013 的写入目标，也不回填。详情 API 可为历史数据保留该字段
以便兼容读取，但对 013 新记录必须返回两个新关联字段和 `unit`。所有新数量均为正精度
`NUMERIC(15,4)`，明细的 `requested_quantity`、`approved_quantity`、`dispensed_quantity` 保留各自的
业务含义；不新增客户端可写的成本列，成本以库存操作明细为准。

### 4.3 库存操作的可追溯设计

不能调用现有的单向 `confirmPackageOutbound` / `confirmPackageInbound` 后只改写其元数据：后者目前会
把入库标识为 `PHARMACY_RETURN`，且逐项调用会形成多张孤立操作。应在 Inventory lib 增加一个专用的
同连接批量转移能力，例如 `confirmReservedPackageTransfer(client, command)`，一次接收整张申领单的
正批准明细并返回双向 detail ID。

该端口必须：

1. 先按稳定键 `(warehouse, material_id, lot_id)` 锁定全部源/目标库存，锁定顺序不得依赖客户端明细
   顺序；
2. 验证源库存的 `locked_quantity` 足以覆盖该申领项的预留，物资仍为 `ACTIVE`，批次仍归属物资且未过期；
3. 写**一张**源仓库 `OUTBOUND` 操作及**一张**目标仓库 `INBOUND` 操作，并为每个正批准项分别写出、入
   两条 `stock_operation_details`；
4. 以源库存计算出的单位成本写入出库明细，并将同一单位成本原样写入目标入库明细，保持成本守恒；
5. 对源仓库执行 `quantity -= quantity`、`locked_quantity -= quantity`，对目标仓库执行
   `quantity += quantity`、`total_cost += quantity * unit_cost`；
6. 在两张库存操作的 `metadata` 中写入 `source = PHARMACY_REQUISITION_TRANSFER`、`requisition_id`、
   `requisition_no`、相对仓库和确认人；每条申领明细通过两个专门列关联相应 detail ID；
7. 对目标库存尚不存在的 `(warehouse, material_id, lot_id)` 使用现有部分唯一索引兼容的并发安全
   upsert/冲突重读后再锁定，不能采用“先 SELECT、未找到再裸 INSERT”的竞争写法；
8. 自身不开启新事务，始终复用 Pharmacy 外层 `SqlConnection`。任一操作、明细或库存写入失败时，
   外层事务回滚源库存、目标库存、预留变化、申领明细和申领状态。

库存端口仅接收服务端从锁定申领明细构造的命令，不能接受浏览器提供的库存行 ID、成本、操作号或
预留量。Pharmacy 不直接写 Inventory 表；Aceso `Main.kt` 只负责把 `StockService` 的同连接适配器注入
`InventoryRequisitionTransferPort`。

## 5. API 契约

以下路径均位于 `/crate-api/pharmacy/v1`。列表始终返回
`{ "records": [...], "meta": { "total": N } }`，即使为空；单条直接返回对象；错误保持
`{ "error": "<message>" }`。ID 为 26 位 Crockford Base32 ULID。

### 5.1 创建与查询

```text
POST /requisitions
GET  /requisitions?warehouse=&destination_warehouse=&department=&status=&limit=&offset=
GET  /requisitions/:id
```

创建要求 `Idempotency-Key`，请求体只允许：

```json
{
  "warehouse": "药房西药库",
  "destination_warehouse": "一护理站库存",
  "department": "一护理站",
  "items": [
    { "material_id": "01J...", "requested_quantity": 10 },
    { "material_id": "01J...", "requested_quantity": 5 }
  ]
}
```

创建规则：

- `warehouse`、`destination_warehouse`、`department`、非空 `items` 和每项 `material_id`、正数
  `requested_quantity` 均必填；
- 同一请求内不接受重复 `material_id`，避免在当前单批次明细模型中产生无法表达的批次拆分；
- 服务端在一笔事务中生成单头和全部明细，设置 `DRAFT`、`unit = PACKAGE`、创建人、时间和幂等键；
  任一明细无效时不得留下单头；
- 创建仅验证物资存在且 `ACTIVE`，不接受 `approved_quantity`、`dispensed_quantity`、`lot_id`、
  `stock_*`、成本、`metadata`、状态或任何操作人字段；
- `GET` 查询不锁库存、不改变状态。详情同时返回源/目标仓库、状态审计字段、每项数量、批次、单位和
  双向库存操作明细 ID；历史 V300 记录的新增字段可为 `null`。

### 5.2 审批、确认调拨和取消

```text
PUT /requisitions/:id/approve
PUT /requisitions/:id/dispense
PUT /requisitions/:id/cancel
```

审批请求必须覆盖全部明细：

```json
{
  "items": [
    { "id": "01J...", "approved_quantity": 8, "lot_id": "01J..." },
    { "id": "01J...", "approved_quantity": 0, "lot_id": null }
  ]
}
```

确认调拨只触发已审批预留的物理转移，不再接受数量或成本。请求体为空对象；服务端从已锁定明细读取
批准数量和批次。取消请求为：

```json
{ "reason": "护理站取消本次补货" }
```

响应和错误规则：

- 创建成功返回 `201`；合法审批、确认、取消和幂等重试返回 `200`；
- 请求体结构、必填字段、数量格式、重复 ID、未知客户端字段或错误 `Idempotency-Key` 返回 `400`；
- 单据或明细不存在返回 `404`；
- 非法状态转换、物资未启用、批次不匹配/过期、源库存不足、预留不足、源/目标仓库相同、同一键不同
  内容、并发更新、以及试图修改已审核/已完成单据返回 `409`；
- 路由不得将业务冲突包装为 `500` 或泄露 SQL、堆栈和内部端口异常。

审批返回的详情必须已经包含持久化后的预留结果；确认调拨返回的详情必须已经包含 `DISPENSED`、
`dispensed_by`、`dispensed_at` 和每项的两侧 detail ID。`DISPENSED` 重试必须读取并返回这份结果，
不得再调用库存端口。

## 6. 后端实施设计

### 6.1 模块职责与事务边界

```text
RequisitionRoutes
    └── 认证身份 + JSON/HTTP 映射
        └── RequisitionService（Pharmacy 外层事务）
            ├── 锁定申领单和明细 / 状态机 / 双向关联回写
            └── InventoryRequisitionTransferPort（传入同一 SqlConnection）
                └── StockService 预留、释放、确认整单 PACKAGE 转移
```

- 将现有字符串 jOOQ 表/字段替换为 Pharmacy 生成表；不要继续以 `get()` 后在 Pool 上逐项更新的方式
  实现审批或发放；
- `RequisitionService.create`、`approve`、`dispense`、`cancel` 均由 `pool.withTransaction` 建立一次外层
  事务，向端口传递同一个 `SqlConnection`；读取列表可使用 Pool；
- `approve` 锁单头和全量明细，按稳定顺序锁源库存并增加预留，随后同时写审批人、时间、批次、批准数量
  与状态；
- `cancel` 锁单头、明细和已预留库存。`DRAFT` 只写取消审计，`APPROVED` 先释放全部正批准项预留、再写
  取消审计和状态；
- `dispense` 锁单头和全量明细，先处理已 `DISPENSED` 的幂等返回，再验证 `APPROVED` 和所有正批准项的
  完整性，调用一次整单转移端口，回写每项出/入库 detail ID 和 `dispensed_quantity`，最后写状态与审计；
- 任一端口 Future 失败必须使外层 Future 失败，不能吞错后继续更新申领单；测试桩必须断言传入的是
  事务连接而非 Pool。

### 6.2 路由、认证和生成源

- 扩展 `PharmacyPorts.kt` 定义 013 专用的预留/释放/批量调拨命令与结果，区分现有发药、退药端口；
- `PharmacyRoutes.create` 和 `RequisitionRoutes.create` 接收新端口；`apps/aceso/Main.kt` 注入
  `StockService` 适配器，不建立跨产品 HTTP 调用；
- 所有写路由使用既有认证 principal 取得操作人。页面不能仅靠隐藏按钮承担权限或审计；
- 新增 V302 后，仅在获得独立可恢复数据库授权时运行
  `PITCHFORK_DB_PASSWORD=... ./gradlew :libs:pharmacy:generateJooq`，提交实际生成的 Pharmacy 表、记录和
  索引源；不得提交 `build/tmp` 渲染物；

  语义；保留的只读历史查询必须明确区分 013 数据和不可追溯历史数据。

## 7. Shared API 与页面设计

在 `@pitchfork/shared/aceso` 新增 snake_case 的申领类型和客户端函数，封装 `Idempotency-Key`、认证 token、
JSON 解析和 `401` 处理。Aceso UI 不直接拼 `/crate-api` 路径，也不直接请求 Inventory 后端。

药房页增加“护理站申领”工作区，可采用申请/审核/待调拨/历史四个筛选区，不要求本期拆成独立路由：

```text
药房管理 / 护理站申领
├── 新建申领（护理站）
│   ├── 药房源仓库、目标护理站仓库、科室
│   └── ACTIVE 物资与正申领数量（可添加多项）
├── 待审核（药房）
│   └── 每项批准数量、可用量、批号、有效期、批次选择
├── 待调拨（药房）
│   └── 已预留数量和批次摘要 → 一次确认调拨
└── 历史
    └── 状态、两侧仓库、操作人、时间、出/入库明细关联
```

页面要求：

- 物资下拉只展示 `ACTIVE` 物资；创建阶段不展示/提交成本、库存行、库存操作 ID 或实际发放量；
- 审批批次列表展示源仓库可用量、批号和有效期；目标仓库的存量不是审批可编辑输入；
- 创建/审批/确认/取消期间禁用相应按钮，`POST` 重试复用同一个尚未完成的幂等键；失败时保留用户输入；
- 确认成功后只刷新受影响的详情和当前列表；库存不足、批次过期、物资停用、状态冲突和重复请求显示
  清晰业务错误；
- 详情同时显示源仓库出库明细与目标护理站入库明细，不能只显示旧的
  `stock_operation_detail_id`；
- 窄屏下物资、批次、双明细 ID 和错误文本不得重叠，表格允许横向滚动；
- 不在本页面加入采购、盘点、拆零、退药、自动补货或根据护理任务自动建单按钮。

## 9. 验收口径

### 9.1 后端、数据与并发

- 创建只接受源/目标仓库、科室、`ACTIVE material_id` 与正数量；客户端成本、库存、批次、状态和
  实发量不会被持久化；
- 一张单可含多个物资，单据和明细原子创建；同一 `Idempotency-Key` 重试不产生第二张单，不同内容
  使用同一键返回 `409`；
- 审批完整覆盖所有明细，批准量不超过申领量和已锁定源库存可用量；批准后源库存数量不变、
  `locked_quantity` 精确增加，审批人/时间/批次可查询；
- 两张并发审批争用同一源批次时，批准总量不能超过可用量；取消已审批单后，`locked_quantity` 恢复，
  不生成库存操作；
- 未审核、已取消、已完成或非法状态的单据不能确认调拨；已审核单不能通过其他 API 改数量、批次、
  仓库或明细；
- 确认调拨成功后，源仓库数量减少、预留减少，目标仓库数量增加，两边数量相等、单位成本一致；
  每个正批准项都有一个出库和一个入库 detail ID，单据状态才为 `DISPENSED`；
- 目标仓库没有对应库存行时能安全创建；并发首次入库不产生重复库存行或重复数量；
- 入库写入失败、明细写入失败、源库存不足、批次失效或状态竞争时，源/目标库存、锁定量、库存操作、
  明细关联和申领状态均无半成品；
- 已 `DISPENSED` 的确认重试返回原结果，不重复写 OUTBOUND/INBOUND 或增减库存；错误响应不泄露 SQL/
  堆栈，列表响应即使无记录仍含 `records` 和 `meta.total`。

### 9.2 页面手测

1. 使用已认证的护理站账号选择药房源仓库、目标护理站仓库和两个 `ACTIVE` 物资，创建申领单；
2. 确认创建页不会提交成本、库存行、库存操作或实际发放量，详情显示 `DRAFT` 与正确创建人；
3. 使用药房账号审核，分别批准完整和部分数量，选择有效批次；确认页面显示已预留数量和批次；
4. 取消另一张已审批单，确认其消失于待调拨列表且源库存预留已释放；
5. 确认第一张调拨，刷新后看见 `DISPENSED`、源/目标仓库、操作人/时间和每个明细的双向库存关联；
6. 再次确认同一单据，确认数量和操作记录不重复；以库存不足、批次过期、物资停用或已取消单据操作，
   确认错误清晰且页面保留可编辑输入；
7. 在窄屏检查多项明细、批号、明细关联和长错误消息不重叠。

## 10. 风险与控制

| 风险 | 影响 | 控制 |
|---|---|---|
| 审批只读库存而不预留 | 并发多单超额批准 | `APPROVED` 原子增加 `locked_quantity`，取消释放、确认扣减 |
| 复用退药入库端口 | 调拨被错误标记为退药，审计失真 | 新建专用批量转移端口和 `PHARMACY_REQUISITION_TRANSFER` 元数据 |
| 一项需求跨多个批次 | 单一 `lot_id` 丢失部分来源 | 013 明确单项单批次；不足时部分批准，自动拆批另立计划 |
| 出库、入库使用不同连接 | 出库已扣而目标未入库 | Pharmacy 外层事务向所有端口传同一 `SqlConnection` |
| 目标库存首次创建并发 | 重复行、唯一冲突或数量丢失 | 按稳定顺序锁定并以部分唯一索引兼容的 upsert/冲突重读处理 |
| 客户端可提交成本或库存 ID | 伪造库存、成本或可追溯关系 | 请求字段白名单；库存命令只由锁定的服务端明细构造 |
| `DISPENSED` 重试再次执行 | 重复扣减和重复入库 | 先锁单并检查终态，再调用库存端口；创建使用幂等键 |
| 历史 V300 没有目标/双向关联 | 错误回填造成假审计 | V302 新列对历史保留 NULL；只保证 013 新数据完整 |
| 无认证 principal 时信任请求体人员 | 审计可伪造 | 写路由只用服务端 principal；先补既有认证挂载，不引入自由 `operator` |
