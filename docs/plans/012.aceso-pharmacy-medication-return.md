# Aceso 福利院药房退药与可追溯退库闭环实施计划

更新时间：2026-08-26

状态：已完成（2026-08-26 评审确认；证据链：隔离 PostgreSQL 集成 + 浏览器 E2E，见 §9.3）

## 1. 背景与目标

011 的发药确认已经能够将福利院用药医嘱对应的包装库存出库，但已发药单不能直接取消，实际业务需要把未使用或错发的包装退回原仓库，并保留从原发药明细到库存回库操作的完整链路。本计划优先实现这一项独立业务能力，不等待 011 及更早计划完成最终验收。

目标是形成以下闭环：

```text
已发药明细 → 创建待确认退药单 → 锁定原物资/批次/成本 → 确认回库
                                          └→ Inventory INBOUND + PHARMACY_RETURN
```

## 2. 范围与约束

必须实现：

- 只允许从 `DISPENSED` 发药单的 `PACKAGE` 明细创建退药；患者、仓库、物资、批次、原出库明细和单位成本全部由服务端从原记录推导。
- 创建退药单时校验正数、退药原因、操作人和 `restockable = true`，并把 `PENDING`/`CONFIRMED` 退药量计入剩余可退数量。
- `PENDING` 退药确认必须在 Pharmacy 外层 `SqlConnection` 内调用库存回库端口，成功后回写退药库存操作明细、成本并置为 `CONFIRMED`。
- 库存回库使用既有 `INBOUND` 操作类型，操作元数据写入 `source = PHARMACY_RETURN`；库存行存在时累加数量和成本，不存在时创建。
- 确认接口幂等；已确认单重试不得重复增加库存；已确认单不可取消。
- Aceso 药房页面提供退药 Tab、创建退药、确认入库和取消待确认退药单入口，并复用 `@pitchfork/shared/aceso` API 客户端。

不在本期范围：拆零退药、退费、自动质检、跨仓调拨、采购/供应商流程。数据库集成验收与浏览器 E2E 为**后置项**：仅在用户提供可恢复的 `aceso_test` 与授权浏览器环境后执行（见 §4 清单与 §5 验证记录），不属于前置实现范围。

## 3. API 契约

路径前缀：`/crate-api/pharmacy/v1`。

```text
POST /returns/from-dispense
GET  /returns
GET  /returns/:id
PUT  /returns/:id/confirm
PUT  /returns/:id/cancel
```

创建请求只接受：

```json
{
  "dispense_id": "01J...",
  "dispense_item_id": "01J...",
  "quantity": 1,
  "return_reason": "老人未使用",
  "operator": "护士甲",
  "restockable": true,
  "remark": "包装完整"
}
```

服务端拒绝旧的通用 `POST /returns/` 入口，避免客户端伪造患者、仓库、物资、批次和单位成本。列表仍返回 `{ "records": [], "meta": { "total": 0 } }`，错误返回 `{ "error": "<message>" }`。
