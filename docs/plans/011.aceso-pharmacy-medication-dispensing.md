# Aceso 福利院药房用药医嘱接方与发药闭环实施计划

更新时间：2026-08-06

状态：待评审（数据库集成测试已通过；浏览器/E2E 后置）

## 1. 编号与前置计划

本文件是 010 医生诊疗工作台之后的药房开发计划，目标是把医生开立的
`MEDICATION` 医嘱接入药房，并完成从待接方到库存出库、发药确认的最小闭环。

前置能力：

- 002 已建立 Aceso `inventories` 库存主数据、批次、库存结存和库存操作模型；
- 005 已建立活动 `ELDERLY_CARE` 入住与精确护理周期关系，并支持离院收束；
- 008 已建立 `healthcare.medical_orders`、医嘱状态机和医嘱到护理任务的关联；
- 010 已实现病程、诊断、四类医嘱、`order_class` 和医生诊疗页面；
- Aceso 已在同一应用中挂载 `/crate-api/inventories/v1`、`/crate-api/healthcare/v1`、
  `/crate-api/pharmacy/v1`，但当前 Pharmacy 仍主要是基础 CRUD，占位页面尚未形成接方闭环。

当前 Pharmacy 的 `V300` 已创建 `pharmacy_dispenses`、`pharmacy_dispense_items`、
`pharmacy_returns`、`pharmacy_return_items`、`pharmacy_requisitions` 和
`pharmacy_requisition_items` 六张表。现有服务存在以下事实，本计划以此为起点：

- `DispenseService` 使用字符串 jOOQ 表引用，创建单据和明细没有外层事务；
- 现有状态更新只更新药房单状态，没有调用库存出库，也没有回写库存操作明细；
- `pharmacy_dispense_items.order_item_id` 和 `order_execution_id` 当前是弱关联；
- 010 的用药医嘱仍以 `order_details.drug_name` 为展示文本，不提前引入
  `medical_order_items`，也没有 `material_id`；
- 库存模块已有 `materials`、`lots`、`stocks`、`stock_operations` 和
  `stock_operation_details`，但没有面向 Pharmacy 的原子出库服务；
- `pharmacy` 页面目前仍为“待实现”占位页。

本计划不依赖旧的 Pharmacy `设计说明.md` 直接复制第二套表结构；实际迁移和当前生成源
以 `V300` 及运行代码为准。若设计说明与本计划冲突，以本计划的角色边界、事务和验收口径为准。

## 2. 目标与范围

### 2.1 必须实现

1. 仅支持福利院活动 `ELDERLY_CARE` 入住下的 `MEDICATION` 医嘱接方和发药；
2. 药房可以查看待接方用药医嘱，看到精确 `medical_order_id`、患者、入住、药名文本、医生、
   医嘱周期、频次和起止时间；
3. 药师必须从库存可用物资中选择 `material_id`，不能把自由文本 `drug_name` 当作库存主键；
4. 创建药房发药单时由服务端从 `medical_order_id` 推导患者和入住，不能接受客户端伪造的
   `patient_id` 或 `encounter_id`；
5. 第一版采用“一条用药医嘱对应一条发药明细”的最小语义，
   `pharmacy_dispense_items.order_item_id` 保存精确的 `medical_orders.id`；
6. 发药确认必须在一个数据库事务内完成：锁定医嘱和药房单、校验状态、调用同连接库存出库、
   回写 `stock_operation_detail_id`，最后将药房单置为 `DISPENSED`；
7. 库存不足、批次不合法、医嘱已停嘱、重复发药或任一步写入失败时，药房和库存均不产生半成品；
8. 明确支持 `PACKAGE` 包装单位出库；`SPLIT` 拆零在本期拒绝并留待后续计划，避免在未完成单位换算审查前扣错库存；
9. 提供 Aceso 药房页面，完成待接方、审方、开始调配、发药确认和取消操作；
10. 通过默认非数据库测试、Pharmacy/Inventories 编译、Aceso 前端构建和 `git diff --check`，
    并在获授权的隔离数据库和浏览器环境完成后置验收。

### 2.2 明确不在本期范围

- 不新建 `prescriptions`、`medication_orders` 或第二套医嘱主表；
- 不在本期引入 `medical_order_items`，不支持一条医生医嘱包含多种药品；
- 不实现采购、供应商、入库、审价、药品目录维护、药品医保信息和药房盘点；
- 不实现退药、退费、申领、护理站调拨或 `pharmacy_returns`/`pharmacy_requisitions` 的新流程；
- 不实现 `SPLIT` 拆零、自动按多批次拆单、自动先进先出分配或有效期替代决策；
- 不按每次 `nursing_task_execution` 自动生成发药单，不把发药等同于护理执行完成；
- 不修改护理任务生成、护理执行、护理消耗和 010 医嘱状态机语义；
- 不实现治疗、检查、检验医嘱的药房流程；这些类型的执行和报告另立计划；
- 不实现权限角色、电子签名、双人复核、收费结算、通知、打印/PDF 或跨机构传输；
- 不把 Pharmacy 直接改造成跨服务 HTTP 调用，也不让 Pharmacy 直接写 Healthcare 或 Inventory 表。

## 3. 领域和数据设计

### 3.1 医嘱来源与药品选择

010 的 `MEDICATION` 医嘱仍是唯一医嘱来源。药房读取：

- `medical_orders.id`；
- `encounter_id`、患者信息和入住状态；
- `order_type = MEDICATION`；
- `status = ACTIVE`；
- `order_content`、`doctor`、`start_time`、`end_time`、`order_class`；
- `order_details.drug_name`、剂量、单位、途径、频次和持续天数。

`drug_name` 只作为药师核对时的临床文本，不自动匹配库存物资。药师必须从库存可用库存中
选择一个 `material_id`，并可看到物资名称、规格、包装单位、批号、有效期和可用数量。若文本
与物资名称不一致，页面显示二次确认信息，但不由服务端用模糊匹配代替药师确认。

第一版明确一条医嘱一条发药明细：

```text
medical_orders.id
└── pharmacy_dispense_items.order_item_id
    └── pharmacy_dispense_items.material_id
```

这里的 `order_item_id` 是为兼容现有 Pharmacy 表和 008/010 关联字段而复用的精确医嘱 ID，
不是凭空创建的药品项目 ID。数据库不添加跨 schema 外键，服务端通过内部端口锁定并验证归属。
未来药房确认一张医嘱包含多种药品时，再另立计划评估 `medical_order_items` 和拆方语义。

### 3.2 最小迁移

在 Pharmacy 归属库新增 `V301__add_dispense_warehouse_and_order_lookup.sql`：

```sql
ALTER TABLE pharmacy.pharmacy_dispenses
    ADD COLUMN warehouse VARCHAR;

CREATE INDEX idx_pharmacy_dispense_items_order_item
    ON pharmacy.pharmacy_dispense_items (order_item_id)
    WHERE order_item_id IS NOT NULL;
```

规则：

- 历史发药单的 `warehouse` 保留 `NULL`，不猜测、不回填；
- 新建 `ELDERLY_ROUTINE` 发药单必须填写 `warehouse`；
- `order_item_id` 的历史弱关联不批量修复；011 新建记录必须写精确 `medical_orders.id`；
- 不为历史重复发药记录添加可能失败的唯一约束；新单重复校验在锁定医嘱的事务内完成；
- 只提交由 V301 实际生成的 Pharmacy jOOQ `warehouse` 字段，不提交 `build/tmp` 配置渲染物；
- 迁移号段只使用 Pharmacy `V300+`，不改 Healthcare 的 V500+ 或 Inventory 的 V200/V201 历史迁移。

### 3.3 药房单状态

011 只允许以下状态流转：

```text
PENDING → REVIEWED → DISPENSING → DISPENSED
    └──────────────→ CANCELLED
    └────────────────────────────→ CANCELLED
```

规则：

- `PENDING`：已从活动用药医嘱创建，等待审方；
- `REVIEWED`：已记录 `reviewer`，允许开始调配；
- `DISPENSING`：已记录 `pharmacist`，尚未扣减库存；
- `DISPENSED`：库存出库成功，明细写入 `stock_operation_detail_id`，写入 `dispensed_at`；
- `CANCELLED`：未发生库存出库的单据被取消；已 `DISPENSED` 的单据不能取消，退药另立计划；
- 养老场景第一版允许同一人完成审方和发药，不引入双人复核权限规则；
- 状态只能由对应动作接口触发，不能通过通用状态接口跳过库存事务直接写 `DISPENSED`。

### 3.4 数量、批次和库存

011 只支持包装单位：

- `unit = PACKAGE`；
- `dispensed_quantity` 为正数，不能大于库存可用数量；
- `lot_id` 对启用批次管控的物资必填；
- 非批次物资不接受伪造的 `lot_id`；
- 物资必须是 `ACTIVE`；
- 库存服务负责锁定目标库存行、校验可用量、写 `OUTBOUND` 操作和明细，并返回
  `stock_operation_detail_id`、实际批次和单位成本；
- Pharmacy 只保存返回的关联 ID，不直接更新 `inventory.stocks` 或 `inventory.stock_operations`。

### 3.5 跨模块事务端口

Pharmacy 不能直接依赖并写 Healthcare/Inventory 表。由 Aceso `Main.kt` 注入两个内部端口：

```text
MedicalOrderReader
└── lockMedicationOrder(client, medicalOrderId)
    → HealthcareService 使用同一 SqlClient 查询和锁定医嘱

InventoryOutboundPort
└── confirmPackageOutbound(client, command)
    → StockService 使用同一 SqlClient 锁库存并写出库操作
```

端口调用禁止重新从 `Pool` 开启新事务，所有读写必须复用 Pharmacy 外层事务的连接。这样
“医嘱已锁定、发药单已变更、库存已扣减、关联明细已回写”才能整体提交或整体回滚。

## 4. API 契约

所有路径位于 `/crate-api/pharmacy/v1`。列表响应保持：

```json
{ "records": [], "meta": { "total": 0 } }
```

错误响应保持：

```json
{ "error": "<message>" }
```

### 4.1 待接方用药医嘱

```text
GET /medication-orders?status=ACTIVE&encounter_id=&search=&limit=&offset=
```

规则：

- 只返回 `order_type = MEDICATION`；
- 默认只返回活动养老入住和 `ACTIVE` 医嘱；
- 可按精确 `encounter_id` 筛选，不按 `patient_id` 猜入住；
- 已存在未取消发药单的医嘱返回 `dispense_id` 和 `dispense_status`，页面显示已接方；
- 读取不写医嘱、不创建任务、不锁库存；
- 返回的患者/入住摘要由 Healthcare 内部端口按精确医嘱归属生成。

响应记录示例：

```json
{
  "order_id": "01J...",
  "encounter_id": "01J...",
  "patient_id": "01J...",
  "patient_name": "李阿姨",
  "encounter_no": "A20260801001",
  "order_type": "MEDICATION",
  "order_type_label": "用药医嘱",
  "order_class": "LONG_TERM",
  "order_class_label": "长期医嘱",
  "drug_name": "降压药",
  "order_content": "降压药每日一次",
  "dose": "1",
  "unit": "片",
  "route": "口服",
  "frequency_code": "QD",
  "frequency_name": "每日一次",
  "start_time": "2026-08-06T08:00:00+08:00",
  "end_time": null,
  "dispense_id": null,
  "dispense_status": null
}
```

### 4.2 从医嘱创建发药单

```text
POST /dispenses/from-medical-order
```

请求：

```json
{
  "medical_order_id": "01J...",
  "warehouse": "西药库",
  "material_id": "01J...",
  "lot_id": "01J...",
  "dispensed_quantity": 1,
  "unit": "PACKAGE"
}
```

服务端规则：

- `medical_order_id`、`warehouse`、`material_id`、`dispensed_quantity` 必填；
- 患者、入住、药名、医生和医嘱内容全部从锁定医嘱读取，不接受请求体覆盖；
- 只允许 `ELDERLY_CARE + ACTIVE encounter + MEDICATION + ACTIVE order`；
- 同一医嘱已有 `PENDING`、`REVIEWED`、`DISPENSING` 或 `DISPENSED` 发药单时返回 `409`；
- 取消单不阻断重新接方，但新单必须有新的 ULID 和完整明细；
- 物资、批次、包装单位和数量先做输入校验，但不在创建阶段扣库存；
- 成功返回 `201`，发药单初始状态为 `PENDING`；
- 写入药房单和明细必须在同一事务内完成，任一写入失败均回滚。

`POST /dispenses/` 现有通用创建入口不得被用来绕过上述规则；对新的
`ELDERLY_ROUTINE` 请求应返回 `400`，前端统一使用本节的新入口。其他历史类型不在本计划内重写。

### 4.3 审方、开始调配、发药确认和取消

```text
POST /dispenses/:id/review
POST /dispenses/:id/start
POST /dispenses/:id/confirm
POST /dispenses/:id/cancel
```

请求示例：

```json
{ "operator": "张药师", "remark": "药名与库存规格已核对" }
```

规则：

- `review` 仅允许 `PENDING`，必须有非空 `operator`，写入 `reviewer`，转为 `REVIEWED`；
- `start` 仅允许 `REVIEWED`，必须有非空 `operator`，写入 `pharmacist`，转为 `DISPENSING`；
- `confirm` 仅允许 `DISPENSING`，锁定医嘱、药房单、明细和库存，调用同连接出库，回写库存明细 ID，
  写 `dispensed_at` 并转为 `DISPENSED`；
- `cancel` 允许 `PENDING`、`REVIEWED`、`DISPENSING`，必须没有库存出库记录，转为 `CANCELLED`；
- 终态重复动作返回 `409`，不存在单据返回 `404`，输入错误返回 `400`；
- `confirm` 重试若已是 `DISPENSED`，返回已有结果且不得再次扣库存；
- 所有业务错误不暴露 SQL、堆栈或内部端口异常。

### 4.4 发药单查询

保持既有只读路径：

```text
GET /dispenses?patient_id=&encounter_id=&status=&dispense_type=ELDERLY_ROUTINE&limit=&offset=
GET /dispenses/:id
```

列表和详情必须返回 `warehouse`、订单关联、药品物资、批次、数量、库存操作明细 ID、操作人和状态。
查询不修改状态、不调用库存、不重新创建发药任务。

已有 `PUT /dispenses/:id/status` 不得允许客户端直接跳到 `DISPENSED`；开发可以保留兼容路由，
但所有 `DISPENSED` 目标必须转发到与 `confirm` 相同的库存事务，不能保留旧的无库存状态更新语义。

## 5. 页面设计

将 `dashboard/pharmacy.astro` 的占位内容替换为 `PharmacyPage.tsx`，页面名称保持“药房管理”。

```text
药房管理
├── 待接方用药医嘱
│   ├── 活动入住/老人筛选
│   ├── 医嘱正文、药名、规格、频次和周期
│   └── 创建发药单
├── 待审方/待调配
│   ├── 药房单详情
│   ├── 选择库存物资、仓库和批次
│   └── 审方、开始调配
├── 待发药
│   ├── 数量和库存可用量
│   └── 发药确认
└── 历史发药
    ├── 已发药/已取消筛选
    └── 库存出库明细关联
```

交互要求：

- 页面只通过 `@pitchfork/shared/aceso` 调用 Pharmacy 和 Inventory API；
- 选择医嘱后展示医生原始药名和库存物资名称，明确二者不是自动匹配结果；
- 创建、审方、开始调配、发药确认期间禁用对应按钮，防止重复提交；
- 请求失败保留用户选择的仓库、物资、批次和数量；
- 发药确认成功后只刷新当前列表和详情，不重置其他筛选；
- 库存不足、有效期问题、医嘱已停嘱和重复接方显示清晰业务错误；
- 011 不在药房页面提供入库、采购、退药、申领、拆零或护理执行按钮；
- 桌面端和窄屏下长医嘱正文、规格、批号和错误消息不重叠，表格可横向滚动。

## 6. 实施顺序

1. **确认当前表和运行边界。** 开发阅读本计划、根/后端/前端 `AGENTS.md`、002、008、010，
   核对 V300/V200/V201、`DispenseService`、`StockService`、`HealthcareService` 和 Aceso `Main.kt`。
   记录现有 Pharmacy 历史数据数量、空 `warehouse` 情况和重复 `order_item_id` 情况；不连接共享开发库，
   只在获授权的只读/隔离环境核对。

2. **新增 V301 和 Pharmacy jOOQ 生成源。** 在 Pharmacy 增加 `warehouse` 列及订单关联查询索引，
   保留历史 NULL，不回填。只有获得独立可恢复数据库授权后执行 `:libs:pharmacy:generateJooq`，
   提交实际变化的 `PharmacyDispenses`、`PharmacyDispensesRecord` 和必要索引生成源。

3. **建立同连接内部端口。**
   - 在 Pharmacy 定义 `MedicalOrderReader` 和 `InventoryOutboundPort`，接口均接受外层 `SqlClient`；
   - 在 `HealthcareService` 增加只供 App 编排的精确医嘱锁读方法，返回受控快照；
   - 在 `StockService` 增加同连接的包装出库方法，锁库存、校验批次/数量、写 `OUTBOUND` 操作和明细；
   - 在 Aceso `Main.kt` 注入适配器，禁止 Pharmacy 自己开启第二个连接或直接拼 Healthcare/Inventory SQL。

4. **重构 Pharmacy 发药服务。** 用生成的 Pharmacy jOOQ 表替换本计划触及的 `DSL.table`/字符串字段，
   实现订单接方、重复锁定、状态动作、库存端口调用、库存关联回写和统一错误映射。保留退药/申领
   既有表与页面占位，不在本计划顺便重写其 CRUD。

5. **注册新路由和 Shared API。** 增加本计划 4.1–4.4 的路由、snake_case 类型和客户端函数；
   `Main.kt` 已有 `/pharmacy/v1` 挂载，只补充端口注入，不新建产品 URL 或跨服务客户端。

6. **实现 Pharmacy UI。** 新增 `PharmacyPage.tsx`，替换 `dashboard/pharmacy.astro` 占位页；
   复用现有库存查询类型和 UI 组件，不修改 010 医生诊疗页的开方语义。

## 7. 验收口径

### 7.1 后端和数据

- 活动福利院 `MEDICATION` 医嘱可以进入待接方列表；治疗/检查/检验医嘱不会进入药房队列；
- 接方请求由服务端从 `medical_order_id` 推导患者和入住，伪造患者或入住字段不会改变结果；
- 非活动、非福利院、非 `MEDICATION`、停嘱/作废/完成医嘱的接方请求失败且不写药房单；
- 同一医嘱重复接方在并发下至多创建一张未取消药房单；
- 药师选择的 `material_id`、仓库、批次和数量被完整保存；自由文本药名不能直接作为物资 ID；
- `PENDING → REVIEWED → DISPENSING → DISPENSED` 只能按动作顺序流转，非法跳转失败；
- 发药确认一次性写库存 `OUTBOUND` 和药房 `stock_operation_detail_id`；重复确认不重复扣减；
- 库存不足、批次不合法、库存写入失败或药房关联写入失败时，药房和库存全部回滚；
- `CANCELLED` 单据没有库存操作，`DISPENSED` 单据不能直接取消；
- 查询返回统一列表/单条/错误响应，读取不产生库存和状态副作用；
- 历史 V300 发药记录不因 V301 被猜测补仓库或补医嘱关联。

### 7.2 页面手测

使用一位活动入住老人完成：

1. 在医生诊疗页确认一条活动 `MEDICATION` 医嘱；
2. 在药房待接方看到同一老人、入住和药名；
3. 选择库存仓库、物资和有效批次，创建待审方单；
4. 审方并开始调配；
5. 确认发药，刷新页面后看到 `DISPENSED` 和库存操作明细；
6. 再次确认同一单据，确认库存不会重复扣减；
7. 使用库存不足或已停嘱医嘱，确认操作失败且页面保留输入；
8. 切换另一位老人，确认药房队列、详情和历史单据不串入住数据。

## 8. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 医生药名是自由文本，可能与库存物资不一致 | 错发药或无法追溯 | 药师必须选择 `material_id`，保存原药名和所选物资，不做静默模糊匹配 |
| Pharmacy 与 Healthcare/Inventory 开启不同事务 | 药房单成功但库存失败，或重复扣库存 | 通过同连接端口注入 `SqlClient`，禁止端口内部重新取 Pool |
| 旧通用发药接口绕过医嘱校验 | 伪造患者、入住或药品来源 | `ELDERLY_ROUTINE` 只能走 `from-medical-order`，通用入口拒绝该类型 |
| V300 历史数据没有仓库或医嘱关联 | 迁移失败或历史被错误改写 | V301 新列可空，不回填；新旧数据读取分支明确区分 |
| 一条医嘱实际需要多种药品 | 当前一条医嘱一条明细无法表达 | 011 明确拒绝多明细；药房确认后另立计划评估 `medical_order_items` |
| 批次/拆零换算不完整 | 数量和库存成本错误 | 011 只支持 `PACKAGE`，批次管控物资必须选 `lot_id`；拆零另立计划 |
| 旧 Pharmacy 服务使用字符串 jOOQ | 列名错误或迁移后运行时失败 | 本计划触及的服务全部改用生成表；不借机重写未触及的退药/申领业务 |
| 发药单状态与护理执行混用 | 医嘱已发药但护理任务被错误完成 | 011 只改变药房和库存，护理任务/执行状态保持 008/010 语义 |
