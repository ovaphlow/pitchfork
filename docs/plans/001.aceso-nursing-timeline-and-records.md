# Aceso 长者照护时间线与日常护理记录实施计划

更新时间：2026-07-30

状态：已完成

前置计划：[Aceso 照护任务执行工作台](./aceso-nursing-execution-workbench.md) 已完成代码开发，**必须先完成其中的迁移验证、自动化测试、构建和验收场景**，再启动本计划。

## 0. 计划文档编号约定

从本文件开始，`docs/plans/` 内每一项新功能开发都必须先创建独立的开发计划文档，文件名固定为：

```text
NNN.descriptive-feature-name.md
```

- `NNN` 为三位、零填充的十进制序号，例如 `001`、`002`、`010`。
- 新建前先扫描 `docs/plans/` 的同格式文件，取最大编号加一；不存在编号文件时从 `001` 开始。
- 序号一经创建不得因文件删除、重命名或实现顺序变化而复用。
- 仅规划、实现、验证同一项功能时持续更新同一文件；出现独立可交付功能时才新建下一个编号文件。
- 历史上未编号的计划文档保留原文件名，不为本规则做批量重命名。

## 1. 目标

在既有“评估 → 计划 → 任务 → 执行”和“今日执行”工作台之上，建立长者可追溯的照护档案闭环：

1. 护理员可以为当前入住长者书写、查看并更正日常护理记录。
2. 长者详情页可以按时间顺序查看评估、计划、任务执行和护理记录，而不需要在多个 tab 间人工拼接事件。
3. 护理记录复用 `healthcare.medical_records` 的 `NURSING_RECORD` 类型，不新建重复的 nursing 记录表。
4. 每条时间线事件都可以追溯到原始领域对象；时间线只是只读聚合视图，不能成为第二份业务事实来源。
5. 既有长者入住、评估、计划、任务、今日执行和历史执行记录能力不回归。

## 2. 当前状态与边界

### 2.1 已有数据与路由

- `nursing_service_periods` 以 `patient_id` 聚合养老机构长者的长期照护周期。
- `nursing_assessments`、`nursing_plans`、`nursing_tasks` 均可关联 `period_id`，且评估、计划、任务可选关联 `encounter_id`。
- `nursing_task_executions` 记录一次任务的计划时间、实际时间、执行人、状态和备注。
- `healthcare.encounters` 表示入住/就诊过程；养老机构入住使用 `encounter_type = ELDERLY_CARE`。
- `healthcare.medical_records` 已有 `encounter_id`、`record_type`、`title`、`content`、`content_blocks`、`physician`、`record_date`、`metadata` 和审计时间字段，但当前 Healthcare API 尚未提供病历文书的读写接口。
- Aceso 已将 `/crate-api/healthcare/v1/*` 和 `/crate-api/nursing/v1/*` 分别挂载至 Healthcare 与 Nursing 路由；前端实际入口仍为 `apps/aceso/src/pages/dashboard/inpatient.astro` 挂载的 `NursingPage.tsx`。

### 2.2 模块所有权

| 事实 | 所有者 | 本期职责 |
|---|---|---|
| 入住、长者、医疗文书 | `healthcare` | 校验入住归属，保存和查询 `NURSING_RECORD` |
| 服务周期、评估、计划、任务、执行 | `nursing` | 返回原始对象；聚合只读时间线 |
| 页面状态、展示和表单 | Aceso UI | 通过 `@pitchfork/shared/aceso` 调用 API，不直接 `fetch` |

Nursing 模块不得直接写入 `healthcare.medical_records`。记录写入、修正关联和记录查询由 Healthcare 服务负责；Nursing 的时间线只能读取 Healthcare 已公开的查询能力。若需要代码级依赖，使用 Healthcare 暴露的服务接口或仓库接口，不得在 Nursing 服务中手写跨 schema 的写入 SQL。

### 2.3 本期不做

- 不实现护理质量评分、护理员工作量、计划完成率或仪表盘图表。
- 不实现库存出库和耗材实际扣减。
- 不实现家庭护理上门排班、签到、轨迹或服务时长。
- 不创建独立的“护理记录管理”路由页面，也不使用仍为占位页的 `dashboard/nursing.astro`。
- 不把任务完成时的 `note` 自动复制成正式护理记录；正式记录必须由护理员确认提交。
- 不删除既有医疗文书，不改写既有任务执行历史，也不对旧数据做批量补写。
- 不引入全文检索、附件上传、富文本编辑器、电子签名或完整病历版本系统；这些需求另立编号计划。

## 3. 领域决策

### 3.1 日常护理记录的存储模型

第一版将一条日常护理记录保存为一条：

```text
healthcare.medical_records
  record_type = "NURSING_RECORD"
```

必填/受控字段如下：

| 字段 | 写入规则 |
|---|---|
| `encounter_id` | 必填；必须属于传入 `period_id` 对应的同一长者 |
| `record_type` | 服务端固定为 `NURSING_RECORD`，客户端不可改写 |
| `title` | 必填，最多 100 字；默认建议为“日常护理记录” |
| `content` | 必填，去首尾空白后不得为空；第一版使用纯文本 |
| `physician` | 从已认证的当前主体取得；不得信任客户端任意指定的人员 ID |
| `record_date` | 必填或由服务端业务当前日期补齐；不得晚于业务当前日期 |
| `metadata.period_id` | 必填，用于回到护理服务周期 |
| `metadata.task_execution_id` | 可选；从任务执行快捷书写时填写 |
| `metadata.task_id` | 可选；仅在有 `task_execution_id` 时由服务端解析后写入 |
| `metadata.record_time` | 必填 ISO 8601 `OffsetDateTime`；保存实际观察/记录时间，不能仅依赖 `record_date` |
| `metadata.record_kind` | `MANUAL`、`EXECUTION` 或 `CORRECTION`；服务端限定枚举 |
| `metadata.corrects_record_id` | 仅更正记录可填；引用被更正的同一长者、同一入住、同一周期的护理记录 |

`content_blocks` 第一版保持空数组。记录展示用 `metadata.record_time` 排序，缺失旧数据才回退到 `record_date` 与 `created_at`。

### 3.2 不可删除与更正规则

- 已提交的 `NURSING_RECORD` 不提供删除接口，也不提供原地修改内容的 `PUT` 接口。
- 护理员发现错误时创建一条 `record_kind = CORRECTION` 的新记录，填写更正说明并使用 `corrects_record_id` 指向原记录。
- 原记录仍保留且显示“已更正”；更正记录显示其关联的原记录。该规则保证档案可追溯，避免静默篡改临床/照护事实。
- 从任务执行快捷创建时，单条执行记录至多拥有一条 `record_kind = EXECUTION` 的原始护理记录；若已存在，界面打开详情或更正入口，不重复创建。
- 未关联任务执行的手工观察可在同日创建多条记录。

### 3.3 时间线事件模型

时间线不增加持久化表。后端在每次查询时从各领域对象读取并标准化为以下响应对象：

```json
{
  "id": "execution:01...",
  "occurred_at": "2026-07-30T09:12:00+08:00",
  "event_type": "TASK_EXECUTION",
  "title": "协助晨间洗漱",
  "summary": "已完成 · 长者配合良好",
  "actor": "01...",
  "status": "COMPLETED",
  "period_id": "01...",
  "encounter_id": "01...",
  "patient_id": "01...",
  "source": {
    "resource": "nursing_task_execution",
    "id": "01..."
  },
  "metadata": {}
}
```

`event_type` 第一版固定为：

| 值 | 事件源 | `occurred_at` 优先级 |
|---|---|---|
| `ASSESSMENT` | `nursing_assessments` | `assess_date`，再以 `created_at` 补足时间 |
| `CARE_PLAN` | `nursing_plans` | `created_at` |
| `TASK` | `nursing_tasks` | `created_at`；只展示创建事件，不把每次查询虚构为状态事件 |
| `TASK_EXECUTION` | `nursing_task_executions` | `actual_time`，否则 `planned_time`，再否则 `created_at` |
| `NURSING_RECORD` | `healthcare.medical_records` | `metadata.record_time`，否则 `record_date`，再否则 `created_at` |

API 返回稳定英文代码；前端统一显示中文标签“护理评估、照护计划、照护任务、任务执行、护理记录”。每个事件必须包含稳定的 `source.resource` 和 `source.id`，供后续详情跳转、审计和测试使用。

### 3.4 查询范围和排序

- 时间线查询必须同时传递 `period_id` 与 `encounter_id`。服务端先验证两者存在、`period.patient_id = encounter.patient_id`，不一致返回 `400`。
- 数据范围为：该 `period_id` 下的护理评估、计划、任务和任务执行，以及该 `encounter_id` 下 `record_type = NURSING_RECORD` 的医疗文书；记录的 `metadata.period_id` 必须等于请求周期。
- 默认按 `occurred_at DESC` 排序；用户可选择日期范围和事件类型；列表使用 `limit`/`offset`，响应仍是 `{ "records": [], "meta": { "total": 0 } }`。
- 为避免错误的分页总数，后端必须在合并、过滤、排序后的事件集合上计算 `total`，再切片返回当前页。第一版限定单个长者/周期查询，最大 `limit` 为 100。
- 只有读操作可以跨模块聚合。查询实现使用批量读取，禁止按每条时间线事件继续请求执行、任务或长者详情而产生 N+1。

## 4. API 设计

### 4.1 Healthcare：护理记录

在既有 `/crate-api/healthcare/v1` 资源下新增护理记录专用端点。不得先借用“通用病历编辑器”接口，因为本期只授权 `NURSING_RECORD` 的受控写入。

#### 创建记录

```http
POST /crate-api/healthcare/v1/nursing-records
Content-Type: application/json

{
  "period_id": "01...",
  "encounter_id": "01...",
  "title": "午间饮食与情绪观察",
  "content": "午餐进食约八成，精神状态平稳。",
  "record_time": "2026-07-30T12:35:00+08:00",
  "task_execution_id": "01..."
}
```

规则：

- `period_id`、`encounter_id`、`title`、`content` 必填；`record_time` 缺省时由服务端写入当前业务时间。
- `record_time` 不得在未来；其日期应与 `record_date` 一致，服务端从 `record_time` 派生 `record_date`，避免前端传入相互矛盾的日期。
- `task_execution_id` 可选；存在时验证执行记录、任务和周期归属一致。服务端从执行记录推导 `task_id`，不接受客户端传入。
- 服务端固定 `record_type = NURSING_RECORD` 与 `record_kind = MANUAL/EXECUTION`，并记录认证主体为 `physician`。
- 若同一执行记录已有原始 `EXECUTION` 护理记录，返回 `409`，响应 `{ "error": "nursing record already exists for task execution" }`。
- 成功返回 `201` 和单条记录对象；参数错误 `400`、来源不存在 `404`、归属不一致或重复 `409`，错误均使用 `{ "error": "<message>" }`。

#### 查询记录

```http
GET /crate-api/healthcare/v1/nursing-records?period_id=...&encounter_id=...&date_from=2026-07-01&date_to=2026-07-31&limit=50&offset=0
```

返回统一分页结构。记录字段至少包含：

```json
{
  "id": "01...",
  "encounter_id": "01...",
  "period_id": "01...",
  "record_type": "NURSING_RECORD",
  "record_kind": "MANUAL",
  "title": "午间饮食与情绪观察",
  "content": "午餐进食约八成，精神状态平稳。",
  "record_time": "2026-07-30T12:35:00+08:00",
  "record_date": "2026-07-30",
  "author": "01...",
  "task_execution_id": null,
  "task_id": null,
  "corrects_record_id": null,
  "created_at": "2026-07-30T12:36:00+08:00",
  "updated_at": "2026-07-30T12:36:00+08:00"
}
```

服务端只能返回当前周期的记录，不能因同一 `encounter_id` 存在其他护理周期而泄漏其记录。

#### 创建更正记录

```http
POST /crate-api/healthcare/v1/nursing-records/:id/corrections
Content-Type: application/json

{
  "content": "更正：午餐实际进食约六成，原记录八成为笔误。",
  "record_time": "2026-07-30T13:00:00+08:00"
}
```

- 原记录必须是 `NURSING_RECORD`；更正记录继承其 `period_id`、`encounter_id` 和任务关联。
- 标题由服务端生成为“更正：{原标题}”，`record_kind = CORRECTION`，并写入 `corrects_record_id`。
- 响应 `201`；原记录查询字段增加 `is_corrected` 和 `correction_count`，或在详情中返回对应更正摘要。

### 4.2 Nursing：长者照护时间线

```http
GET /crate-api/nursing/v1/timeline?period_id=...&encounter_id=...&date_from=2026-07-01&date_to=2026-07-31&event_type=NURSING_RECORD&limit=50&offset=0
```

参数：

| 参数 | 规则 |
|---|---|
| `period_id` | 必填，护理服务周期 ID |
| `encounter_id` | 必填，当前养老入住记录 ID |
| `date_from` / `date_to` | 可选 `YYYY-MM-DD`；缺省返回全部历史；`date_from` 不得晚于 `date_to` |
| `event_type` | 可选，可重复或逗号分隔；仅接受第 3.3 节定义的稳定代码 |
| `limit` / `offset` | 遵循统一分页约定；`limit` 为 1–100，`offset` 不小于 0 |

实现要求：

- 先查询并校验周期和入住记录归属，再并行读取各来源。
- 所有可读来源字段统一为 `NursingTimelineEvent`，再进行日期和类型过滤、排序、分页。
- 评估、计划和任务的详情不得通过时间线接口重复嵌套返回；只带显示所需摘要。查看详情继续走其既有 API。
- 时间线不得触发任务实例生成、状态更新、记录写入或任何副作用。
- 返回格式固定为 `{ "records": [...], "meta": { "total": N } }`；没有记录时返回空数组和 `total: 0`。

## 5. 数据库与迁移

### 5.1 不新增护理记录表

护理记录使用既有 `healthcare.medical_records`，因此不创建 `nursing_records` 表，也不改变 `nursing_task_executions` 的既有 `note` 语义。执行备注仍是执行事实的简要说明；护理记录是护理员明确提交的正式照护档案。

### 5.2 Healthcare 迁移

在 `libs/healthcare/src/main/resources/db/migration/` 新增下一个 healthcare 号段迁移：

```text
V501__add_nursing_record_indexes.sql
```

迁移内容：

1. 增加部分唯一索引，保证 `record_type = 'NURSING_RECORD'` 且 `metadata.record_kind = 'EXECUTION'` 时，同一 `metadata.task_execution_id` 只有一条原始记录。索引仅覆盖 `task_execution_id` 非空的行，允许没有任务来源的手工记录。
2. 增加复合查询索引，以 `record_type`、`encounter_id`、`record_date DESC` 支持按入住记录和日期范围读取护理记录。
3. 不修改、不删除既有 `medical_records`；迁移应使用 `IF NOT EXISTS`，并在上线前检查历史 JSONB 数据是否会与新唯一约束冲突。

不要为时间线的理论未来筛选提前创建大量 JSONB 索引。若 `period_id` 的实际查询计划显示现有索引不足，再基于真实 SQL 增加精确表达式索引，并附带 `EXPLAIN` 依据。

### 5.3 jOOQ 与依赖

- 迁移影响 Healthcare 表结构或索引后，按仓库流程运行 Healthcare jOOQ codegen 并只提交确有变化的生成文件。
- Nursing 时间线若需要调用 Healthcare 的公开查询服务，在 `libs/nursing/build.gradle.kts` 增加对 `:libs:healthcare` 的单向依赖；Healthcare 不得反向依赖 Nursing，避免循环依赖。
- 不修改全局 Flyway 行为来迁就本计划的迁移顺序。若现有数据库已执行更高版本迁移，先按仓库迁移策略确认可安全应用 V501，再实施。

## 6. 后端实现设计

### 6.1 Healthcare 护理记录服务

在 `HealthcareService` 中拆出清晰的护理记录方法，例如：

```text
createNursingRecord(body, authenticatedSubject)
listNursingRecords(periodId, encounterId, dateFrom, dateTo, limit, offset)
createNursingRecordCorrection(recordId, body, authenticatedSubject)
getNursingRecord(recordId)
```

实现步骤：

1. 解析并验证请求体、日期与认证主体。
2. 查询护理周期与入住记录，验证两者均存在且长者相同；不允许客户端用任意 `encounter_id` 为其他长者写记录。
3. 有任务执行来源时，查询执行记录及其任务，验证任务周期、任务入住记录（若已设置）与请求归属一致。
4. 构造受控 `metadata`，只写入计划内键；不得把未经校验的客户端 JSON 直接存入元数据。
5. 使用 ULID 创建记录，并在冲突时将唯一索引错误映射为 `409`。
6. 查询、序列化并返回 snake_case 字段；日期、时间统一使用项目的 `OffsetDateTime` 约定。
7. 更正记录只能从原护理记录派生，继承来源归属，禁止客户端替换 `period_id`、`encounter_id` 或原始任务关联。

在 `HealthcareRoutes` 注册上述端点，并复用现有 `BodyHandler`、参数范围限制、分页格式和错误响应习惯。路由静态段必须先于 `/:id` 类动态路由注册。

### 6.2 Nursing 时间线服务

新增 `NursingTimelineService`（或等价的独立只读查询服务），避免将合并逻辑塞入现有 `TaskExecutionService`。建议职责：

```text
validateTimelineScope(periodId, encounterId)
listTimeline(periodId, encounterId, filters, limit, offset)
mapAssessmentEvent(...)
mapPlanEvent(...)
mapTaskEvent(...)
mapExecutionEvent(...)
mapNursingRecordEvent(...)
```

实现步骤：

1. 以 `period_id` 查询护理周期，以 `encounter_id` 查询 Healthcare 入住，验证 `patient_id` 一致。
2. 批量读取该周期的护理评估、计划、任务及执行记录；执行记录查询通过任务集合完成，不对每条记录再发 SQL。
3. 调用 Healthcare 的护理记录查询能力，限定同一周期与入住。
4. 将每种来源映射到第 3.3 节的稳定事件模型，安全处理可空时间字段。
5. 在同一内存集合中完成过滤、降序排序、总数统计和分页；单次最多处理一个周期，限制数据量并记录耗时日志。
6. 所有来源异常必须返回可诊断错误；不得吞掉医疗记录查询失败后伪装成“暂无记录”。

在 `NursingRoutes` 下新增 `/timeline`，静态路由必须在任何 `/:id` 路由前注册。保持既有评估、计划、任务和执行 API 不变。

### 6.3 认证、授权和审计

- 记录作者从当前认证主体取得，不使用前端可编辑的 `author`、`physician` 或 `executor` 字段作为事实来源。
- 复用 Aceso 现有权限/主体获取机制；若当前路由层尚未暴露主体，先补齐统一的 request context，再编写记录写入功能，不要在组件里伪造用户 ID。
- 至少执行“可查看该长者护理档案”和“可创建护理记录”的既有权限检查；无权限返回 `403`。
- 日志中记录记录 ID、周期 ID、入住 ID、来源执行 ID 与操作者 ID，不记录 `content` 正文或其他敏感照护描述。

## 7. 前端实施设计

### 7.1 页面位置和信息架构

继续在 `ui-astro/apps/aceso/src/components/NursingPage.tsx` 实现，不创建重复护理页面。顶层仍保留：

```text
照护管理
├── 今日执行
└── 长者照护档案
    ├── 概览
    ├── 照护时间线       ← 本期新增
    ├── 护理评估
    ├── 照护计划
    └── 任务执行
```

“照护时间线”必须先选择长者、活动入住记录和护理服务周期后加载。未选择时明确提示用户先到长者档案选择入住长者；不能因缺少上下文向 API 发送空 ID。

### 7.2 时间线界面

至少提供：

- 默认显示最近 30 天，支持开始/结束日期；日期变化后保留长者和周期上下文。
- 事件类型多选筛选：全部、护理评估、照护计划、照护任务、任务执行、护理记录。
- 按事件时间倒序的竖向时间线；每项显示时间、中文类型 Badge、标题、摘要、记录人/执行人和状态。
- 任务执行事件显示完成、跳过、取消及备注摘要；护理记录显示正文摘要、更正状态和来源任务。
- “查看原始记录/详情”操作，复用已有详情数据或显示只读弹窗；不重复维护第二套编辑状态。
- 分页加载、加载中、空状态、错误状态和重新加载按钮。
- 移动宽度下保持单列可读，筛选区域折行，长正文截断并可展开；不把时间线塞进需要横向滚动的表格。

### 7.3 护理记录交互

在“照护时间线”顶部提供“新增护理记录”；在可完成或已完成的任务执行详情提供“写护理记录”快捷入口。

表单字段：

| 字段 | 规则 |
|---|---|
| 标题 | 必填，默认“日常护理记录” |
| 观察/记录时间 | 必填，默认当前业务时间，不得晚于现在 |
| 正文 | 必填，显示字符计数与空白校验 |
| 关联执行 | 快捷入口预填并只读；手工入口可不关联 |

交互规则：

- 表单提交时禁用重复提交；成功后关闭弹窗并仅刷新当前周期的时间线和护理记录，不重置当前长者、筛选或顶层视图。
- 快捷入口若已有来源执行的护理记录，显示已有记录并禁止再次创建原始记录。
- 原记录详情提供“更正记录”入口；更正弹窗仅收集更正正文和时间，归属由服务端继承。
- 前端不显示可编辑作者字段；作者由服务端当前认证主体写入。
- 网络失败时保留已输入正文和时间，并展示接口返回的错误消息。

### 7.4 Shared API 类型

在 `ui-astro/packages/shared/src/aceso.ts` 中增加明确的 snake_case 类型与请求函数：

```text

NursingRecordCorrectionInput
NursingTimelineEvent
NursingTimelineEventType
createNursingRecord(...)
listNursingRecords(...)
createNursingRecordCorrection(...)

```

- 复用既有 `request`、`nursingQuery`、认证注入和分页类型；组件内不得重新实现 `fetch`、Token 和 401 处理。
- 所有日期参数显式使用 `YYYY-MM-DD`，所有时间字段使用 ISO 8601 字符串。
- 以字典函数集中映射事件类型、状态和记录种类为中文展示，避免组件内散落字符串判断。

## 8. 测试与验证计划

### 8.1 Healthcare 后端测试

至少覆盖：

1. 创建合法 `NURSING_RECORD`，服务端写入固定类型、当前主体、周期元数据和正确的 `record_date`。
2. 周期与入住属于不同长者时拒绝写入，不产生记录。
3. `record_time` 在未来、正文为空、日期格式非法时返回 `400`。
4. 关联不存在的周期、入住或任务执行时返回 `404`。
5. 关联的任务执行不属于指定周期或入住时返回 `409`。
6. 同一 `task_execution_id` 创建第二条原始执行护理记录时返回 `409`，并由数据库唯一索引兜底。
7. 手工记录可同日多条；不同执行记录可各有一条原始记录。
8. 更正记录继承归属并关联原记录；不能更正非 `NURSING_RECORD`。
9. 查询按周期、入住、日期范围分页，且不会返回同一入住下其他周期的记录。
10. 权限不足时返回 `403`；日志不包含记录正文。

### 8.2 Nursing 时间线后端测试

至少覆盖：

1. 同一周期同时含评估、计划、任务、执行和护理记录时，返回所有对应事件。
2. 事件按统一 `occurred_at DESC` 排序，执行记录时间的回退顺序正确。
3. 指定 `event_type` 和日期范围只返回匹配事件。
4. `period_id`、`encounter_id` 缺失、格式非法或长者不一致时返回 `400`/`404`。
5. 合并后的 `meta.total` 是过滤后的完整总数，分页不会漏项或重复项。
6. 空时间线返回 `{ records: [], meta: { total: 0 } }`。
7. Healthcare 护理记录读取失败时返回可诊断错误，不能静默省略记录。
8. 对多个执行记录采用批量查询，测试或日志断言不存在 N+1 查询模式。

### 8.3 前端验证

至少验证：

1. 选择长者和周期后，默认加载近 30 天时间线。
2. 切换日期、事件类型与分页参数会请求正确 API，且保留筛选条件。
3. 护理记录能从手工入口和任务执行快捷入口创建，成功后显示在时间线。
4. 空正文、未来记录时间、重复快捷记录、接口失败均有明确反馈且不丢失输入。
5. 更正记录显示关联关系，原记录不可原地编辑或删除。
6. 既有今日执行、评估、计划、任务和执行历史功能不回归。
7. Aceso 响应式布局在移动宽度可读取时间线和弹窗表单。

## 9. 验收场景

### 场景 A：从长者档案查看时间线

给一位活动入住长者准备一份评估、一个计划、一个任务、一个已完成执行记录和一条护理记录：

- 选择该长者、活动入住和护理周期后，可在同一时间线看到五种事件；
- 事件按发生时间倒序，显示正确中文标签、摘要和来源；
- 仅筛选“护理记录”时不显示其他事件；
- 刷新页面后结果一致，不产生任何新执行记录或数据变化。

### 场景 B：手工创建日常护理记录

- 在时间线点击“新增护理记录”，填写标题、观察时间和正文后创建成功；
- 记录关联当前长者、入住和周期，显示当前登录主体为记录人；
- 护理记录立刻位于正确时间位置，重新加载后仍存在；
- 尝试选择未来时间或提交空正文会被拒绝，输入内容不丢失。

### 场景 C：由任务执行补充护理记录

- 从已完成任务执行打开“写护理记录”，任务来源在表单中明确显示；
- 提交后时间线同时保留“任务执行”和“护理记录”两项，且均能追溯到自己的原始对象；
- 再次从同一执行进入，系统显示已存在记录，不能生成重复原始记录；
- 执行本身的 `note` 未被覆盖或修改。

### 场景 D：更正与数据隔离

- 对一条护理记录创建更正后，原记录正文仍可查看并标注已更正；
- 更正记录指向原记录且继承同一长者、入住和周期；
- 不同长者或同一长者的其他周期记录不能通过查询参数、快捷入口或更正接口被读写；
- 不存在删除和原地覆盖已提交护理记录的入口。
