# Aceso 照护任务执行工作台实施计划

更新时间：2026-07-30

状态：已完成

## 1. 目标

将 Aceso 当前已经能够创建照护周期、评估、照护计划、照护任务和一条完成记录的演示流程，推进为养老机构可以持续使用的“今日待办 → 执行 → 完成/跳过/异常”工作流。

本计划交给实现 agent 执行。实现完成后，护理员应当能够打开照护管理，看到今天所有长者的待执行任务，而不是必须先进入某一位长者再手动创建一条执行记录。

## 2. 当前状态

护理模块的业务主干已经确定为“评估 → 计划 → 任务 → 执行”，见 `service-vertx-kotlin/libs/nursing/设计说明.md`。当前代码已有以下能力：

- Aceso 后端挂载 `periods`、`assessments`、`plans`、`tasks`、`executions` 和 `visit-schedules` 路由。
- Aceso 前端的照护管理实际使用 `ui-astro/apps/aceso/src/pages/dashboard/inpatient.astro` 和 `NursingPage.tsx`；`dashboard/nursing.astro` 仍是占位页面，不要把本计划实现到该占位路由。
- `NursingPage.tsx` 可以读取某一位长者的任务执行记录。
- “登记任务完成”会创建一条执行记录，然后依次将其状态变为 `IN_PROGRESS` 和 `COMPLETED`。
- `nursing_tasks` 已有 `frequency_code`、`frequency_name`、`start_date`、`end_date`，`nursing_task_executions` 已有 `planned_time`、`actual_time`、`executor`、`status`、`note`。
- 目前频次只是任务属性，没有按照频次生成每一天或每一班的执行记录；页面也没有跨长者的今日待办视图。
- 当前执行状态流转为：`PENDING → IN_PROGRESS → COMPLETED`，`PENDING` 可转为 `SKIPPED` 或 `CANCELLED`，终态不可再次流转。

## 3. 本次范围

### 3.1 必须实现

1. 后端能够按照任务日期范围和频次，为指定日期生成幂等的执行记录。
2. 提供今日执行任务查询，返回执行记录及其对应的任务和长者摘要，前端不再对每个任务逐个发起执行记录查询。
3. 前端增加“今日执行”工作台，展示所有活动入住长者的任务，而不局限于当前选中的长者。
4. 支持从工作台执行“开始执行”“完成”“跳过”“取消”。
5. 支持执行备注和跳过/取消原因。
6. 重复刷新、重复点击生成或重复调用接口都不能生成重复的同一任务同一计划时间记录。
7. 保留当前已有的长者详情、评估、计划、任务和历史执行记录能力。

### 3.2 不在本次范围

- 不实现家庭护理的上门排班页面；`nursing_visit_schedules` 继续作为后续家庭照护功能使用。
- 不实现护理员移动端独立应用；本次先完成 Aceso 管理端的响应式工作台。
- 不实现药品、生活用品或耗材的真实库存出库联动；本次保留执行记录已有的耗材字段。
- 不实现护理质量统计、工作量报表和仪表盘图表。
- 不重做入住管理、长者档案、评估表单或照护计划表单。
- 不删除或迁移 `dashboard/nursing.astro` 占位路由，除非实现 agent 发现路由冲突并有明确理由。
- 不改变既有 API 的分页响应格式：列表仍返回 `{ records: [...], meta: { total: N } }`。

## 4. 产品规则

### 4.1 任务和执行记录的关系

- `nursing_tasks` 表示长期或临时的照护任务定义。
- `nursing_task_executions` 表示某个任务在某个计划时间的一次执行实例。
- 一个周期性任务可以拥有多条执行记录。
- 完成一条执行记录，不自动把周期性任务置为 `COMPLETED`；任务仍保持 `ACTIVE`，直到任务结束日期、计划终止或人工终止。
- 一次性任务可以在完成唯一执行记录后由现有任务状态操作置为 `COMPLETED`，但不要用“一条执行完成”作为所有任务自动完成的通用规则。
- 已存在的手工登记完成记录必须继续显示在历史中，不得被自动生成逻辑覆盖或重复生成。

### 4.2 任务是否应该生成执行记录

只有同时满足以下条件的任务才参与自动生成：

- `status = ACTIVE`；
- 所属照护周期仍为 `ACTIVE`；
- `start_date` 为空，或任务开始日期不晚于目标日期；
- `end_date` 为空，或任务结束日期不早于目标日期；
- 任务频次可识别且不是纯手工频次。

`PRN`（按需）不自动生成固定时间实例，由护理员在实际需要时手动创建；`STAT`（立即/临时）只允许由任务创建或人工操作产生，不进行跨日自动生成。

### 4.3 第一版频次支持

第一版至少支持当前前端已有的频次编码：

| 编码 | 规则 |
|---|---|
| `QD` | 每日一条 |
| `BID` | 每日两条 |
| `TID` | 每日三条 |
| `QID` | 每日四条 |
| `QOD` | 隔日一条，以任务 `start_date` 为第一天 |
| `QW` | 每周一条，以任务 `start_date` 所在星期为执行日 |
| `BIW` | 每周两条，以任务开始周的星期为基准 |
| `TIW` | 每周三条，以任务开始周的星期为基准 |

`Q2H`、其他小时级频次、复杂节假日规则和自定义排班不属于第一版。不要用模糊的字符串匹配猜测未知频次；未知编码应被标记为不可自动生成，并通过日志或接口错误返回可诊断信息。

### 4.4 计划时间

现有任务只有日期，没有明确的日内执行时段。第一版应采用简单、可解释的默认时段，并为后续扩展保留空间：

- 将日内时间存入任务 `metadata.schedule_times`，格式为 ISO `HH:mm` 字符串数组。
- 创建任务时如果没有指定时段，使用频次对应的默认时间：
  - `QD`: `09:00`
  - `BID`: `09:00`, `18:00`
  - `TID`: `08:00`, `12:00`, `18:00`
  - `QID`: `08:00`, `12:00`, `18:00`, `22:00`
  - `QOD`、`QW`、`BIW`、`TIW`: `09:00`
- 对于已有任务，如果 `metadata.schedule_times` 不存在，使用以上默认值，不要求数据迁移补写旧任务。
- `planned_time` 必须使用项目现有的 `OffsetDateTime` 约定；日期查询使用明确的业务时区，不要在前端和后端各自用不同的本地时区计算日期。
- 如果实现 agent 认为直接新增正式时段字段优于使用 `metadata`，必须说明原因并补充 Flyway 迁移、jOOQ 生成/依赖流程及兼容旧数据；默认优先使用已有 `metadata`，避免无必要的表结构扩展。

## 5. 后端实施方案

### 5.1 执行实例生成服务

在 `TaskExecutionService` 中增加一个可重复调用的生成能力，建议拆出明确的方法，不要把复杂频次逻辑全部塞进现有 `list` 方法。

建议职责：

1. 查询目标日期范围内可执行的活动任务。
2. 根据任务频次和 `metadata.schedule_times` 计算计划时间。
3. 为每个计划时间创建 `PENDING` 执行记录。
4. 对已存在相同 `task_id + planned_time` 的执行记录跳过插入。
5. 返回生成数量、跳过数量和无法生成的任务信息，便于日志和测试诊断。

建议提供内部服务方法：

```text
ensureExecutionsForDate(date, periodId?, executor?)
ensureExecutionsForDateRange(dateFrom, dateTo, periodId?)
```

第一版不要求后台定时任务。访问今日工作台时先执行当天的幂等补全，再查询当天记录，既能支持新建任务，也能支持服务重启后补齐数据。

### 5.2 数据一致性

为避免并发请求重复插入，不能只依赖“先查询、再插入”的应用层判断。实现 agent 应选择以下方案之一，并优先使用数据库约束保障：

- 在 `nursing_task_executions` 上增加 `(task_id, planned_time)` 的唯一索引，并使用 PostgreSQL `ON CONFLICT DO NOTHING`；或
- 使用等价的数据库级幂等写入方案，并在计划文档的实现记录中说明其并发安全性。

如果增加唯一索引，新增 nursing 模块迁移应使用下一个可用版本号，并遵循仓库的 per-lib Flyway 约定。执行前先检查现有数据是否存在相同任务和计划时间的重复记录。

### 5.3 API

在现有 `/crate-api/nursing/v1/executions` 资源上扩展，保持现有资源风格。

#### 今日待办

建议增加：

```http
GET /crate-api/nursing/v1/executions/today?date=2026-07-30&period_id=&executor=&status=&limit=50&offset=0
```

约定：

- `date` 可选，缺省为业务当前日期；测试必须能够传入固定日期。
- 访问接口时执行该日期的幂等生成，然后查询当天 `planned_time` 落在该日期的记录。
- `period_id`、`executor`、`status` 可选过滤。
- 默认返回 `PENDING`、`IN_PROGRESS`、`COMPLETED`、`SKIPPED`、`CANCELLED` 全部状态，前端再按看板分组；如果实现 agent 选择默认只返回未完成状态，必须保留查看已完成记录的参数。
- 返回执行记录字段，并附带最小任务和长者摘要，至少包括：`task_id`、`description`、`task_type`、`frequency_name`、`period_id`、`patient_id`、`patient_name`、`planned_time`、`actual_time`、`executor`、`status`、`note`。
- 返回格式仍为 `{ records, meta }`。
- 查询应使用后端 JOIN 或批量查询，禁止让前端对每一条执行记录逐个请求任务和患者详情。

#### 批量补全

可以增加内部或管理端使用的：

```http
POST /crate-api/nursing/v1/executions/generate
```

请求体：

```json
{
  "date_from": "2026-07-30",
  "date_to": "2026-08-05",
  "period_id": "可选"
}
```

如果实现 agent 认为公开该接口没有必要，也可以只保留服务内部方法和 `today` 接口中的懒生成，但必须覆盖日期范围回补的测试方式。

#### 状态和备注

继续使用：

```http
PATCH /crate-api/nursing/v1/executions/:id/status
```

请求体至少支持：

```json
{
  "status": "COMPLETED",
  "note": "长者配合良好"
}
```

要求：

- 保留现有合法状态流转校验。
- `IN_PROGRESS` 自动写入 `actual_time`，没有传入时使用服务端当前时间。
- `COMPLETED` 自动写入 `actual_time`，没有传入时使用服务端当前时间。
- `SKIPPED` 和 `CANCELLED` 支持保存原因，前端应要求填写原因；后端至少保存 `note`，不应丢弃该信息。
- 终态不能重复转换。
- 404、400 和内部错误遵循仓库现有错误响应格式。

### 5.4 查询性能

今日工作台的查询会成为高频路径，至少检查以下条件：

- `planned_time` 日期范围过滤是否能使用索引；
- `task_id` 查询是否保留现有索引；
- `status`、`executor`、`period_id` 的组合过滤是否造成全表扫描；
- JOIN 长者信息是否重复执行 N+1 查询。

只有在实际查询需要时才新增索引，并为新增索引提供 migration。不要为了计划中的统计功能提前加入大量索引。

## 6. 前端实施方案

### 6.1 页面位置

在现有 `NursingPage.tsx` 中增加“今日执行”视图或顶层 tab，继续由 `apps/aceso/src/pages/dashboard/inpatient.astro` 挂载。不要新建重复的护理管理页面，也不要把主要实现放进当前 `dashboard/nursing.astro` 占位页。

建议顶层结构：

```text
照护管理
├── 今日执行
├── 长者照护档案
│   ├── 评估
│   ├── 计划
│   ├── 任务
│   └── 执行历史
```

如果不适合增加嵌套 tab，也可以将“今日执行”作为现有页面顶部的独立 Card，但必须能够在不选择具体长者的情况下查看全部待办。

### 6.2 今日执行工作台

页面至少包含：

- 日期选择器，默认今天；
- 状态统计：待执行、执行中、已完成、已跳过、已取消、逾期；
- 执行人筛选；
- 任务类型筛选；
- 长者姓名/房间或照护单元搜索（如果现有入住接口有对应字段）；
- 任务列表，按计划时间升序；
- 当前用户的任务快捷筛选；
- 刷新按钮和加载状态；
- 空状态和接口错误状态。

列表列建议：

| 列 | 内容 |
|---|---|
| 计划时间 | `planned_time`，显示为本地日期时间 |
| 长者 | `patient_name`，无法解析时显示 `patient_id` |
| 任务 | 任务描述 |
| 类型 | 生活照料、护理操作、康复训练、健康教育等 |
| 执行人 | 显示姓名，无法解析时显示主体 ID |
| 状态 | 中文状态 Badge |
| 备注 | 已完成或异常的摘要 |
| 操作 | 开始、完成、跳过、取消、查看详情 |

### 6.3 操作规则

- `PENDING` 显示“开始执行”“跳过”“取消”。
- `IN_PROGRESS` 显示“完成”“取消”。
- `COMPLETED`、`SKIPPED`、`CANCELLED` 只显示查看详情。
- 完成操作可填写执行备注；跳过和取消必须填写原因。
- 默认执行人使用当前登录主体；如现有业务允许代执行，保留执行人选择，但不要默认选中无关主体。
- 操作成功后只刷新当前日期的工作台数据，不要重置当前长者、tab 或筛选条件。
- 对同一行操作时禁用重复提交，并在失败后保留用户输入的备注。

### 6.4 现有长者详情兼容

保留现有详情页能力：

- 长者选择和入住记录查询；
- 评估列表和新增评估；
- 照护计划及计划措施；
- 照护任务；
- 该长者的执行历史。

将当前每个任务独立调用 `listNursingTaskExecutions` 的方式改为优先复用已加载数据；如果详情仍需要历史分页，可以保留按任务查询，但今日工作台必须使用批量接口。

### 6.5 Shared API 类型

在 `ui-astro/packages/shared/src/aceso.ts` 中：

- 为今日执行返回值增加明确的 TypeScript 类型；
- 类型字段使用现有 snake_case API 命名；
- 新增 `listNursingTodayExecutions` 或等价方法；
- 新增状态更新时的请求类型，允许 `status` 和可选 `note`；
- 复用已有 `request`、分页类型和认证处理，不在组件内重新实现 fetch、token 或 401 处理。

## 7. 测试计划

### 7.1 后端单元或服务测试

至少覆盖：

1. `QD` 在目标日期产生一条记录。
2. `BID`、`TID`、`QID` 产生正确数量和计划时间。
3. `QOD` 只在隔日产生记录。
4. 周频任务只在对应星期产生记录。
5. 任务开始日期之前和结束日期之后不产生记录。
6. `COMPLETED`、`CANCELLED` 任务不产生新记录。
7. `PRN`、`STAT` 不被自动生成逻辑处理。
8. 相同任务和相同计划时间重复生成不会增加记录。
9. 并发生成不会产生重复记录，若使用唯一索引则验证冲突处理。
10. 已经手工创建的 `planned_time` 记录不会被覆盖。
11. 状态流转合法性和非法流转。
12. 跳过、取消可以保存原因。
13. 今日查询按日期、状态、执行人和周期过滤正确。
14. 返回分页格式正确，并且任务/长者摘要不会导致 N+1 查询。

如果当前 nursing 模块没有现成测试基础设施，先检查相邻模块的测试模式；不要为了本功能引入一套与仓库不一致的测试框架。至少应通过编译、API 层测试或可重复的服务测试验证核心生成逻辑。

### 7.2 前端验证

至少验证：

- 今日工作台默认加载当前日期；
- 切换日期会请求对应日期；
- 状态筛选和执行人筛选会保留；
- 空数据、加载中、接口错误均有明确展示；
- 开始、完成、跳过、取消对应正确状态和按钮；
- 跳过/取消不填写原因时不能提交；
- 重复点击不会产生重复请求或重复提示；
- 既有长者详情的评估、计划、任务功能不回归；
- 移动宽度下列表仍可横向查看或合理折叠；
- 不引入对 `dashboard/nursing.astro` 的错误依赖。

## 8. 验收场景

使用至少一位活动入住长者、一个 `QD` 生活照料任务和一个已有的已完成执行记录验收：

### 场景 A：首次打开今日工作台

- 能看到今天应执行的任务；
- 任务状态为“待执行”；
- 刷新页面后任务数量不增加；
- 显示长者姓名、任务描述和计划时间。

### 场景 B：完成任务

- 点击“开始执行”，状态变为“执行中”；
- 点击“完成”，状态变为“已完成”，写入实际执行时间；
- 填写的执行备注可再次查看；
- 该任务的下一次周期执行记录仍能正常生成，不会因为今天完成而停止长期任务。

### 场景 C：跳过任务

- 未填写原因不能提交；
- 填写原因后状态变为“已跳过”；
- 原因在列表详情和长者执行历史中可见；
- 已跳过记录不能再次开始或完成。

### 场景 D：历史和兼容

- 当前已有的登记完成记录继续显示；
- 旧任务没有 `metadata.schedule_times` 时仍能生成默认时间；
- 既有评估、计划和任务创建流程不受影响；
- API 仍返回统一分页结构和错误结构。

## 9. 实施顺序

实现 agent 按以下顺序执行，每一步完成后保持工作区可编译：

## 10. 完成标准

只有满足以下条件才算本计划完成：

- 后端频次生成逻辑有自动化测试或等价的可重复验证；
- 相同任务同一计划时间不会重复生成执行记录；
- 今日工作台无需先选择长者即可看到全部活动长者的执行任务；
- 执行状态和异常原因可操作、可查询、可追溯；
- 当前已有照护数据和已完成记录不受破坏；
- 前端构建通过，后端 Aceso 编译通过；
- 变更文件、数据库迁移和验证命令在实现 agent 的交付说明中列出；
- 未扩大到家庭上门排班、库存联动或统计报表等非本期范围。

## 11. 后续路线

本计划完成后，建议按以下优先级继续：

2. 耗材使用和库存出库联动。
3. 护理员工作量和计划完成率统计。
