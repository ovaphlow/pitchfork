## 1. 背景与目标

**症状**：药房列表「护士核对」列显示 `01M3ZR3CDAQ6ZKHCYD065RSYMT` 而不是「护理员一号」。同类现象此前在病程记录、配餐名单出现过，本轮"没清干净"。

**根因**（与 042 §2 同源）：这些列都用同一个模式把主体 ID 映射成姓名——

```tsx
const subjectMap = new Map(subjects.map((s) => [s.id, s.display_name]));
// subjects 来自 listIdentitySubjects(1,100) → GET /identity/v1/subjects（管理员接口）
// 非管理员 403 → 空 map → subjectLabel 回退原始 ID（且错误被静默吞掉）
```

**写侧是干净的**：`nurseCheckMedicalOrder` 的核对人由服务端从会话取得、请求体必须为空；护理打卡的 `executor` 同样服务端派生。问题**只在读侧**——非管理员拿不到主体目录。

**目标**：给业务账号一个**只读、字段最小**的主体目录，让"主体 ID → 姓名"在所有消费点统一解析；顺带解掉 042 §7 的两个筛选下拉（今日执行人 / 统计执行人）为空的问题。

## 3. 设计决策

### D1 — 新端点放在 IDP，字段最小化

`GET /crate-api/identity/v1/directory`：仅返回 `{ id, display_name }`，**不含** `identifier`（账号）、`status`、`security_version`、`platform_admin`、`created_at` 等管理字段。

- 归属理由：目录数据在 IDP（`identity_profiles`），放 Nexus 需要跨服务聚合；放 Aceso 则 Nexus 直连场景没有目录可用。
- 授权：仅要求**有效完整会话**（与其它 `/crate-api/*` 一致，默认拒绝总闸内），**不是**管理员接口——这正是本条的目的。
- 只返回**启用**主体（`identity_subjects.status = '启用'`），避免把已禁用账号当作可选操作人。

### D2 — 暴露面与残余风险（明确记录）

- 暴露的是"本系统里有哪些同事、叫什么"，属组织内部信息；不含登录标识，不能用于撞库或枚举账号。
- 不在本轮做"仅返回有业务角色的人"的收窄（需要跨服务 join Nexus `subject_roles`，且会让"刚建号还没分配角色的人"在目录里消失，反而制造新的空下拉）。
- 残余风险：任何登录用户可枚举全部启用主体的姓名与 ULID。评审须确认该暴露面可接受（§10 待裁定 1）。

### D3 — 分页与检索

`limit`（默认 50，上限 200）+ `offset` + 可选 `search`（按 `display_name` 模糊匹配，大小写不敏感）。响应沿用仓库契约：`{ "records": [ { "id", "display_name" } ], "meta": { "total": N } }`。

- 下拉与筛选：取 `limit=200` 一页即可（当前规模 11 个主体）。
- 姓名解析：UI 仍只加载第一页并建 map；未命中**保持**现有"回退原始 ID"语义（不隐藏信息）。

### D4 — 消费点统一改用一个 hook

`lib/identity.ts` 的 `useSubjectDirectory()` 改为消费新端点，并**不再静默吞错**（失败时暴露 `error`，由页面决定是否提示）；各页面的本地 `subjectMap` 收敛到该 hook（`PharmacyPage` 当前为了省一次请求自建 map，改为复用 hook）。

- 表单候选（042 的非管理员只读态不再需要候选；平台管理员仍用管理员接口 `listIdentitySubjects` 挑选他人）与筛选下拉改用新端点。
- `UsersPage` 继续用管理员接口（它是管理页，需要 `identifier`/`status`）。

### D5 — 与 042 / 043 的边界

- **不改** `/identity/v1/subjects` 的管理员口径（043 §6 已明确）。
- 042 的 L-UI 车道在实现"非管理员只读操作人"时，姓名直接取自本端点的 `display_name`（042 的 `/session.display_name` 只解决"我自己是谁"）。
- 043 的门禁不涉及本端点（它是读接口）。

## 4. 接口契约（冻结）

```text
GET /crate-api/identity/v1/directory?limit=50&offset=0&search=护
  （需有效完整会话；非管理员可用）
200 { "records": [ { "id": "01M3ZR3CDAQ6ZKHCYD065RSYMT", "display_name": "护理员一号" } ],
      "meta": { "total": 11 } }
400 limit/offset 非法（沿用 identity 侧参数校验口径）
401 未认证
```

不变式：只读；不改 `identity_subjects` / `identity_profiles` 任何数据；不触发登录节流；不返回管理字段。

## 5. 验收口径

1. **姓名解析（主症状）**：以 `pharmacist01` 登录，药房列表「护士核对」列显示护士**姓名**；同一行在 `nurse01` 视角下同样显示姓名。
2. **同类消费点**：以 `nurse01` 登录，病程/评估记录的人名列、康复活动列表的「执行人」列、配餐名单、入住列表的「责任医生/照护师」列均显示姓名（不再是 ULID）。
3. **筛选下拉可用**：今日执行人筛选、统计执行人筛选对 `nurse01` 有候选（不再是空列表）。
4. **最小字段**：`GET /identity/v1/directory` 响应逐字段断言只有 `id` + `display_name`；**不含** `identifier` / `status` / `security_version` / `platform_admin`。
5. **禁用主体不出现**：把一个测试主体置为禁用后，目录里不再出现（回读断言）。
6. **管理页不变**：`UsersPage` 仍走管理员接口，非平台管理员打开时按 043 的无权限态呈现（不因本计划而变成可读）。
7. **降级语义不变**：目录请求失败时，未命中项仍回退显示原始 ID（不隐藏信息），且页面给出可见的失败提示（不再静默）。
8. **回归**：`go test ./...`（idp）、`./gradlew :apps:aceso:test`、`pnpm --filter @pitchfork/aceso build`、`pnpm test:unit:aceso` 全绿。

## 10. 裁定记录（2026-10-03 调度者裁定：按建议）

1. **暴露面：接受** —— 目录对所有登录用户开放，仅返回 `id` + `display_name`，仅含**启用**主体。
   - 理由：业务账号本来就要在表单里挑同事、在列表里看责任人姓名；暴露的是"本系统里有哪些同事、叫什么"，**不含**登录账号（`nurse01`）、密码状态、角色、权限、部门、联系方式，无法用于撞库或定向提权。
   - 现状对比：非管理员在医嘱/任务/账单等业务数据里本就能看到主体 ULID，且 `/subject-permissions?subject_id=X` 现可读任意主体的角色/权限（043 D5 收紧）；本端点新增的只是"姓名"。
   - 备选"只返回有业务角色的人"被否：需跨服务 join Nexus，且会让"新建未分配角色的人"从目录消失，反而制造新的空下拉。
2. **实施时机：042 之后单独一轮** —— 044 不被 042 阻塞（042 非管理员场景显示的是自己的名字，来自 `/session.display_name`），也不阻塞 042。
   - 顺序理由：042 的 L-UI 与 044 的 L-UI-CONSUME 改**同一批文件**（`PharmacyPage.tsx`、`NursingPage.tsx`）——042 改操作人字段、044 改同文件的姓名解析；顺序执行可避免同文件冲突与"改完又被覆盖"的返工。
   - 另：044 单独交付体量小（1 个新端点 + 6 个消费点），可独立验收与回滚。
