## 1. 背景与问题定性

用户实测提出的三条现象：

1. 用户身上的 `identity.admin` 来自 identity 服务，在「角色管理」里看不到（角色目录为 0 条时，用户照样显示 `identity.admin`）；
2. 「角色管理」里建的 `nursing.staff`（带权限码）没有任何用户能挂上；
3. 页面文案自称「管理共享角色目录与每个角色的权限码集合，供各产品消费」，但没有任何产品在消费它。

**核实结论**：第 2 条已被 036 解决（Nexus `subject_roles` + 用户页「编辑角色」），第 1、3 条成立；并且实际情况比"两套"更严重——
原本存在**三套**，其中第三套是纯僵尸（无迁移建表、无消费者），已随本次删除移除。

| 体系 | 存储 / 位置 | 2026-10-02 核实状态 | 处置 |
| --- | --- | --- | --- |
| A. IDP 控制面角色 | `identity_roles` / `identity_subject_roles` | 仅 2 条 seed：`identity.admin`（IDP 管理台 3 处 `HasRole` 在用）、`identity.audit.read`（**播种了但零消费**）；活库 3 个主体全是 `identity.admin` | 保留（**不合并进产品目录**，见 D1），新增只读端点让它在 UI 可见 |

| C. Kotlin `libs:permissions` RBAC/ABAC | Trainova 挂 `/permission/v1/*`；配套 JS 客户端在 `ui-astro/packages/shared/src/index.ts` | 引用 `roles`/`permissions`/`role_permissions`/`rbac_assignments` 四张表，**全仓库无任何迁移或 DDL 建过**；Kotlin 部分已于 2026-10-02 删除 | Kotlin 已删；JS 客户端待删（阶段 1） |

## 3. 设计决策（本计划推荐口径，确认即冻结）

### D1 — 存储保持两层，不合并角色表（推荐）

- IDP 是鉴权根：Nexus 的 `require_identity` **每次请求都要问 IDP**。若 IDP 判断角色反过来依赖 Nexus，Nexus 故障将导致管理员无法进入 IDP 管理台（循环依赖 + 锁死），因此控制面角色必须留在 IDP 自己的库里。
- 产品角色留在 Nexus，是因为目录与分配同库才能用外键保证"不能分配不存在的角色"（036 已实现）。
- 结论：**一套用户可见模型，两层存储**。要消除的是"用户看不到、说不清来源"，不是把表并起来。

### D2 — 呈现收敛：角色页分两组、用户页标来源（推荐）

- 角色管理页两组：**平台内置角色**（来自 IDP，只读、标注来源、不可编辑删除）+ **产品角色**（Nexus 目录，可增删改、可分配）。
- 用户页「角色」列按来源分组：产品角色徽标（可编辑）+ 平台内置角色徽标（只读，标注"身份服务"）。
- 目的：`identity.admin` 不再是一个"点不动又说不清"的灰色徽标；页面文案也不再说"供各产品消费"却不说明消费状态。

### D3 — 消费点放在产品后端，不塞进 IDP 会话（推荐）

- 产品后端（本计划先做 Aceso）在请求进入时解析"当前主体 → 角色码 → 权限码"，再按路由所需权限码放行/拒绝。
- 不把产品角色写进 IDP 的会话/token：那会把产品语义固化进身份服务，且每次授权变更都得重新登录才生效。

### D4 — 权限码语义与权威（推荐）

- **权威**：Nexus `roles.permission_codes`（角色管理页就是它的编辑面）。IDP 不定义产品权限码。
- **格式**：`<域>:<动作>`，域用模块名（`nursing`、`pharmacy`、`billing`…），动作用动词（`execute`、`read`、`write`、`refund`）。现有数据 `nursing:execute` / `pharmacy:manage` 已符合。
- **路由 → 权限码对照表**：在产品后端以显式常量清单维护（`路径 + 方法 → 权限码`），不散落在各 handler 里；对照表就是"哪些角色能做什么"的单一事实来源。
- **宽松匹配**：角色上出现未知权限码不报错（目录是共享的，可能属于别的产品）；路由需要的权限码无人拥有时按未授权处理。

### D5 — 取值方式、缓存与可用性策略（推荐，含待裁定项）

- 产品后端向 Nexus 取"该主体的有效权限码集合"，一次调用拿聚合结果（见 §5 的新端点），带**短 TTL 内存缓存**（建议 30–60s）与"分配变更后失效"（Nexus 写入时 bump 版本号或由产品侧 TTL 兜底）。
- **Nexus 不可用时的行为**：推荐**fail-closed 仅针对受保护的写操作**（拒绝并 503），读操作放行（fail-open）。理由：仓库既有先例——025 药品目录未接线时 `MEDICATION` 医嘱 fail-closed 返回 503，"绝不退化为自由文本开药"。
- 该策略是本计划最需要产品确认的一项（见 §11）。

### D6 — 平台内置角色只读投影，不进 Nexus 目录（推荐）

- 新增 IDP 只读端点 `GET /crate-api/identity/v1/roles`（仅管理员），返回 IDP 自己的角色 + 分配人数。
- 不做双向同步：IDP 与 Nexus 表都不是对方的镜像，同步会引入第二个真相来源。

## 4. 分期与交付顺序

### 阶段 1 — 来源可见 + 清账（不改变任何鉴权行为）

1. IDP 新增只读 `GET /identity/v1/roles`（§5 契约）；补单元/路由测试。
2. 角色管理页分两组渲染；产品组保持现有 CRUD，平台组只读 + 来源标注。
3. 用户页角色列按来源分组（产品角色可编辑、平台角色只读）。
4. 删除死 JS 客户端 `ui-astro/packages/shared/src/index.ts:310-327`（若确认整份 `index.ts` 无入口引用，可整体删除该文件；`package.json` 的 `main`/`exports` 已不指向它）。

**完成标志**：角色目录 0 条时，页面仍能看到"平台内置角色 2 个"，并注明来源与分配人数；`identity.admin` 的归属不再需要靠猜。

### 阶段 2 — 让角色真的起作用（Aceso 试点）

1. Nexus 新增 `GET /shared/v1/subject-permissions?subject_id=<ulid>` 聚合端点（§5）。
2. Aceso 后端新增权限中间件：主体 → 权限码（带 TTL 缓存）→ 按对照表判定；先接**护理执行**一组路由（`nursing` 域）。
3. 用户页显示"该用户当前有效权限码"（只读），让配置结果可自查。
4. 缺口提示：角色所需的权限码未出现在任何对照表项时，角色页给出"未被任何接口使用"的弱提示（避免再次堆积死配置）。

**完成标志**：给用户挂 `nursing.staff`（含 `nursing:execute`）后能执行护理动作；取消该角色后同一动作返回 403；对照表之外的接口行为不变。

### 阶段 3 — 平台化（可选，单独立项）

- 把对照表与中间件下沉为共享能力，供 Trainova 等产品复用；评估是否引入"资源级"权限（当前只做动作级）。

## 5. 接口契约（冻结，车道不得改）

```text
GET /crate-api/identity/v1/roles                    （新增，IDP，仅管理员）
  → 200 { "records": [ { "role_code": "identity.admin", "display_name": "身份管理员",
                         "description": "...", "assignment_count": 3 } ],
          "meta": { "total": 2 } }
  （IDP 列表统一为 records/meta，与根 AGENTS.md 契约一致；无视：无会话 401 / 非管理员 403）

GET /crate-api/shared/v1/subject-permissions?subject_id=<ulid>   （新增，Nexus）
  → 200 { "subject_id": "...", "role_codes": ["nursing.staff"],
          "permission_codes": ["nursing:execute"], "source": "nexus" }
  → 400 subject_id 非 ULID；401 无会话
  （`permission_codes` 为角色权限码去重并集；无角色时为两个空数组）
```

不变式：036 的 `subject-roles` 三个端点与 018 的 `roles` 端点行为不变；`PATCH /identity/v1/subjects/{id}` 仍不接受 `roles`。

## 6. 验收口径

1. **来源可见**：IDP 有 2 个角色、Nexus 目录 0 条时，角色页显示两组（平台内置 2、产品 0），平台组只读且标注来源；用户页 `identity.admin` 显示为只读平台角色。
2. **分配仍可用**：036 的分配/清空/409 行为不回归（沿用 036 验收 1–5）。
3. **有用例覆盖聚合**：`GET /subject-permissions` 对多角色权限码去重求并集；无角色返回空数组；非法 ULID 400。
4. **消费生效（阶段 2）**：挂 `nursing.staff` → 护理执行 200；摘掉 → 403；未受保护的接口行为不变。
5. **Nexus 不可用**：受保护写操作返回 503 且不落数据；读操作按 §11 裁定结果执行。
6. **清账**：`/permission/v1/*` 在代码与文档中无残留（`rg "permission/v1|crate.permission|libs:permissions"` 仅命中历史计划文档）。

## 7. 范围与明确不做

- 不合并 IDP 与 Nexus 的角色表（D1），不做跨服务角色同步。
- 不把产品角色放进 IDP 会话/token，不改 JWT。
- 不做资源级/数据级权限（ABAC）、不做角色继承与互斥、不做有效期。
- 不恢复已删除的 Kotlin `libs:permissions`（其表从未存在，能力由 Nexus + 产品中间件取代）。
- 不改 018/033/034/036 的历史记录（历史文档中的旧表述保留）。
- 不启停用户管理的服务（8420 / 8422 / 4324 / 5432）。

### 偏差与残余风险

1. **权限码使用情况提示的做法**：没有新建独立模块，而是挂在 Aceso 自身的只读自省端点
   `GET /crate-api/access/v1/permissions` 上（登记 `DECLARED_PERMISSIONS`，与接线共用同一个权限码常量，
   漂移由 `DeclaredPermissionsTest` 兜住）。前端拿不到清单时**不做任何标记**，避免误报"未接线"。
2. **上线影响（必须知道）**：护理执行的两条写路由现在要求 `nursing:execute`。当前 Nexus 角色目录是 0 条、
   没有任何用户被分配角色，**所以这两条路由会对所有人返回 403**，直到建好角色并分配。建议的重启顺序：
   重启 Aceso 前先在「角色管理」建 `nursing.staff`（权限码 `nursing:execute`），重启后在「用户管理」把它分配给
   需要用护理执行的账号。
3. 权限缓存 TTL 60s：撤销角色最多 1 分钟后生效；会话吊销不受影响（每个请求先过 IDP 会话校验）。
4. 运行中的服务是旧二进制：Nexus 的 `subject-permissions`、Aceso 的权限闸门都需要**用户手动重启**后才生效。
