## 1. 当前事实与问题

`healthcare.medical_orders` 医嘱表自 V500 起已存在且 jOOQ 源已生成，但没有任何服务或路由：目前系统中不存在开嘱、停嘱或查询医嘱的入口，该表是未激活的存量表。`nursing.nursing_tasks.order_item_id` 与 `pharmacy.pharmacy_dispense_items.order_item_id / order_execution_id` 均为医嘱链路预留的弱关联字段，同样未被使用。

005 已使入住、周期精确绑定，离院在同一事务收束周期；006 已提供离院档案快照。但核心业务闭环仍然缺失：医生/保健师无法开立用药医嘱与诊疗医嘱，医嘱无法派生可执行的护理任务并按频次生成执行记录，离院时没有医嘱停嘱语义，系统更不存在“去世”这一养老机构常见终局——`encounters` 应用层状态集合只有 `ACTIVE/DISCHARGED/TRANSFERRED`，`patients.status` 虽有 `DECEASED` 却无任何流程写入。

不打通该闭环，护理工作台只能依赖手工创建的任务，用药/诊疗过程不可追溯，离院或去世后活动医嘱会成为无人负责的悬挂数据。

## 2. 目标

1. 激活 `healthcare.medical_orders`：为 `ELDERLY_CARE` 入住提供开嘱、查询、停嘱/作废/完成的完整医嘱生命周期，医嘱内容一经创建不可修改（更正 = 停嘱后新开）。
2. 用药医嘱（`MEDICATION`）与诊疗医嘱（`THERAPY/EXAMINATION/LAB_TEST`）以受控 `order_details` 结构化落库，服务端按白名单校验，不接受客户端任意 JSON。
3. 每条医嘱在同一事务内派生一条精确关联的护理任务（`nursing_tasks.order_item_id = 医嘱 id`），复用既有频次与执行生成机制产生 `nursing_task_executions`；护士仍在既有工作台完成执行，医嘱页只读展示执行汇总。
4. 离院（既有接口）与去世（新增接口）在同一事务内收束周期、停嘱、取消未完成医嘱任务并阻断 `IN_PROGRESS` 执行；去世同时将患者置为 `DECEASED`，此后不再为该入住生成新执行。
5. 全程保持 005/006 既有语义：不修改既有评估、计划、任务、执行、护理记录、耗材或库存数据，不改变非养老 encounter 的行为。

## 3. 范围

### 3.1 必须实现

- Healthcare 医嘱服务与路由：`POST /encounters/:id/orders`、`GET /encounters/:id/orders`、`GET /orders/:id`、`PATCH /orders/:id/status`。
- 医嘱类型白名单：`MEDICATION`（用药医嘱）、`THERAPY`（治疗/处置医嘱）、`EXAMINATION`（检查医嘱）、`LAB_TEST`（检验医嘱）；其余类型（`NURSING/DIET/VACCINE` 等）返回 `400`。
- 医嘱状态机：`ACTIVE → DISCONTINUED | CANCELLED | COMPLETED`，终态不可再转；创建后内容不可编辑。
- 医嘱 → 护理任务派生：同一事务写入 `nursing_tasks`（`task_type = MEDICATION | TREATMENT`，`order_item_id`、`period_id`、`encounter_id`、频次、起止日期透传），复用 `ensureExecutionsForDateRange` 生成执行。
- `nursing_tasks.task_type` 约束扩展（V405）以容纳 `MEDICATION`/`TREATMENT`；公共任务路由的 `task_type` 白名单保持既有 5 类不变，两类新值仅允许医嘱编排内部使用。
- 离院收束扩展：`PATCH /encounters/:id/discharge` 在同一事务内将本入住全部 `ACTIVE` 医嘱置为 `DISCONTINUED`、关联 `ACTIVE` 任务置为 `CANCELLED`；既有周期收束、`IN_PROGRESS` 阻断与响应形状不变。
- 新增去世流程：`PATCH /encounters/:id/death`，同一事务内完成 encounter `DECEASED`（含 `death_date`/`death_cause`）、周期 `COMPLETED`、患者 `DECEASED`、医嘱停嘱与任务取消。
- `@pitchfork/shared/aceso` 类型与客户端方法；Aceso UI 新增医嘱管理页，入住管理页增加去世办理与医嘱入口。
- 覆盖输入校验、状态机、事务原子性、精确关联、终局收束、无副作用与错误形状的测试证据。

## 4. 领域规则与数据边界

### 4.1 医嘱归属与资格

医嘱始终由路径中的 `encounter_id` 唯一归属。服务端必须在同一数据库事务中按顺序锁定并验证：

1. 锁定 Healthcare encounter；不存在返回 `404`。
2. encounter 类型必须为 `ELDERLY_CARE`，否则 `400`。
3. encounter 状态必须为 `ACTIVE`，否则 `409`（提示先恢复或已办理终局）。
4. 锁定 `nursing_service_periods.encounter_id = encounter.id` 的唯一关联周期；缺失或状态不为 `ACTIVE/SUSPENDED` 返回 `409`。医嘱任务只写该周期，不得按 `patient_id` 猜测。

### 4.2 医嘱内容与类型

`order_content`（医嘱正文）、`doctor`（开嘱医生）、`start_time`（医嘱生效业务时间）必填，去首尾空白后校验；`doctor` 最多 100 字符，正文最多 2,000 字符。`order_details` 只接受下列白名单键，出现未知键返回 `400`，不得将客户端任意 JSON 落入 `metadata`：

- `MEDICATION`：`drug_name`（必填）、`dose`、`unit`、`route`（给药途径）、`frequency_code`、`frequency_name`、`duration_days`、`remark`。
- `THERAPY`：`treatment_item`（必填）、`frequency_code`、`frequency_name`、`duration_days`、`remark`。
- `EXAMINATION`、`LAB_TEST`：`item_name`（必填）、`remark`。

创建后 `order_content`、`order_details`、`doctor`、`start_time` 均不可修改；更正语义为停嘱后新开医嘱。`nurse` 字段由执行记录承载，创建时不要求填写。

### 4.3 状态机与任务联动

- `ACTIVE → DISCONTINUED`（停嘱）：同一事务将关联 `ACTIVE` 任务置为 `CANCELLED`；该任务不再生成新执行，既有执行原样保留。
- `ACTIVE → CANCELLED`（作废）：同上。
- `ACTIVE → COMPLETED`（完成）：同一事务将关联 `ACTIVE` 任务置为 `COMPLETED`。
- 终态医嘱不得再转换，`PATCH` 返回 `409`；目标状态非法返回 `400`；医嘱不存在返回 `404`。
- 任务联动失败（任务缺失、状态异常、写入冲突）使整个医嘱事务回滚；不允许出现“医嘱已停而任务仍 ACTIVE”或相反。

### 4.4 终局收束（离院/去世）

离院与去世共用同一收束语义，均在同一事务内完成：

1. 按 005 加锁顺序锁定 encounter 与精确关联周期。
2. 若该周期存在 `IN_PROGRESS` 的执行记录，返回 `409`，所有行不变；护理人员先完成或取消该执行。
3. 本入住全部 `ACTIVE` 医嘱置为 `DISCONTINUED`，关联 `ACTIVE` 任务置为 `CANCELLED`；`end_time` 写入终局业务时间。
4. 周期置为 `COMPLETED`，`end_date` 写终局业务日期；encounter 置为 `DISCHARGED`（离院）或 `DECEASED`（去世）。
5. 服务期终态使 `ensureExecutionsForDateRange` 不再为该周期生成新记录；今日工作台只展示活动周期的执行，统计与时间线继续可查历史。

去世流程额外要求：

- 请求体 `death_time` 必填（业务时间），`death_cause` 可选（最多 500 字符）。
- encounter 写 `death_date = death_time`、`death_cause`；`discharge_date` 保持 `null`。
- 同一事务将 `healthcare.patients.status` 置为 `DECEASED`；若该患者名下还存在其他 `ACTIVE` encounter，返回 `409` 并提示先收束其他入住，不得留下半收束状态。
- 已 `DECEASED` 或已 `DISCHARGED` 的入住再次办理去世返回 `409`；已 `DECEASED` 入住办理离院同样返回 `409`。
- 去世后不自动生成死亡小结/死亡档案文书（见 3.2）。

## 5. API 契约

### 5.1 开立医嘱

```http
POST /crate-api/healthcare/v1/encounters/:id/orders
Content-Type: application/json

{
  "order_type": "MEDICATION",
  "order_content": "阿莫西林胶囊 0.5g bid 口服",
  "doctor": "张医生",
  "start_time": "2026-08-02T09:00:00+08:00",
  "order_details": {
    "drug_name": "阿莫西林胶囊",
    "dose": "0.5",
    "unit": "g",
    "route": "口服",
    "frequency_code": "BID",
    "frequency_name": "每日两次",
    "duration_days": 7
  }
}
```

- 首次成功返回 `201` 与单个医嘱对象：`id`、`encounter_id`、`order_type`、`order_content`、`order_details`、`doctor`、`start_time`、`end_time`（`null`）、`status`（`ACTIVE`）、`task_id`（同事务派生的护理任务 id，用于执行汇总查询）。
- 客户端不得提交 `status`、`task_id`、`end_time`、`metadata` 或任何非白名单 `order_details` 键；违反返回 `400`。
- 资格错误按第 4.1 节映射 `404/400/409`；所有失败保持 `{ "error": "<message>" }`。

### 5.2 医嘱列表与详情

```http
GET /crate-api/healthcare/v1/encounters/:id/orders?order_type=MEDICATION&status=ACTIVE&limit=50&offset=0
GET /crate-api/healthcare/v1/orders/:id
```

- 列表返回统一 `{ "records": [...], "meta": { "total": N } }`；空列表返回 `records: []` 与 `total: 0`。列表项不含执行明细。
- 详情返回单个医嘱对象，含 `task_id` 与只读执行汇总 `execution_summary: { PENDING, IN_PROGRESS, COMPLETED, SKIPPED, CANCELLED }`（零计数，不省略字段）；执行通过 `nursing_tasks.order_item_id` 精确关联，不得按患者或日期范围猜测。
- 列表/详情均不触发任务创建、执行生成或任何写入。

### 5.3 停嘱/作废/完成

```http
PATCH /crate-api/healthcare/v1/orders/:id/status
Content-Type: application/json

{ "status": "DISCONTINUED" }
```

- `status` 只接受 `DISCONTINUED`、`CANCELLED`、`COMPLETED`，否则 `400`。
- 医嘱不存在 `404`；非 `ACTIVE` 医嘱转换 `409`；成功返回 `200` 与更新后的医嘱对象（含任务联动结果）。
- 联动任务的 `CANCELLED`/`COMPLETED` 与医嘱状态转换在同一事务，失败整体回滚。

### 5.4 办理去世

```http
PATCH /crate-api/healthcare/v1/encounters/:id/death
Content-Type: application/json

{
  "death_time": "2026-08-02T14:30:00+08:00",
  "death_cause": "心源性猝死"
}
```

- 成功返回 `200` 与 encounter 对象（含 `status: "DECEASED"`、`death_date`、`death_cause`）。
- `death_time` 缺失/类型错误返回 `400`；encounter 不存在 `404`；非养老入住 `400`；已终局、存在 `IN_PROGRESS` 执行或患者名下仍有其他活动入住返回 `409`。
- 失败响应保持 `{ "error": "<message>" }`，不返回半收束数据或数据库错误。

### 5.5 离院扩展

`PATCH /crate-api/healthcare/v1/encounters/:id/discharge` 的请求/响应形状与 005 完全一致；本计划仅在成功路径上追加第 4.4 节第 3 步的医嘱停嘱与任务取消，并在 `IN_PROGRESS` 阻断时保证医嘱与任务也不变。

## 6. 后端实施设计

### 6.1 迁移与 jOOQ

新增 Healthcare 所有的 `V505__add_encounter_death_and_order_closure.sql`：

1. `encounters` 增加可空 `death_date TIMESTAMPTZ`、`death_cause TEXT`；不加 CHECK（遵循 V500 “类型字段由应用层管控”的设计原则）。
2. 不新增表、列、跨 schema 外键，不修改 `V500`–`V504`，不回填历史数据，不使用全局 `outOfOrder`。
3. 为 `(status)` 与 `(encounter_type)` 查询复用既有索引；如去世列表查询实测需要再评估最小索引，不得附带报表类索引。

新增 Nursing 所有的 `V405__extend_task_type_for_medical_orders.sql`：

1. 替换 `nursing_tasks.task_type` CHECK 约束为 `('NURSING','REHABILITATION','LIVING_CARE','HEALTH_EDUCATION','OTHER','MEDICATION','TREATMENT')`；不动 `V400`–`V404`。
2. 不新增列；`order_item_id` 维持弱关联，不加外键。

在获授权、可恢复的 codegen 环境执行 Healthcare/Nursing 的 jOOQ 生成并提交受影响生成源（如 `Encounters.java`、`EncountersRecord.java`、`NursingTasks.java` 相关枚举）；不得以 `DSL.table`/字符串字段替代已有表类，也不得把本地生成配置提交到仓库。

### 6.2 Healthcare 医嘱服务

在 `HealthcareService`（或本计划新建的医嘱服务类）实现：

1. `createOrder(encounterId, body)`：按第 4.1 节锁定并校验，按 4.2 节校验字段与 `order_details` 白名单，写入 `medical_orders`（`status=ACTIVE`，`end_time=null`）。
2. 同一 `Pool.withTransaction` 连接内调用 Nursing 的连接绑定任务创建（见 6.3），以 `order_item_id = 医嘱 id`、`task_type = MEDICATION | TREATMENT`、`period_id`、`encounter_id`、频次与 `start_date = start_time 业务日期`、`end_date = start_date + duration_days`（无时长则 `null`）写入任务；成功后组合 `{ ...order, task_id }` 返回。
3. `listOrders`/`getOrder`：只读批量查询；详情执行汇总按 `task_id` 单次聚合，避免 N+1；`getOrder` 不触发创建、停嘱或执行生成。
4. `updateOrderStatus(id, target)`：锁定医嘱行，校验状态机，同一事务内联动任务状态（任务不存在或状态异常使事务回滚），写 `end_time` 并返回更新后对象。
5. 复用既有 `IllegalArgumentException`、`HealthcareNotFoundException`、`ConflictException` 的 `{ "error": ... }` 映射；只为本计划新增必要的 `409` 分支，不改通用入住、离院、护理记录接口语义。

### 6.3 Nursing 连接绑定任务创建与执行生成适配

1. 在 Nursing 增加连接绑定、供 Healthcare 调用的内部任务创建方法（接受外层 `SqlConnection`），只允许 `task_type ∈ {MEDICATION, TREATMENT}` 且 `order_item_id` 非空；不注册新的公开 `/crate-api/nursing/*` 路由。
2. `TaskService.create` 的公共入口与 `VALID_TASK_TYPES` 白名单保持既有 5 类不变；`MEDICATION/TREATMENT` 不得经公共路由创建。
3. 核对 `ensureExecutionsForDateRange` 与今日执行查询对任务的选择条件：order 派生任务（`order_item_id` 非空）必须与其他任务一样按频次生成执行，且同样受“仅 ACTIVE 周期”约束；若现有选择条件显式排除或未覆盖 order 任务，做最小适配并补测试，不得改变既有计划任务行为。
4. `nursing_tasks` 既有字符串表访问属存量代码；本计划新建代码使用生成 jOOQ 表类。

### 6.4 离院与去世编排

1. `dischargeEncounter` 在 005 事务内追加：读取本入住 `ACTIVE` 医嘱集合，逐条置 `DISCONTINUED`（`end_time = 终局业务时间`）并联动取消任务；与周期收束、encounter 状态更新同一事务。
2. 新增 `deathEncounter(id, body)`：按 4.4 节校验并锁读 encounter、周期；校验患者名下无其他 `ACTIVE` encounter；同事务写 encounter（`DECEASED` + `death_date`/`death_cause`）、周期（`COMPLETED`）、患者（`DECEASED`）、医嘱与任务收束。
3. `encounterStatuses` 集合增加 `DECEASED`；离院与去世互斥（任一终局后另一操作返回 `409`）。
4. 不新增后台任务、补偿队列或前端多次请求模拟事务。

### 6.5 Shared API 与前端

在 `@pitchfork/shared/aceso` 增加明确的 snake_case TypeScript 类型：`MedicalOrder`、`MedicalOrderInput`、`MedicalOrderList`、`MedicalOrderStatusUpdate`、`DeathInput` 及执行汇总类型。新增：

```text
createMedicalOrder(encounterId, input)
listMedicalOrders(encounterId, params?)
getMedicalOrder(orderId)
updateMedicalOrderStatus(orderId, { status })
markEncounterDeath(encounterId, input)
```

全部复用既有 `request`、Bearer token、JSON 解析和 `401` 处理；组件内不得自行 `fetch` 或维护第二套 API 基址。

Aceso UI：

1. 新建 `OrdersPage.tsx` 与 `/orders` 路由，`Sidebar` 增加“医嘱”导航：选择活动入住 → 医嘱列表（按 `order_type` 过滤用药/诊疗）→ “开医嘱”受控表单（类型、正文、医生、生效时间、结构化明细字段）→ 行操作“停嘱/作废/完成” → 详情弹窗展示执行汇总（只读）。表单校验与错误独立展示，提交期间禁用重复操作，失败保留输入。
2. `AdmissionsPage` 在活动入住行增加“办理去世”入口：受控表单（`death_time`、`death_cause`）提交 `markEncounterDeath`，成功后刷新列表；已终局入住不显示该入口。离院流程与已离院档案保持不变。
3. 医嘱页只读展示执行汇总，不提供执行操作；执行继续在既有护理工作台完成。窄屏采用纵向区块与可横向滚动表格。

### 7.1 开发：非数据库单元与嵌入式路由测试

开发增加或扩展不访问数据库的测试，至少覆盖：

1. 开嘱输入：`order_type` 白名单、`doctor/order_content/start_time` 必填与长度、`order_details` 白名单键（未知键 `400`）、客户端注入 `status/task_id/end_time/metadata` 不被采用。

3. 状态机：`ACTIVE → DISCONTINUED/CANCELLED/COMPLETED` 成功并联动任务；终态再转 `409`；非法目标 `400`；路由精确匹配不被泛型路径吞掉。

## 9. 完成标准

- 医嘱可通过第 5 节接口开立、查询、停嘱/作废/完成；`MEDICATION`/`THERAPY`/`EXAMINATION`/`LAB_TEST` 之外的类型与未知 `order_details` 键被拒绝。
- 每条医嘱与唯一护理任务精确关联（`order_item_id`），执行由既有频次机制生成且可由医嘱页按 `task_id` 汇总；公共任务路由不开放两类新任务类型。
- 离院与去世在同一事务内收束周期、停嘱、取消任务并阻断 `IN_PROGRESS` 执行；去世同时置 encounter/患者终态，且不再生成新执行。
- 既有评估、计划、任务、执行、耗材、护理记录、时间线与 006 归档快照不受本计划写入影响；非养老 encounter 行为不变。
- Aceso UI 仅通过 `@pitchfork/shared/aceso` 使用医嘱与去世能力，提供响应式只读执行汇总与清晰错误状态。
- 开发的非数据库测试、Aceso 编译、前端构建和 `git diff --check` 有实际结果；测试的授权 PostgreSQL 与用户管理浏览器验收有可复验记录；评审已记录最终结论。
