## 1. 背景与目标

QA 第 7 轮报告（**已核实，其中一条前提有误，见 §2.1**）：

1. 🔴 **权限模型只覆盖 1/4 的科室**。`doctor01`（无任何产品角色）能开医嘱、写诊断并成功落库；`dietitian01`、`logistics01` 同理。接口层用 `doctor01` 直接打，只有 `POST /shared/v1/departments` 守住（`403 permission-required`）。
2. 🟡 **医嘱/诊断/病程的「医生」字段仍是自由文本必填**。`doctor01` 已登录却要手打「医生一号」，且**可伪造他人署名**——责任归属不可信。药房「操作人」在 042 已改为服务端派生，两者口径不一致。

目标：

- 把 5 个业务域（临床、膳食、物资-采购、药房、收费）的**主写路由**接上权限门禁，使「有账号就能干任何事」不再成立；
- 门禁判定采用**双轨**（平台管理员 ∨ 权限码），避免接线当刻全员 403；
- 临床署名（医嘱 `doctor`、诊断/病程 `physician`）改为**服务端按会话派生、只读、不开放代签**，与 `attending_physician`/V524/药房 `operator` 同口径；
- 权限不足在 UI 上是**可见**的错误，不是「保存成功」。

## 3. 设计决策

### D1 — 门禁判定：**双轨**（平台管理员 ∨ 权限码）

```text
allow ⇔ ctx["platformAdmin"] == true
       ∨ required_permission ∈ Nexus 返回的该主体 permission_codes
```

- 与 043 D2 的 Nexus 裁定一致；平台管理员是**引导者**，因此**不需要 040 §9.1 的放量协议**：接线当刻平台管理员仍可操作，不会「全员 403」。
- 实现位置：`SubjectPermissionGate.kt` 的 `requireAnyPermission` 在取 `subjectId` 后、查询 Nexus **之前**短路 `ctx.get<Boolean>("platformAdmin") == true → ctx.next()`（少一次上游调用）。
- 失败路径不变：无会话 → `401`；Nexus 不可用 → `503` + `Retry-After`；无权限 → `403` + `required_permission`。

### D2 — 接线方式：**集中式声明驱动门禁**，不逐个改 lib 的 `create()`

在 `Main.kt` 的 `apiAuthenticationGate` **之后、所有模块子路由之前**，按 `DECLARED_PERMISSIONS` 注册门禁路由：

```kotlin
DECLARED_PERMISSIONS.filter { it.wiring == PermissionWiring.CENTRAL }
    .groupBy { it.method to it.path }
    .forEach { (key, decls) ->
        apiRouter.route(HttpMethod.valueOf(key.first), key.second)
            .handler(requireAnyPermission(permissionClient, decls.map { it.permissionCode }))
    }
```

理由：

1. `DECLARED_PERMISSIONS` 已是「产品侧把码接在哪些路由上」的**唯一声明源**（自省端点 `GET /access/v1/permissions` 也是它派生），集中注册让**声明与实际接线共用一份数据**，天然不可漂移；
2. 4 个 lib 的 `create()` 与嵌入式测试挂载**完全不动**（`healthcare` 的 11 个 auth handler 形参、`inventories` 无 auth 形参等均不改）；
3. 路径用 `route(method, path)`（支持 `:id` 占位）注册在 `apiRouter` 上，path 用**请求实际路径**（无尾斜杠）。

**新增 `wiring` 标记**：`DeclaredPermission` 增 `wiring: PermissionWiring = CENTRAL`。护理 3 条（`administration`、`status`×2）标 `INJECTED`——它们由 `TaskExecutionRoutes` 的注入式门禁承载（打卡需按 `task_type` **读库选码**，集中式无法做），**不重复注册**（重复注册虽不弱化最终判定，但会让 403 的 `required_permission` 文案退化）。

`SubjectPermissionClient` **全应用共用一个实例**（替换现有 `nursingPermissionClient`，键仍是 subjectId、TTL 60s）。

**BodyHandler 顺序不变式**：门禁是异步的，会 `ctx.next()`；模块子路由里的 `BodyHandler` 仍不是「首个 BodyHandler」（顶层 `BodyHandler` 已在 `apiAuthenticationGate` 之前注册），因此**不会**重演 2026-09-29「写请求永久挂起」P0。该不变式由 `ApiBodyHandlingTest` 回归（§6.7）。

### D3 — 权限码目录：新增 3 条，接线 2 条既有码

| 码 | 说明 | 接线后 `enforced_by` |
| --- | --- | --- |
| `clinical:write` | 临床写入（医嘱、诊断、病程） | `aceso` |
| `dining:manage` | 膳食管理（饮食档案、菜品、周菜单、配餐名单、用餐执行） | `aceso` |
| `inventory:write` | 物资与采购（物资目录、批次、入库、采购订单与收货） | `aceso` |
| `pharmacy:dispense` | 发药确认（发药单全链、退药） | `null` → `aceso` |
| `billing:write` | 账单与费用写操作（生成、加项、缴费、红冲、结算、押金） | `null` → `aceso` |

- `nursing:execute` 复用一条新路由（`PATCH /orders/:id/nurse-check`，护士核对用药医嘱），目录说明随之扩为「护理执行（记录给药、非康复活动的执行状态更新、用药医嘱护士核对）」。
- `nursing:execute`/`rehab:execute`/`access:manage`/`base_data:manage` **不变**。
- 码格式沿用 040 D2 正则 `^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$`，5 个码均合规。
- **不新增** doctor/nurse/dietitian 这类**岗位**码——岗位由角色承载，权限码只表达能力（与既有 6 码一致）。

### D4 — 接线范围：每个域只接**主写路由**，不做全量

见 §4.1 冻结矩阵。跨域/历史遗留（住院登记、床位、患者档案、费用项、体检、随访、慢病、体征、护理不良事件与交接班、护理站申领调拨、护理评估/计划/复评）**不在本轮**（§6 残项）。

### D5 — 临床署名：服务端派生、只读、**不开放代签**

三个端点的字段由**路由层**解析后覆写请求体，服务层校验逻辑**不变**：

```kotlin
when (val r = resolveOperator(ctx.get("userId"), platformAdmin = false, requested = body.getString(field))) {
    is Resolved    -> body.put(field, r.subjectId)
    is Delegated   -> body.put(field, r.requested)     // 仅无会话挂载（嵌入式/集成测试）回落
    is Absent      -> respond(401, "authentication required")
    NotDelegatable -> respond(400, "operator cannot be delegated")
}
```

- **`platformAdmin` 硬编码 `false`**：本轮明确**不开放代签**——署名即责任。平台管理员提交他人同样 `400`。
- 客户端提交**自己**的 subject id 等价于未提交（`Resolved`）。
- 前端字段改为**只读**展示 `<display_name>（当前登录用户）`，提交体**不含**该字段；因此生产路径永远走 `Resolved`。
- `Delegated` 分支只为**无认证挂载的嵌入式/集成测试**保留（042 D4 已有先例），**不是生产放行路径**：生产由 `/crate-api/*` 默认认证总闸保证 `ctx["userId"]` 存在。
- 存储值 = **认证主体 ID**（ULID），与 `attending_physician`、V524、药房 `operator` 同口径；存量自由文本（如「医生一号」）在 UI 侧由 `subjectLabel` 原值回退，不迁移、不回填。
- 服务层 `requiredText(body, "doctor"|"physician")` 与 `≤100` 校验**保留**：路由层已把派生值写入请求体，因此服务层不变、`DoctorClinicalTest`（服务级）不受影响。

### D6 — 权限不足必须**可见**

接线后受影响页面的写操作会拿到 `403 {"error":"forbidden","required_permission":"<code>"}`。UI 必须用既有 `problemMessage()` 渲染到表单错误位（`packages/shared/src/problem-message.ts` 已把带 `required_permission` 的 403 翻成「权限不足：需要「<code>」权限…」），**不得静默吞错**。本轮只做「错误可见」，不做前端权限感知（菜单/按钮置灰——040 D5 已裁定不做）。

### D7 — 门禁只挂写路由，读路由保持开放

读路由（各模块 `GET`）不加门禁：目录与列表是页面渲染的输入，收紧读会产生新的 403 面并超出本轮范围。

### D8 — 不做：全量接线、前端权限感知、岗位码、`enforced_by` 多值

- 全量把 4 个模块的写路由接完需分轮放量与码位扩充 → §6 残项。
- `enforced_by` 保持单值 `"aceso" | "nexus" | null`：本轮**每个码只由一层接线**（`access:manage`/`base_data:manage` 仍只在 Nexus），不引入多值形态以免破坏 043 §4.3 冻结的自省契约。

```text
allow  ⇔ platform_admin == true
       ∨ required_permission ∈ 该主体在 Nexus 角色目录里的 permission_codes
deny   → 403 {"error":"forbidden","required_permission":"<code>[ 或 <code2>]"}
未认证 → 401 {"error":"authentication required"}
上游不可用 → 503 {"error":"permission service unavailable"} + Retry-After: 5
```

### 4.3 临床署名字段契约（冻结）

| 端点 | 字段 | 改前 | 改后 |
| --- | --- | --- | --- |
| `POST /healthcare/v1/encounters/:id/orders` | `doctor` | 必填自由文本 | **请求体可省略**；服务端以会话主体覆写 |
| `POST /healthcare/v1/encounters/:id/diagnoses` | `physician` | 必填自由文本 | 同上 |
| `POST /healthcare/v1/encounters/:id/progress-notes` | `physician` | 必填自由文本 | 同上 |

```text
请求体字段缺省或等于会话主体      → 落库值 = 会话主体 ID
请求体字段为他人 && 有会话         → 400 {"error":"operator cannot be delegated"}
请求体字段为他人 && 无会话（测试）   → 落库值 = 请求体值（Delegated 回落）
无会话且请求体也未给              → 401
长度 > 100                       → 400（沿用服务层校验）
```

## 5. 放量协议与上线前置（运行期，非代码）

双轨使**平台管理员不受接线影响**，因此接线本身无「全员 403」风险。但业务账号在接线后需要角色，否则会（正确地）被拒。上线前/当刻由平台管理员在「角色管理」建并分配：

| 角色（建议 `role_code`） | 权限码 | 分配对象（示例） |
| --- | --- | --- |
| `clinical.staff` | `clinical:write` | `doctor01` |
| `dining.staff` | `dining:manage` | `dietitian01` |
| `inventory.staff` | `inventory:write` | `logistics01` |
| `pharmacy.staff` | `pharmacy:dispense` | `pharmacist01` |
| `billing.staff` | `billing:write` | `cashier01` |
| `nursing.staff`（已存在） | `nursing:execute` | `nurse01`（如未分配） |

- 建角色/分配走 Nexus（043 双轨：平台管理员可引导）；
- **未分配 = 403**，这是预期行为，不是回归；
- 权限变更经 Nexus 侧即时生效，Aceso 侧权限缓存 TTL ≤ 60s。

## 6. 验收口径

1. **未分配即被拒**：`doctor01`（无 `clinical:write`）→ §4.1 的 6 条 `clinical:write` 路由全部 `403` + `required_permission: "clinical:write"`；库内 `medical_orders`/`diagnoses`/`progress_notes` 计数不变（回读断言）。
2. **分配即放行**：平台管理员分配 `clinical.staff` 后（等过 TTL），`doctor01` 同一请求进入业务逻辑（合法请求 `201`；非法请求 `400`，**不是** `403`）。
3. **双轨引导者**：平台管理员（无任何上述码）能完成 1–2 的全流程，且能建角色、分配角色。
4. **5 个域一致**：`dining:manage`（16 条）、`inventory:write`（11 条，含 `/pharmacy/v1/purchase-orders/*`）、`pharmacy:dispense`（11 条）、`billing:write`（7 条）逐条同上；`dietitian01`/`logistics01`/`pharmacist01`/`cashier01` 未分配时均 `403`，分配后放行。
5. **读路由不回归**：上述各模块的 `GET` 路由对未分配账号仍 `200`。
6. **署名不可伪造**：`doctor01` 提交 `doctor="李医生"`（他人）→ `400 operator cannot be delegated`；不提交 `doctor` → 落库 `doctor` = `doctor01` 的主体 ID；UI 该字段只读显示「<姓名>（当前登录用户）」，提交体不含该字段。诊断/病程 `physician` 同。
7. **不挂起（P0 回归）**：门禁接线后，带请求体的写请求仍能拿到响应（`ApiBodyHandlingTest` 现有用例 + 新增「已接线路由」用例），**不出现** pending 挂起。
8. **声明与接线一致（护栏）**：对已接线模块，构造真实 Router 并递归枚举 `Router.routes()`，断言**每个写方法路由都在 `DECLARED_PERMISSIONS` 里**（漏登记即测试失败）；`INJECTED` 项与护理 3 条一一对应。
9. **403 可见**：受影响页面（`OrdersPage`/`DiningPage`/`PurchaseOrdersSection`/`PharmacyPage`/`BillingPage`/物资页）写操作 403 时显示中文「权限不足：需要「<code>」权限…」，不静默吞错、不出现「保存成功」的假象。
10. **回归**：`./gradlew :apps:aceso:test`、相关 `libs` 单测、`pnpm --filter @pitchfork/aceso build`、`pnpm test:unit:aceso` 全绿；`GET /access/v1/permissions` 形状与既有消费方（角色页）兼容。
