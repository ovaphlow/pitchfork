## 1. 背景与目标

QA 第 5 轮堵点：**业务账号的操作人下拉是空的，药房流程走不完**。

现象：`pharmacist01` 创建发药单时「操作人」下拉只有占位项"请选择操作人"，而表单强制必填 → 提交不了。

根因（源码 + 实测双证，见 §2）：这些表单的操作人候选来自 **IDP 管理员接口** `GET /crate-api/identity/v1/subjects`，非管理员一律 403，前端又静默吞掉错误 → 下拉空。

目标：

1. **操作人的权威来源改为认证会话**（`ctx["userId"]`），与「办理入住」的责任照护人、V524 的离院/去世操作人、护理打卡的 `executor` 同一口径；
2. 保留**代操作**能力，但只对**平台管理员**开放（IDP `is_platform_admin`，039 裁定的唯一根权限）；
3. 顺带堵住一个真实的安全面：现在药房 `operator` 完全由客户端提交、服务端只校验非空，任何登录用户都能把操作人写成别人（伪造留痕）。

## 3. 设计决策

### D1 — 操作人权威来源 = 认证会话，客户端值只是"请求"，不是"事实"

所有受影响端点的操作人一律由服务端从 `ctx["userId"]` 派生。libs 不感知 HTTP/会话，由**路由层**解析后以参数注入（沿用 `dischargeEncounter(id, body, operator)` 的既有形状）。

### D2 — 代操作门禁用 IDP `platform_admin`，不引 Nexus 权限码

- 依据 039 裁定：IDP 只保留「平台管理员」这一个不依赖 Nexus 的根权限；角色/权限目录全归 Nexus。
- 不选权限码（如 `pharmacy:act_on_behalf`）的理由：会引入"先建角色 → 分配 → 再接线"的放量耦合（040 §9.1 的教训），而代操作是**极小概率的兜底路径**，不值得占一个权限码；且平台管理员天然可信。
- 实现：`GET /crate-api/identity/v1/session` 响应新增 `platform_admin`，Aceso 会话中间件存进 `ctx["platformAdmin"]`。

### D3 — 非管理员提交"他人 operator"→ 400，不静默改写

`400 {"error":"operator cannot be delegated"}`。理由：静默改写会让前端以为提交生效（`confirm` 类端点尤其危险），而 fail-closed 的边界可被测试断言。UI 侧非管理员**根本不提交**该字段（见 D7），所以正常路径不会撞到这个 400。

### D4 — 无认证挂载（嵌入式/集成测试）回落 `body.operator`

`ctx["userId"]` 为空时按现状使用 `body.operator`。理由：`DispenseIntegrationTest` / `ReturnIntegrationTest` / `MedicationAdministrationIntegrationTest` 等以自由文本（`"审方药师"`、`"护士甲"`）驱动嵌入式路由，强制会话会让一大片既有测试变红；且这与 `TaskExecutionRoutes.kt:462` 注释的既有口径（"未注入认证时保持原有行为"）一致。

### D5 — 发药单创建：删字段，后端零改动

服务端从不接收该字段（`rejectUnknown` 白名单不含 `operator`），补绑用的操作人早已是 `ctx["userId"]`。因此 `PharmacyPage.tsx` 的创建弹窗**移除操作人下拉与必填校验**即可解堵，不产生任何 API 契约变更。

### D6 — 护理三字段同口径纳入

评估人（`assessor`）、制定人（`created_by`）、执行人（`executor`）语义都是"谁做的这件事"，与药房操作人同源，一并派生。其中复评/修订两处经 healthcare 的 `care-plan-revisions` 路由，需给 `HealthcareService.createCarePlanRevision` 增加 `operator` 参数（与 `dischargeEncounter` 同形）。

### D7 — `/session` 同时返回 `display_name`

非管理员拿不到主体目录，无法把自己的 ULID 渲染成姓名。若只返回 `platform_admin`，UI 只能显示"当前登录用户（01M3ZR3…）"。因此 `/session` 一并返回 `display_name`（自己的姓名不属于目录信息，无泄露面），UI 显示"操作人：药师一号（当前登录用户）"。

**零额外查询**：`CurrentSession` 现有的 `getEnabledSubjectSecurityVersion`（`session.go:73`）改为新的 `getEnabledSubjectSessionFacts`，`LEFT JOIN identity_profiles` 取 `display_name`，并取 `is_platform_admin`。登录路径（`session.go:170`）保持用原查询，不动。

### D8 — 筛选类下拉与显示降级不在本轮

`今日执行人筛选`、`统计执行人筛选` 对非管理员仍为空；`subjectMap` 仍降级显示 ULID。这两类问题的正解是"一个非管理员可读的业务人员目录"（IDP `/subjects` 是管理员接口且只覆盖前 100 条），属新接口 + 新授权面——**已立项 044**，本计划不再承接。

### D9 — UI 分流：管理员可挑、非管理员只读（§11 裁定：保留代操作入口）

- **平台管理员**：渲染可挑选下拉，候选来自 `listIdentitySubjects(1,100)`（该接口本就仅管理员可用）；**option value 改为 `subject.id`** —— 现状四处均为 `value={subject.display_name}`（`PharmacyPage.tsx:1470/1674/1727/1870`），提交姓名既不是主体 ID，也无法通过 D3 的边界。目录加载失败时显示"目录加载失败，留空则按本人记录"，不再静默吞错。
- **非管理员**：不渲染下拉，渲染只读文本 `操作人：<display_name>（当前登录用户）`（`display_name` 来自 D7 的 `/session`），提交体**不含** `operator`（服务端按 D1 派生）。
- 该分流在药房 3 处（发药动作、退药创建、退药确认）+ 护理 5 处（评估人×2、制定人×2、执行人）生效；发药单创建按 D5 直接删字段。

## 4. 接口契约（冻结）

### 4.1 IDP 会话响应（向后兼容，纯新增字段）

```text
GET /crate-api/identity/v1/session        （既有端点，需有效完整会话）
200 { "subject_id": "<26 位 ULID>",
      "access": "完整",
      "platform_admin": true,             // 新增
      "display_name": "药师一号" }         // 新增；档案缺失时为空串
401 会话无效（行为不变）
```

- 新增字段**不得**改变既有消费方（Aceso `subjectIdOrNull` 只读 `subject_id`，Nexus 只读 `subject_id` + `access`）。
- `platform_admin` 查询失败（库不可用）→ 沿用 `CurrentSession` 现有错误路径（500），**不得**静默降级为 `false`。

### 4.2 Aceso 路由上下文（新增一个键）

| ctx 键 | 类型 | 来源 | 现状 |
| --- | --- | --- | --- |
| `userId` | `String`（ULID） | 会话中间件 | 已有 |
| `platformAdmin` | `Boolean` | 会话中间件 | **新增**；上游缺该字段或非 `true` 一律按 `false` |

### 4.3 操作人解析（唯一口径，所有受影响端点共用）

```kotlin
// libs/common：纯函数，不依赖 vertx（libs/common 无 vertx 依赖，pharmacy/nursing/healthcare 均已 api 依赖它）
sealed interface OperatorResolution {
    data class Resolved(val subjectId: String) : OperatorResolution
    data class Delegated(val requested: String) : OperatorResolution
    data object Absent : OperatorResolution            // 无认证挂载且请求体未提供
    data object NotDelegatable : OperatorResolution    // 非管理员提交他人
}

fun resolveOperator(actorId: String?, platformAdmin: Boolean, requested: String?): OperatorResolution {
    val actor = actorId?.trim()?.takeIf { it.isNotBlank() }
    val ask = requested?.trim()?.takeIf { it.isNotBlank() }
    if (actor == null) return ask?.let { OperatorResolution.Delegated(it) } ?: OperatorResolution.Absent
    if (ask == null || ask == actor) return OperatorResolution.Resolved(actor)
    return if (platformAdmin) OperatorResolution.Delegated(ask) else OperatorResolution.NotDelegatable
}
```

映射：`Resolved`/`Delegated` → 写入该值；`Absent` → 保留现状（字段可空处不写，必填处 400/401）；`NotDelegatable` → `400 operator cannot be delegated`。

## 5. 验收口径

1. **药房主链路可用（核心）**：以 `pharmacist01`（无平台管理员、有 `pharmacy.staff`）登录，创建发药单 → 审方 → 调配 → 确认，四步全通；`reviewer` / `pharmacist` 回读等于 `pharmacist01` 的 `subject_id`。
2. **退药链路可用**：`pharmacist01` 创建退药单 + 确认，`operator` 回读等于其 `subject_id`。
3. **护理责任人落库**：`nurse01` 建评估记录（评估人）、建照护计划（制定人）、建执行记录（执行人）、提交复评与计划修订，五个字段回读均为 `nurse01` 的 `subject_id`（**不再是 NULL**）。
4. **代操作门禁**：平台管理员提交他人 `subject_id` → 写入该值；非管理员提交他人 `subject_id` → `400 operator cannot be delegated`，且库内不变。
5. **无认证挂载兼容**：嵌入式路由测试传自由文本 operator 仍通过（既有测试不改断言）。
6. **`/session` 兼容**：响应新增 `platform_admin` + `display_name`；Nexus 会话校验与 Aceso 会话中间件对旧形状（缺字段）不崩、按 `false` 处理。
7. **UI 无死字段**：发药单创建弹窗不再有操作人下拉；非管理员在其余 8 处看到只读"操作人：<自己姓名>（当前登录用户）"且提交体不含 `operator`；管理员看到可挑选下拉且**提交的是主体 ID**（不是姓名），选定后回读等于所选主体。
8. **回归**：`./gradlew :apps:aceso:test :libs:pharmacy:test :libs:nursing:test :libs:healthcare:test`、`cargo test`（Nexus 未改，作对照）、`pnpm --filter @pitchfork/aceso build`、`pnpm test:unit:aceso` 全绿；`go test ./...`（idp）全绿。
