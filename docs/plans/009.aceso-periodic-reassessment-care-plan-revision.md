# Aceso 定期复评与照护计划修订 MVP 实施计划

更新时间：2026-08-05

状态：待实施

## 编号与前置计划

本文件是 008 医嘱核心流程之后的下一项业务计划，编号按 `docs/plans/` 当前最大有效编号递增。

前置能力：

- 001 已提供护理评估、照护计划、任务、执行和时间线的基础数据及工作台。
- 005 已保证活动 `ELDERLY_CARE` encounter 与唯一活动护理周期的精确关系，并在离院时收束周期。
- 006 已提供离院交接摘要的只读归档语义；本计划不修改归档快照。
- 008 已完成医嘱与护理任务的核心闭环；本计划创建的护理任务不改变医嘱、药房或库存语义。

当前代码已经存在通用评估和计划 CRUD，但它们可以分别写入，不能在一次操作中表达“复评完成后产生新的照护计划版本”。本计划增加复评聚合流程，不重写既有通用创建接口的历史数据，也不把演示需求扩展成完整临床决策系统。

## 目标与范围

### 必须实现

1. 仅活动的 `ELDERLY_CARE` encounter 和其精确活动护理周期可以提交复评及计划修订；服务端不根据 `patient_id` 猜测周期。
2. 在一个数据库事务中完成：创建复评、收束当前活动计划、创建新计划及措施、创建新计划对应的护理任务、写入修订关系。任一步失败时整笔事务回滚。
3. 复评继续使用既有评估类型值：`FALL_RISK`、`PRESSURE_SORE`、`PAIN`、`BARTHEL`、`NUTRITION`、`HOME_ENVIRONMENT`、`OTHER`。不新增新的英文评估 code；请求路径本身表达“复评”语义。
4. 每个护理周期的修订记录具有递增 `revision_no`，记录复评 ID、上一版计划 ID、新计划 ID、encounter、period 和创建时间；上一版计划内容、措施内容、已完成任务和历史执行保持可追溯。
5. 修订成功后，上一版活动计划转为 `DISCONTINUED`，其活动措施转为 `DISCONTINUED`，其活动任务转为 `CANCELLED`；已完成或已取消任务不改写，既有执行记录不删除、不改写。
6. 新计划以 `ACTIVE` 创建；每条新措施派生一条 `NURSING` 任务，精确写入 `plan_item_id`、`period_id` 和 `encounter_id`，并复用既有频次、日期和执行生成机制。
7. 提供 Healthcare 聚合 API、`@pitchfork/shared/aceso` 类型化客户端，以及护理工作台中的“复评并修订计划”交互。前端不直接请求 Nursing API。
8. 提供修订历史列表和详情，展示评估、计划版本、措施和任务关联；读取不生成任务、执行或库存写入。

### 明确不在本期范围

- 不做自动风险评分、AI 推荐、处方建议、临床规则引擎或评估量表计算；`total_score` 和 `result_level` 仍由用户填写。
- 不修改既有评估、计划、计划措施、已完成任务、执行、护理记录、时间线、耗材、库存和 006 离院交接摘要的历史正文。
- 不做计划版本的编辑、删除、合并、回滚或历史任务重算；修订只能通过“创建新版本”完成。
- 不修改 008 医嘱状态机、药房发药、库存扣减、死亡档案、权限模型或操作审计。
- 不改变通用 `POST /crate-api/nursing/v1/assessments`、`POST /crate-api/nursing/v1/plans` 和 `POST /crate-api/nursing/v1/tasks` 的既有响应形状；仅限制其不能绕过修订接口制造第二个活动计划。
- 不实现非 `ELDERLY_CARE` encounter、家庭照护周期或跨患者/跨入住的计划修订。
- 不在本轮要求 PostgreSQL 全量集成矩阵或 Chromium 全量验收；先交付可编译、可构建、可人工操作的 MVP，真实业务逻辑由用户后续手动验证。

## 领域规则与事务边界

### 复评资格

服务端按以下顺序校验：

1. encounter 不存在返回 `404`。
2. encounter 类型不是 `ELDERLY_CARE` 返回 `400`。
3. encounter 不是 `ACTIVE` 返回 `409`。
4. 找不到该 encounter 唯一精确 period 返回 `409`。
5. period 的 `encounter_id` 不等于路径 encounter、period 状态不是 `ACTIVE` 返回 `409`。
6. 当前周期没有且只有一个活动计划时返回 `409`；没有基线计划不能使用“修订”接口，必须先走既有初次计划创建流程。历史上存在多个活动计划时不得猜选，返回 `409` 并提示数据需要人工整理。
7. 当前活动计划关联任务存在 `IN_PROGRESS` 执行时返回 `409`，encounter、period、旧计划和执行均保持不变。

创建请求中的 encounter、period、旧计划、修订号和关联 ID 均由服务端从锁定数据推导，客户端不能覆盖。

### 请求与响应

新增 Healthcare 路由：

```text
POST /crate-api/healthcare/v1/encounters/:id/care-plan-revisions
GET  /crate-api/healthcare/v1/encounters/:id/care-plan-revisions
GET  /crate-api/healthcare/v1/care-plan-revisions/:id
```

创建请求的允许结构为：

```json
{
  "assessment": {
    "assess_type": "BARTHEL",
    "assess_date": "2026-08-05",
    "assessor": "护理员",
    "total_score": 65,
    "result_level": "中度依赖",
    "detail": { "note": "近期步行能力下降" },
    "remark": "复评说明"
  },
  "plan": {
    "plan_name": "第二阶段照护计划",
    "goals": "提高日常活动能力",
    "created_by": "护理员",
    "start_date": "2026-08-05",
    "end_date": "2026-08-19",
    "items": [
      {
        "action": "每日协助步行训练",
        "frequency_code": "QD",
        "frequency_name": "每日一次",
        "duration_days": 14,
        "remark": "根据耐受程度调整"
      }
    ]
  }
}
```

服务端只接受上述字段；客户端传入的 `id`、`status`、`period_id`、`encounter_id`、`plan_id`、`task_id`、`revision_no`、`metadata` 或其他未知键必须拒绝。`detail` 仅作为既有评估详情对象保存，不改变公共 `metadata` 约定。

创建成功返回 `201`，响应包含：

- `revision_id`、`revision_no`、`assessment`；
- `previous_plan` 的 ID 和终态；
- `plan`、`items`；
- 新建任务的 `task_id`、`plan_item_id`、状态和起止日期。

列表返回 `{ "records": [...], "meta": { "total": N } }`，按修订号倒序；空列表必须返回空 `records` 和 `total: 0`。详情只按修订 ID 读取，并再次校验其 period/encounter 归属。

### 日期、任务与执行

- `assess_date` 必填，使用上海业务日期，不能早于精确 period 的开始日期或晚于当前业务日期。
- `plan.start_date` 必填且不得早于 `assess_date`；`end_date` 如提供不得早于 `start_date`。
- `duration_days` 如提供必须为非负整数；任务结束日期按已有业务日规则计算，未提供时为空。
- 每个计划措施创建一个 `NURSING` 任务，`description` 来自 `action`，频次和日期来自措施；没有频次的措施仍保留活动任务，但不生成计划执行。
- `PRN`、`STAT` 或无频次继续遵循既有执行生成规则；本接口不主动调用执行生成器。护理工作台/既有生成入口按当前活动任务生成执行。
- 旧任务取消后不能再生成未来执行；旧执行行保持原样，新任务只能按新 `plan_item_id` 生成。

### 事务顺序

所有写操作由 Healthcare 在一个 `Pool.withTransaction` 中完成，并将同一 `SqlConnection` 传入 Nursing 内部方法：

1. 锁定 encounter；验证类型和活动状态。
2. 锁定精确 period；验证 `ACTIVE` 和 encounter 关系。
3. 锁定当前活动计划、措施和关联任务；检查是否存在 `IN_PROGRESS` 执行。
4. 计算下一个 `revision_no`，锁定同周期修订记录的序列化依据。
5. 写入复评。
6. 将旧计划、旧措施和旧活动任务收束。
7. 写入新计划和措施，写入新任务。
8. 写入修订关系，提交事务并组装响应。

任何校验、关联、任务写入或唯一约束失败都回滚第 5–8 步，不留下复评、计划、措施、任务或修订孤儿数据。

## 数据库与模块边界

### V406 迁移

在 Nursing 新增 `V406__create_care_plan_revisions.sql`，只新增修订关系表，不修改 `V400`–`V405`：

- `id VARCHAR(32) PRIMARY KEY`；
- `period_id VARCHAR(32) NOT NULL REFERENCES nursing_service_periods(id)`；
- `encounter_id VARCHAR(32) NOT NULL`，保持跨 schema 弱关联；
- `assessment_id VARCHAR(32) NOT NULL REFERENCES nursing_assessments(id)`；
- `previous_plan_id VARCHAR(32) REFERENCES nursing_plans(id)`；
- `new_plan_id VARCHAR(32) NOT NULL UNIQUE REFERENCES nursing_plans(id)`；
- `revision_no INT NOT NULL CHECK (revision_no > 0)`；
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`；
- `UNIQUE (period_id, revision_no)`；
- `period_id`、`assessment_id`、`previous_plan_id` 建查询索引。

迁移不回填既有计划，不删除旧数据；首次修订从 `revision_no = 1` 开始。服务端在精确 period 锁内处理同周期并发修订，数据库唯一约束作为最后一道防线。

### 依赖方向

- Healthcare 负责 encounter 资格、事务外层和公开 API。
- Nursing 负责评估、计划、措施、任务和修订关系的连接绑定读写。
- Nursing 不依赖 Healthcare Kotlin 库、不读取 Healthcare 表；`encounter_id` 由 Healthcare 校验后作为受控参数传入。
- 新增查询使用生成的 jOOQ 表类；不为本功能重构现有服务中的字符串表访问。
- 不新增 HTTP 回调、后台任务或跨产品依赖。

## API 验收口径

### 创建成功

对有唯一活动基线计划的活动养老入住提交修订：

- 返回 `201`；
- 复评、修订关系、新计划、计划措施和新任务各有对应行；
- `revision_no` 比上一条修订递增；
- 旧计划为 `DISCONTINUED`，旧活动措施为 `DISCONTINUED`，旧活动任务为 `CANCELLED`；
- 旧已完成/已取消任务、旧执行记录内容不变；
- 新任务精确绑定新计划措施、period 和 encounter；
- 列表、详情和 Nursing 时间线可读取新复评与新计划。

### 拒绝与回滚

至少定义以下结果：

- encounter 不存在：`404`；
- 非养老 encounter：`400`；
- 非活动 encounter、缺 period、非活动 period：`409`；
- 没有或有多个活动计划：`409`；
- 当前计划存在 `IN_PROGRESS` 执行：`409` 且所有相关表不变；
- 评估类型、日期、计划名称、措施、频次或日期非法：`400`；
- 客户端注入 ID、状态、metadata 或未知键：`400`；
- 旧计划、复评或任务任一步写入失败：事务整体回滚；
- 非同一 encounter 的 period、计划或任务不得出现在响应中。

5. 当前任务有 `IN_PROGRESS` 执行时修订被拒绝且页面数据不变；
6. 离院或去世后不能再创建修订，008 的医嘱收束语义不变。

用户反馈问题时提供：前置入住/周期/计划状态、最小操作步骤、预期结果、实际结果、脱敏响应和页面截图路径；不要求先建立完整自动化 fixture。

### 后置验证

只有在用户明确要求并提供独立可清理 `aceso_test`、已运行 API/UI 和隔离账户后，测试角色才补充 `CarePlanRevisionIntegrationTest` 与 `care-plan-revision.spec.ts`。后置验证不连接共享开发库、业务库或生产库，也不启动/停止用户管理的服务。

## 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 当前 period 有多个活动计划 | 修订可能选错基线 | 锁定后发现数量不是 1 即返回 `409`，不猜选、不自动迁移。 |
| 旧任务存在进行中执行 | 中途切换计划导致执行链断裂 | 在同一事务内检查 `IN_PROGRESS`，发现即整体拒绝。 |
| 计划、任务跨连接写入 | 产生半版本数据 | Healthcare 传递同一 `SqlConnection` 给 Nursing 内部协作。 |
| 修订后旧任务仍生成未来执行 | 新旧版本混杂 | 收束旧活动任务为 `CANCELLED`，执行生成逻辑只选择活动任务；不改写历史执行。 |
| 并发提交两个修订 | 出现重复版本 | 锁定精确 period，使用 `UNIQUE(period_id, revision_no)` 兜底。 |
| 现有服务使用字符串 jOOQ 表 | 扩大重构带来回归 | 新增查询使用生成表类，旧实现不在本期重构。 |
| 用户只做手动测试 | 边界回归证据不足 | MVP 只承诺编译、构建和主线手测；数据库/E2E 风险显式留存，不宣称已覆盖。 |
