## 1. 背景与问题定性

用户实测结论：**当前版本不存在「给用户分配角色」的能力**——不是界面漏做，也不是接口漏传参数，而是端到端的能力缺失。

| --- | --- |

## 3. 设计决策（本计划推荐口径，确认即冻结）

### D1 — 归属：Nexus Shared 持有「用户 ↔ 角色」分配（推荐）

- 角色目录已在 Nexus（018），**目录与分配同库**可以用外键保证「不能分配一个不存在的角色」，且不需要跨服务同步。
- 各产品后端已通过 `/crate-api/shared/v1/*` 消费 Nexus（settings/messages/files 同款路径），未来做权限判定时可继续从这里读。
- `subject_id` 使用 IDP 主体 ULID（跨系统引用，IDP 架构文档明确规定「A product stores it in an `identity_subject_id` column」）。

**否决的备选**：

- 备选 A：IDP `PATCH /subjects/{id}` 接受 `roles` —— 违反 `service-idp-go.md:202` 的「never product roles」边界；IDP 无法校验 Nexus 角色码，必然产生第二份角色目录；且 `DisallowUnknownFields` 的严格契约会被打开一个语义模糊的口子。
- 备选 B：Aceso Kotlin 自持分配表（新 lib + `V700+` 迁移）—— 写路径需跨服务向 Nexus 校验角色码，Trainova 复用时再抄一份，与 018 的集中式目录口径相反，收益仅是「产品自持」这一形式。

### D2 — 契约：资源化的 `subject-roles`，全量替换（推荐）

- 读取：`GET /crate-api/shared/v1/subject-roles?subject_ids=<逗号分隔 ULID>`（列表返回 JSON 数组，与 Nexus 既有约定一致）。
- 写入：`PUT /crate-api/shared/v1/subject-roles/subjects/{subjectID}`，请求体 `{"role_codes":["nursing.staff"]}`，**全量替换**该用户的角色集合。
- 理由：分配是「集合」语义，UI 是「勾选后保存」；全量替换避免增量接口的重复/竞态，且一次请求即可完成增删。空数组 `[]` 表示清空角色，合法。

### D3 — 角色删除：加外键 `RESTRICT`，被引用时返回 409（018 口径修订）

- 018 §1.2 写的是「删除直接移除目录项，不做引用检查」。有了分配表后该口径不再成立：已分配的角色被删会留下悬空引用。
- 推荐**失败要响**：`DELETE /roles/{id}` 在仍被分配时返回 `409 role-in-use`，提示先解除分配；不做级联静默清空。
- 影响面：`RolesPage.tsx` 已有 `deleteError` 展示（:49,:137,:260），无需新 UI；只需 Nexus 把 SQLite 外键错误（code `1811`）映射为 `Conflict`，并把文案写清。
- 本决定修订 018 §1.2 的对应条目；**不修改 018 正文**，以本计划为准。

### D4 — `subject_id` 校验：只校验 ULID 形态，不做跨服务探活（推荐，含残余风险）

- 写入时校验 `subject_id` 为 26 位 Crockford Base32 ULID；不存在的 subject 不会被发现（Nexus 无法在不引入 IDP 管理面依赖的前提下确认主体存在）。
- 备选：Nexus 用调用者 cookie 反查 IDP `GET /subjects/{id}`（该端点要求管理员会话）。代价是每次写分配都多一次跨服务调用，并让 Nexus 依赖 IDP 的管理面路由；**不在本轮**。
- 风险控制：UI 只从真实用户行发起分配，正常路径不会产生孤儿；残余风险记入第 12 节。

### D5 — 审计：本轮不写审计事件（推荐，含残余风险）

- Nexus 无审计表，IDP 的 `角色授予/角色撤销` 动作属控制面语义，本计划不越界写入 IDP。
- 分配变更的留痕（谁在何时改了什么）本轮只有 `granted_by_subject_id` + `created_at/updated_at`。
- 完整审计留给后续「操作审计」计划；残余风险记入第 12 节。

### D6 — 添加用户时可选角色：先建主体，再写分配（推荐）

- 「添加用户」弹窗新增角色多选；提交顺序为 IDP `POST /subjects` → Nexus `PUT /subject-roles/subjects/{新 ULID}`。
- 两个服务之间**无法原子**：若第二步失败，主体已创建成功。UI 必须区分提示「用户已创建，但角色分配失败」，并保留列表行内编辑作为补救路径。
- 不引入分布式事务、不做回滚删除（删主体是更危险的操作）。

### D7 — 列表展示：产品角色可编辑，控制面角色只读（推荐）

- 「角色」列主体展示 Nexus 分配（`role_code` 徽标，可点「编辑角色」）。
- IDP `subject.roles`（如 `identity.admin`）改为**只读的第二组徽标**，加「IdP 控制面角色」说明，不在本页编辑。
- 理由：两套角色语义不同（018 §1.2 的「并存歧义」风险），同列不做区分会让用户以为 `identity.admin` 可以在这里取消。

## 4. 数据模型（`service-nexus-shared/migrations/0003_subject_roles.sql`）

```sql
CREATE TABLE IF NOT EXISTS subject_roles (
    id                    TEXT PRIMARY KEY,                 -- ULID
    subject_id            TEXT NOT NULL,                    -- IDP identity_subjects.id（跨服务引用，无 FK）
    role_id               TEXT NOT NULL
        REFERENCES roles(id) ON DELETE RESTRICT,             -- 角色必须已存在于目录
    granted_by_subject_id TEXT NOT NULL DEFAULT '',         -- 操作者 IDP 主体 ID
    created_at            TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    updated_at            TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now')),
    UNIQUE(subject_id, role_id)
);

CREATE INDEX IF NOT EXISTS idx_subject_roles_subject ON subject_roles(subject_id);
CREATE INDEX IF NOT EXISTS idx_subject_roles_role ON subject_roles(role_id);
```

- `UNIQUE(subject_id, role_id)` 保证同一用户同一角色不重复；`PUT` 全量替换时按 `subject_id` 删除后重插（或取差集），结果集合稳定按 `role_code` 升序返回。
- 不新增 `roles` 表字段；不改 `0001`/`0002`。
- `ON DELETE RESTRICT` 是 D3 的实现基础（SQLite 需 `PRAGMA foreign_keys=ON`，连接池开启时确认）。

## 5. 接口契约（冻结，车道不得改）

前缀 `/crate-api/shared/v1`；认证同既有模块（`require_identity`，无会话 `401`）；错误体为 RFC9457 Problem Details。

```text
GET /subject-roles?subject_ids=<ulid,ulid>
  → 200 [ { id, subject_id, role_id, role_code, role_display_name,
            granted_by_subject_id, created_at, updated_at }, ... ]
  → 400 subject_ids 含非法 ULID
  （subject_ids 省略时返回全部，按 subject_id、role_code 升序；UI 始终显式传当前页 ID）

PUT /subject-roles/subjects/{subjectID}
  body: { "role_codes": ["nursing.staff", "pharmacy.manager"] }
  → 200 [ ...该 subjectID 的分配，按 role_code 升序... ]
  → 400 subjectID 非 ULID / role_codes 含目录不存在的 code / body 非法
  → 401 无会话
  （空数组 = 清空；重复 code 去重；每次请求记录 granted_by_subject_id = 调用者）

DELETE /roles/{id}
  → 204 未分配
  → 409 role-in-use（仍被分配，detail 说明受影响分配数）
  → 404 不存在
```

**明确不变**：

- `PATCH /crate-api/identity/v1/subjects/{id}` 仍只接受 `{status}` / `{temporary_password}`；发 `roles` 仍为 `400`。前端不得再尝试该路径。
- `GET /roles` 等 018 既有端点行为不变（除 DELETE 的 409，见 D3）。

## 6. 前端行为（`UsersPage.tsx`）

1. 列表加载：`listIdentitySubjects(page,20)` 后，用当前页 `id` 列表调用 `listSubjectRoles(ids)`，按 `subject_id` 建索引渲染徽标。
2. 角色列：Nexus 分配徽标（`role_code`）+ 行内「编辑角色」按钮；IDP 控制面角色单独一组只读徽标。
3. 编辑角色弹窗：`listRoles({page_size:100})` 拉取全量目录（最大页 100，规避 018 「仅第一页 20 条」风险）；多选 checkbox；保存调用 `replaceSubjectRoles(subjectId, codes)`；提交中禁用按钮；失败保留选择并展示错误；成功后关闭并刷新当前页。
4. 目录为空时提示「请先在『角色』页创建角色」并禁用保存。
5. 添加用户弹窗：新增角色多选（同上数据源）；`createIdentitySubject` 成功后调用 `replaceSubjectRoles`；第二步失败时提示「用户已创建，角色未保存：<原因>」，并刷新列表让用户行内补配。
6. 错误一律经 `errorMessage()` 展示，不出现 SQL/堆栈；只经 `@pitchfork/shared/aceso` 请求，不直接 `fetch`。

- **不做鉴权落地**：不做 `require_role`/权限中间件，不让角色影响任何业务接口的准入（018 也已把 RBAC 中间件列为后续）；本计划只交付「分配 + 展示 + 可编辑」。
- 不做角色继承、互斥、有效期、批量导入/导出。
- 不做 Nexus 列表分页控件（沿用 018 口径）。
- 不改 IDP（含 `PATCH /subjects/{id}`、`identity_subject_roles`、审计写入）。
- 不重构 Kotlin `libs/permissions`（现存但未被 aceso 挂载的 RBAC 库），不接 `nursing.staff` 到任何后端鉴权。
- 不动 `ui-astro/packages/ui`、Trainova 应用、其它 lib 与迁移号段。
- 不启停用户管理的服务（8420 / 8422 / 4324 / 5432 / 8421 开发实例）。

## 9. 验收口径

1. **可分配**：在用户页对某用户勾选 `nursing.staff` 保存 → 重新加载页面，该用户角色列显示 `nursing.staff`；`GET /subject-roles?subject_ids=<id>` 返回该分配且 `granted_by_subject_id` 为当前操作者。
2. **可解除**：取消全部勾选保存 → 该用户分配清空（列表 `-`），`GET` 返回空数组；其余用户不受影响。
3. **可建即配**：添加用户时勾选角色，创建成功后列表即显示该角色；故意让第二步失败（如传目录中不存在的 code）时，提示明确且用户行仍可编辑。
4. **校验**：未知 `role_code` → 400（detail 指名 code）；非 ULID `subject_id` → 400；重复 code 去重后只落一条；无会话 → 401。
5. **引用保护**：已分配角色执行 `DELETE /roles/{id}` → 409，角色仍在目录；解除分配后可删 → 204。
6. **回归**：018 角色目录 CRUD 行为不变（除 DELETE 409）；`cargo test`、`cargo check` 全绿；`pnpm --filter @pitchfork/aceso build` 0 error；`git diff --check` 干净；IDP 未改动（`git status` 不含 `service-idp-go/`）。
7. **两套角色不混淆**：同时具备 IDP 控制面角色与产品角色的用户，两类徽标视觉可分、控制面角色不可在本页编辑。

**集成测试发现的缺陷（已修）**

`assigned_role_cannot_be_deleted` 首次执行失败：删除仍被分配的角色返回 `500` 而非 `409`。根因是
SQLite 的 `ON DELETE RESTRICT` 由内部触发器实现，报 **`CONSTRAINT_TRIGGER(1811)`**，而不是
`CONSTRAINT_FOREIGNKEY(787)`；`src/roles/mod.rs` 的判定已改为同时认 `19/787/1811` 并以
`message contains "FOREIGN KEY"` 兜底。修复后该用例通过。
