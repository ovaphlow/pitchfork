# Aceso 库存基础数量优先与包装规格辅助实施计划

更新时间：2026-08-09

状态：开发候选版本（残余 P2 已修复并交付，默认验证通过，待测试复验/评审确认与隔离库/浏览器验收）

相关决策：[ADR-001：库存以最小可发放／可消耗单位记账](../decisions/ADR-001-inventory-base-unit-of-measure.md)。
本计划在实施第 0 步完成 ADR 的相应收敛后，以本文件的范围和验收口径为准。

## 1. 决策、目标与术语

### 1.1 已确认的切换决策

产品尚未形成正式版本，Aceso 的开发数据库、候选迁移、候选 jOOQ 源和 API 均允许破坏性调整。后续
Inventory、Pharmacy 和 Nursing 的库存余额、锁定量、库存流水、单位成本以及**默认的后端请求和响应**
都只使用物资的**基础单位／基础数量**。物资可选维护 `package_unit + package_size`，仅供页面展示和
盘点辅助；它不产生第二套库存数量、成本、锁定量或流水，也不让客户端选择业务记账单位。系统删除
`PACKAGE` / `SPLIT` 枚举、`split_unit`、`split_ratio`、旧换算端口和历史兼容投影。

“基础单位”是物资可合法发放／可实际消耗的最小业务单位，而不是物理上无限可分的最小颗粒：

- 阿莫西林可以定义为“片”，数量精度为 `0`；入库、发药、退药和护理消耗均提交片数；
- 允许体积分装的消毒液可以定义为“mL”，并由物资设置 `0..6` 位小数精度；
- 无菌最小包、不可回库的单支注射剂或整瓶药液可分别定义为“包、支、瓶”，数量精度通常为 `0`；
  这不是“整包模式”，而是该物资本身的基础单位。

包装规格描述一个包装包含多少基础单位，例如“1 盒 = 24 片”。页面可据此将基础数量显示为“2 盒 + 5
片”，或在盘点辅助输入中先求得基础数量；传入后端的常规库存、药房和护理请求仍是基础数量。若未来
提供专门的整包输入接口，服务端必须由受控物资规格精确换算出基础数量，并在响应中保留基础数量作为
权威值；客户端不得传换算率、伪造基础数量或包装成本。

### 1.2 目标终态

| 范围 | 终态 |
| --- | --- |
| 物资 | 一个 `base_unit` 和一个 `quantity_scale`；可选 `package_unit + package_size` 作为展示／盘点辅助规格；存在库存或确认事实后不可修改基础单位、精度和已使用的包装规格。 |
| 库存结存 | `stocks.quantity`、`stocks.locked_quantity` 直接表示基础数量；无并行 `base_quantity` 列。 |
| 库存流水 | `stock_operation_details.quantity`、`unit`、`unit_cost`、`total_cost` 都是基础数量/基础单位/每基础单位成本/总成本的不可变快照。 |
| 药房单据 | 发药、退药、申领、调拨、采购订单与收货的数量均为基础数量；单位由服务端从物资快照写入，不接受客户端选择。 |
| 护理耗材 | 依据 `stock_id` 确定物资和基础单位，只接受基础数量。 |
| API 与 UI | 默认数量字段均为基础数量，成本均为每基础单位成本；物资 API 和页面可读写／展示 `package_unit`、`package_size`。不接受、不返回 `PACKAGE`、`SPLIT`、`split_unit`、`split_ratio`、`unit_spec_id`、`input_quantity`、`conversion_ratio` 或 `split_quantity`。 |

### 1.3 明确不在本期范围

- 供应商档案、包装条码、供应商箱规、采购价格协议、发票、供应商退货和采购退货；
- 完整盘点单、账实调整、报损、召回、自动补货、成本报表或先进先出；本期只提供物资包装规格和页面盘点辅助，不新增盘点业务流程；
- 医嘱、发药、护理给药的状态机重构，或将发药与实际给药合并；
- 保留任何现有开发数据库的数据，或为历史 API 提供兼容端口；
- 修改 Trainova、共享服务或未经本计划列出的产品边界。

## 3. 实施门槛与破坏性切换规则

### 3.1 实施前必须满足

1. 用户业务确认每种物资的 `base_unit`、`quantity_scale` 和不可拆分规则，至少覆盖片/粒、支/瓶、
   液体、无菌组合包装与普通耗材；
2. ADR-001 明确基础数量是默认后端请求、响应和全部库存事实的唯一权威口径；`package_unit + package_size` 仅用于展示和盘点辅助，不能形成旧兼容输入或第二套数量；
3. 评审确认 015 候选的 V202/V407、`UnitConversionService`、`PACKAGE/SPLIT` 端口和生成源不会进入待合并变更；
4. 测试提供独立、可恢复、可清理的 `aceso_test`。禁止连接共享开发库、业务库或生产库；
5. 开发和测试确认所有本地 Aceso 开发数据库都可重建。若有必须保留的数据，本计划停止，不以
   “尚未发布”为由覆盖或重写该数据。

### 3.2 数据库重建规则

本计划授权的是**未发布 Flyway 基线的重写**，不是对已有业务数据库做原地迁移：

- 开发在代码审查后修改 V200/V201/V203、V300--V303、V402/V403，使其从空库直接创建基础数量权威模型及可选包装规格；
- 开发删除 V202、V407 及其 jOOQ 生成的表/列，不创建 `MIGRATION_BLOCKED`、旧规格表、回填或兼容列；允许 `materials.package_unit/package_size` 及其真实 jOOQ 生成源；
- 已应用旧校验和的本地数据库必须由其所有者或测试单命令入口删除并重建，不能通过 `outOfOrder`、
  手工更新 Flyway 历史或直接 UPDATE 业务表规避；
- 测试只在 `aceso_test` 验证“空库 -> 当前所有迁移 -> 当前 jOOQ/API”，并在报告中记录清理结果；
- 任何环境被发现包含需保留数据时，立即停止破坏性路径，由计划和用户重新决定迁移方案。

## 4. 数据与 API 契约

### 4.1 Inventory 基线

开发修改 `libs/inventories` 的 V200/V201，并保留 V203 的物资包装规格：

| 对象 | 必须保留/新增 | 必须删除 |
| --- | --- | --- |
| `materials` | `base_unit VARCHAR NOT NULL`、`quantity_scale SMALLINT NOT NULL CHECK (0..6)`、可选且成对存在的 `package_unit VARCHAR` 与 `package_size NUMERIC(20,6) CHECK (> 0)`、状态、批次控制、成本方法和审计字段 | `split_unit`、`split_ratio`、`unit_model_status`。 |
| `stocks` | `quantity NUMERIC(20,6)`、`locked_quantity NUMERIC(20,6)`、`total_cost NUMERIC(24,8)`，并约束 `quantity >= locked_quantity >= 0` | `base_quantity`、`locked_base_quantity` 及任何包装数量投影。 |
| `stock_operation_details` | `quantity NUMERIC(20,6)`、`unit`（基础单位快照）、`unit_cost NUMERIC(24,8)`、`total_cost NUMERIC(24,8)` | `split_quantity`、`unit_spec_id`、`input_quantity`、`input_unit`、`conversion_ratio`、`base_quantity`、`base_unit`、`input_unit_cost`、`base_unit_cost`。 |
| 计量规格/异常表 | 不保留 | `material_unit_specs`、`inventory_unit_migration_issues` 及相应约束、索引、jOOQ 表。 |

服务端从十进制文本构造 `BigDecimal`，数量精度以 `RoundingMode.UNNECESSARY` 验证，拒绝超精度而不静默
进位或四舍五入。库存锁定、可用量、批次、成本累计与所有操作均只读取和写入这一套数量。

### 4.2 写入请求和响应

新 API 不提供兼容格式。服务端对未知字段返回 `400`，不忽略旧字段。所有数量、单价、总成本和
`package_size` 均以 JSON 十进制文本传输，例如 `"48"`、`"0.125"`、`"12.50"`；不得使用 JSON
`number` 或 `Double` 作为这些字段的传输或响应类型，以免截断合法的 `NUMERIC(20,6)`／`NUMERIC(24,8)`
值。非金额、非数量的计数、分页和评分等字段不受此规则影响：

| 用例 | 请求中允许的数量字段 | 服务端确定的单位/成本语义 |
| --- | --- | --- |
| 手工入库 | `items[].quantity`、`items[].unit_cost` | 数量是物资基础数量；成本是每基础单位成本。 |
| Pharmacy 发药/退药 | `dispensed_quantity` / `quantity`、必要的批次与业务字段 | 数量是基础数量；物资单位由服务端写入明细快照。 |
| Pharmacy 申领/调拨 | `requested_quantity` / `approved_quantity` | 全部是基础数量；预留、释放和转移同口径。 |
| Pharmacy 采购/收货 | `ordered_quantity` / `received_quantity`、`unit_cost` | 数量和单位成本均为基础口径。 |
| Nursing 耗材消耗 | `consumptions[].stock_id`、`consumptions[].quantity` | `stock_id` 确定物资、批次和基础单位；客户端不传单位、规格或换算率。 |

库存、药房和护理响应的业务数量及单位均为基础口径；物资响应可额外返回 `package_unit`、`package_size`
供页面展示或盘点辅助。列表仍遵从 `{ "records": [...], "meta": { "total": N } }`。包装规格不能替代、
覆盖或并行保存任何库存／流水数量。

## 5. 开发实施顺序

### 5.1 第 0 步：废弃候选并冻结目标

1. 开发从待合并集合删除 015 候选的 V202/V407、`UnitConversionService`、`MaterialUnitSpecs`、
   `InventoryUnitMigrationIssues` 及其 jOOQ 源；
2. 计划更新 ADR-001 和 015 替代说明，删除历史兼容和 `PACKAGE/SPLIT` 输入验收口径，同时保留基础数量优先的包装规格展示／盘点辅助口径；
3. 评审确认分支中没有将旧候选与本计划混合的提交；测试不对 015 候选执行数据库验收。

### 5.2 第 1 步：重写未发布数据库基线并生成 jOOQ

1. 在 V200/V203 中把物资单位模型改为 `base_unit + quantity_scale`，并保留可选的 `package_unit + package_size` 展示／盘点辅助规格；
2. 在 V201 中将库存和库存明细改为唯一基础数量模型，移除 `PACKAGE` / `SPLIT` 检查约束；
3. 在 V402/V403 中把护理耗材关联改为基础数量和基础单位快照，删除 `split_quantity` 与枚举约束；
4. 在 V300--V303 中把 Pharmacy 明细数量、单位成本和单位快照改为基础口径，删除默认/固定的
   `PACKAGE` 值、`SPLIT` 枚举和 `split_quantity`；
5. 删除 V202/V407；在授权的空 `aceso_test` 运行当前 Flyway 基线，再运行实际 `generateJooq`；
6. 提交真实生成源以及 `Keys`、`Indexes`、`Tables` 变更，不提交 `build/tmp` 或手工伪造的生成文件。

### 5.3 第 2 步：收敛 Inventory 服务、路由和单元测试

1. 将 `MaterialService` 的创建/更新契约改为一次性提交 `base_unit` 与 `quantity_scale`，并允许成对维护
   `package_unit + package_size`；删除 `activateUnitModel`、旧规格 CRUD、默认规格、拆零字段和历史兼容 JSON 字段；
2. 删除 `UnitConversionService`、`resolvePackagePort`、`resolveSplitPort`、`legacyDetailColumns`、
   `PackageInboundCommand`、`PackageOutboundCommand` 和所有 `*Package*` 库存服务方法；
3. 让 `StockService` 的入库、出库、预留、释放、调拨和采购收货只携带基础 `quantity` 与每基础单位成本，
   一次写入 `stocks.quantity`、`locked_quantity` 和流水数量；
4. 更新 `InventoriesRoutes`、`MaterialRoutes`、响应序列化及错误映射：物资包装规格字段可读写；库存操作默认只接受十进制文本形式的基础 `quantity` 与 `unit_cost`，并将数量／成本字段序列化为十进制文本；旧字段和数值 JSON 输入一律 `400`，不存在过渡回退；
5. 用基础数量测试替换 `PACKAGE`、`SPLIT`、旧换算比、规格切换、双写和旧字段投影测试；新增包装规格成对校验、页面／盘点辅助换算后提交基础数量、最大合法精度文本原样往返及数值 JSON 输入 `400` 的测试。

### 5.4 第 3 步：收敛 Pharmacy 的数量口径

1. 将 `PharmacyPorts` 的 `Package*` 数据类、接口方法和实现改为不含包装语义的库存端口；
2. 修改 `DispenseService`、`ReturnService`、`RequisitionService`、`PurchaseOrderService`：删除
   `unit == "PACKAGE"` 限制，数量、可退数量、预留量、订单累计量和成本均直接按基础单位处理；
3. 更新相应路由和 Shared API：客户端不可传 `PACKAGE`、`SPLIT` 或任意单位选择；数量和成本请求／响应均使用十进制文本；
4. 保持现有医嘱有效性检查、幂等、同事务库存写入、退药上限、批次校验和状态机边界，不以单位切换
   顺带改变这些规则；
5. 更新非数据库测试，覆盖基础数量发药、部分退药、申领预留/释放/调拨和采购部分收货。

### 5.5 第 4 步：收敛 Nursing 耗材执行

1. 将 `TaskExecutionService.ConsumptionInput` 和 `InventoryConsumptionService.ConsumptionItem` 收敛为
   `stockId + quantity`；
2. 删除护理路由对 `unit`、`quantity`、`split_quantity` 和规格输入的互斥分支，只校验基础数量为正且
   适合该物资精度；
3. 护理耗材关联和关联库存操作明细必须在同一事务内写入相同的基础数量、单位和成本，并以十进制文本响应；
4. 保持任务状态流转、幂等重试和失败全事务回滚；测试以基础单位快照比较重复提交。

### 5.6 第 5 步：更新 Shared API 与 Aceso UI

1. 保留 `@pitchfork/shared/aceso` 中物资 `package_unit`、`package_size` 类型；删除拆零、旧规格、换算率和 `PACKAGE/SPLIT` 兼容接口／类型；所有默认数量、成本和 `package_size` 均使用 `DecimalText`，与基础口径 API 一致；
2. 库存页面可配置并展示物资包装规格；展示和盘点辅助可以由“整包数 + 余数”推导基础数量，但提交后端的库存操作仍只有原始十进制文本形式的基础 `quantity` 与每基础单位 `unit_cost`，不得先转换为 JavaScript `number`；
3. 入库、发药、退药、申领、采购和护理消耗表单均以基础单位为标签、校验和默认提交口径；
4. 删除 Nursing 页面 `PACKAGE/SPLIT` 选择、旧包装预览和由包装可用量驱动库存操作的提示；
5. 删除 Pharmacy 页面基于 `unit === "PACKAGE"` 的筛选、显示与可退条件；可显示物资包装规格，但不得把它作为发药、退药、申领或采购收货的业务单位；
6. 页面必须仍通过 `@pitchfork/shared/aceso` 请求 API，且在窄屏显示长单位名、六位数量、批次和错误文本
   时不重叠。

### 5.7 第 6 步：清理、审查与交付
