#### P0 范围补充（L1 实现期发现）

修完 9 处 `"t"` → `"true"` 后，同一用例内又暴露**第二处**既有断言缺陷：

#### P0 第三处缺陷与确定性要求（V2 验证期发现，追加 L7 车道）

L1 修完两处断言后，**真库套件仍不确定绿**：`closeExpiredOrders真库收束到期医嘱且保留end_time并零改写护理执行`
在定点重复 14 次中失败 8 次（约 57%），失败于 `MedicalOrderIntegrationTest.kt:1110` 的
`updated_at 必须与收束时刻同源`。**根因是产品侧精度不一致，不是断言缺陷**：

- 产品用**同一个 `now`** 写两处：`metadata.convergence.at = now.toString()`（JSON 文本，纳秒 9 位）
  与 `.set(MEDICAL_ORDERS.UPDATED_AT, now)`（JDBC 绑定 → `TIMESTAMPTZ` 只到**微秒**，第 7 位起被截断）；
- 断言 SQL `updated_at = (metadata->'convergence'->>'at')::timestamptz` 中，PostgreSQL 对文本 cast 到
  `timestamptz` 是**四舍五入**：`…972084815` → `…972085`（比列值大 1µs），`…240898350` → `…240898`（相等）；
- ⇒ **亚微秒部分 ≥ 500ns 时必然不等（约 50%）**，L1 的修复把「恒失败」变成了「约半数失败」。

裁定：**修产品，不放宽断言**（断言「同一时刻两处同源相等」本身合理）。L7 新增文件私有
`auditNow() = OffsetDateTime.now().truncatedTo(ChronoUnit.MICROS)`，凡「同一个 `now` 同时写 JSON 时间戳字段
与 TIMESTAMPTZ 列」的孪生点统一使用；`MedicalOrderService` 内恰好 2 个孪生点
（`convergence.at`+`updated_at`、`order_details.material_bound_at`+`updated_at`）。
`TaskExecutionService.convergencePayload` 经核对**不同源**，不改。

**P0 验收口径加严**：除「3 例不再失败」外，还必须给出**真库定点连续 ≥10 次全绿**的逐次数据
（修复前基线：10 次里 4–8 次红）。

### P2 IdP 依赖降级（L2）
现状：`Main.kt` 的 `idpSessionAuthHandler`（`private`）无上游超时，`onFailure` 一律 401 → 前端 `aceso.ts:432`
只对 401 跳登录，于是「IdP 抖动」被误判为「会话失效」。已把空闲窗口从 30m 放宽到 2h，但这条与 TTL 无关。

要求：
1. 上游加显式超时（连接 + 请求整体），默认 3000ms，允许 `identity.session-timeout-ms` 配置覆盖；
2. 区分两类失败：
   - 上游 **401/403** → 本地 `401 {"error":"authentication required"}`（会话无效，前端登出，行为不变）；
   - 上游 **5xx / 连接失败 / 超时 / 无响应** → **`503`** + `Retry-After: 5` + `{"error":"identity service unavailable"}`
     （依赖不可用，前端不登出，只报错）；
   - 上游 200 但缺 `subject_id` → 保持 401（响应形状异常，按会话无效处理，与现状一致）。
3. 为可测性把该 handler 从 `private` 放宽为 `internal`（同模块测试可访问），**不得**改变挂载方式与顺序；
4. 新增测试（不访问数据库）：起一个假 IdP `HttpServer`，覆盖 200+subject_id / 401 / 500 / 挂起不响应 四类，
   断言本地状态码与 `Retry-After`；挂起用例断言在超时窗口内返回 503 而不是无限等待。
   现成骨架可参考 `apps/aceso/src/test/.../DefaultAuthenticationTest.kt`（它用假 sessionAuth，不覆盖真实 handler，
   因此本项必须新增真实 handler 的测试）。

### P4 剂量预填（L3 后端 + 契约；L4 前端）
根因：开嘱表单只录 `dose`（剂量强度，如 `500mg`）与 `unit`（如 `片/次`），**没有「每次基础单位数量」**，
因此药房发药量无法从医嘱推导，只能手填 1（031 的 W7 到此为止）。

**契约（父代理已在集成分支冻结，车道不得再改）**：
- 医嘱明细新增允许键 `order_details.dose_quantity`：字符串十进制文本，> 0，最多 6 位小数（沿用数量精度口径）；
- 药房待接方行（`listMedicationOrdersForPharmacy` 的记录）新增：
  `dose_quantity: string | null`、`daily_dose_count: number | null`、`duration_days: number | null`、
  `prescribed_total_quantity: string | null`；
- 给药来源行（`GET /nursing/v1/executions/{id}/administration/sources`）新增 `dose_quantity: string | null`；
- TS 类型已同步（`packages/shared/src/aceso.ts` 的 `PharmacyMedicationOrder`、`MedicationAdministrationSource`）。

后端口径（L3，服务端算，前端不得复制频次规则）：
- `daily_dose_count`：**只对「每日给药」频次有定义** —— `QD=1`、`BID=2`、`TID=3`、`QID=4`；
  其余非每日频次（`QOD`/`QW`/`BIW`/`TIW` 等）一律 `null`，`PRN`/`STAT`/空白/未知也 `null`。
  **不得**用 `scheduleTimes` 条数冒充每日次数（见下方「频次语义决策」）。
- `duration_days`：`order_details.duration_days`，缺失 → `null`；
- `prescribed_total_quantity`：
  - `dose_quantity` 与 `daily_dose_count` 与 `duration_days` 三者齐备 → 乘积十进制文本；
  - `frequency_code = "STAT"` → 等于 `dose_quantity`（一次性）；
  - 其余（含非每日频次、`dose_quantity` 缺失、缺 `duration_days`）→ `null`（**不猜、不预填**）。

#### 频次语义决策（2026-09-30，L3 实现期提出并由父代理裁定）

L3 发现 `FrequencyCalculator.defaultTimes` 的「已知频次」除 `QD/BID/TID/QID` 外还含 `QOD/QW/BIW/TIW`，
它们**不是每日给药**。若按「已知 → `scheduleTimes` 条数」字面实现，`daily_dose_count` 会得到 1，
于是 `QW + dose_quantity=1 + duration_days=28` 会把预填量高估成 `28`（实际疗程约 4 次），`QOD` 则 2 倍高估。
发药弹窗会用该值预填，属**用药安全**问题。

**裁定：只对每日频次给出次数，非每日频次返回 `null`（不预填，药师手填 + 既有频次/疗程提示）。**
理由：契约已定「无法可信推导 → null，不猜」；宁可退回人工，也不给出可能高估的预填值。
（留作后续扩展：若产品确认非每日频次的完整排程，可用既有公开的 `plannedTimesForDate` 在疗程区间内精确累加，
而不是引入前端换算或新的近似规则。）

`dose_quantity` 输出：按 D5 去尾零规范化（`"1.500"` → `"1.5"`），与同文件 `decimalApi` 同口径，全程 `BigDecimal`、不经 `Double`。

前端口径（L4）：
- 开嘱表单新增「每次数量（基础单位）」输入（数值文本，可留空），提交为 `order_details.dose_quantity`；
  仅在填入时才可能产生预填，留空时行为与现状完全一致（回归安全）；
- 发药弹窗：`prescribed_total_quantity` 非空则预填数量，并显示依据（每次 × 每日 × 天 或「一次性」）；
  为空则保留 1 与 031 已加的频次/疗程提示；库存上限校验不放松，药师仍可手改；
- 给药弹窗（已服/部分服）：来源行 `dose_quantity` 非空则用 `min(dose_quantity, remaining_quantity)` 预填实际给药数量；
  为空保持手填；
- 前端不得实现「频次 → 每日次数」的换算。
