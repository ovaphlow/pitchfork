# 流水线教训（loop-lessons）

本文件由评审 worker 在验收通过时追加「流程类教训」（非代码缺陷），
计划 worker 起草计划前必读，避免同类问题反复发生。

## 已记录教训

1. **验证已提交的改动不要用工作区 git diff**
   开发角色会把实现提交到分支，工作区 == 索引 == HEAD 时 `git diff` 为空属正常。
   验证已提交改动应使用 `git diff <sha>~1 <sha>`、`git show --stat <sha>` 或
   `git diff 基线...HEAD`；测试清单中的命令必须与流水线的 git 提交流程对齐。

2. **计划编号写入前要检查占用**
   docs/plans/NNN.<slug>.md 的编号由脚本分配，但并发/手工建卡可能撞号；
   计划角色写入前必须确认 NNN 未被占用，被占用则用当前最大编号 +1 并注明实际编号。

3. **测试命令语义错误要修正设计，不要重解释结果**
   测试角色发现命令语义有误时，应修正命令设计并在报告中记录（原命令/原因/修正后命令），
   然后字面执行、如实报告；绝不允许把失败重解释为通过。

4. **评审只抽查，不全面复跑**
   全面复跑测试清单是测试角色的职责；评审只重跑与结论相关的 1-3 条关键命令，
   其余靠读 diff 与测试报告判断，避免重复劳动。

5. **评审更新计划状态字段必须提交，保持分支干净**
   评审通过时把计划「最终状态」更新为已完成，若该字段改动只留在工作区而不提交，
   会遗留脏工作区，阻塞后续合并命令；批准通过后计划停留在「待实施」也使最终状态
   无法落入 git 历史。评审通过时须把计划状态字段的改动一并提交（docs(plan) 提交）。
