## 1. 背景与根因

用户在 Aceso 手工测试清单第 5 条报告：用药医嘱派生的护理任务只显示医嘱正文，
护士看不出是什么药、几片、怎么给。

根因链（均可在提交前代码中核对）：

| # | 位置 | 事实 |
|---|---|---|
| 1 | `libs/healthcare/.../MedicalOrderService.kt:184` | `taskService.createOrderTask(..., description = input.orderContent, ...)` — 护理任务描述直接取医嘱正文（自由文本，如「高血压引起的头痛」） |
| 2 | `libs/healthcare/.../MedicalOrderService.kt:66-71` | 结构化事实在 `medical_orders.order_details` JSONB（白名单键 `drug_name` / `dose` / `unit` / `route` / `material_name`…），与任务描述无关联 |
| 3 | `libs/nursing/.../TaskService.kt:53-70`（改前） | `toJson` 只投影 `nursing_tasks` 自身列，不带绑定医嘱 |
| 4 | `libs/nursing/.../TaskExecutionService.kt:1121-1140`（改前） | `todayExecutions` 的 `allColumns` 只到 `patient_name`，今日工作台同样看不到药品 |
| 5 | `libs/nursing/.../MedicationAdministrationService.kt:438-461`（改前） | 给药/MAR 读模型只带 `task_description`，与任务同病 |

| 7 | `ui-astro/apps/aceso/src/components/NursingPage.tsx:1187,1542`（改前） | 今日执行表与长者任务表只有「任务」列 |
| 8 | `ui-astro/apps/aceso/src/components/NursingPage.tsx:2050`（改前） | 医嘱核对面板读 `details.dosage`，而白名单键是 `dose`（`MedicalOrderService.kt:70`）→ 剂量从未渲染 |

`order_item_id → medical_orders.id` 关联读取，历史任务行同样被修好——这是重写描述做不到的。

## 3. 设计要点

1. **JOIN 与列歧义**：`medical_orders` 与 `nursing_tasks` 共有 `id/status/metadata/created_at/encounter_id`，
   未限定列名在 PG 会报 `column reference is ambiguous`。因此
   - `TaskService` 读路径给任务表起别名 `nt`、医嘱表 `mo`，`WHERE`/`ORDER BY` 全部用
     `DSL.field("nt.列名", …)` 限定（别名表的 `Table.field(String)` 在 jOOQ 3.19 返回可空，
     故不使用）；计数查询保持原样（未限定列、无 JOIN），行数与 SQL 语义不变。渲染结果：
     `select "nt".*, mo.order_details as "order_details", mo.order_type as "order_type" from "nursing"."nursing_tasks" as "nt" left outer join "healthcare"."medical_orders" as "mo" on nt.order_item_id = mo.id …`
   - `TaskExecutionService.todayExecutions` 只在 `baseSelect` 上加 JOIN 与两列；
     `countQuery` / `overdueTotalQuery` 不加 JOIN（`medical_orders.id` 是主键，1:1，但不动计数口径更稳）。
   - `MedicationAdministrationService` 的 `listAdministrations`（baseFrom）与 `readAdministration`
     加同一 LEFT JOIN；其 COUNT 查询不变；条件/排序本就全部带 `ma.`/`p.` 限定，无歧义。
2. **形状一致**：`TaskService.toJson` 用 `row.getColumnIndex(列) >= 0` 探测后再取值，因此
   同一函数既能服务带 JOIN 的 `list/get`，也能服务 `lockOrderTask`/`lockActivePlanTasks`/
   `CarePlanRevisionService` 等不带该列的行；`create`/`createOrderTask`/`createPlanTask`
   显式返回 `order_details: null, order_type: null`。
3. **展示推导唯一化**：`formatOrderItemLabel(orderType, orderDetails)` 为医生页与护理页共用；
   MEDICATION 生成 `药名 剂量 单位 途径`（空值跳过，药名优先 `drug_name`，缺失退回
   `material_name`），其它类型只显示主明细字段，无可用明细返回 `null`。

## 7. 残余风险与未验证项

1. **JOIN 未在真实 PostgreSQL 上执行**（无库授权）：仅以 jOOQ 渲染 SQL（见 §3.1 引文）与
   字符串断言间接证明无列歧义；实际执行、行数与 NULL 行为未实测。
2. **E2E 未运行**：静态检查 `apps/aceso/e2e/*.spec.ts`，未发现按列序号/列数断言的用例
   （今日表定位用 `hasText: "计划时间"` + 行内文本）；`nursing-consumption.spec.ts` 用
   `modal.locator('input[type="number"]')` 计数，弹窗新增为文本行，不受影响；
   `medical-orders.spec.ts` 的「剂量：0.5g」来自 `OrdersPage` 明细弹窗的 `ORDER_DETAIL_LABELS`（未改）。
   新增文案「药品 / 项目」「药品：」无既有断言。以上均为静态推理，未在浏览器验证。
3. **交班/时间线/统计的纯文本摘要未改**，仍只有医嘱正文；如需一致需另立计划（不在本次范围）。
4. **`TaskExecutionService.list()/get()` 未加字段**：为避免 `nursing_task_executions` 与
   `medical_orders` 的 `id/status/metadata/created_at` 歧义扩散（需整体改写该读模型），
   本轮按设计只覆盖今日工作台。
5. **医生页列的口径微调**：`formatOrderItemLabel` 对 MEDICATION 增加 `material_name` 回退
   （设计明确要求，服务 025 之前的历史行），因此该列在「有 `material_name` 但无 `drug_name`」

   （`TaskServiceMedicalOrderTest`、`CarePlanRevisionServiceTest` 的 `mockRow` 增补
