## 3. 调度者裁决（用户不在场，记录取舍）

- **D1 不新建床位主数据。** 以 `encounters.department/ward` 为占用事实来源做区间校验 + 只读占用查询 + 表单提示。理由：床位主数据是净新增域（表+种子+服务+路由+UI），而校验的正确性不依赖主数据；在自由文本之上仍能拦住「同床位同时段重复入住」。残余 R1：`'001'` 与 `'01'`/`' 001'` 仍可能被当成不同床位，故比较时对 `department`/`ward` 做 `trim` 后精确比较（不做大小写/全角归一）。
- **D2 占用口径 = 半开区间 `[admit_date, discharge_date)`。** 冲突判定：存在另一条 `ELDERLY_CARE` 记录 `O`，`O.admit_date < X` 且 `coalesce(O.discharge_date, ∞) > S`（`S`/`X` 为本次入住的开始/结束，新建时 `X = ∞`）。首尾相接不算冲突（07:00 离院、10:00 再入住通过；恰好同一时刻也通过）。仅覆盖 `ELDERLY_CARE`（与 V501 同口径），非养老 encounter 不参与（残余 R2）。
- **D3 同一长者区间重叠也拦。** 补 V501「只拦两条同时 ACTIVE」的缺口：已离院记录与新入住区间重叠同样拒绝。
- **D4 告警归属 = 请求体优先 + 唯一活动入住自动挂接。** 请求体给了 `encounter_id` 就用它（沿用既有归属校验）；未给且该长者恰有一条 `ACTIVE` `ELDERLY_CARE` 时由服务端自动挂接（V501 部分唯一索引保证唯一）；无入住（居家/社区）仍为 `null`，保持 `VitalSignServiceTest.kt:211-224` 的既有语义。多段入住时由表单让操作者显式选择。
- **D5 数量去尾零放在后端响应层。** `stripTrailingZeros().toPlainString()` 值不变、文本变短；前端格式化需要改约 20 处渲染点，后端只改 7 个构造点。同步修正「把 6 位文本当契约」的测试：断言改为**数值相等**（`BigDecimal(...).compareTo(...) == 0`）而不是字面串相等，保留「不经 Double 截断」的原意。
- **D6 术语**：用户可见「老人」→「长者」；「结算收束」→「结算关账」；「已结算收束」→「已关账」。只改 UI 文案与中文注释，不改后端英文错误串。
- **D7 逾期/通知不做**（见 §1.1）。
- **D8 收费链路不改**（见 §1.1）。
- **D9 首屏标题用内联 head 脚本。** `DashboardLayout.astro` 增加可选 `titleDomainLabels` 属性，用 `is:inline` + `define:vars` 的**经典（非 module）**脚本在首屏前读 `localStorage["aceso-domain"]` 改写 `document.title`；四个域相关页面把静态 `title` 改为基础（医疗）名并与 `Sidebar` 的 `domainLabels` 同源。理由：静态构建期无法得知域，`BreadcrumbTitle`/`Sidebar` 都是 `client:only`，只有同步内联脚本能消除闪烁；既有主题脚本是 `type="module"`（deferred），不能照抄。
- **D10 照护计划前置校验放服务端。** 优先放 `PlanService.create`（`ConflictException` → 409，`PlanRoutes.kt:22` 已映射）。**开发必须先确认没有自动创建照护计划的内部调用者**；若存在，则下沉到 `PlanRoutes` 的 POST 处理层，避免拦住自动化链路，并在计划记录中说明。→ 实施结论：`PlanService.create` 的唯一调用者是 `PlanRoutes` 的 `POST /`；复评修订走另一方法 `createPlanWithItems`，不受影响，故校验落在服务层。
- **D11 健康监测的「入住」下拉列出该长者全部入住（含已离院）。** 理由：体征表自带 `measured_at`，允许补录历史测量并挂到对应那一段入住，正是「多段入住可追溯」的目标；下拉项标注状态与住院号，由操作者显式选择，默认只在「恰有一条 ACTIVE」时预选。残余 R3 不变。
- **D12 医嘱到期「收束」保留原文案。** 027 的「收束已到期医嘱」是另一个语义（收敛 → 已完成），与收费域的「结算收束」无关；本期只改收费域（D6），避免动 027 已交付口径。故 UI 中仍同时存在「结算关账」（收费）与「收束已到期医嘱」（医嘱），二者分属不同域、不再混用同一词。

## 4. 接口与文案契约（跨工作包冻结）

### 4.1 `GET /crate-api/healthcare/v1/bed-occupancy`

- query：`department?`（trim 后精确）、`ward?`（trim 后精确）、`limit`（默认 50，1..100）、`offset`
- 语义：`encounter_type = 'ELDERLY_CARE'` 且 `discharge_date IS NULL OR discharge_date > now()` 的记录（即「当前占用」），按 `department, ward, admit_date` 升序
- 响应：`{ "records": [ { "encounter_id", "encounter_no", "patient_id", "patient_name", "department", "ward", "admit_date", "discharge_date", "status" } ], "meta": { "total": N } }`；空结果仍返回 `records: []`

| 场景 | 状态 | 消息（`{"error": ...}`） |

| 床位被占 | 409 | `bed already occupied: department=<d> ward=<w> encounter_no=<no> until=<ISO8601\|ongoing>` |
| 长者区间重叠 | 409 | `admission interval overlaps existing encounter: encounter_no=<no> until=<ISO8601\|ongoing>` |
| 已有活动入住 | 409 | `patient already has an active elderly admission: encounter_no=<no>` |
| 住院号重复 | 409 | `encounter_no already exists`（既有，不变） |

## 8. 残余风险与未决项

- **R1** 床位仍是自由文本，无主数据。「同一床位不同写法」不会被识别为冲突（D1 取舍）。
- **R2** 床位/区间校验只覆盖 `ELDERLY_CARE`；`INPATIENT`/`OUTPATIENT` 不参与，跨类型抢床不拦。
- **R3** 告警自动挂接依赖「恰有一条 ACTIVE 养老入住」；若长者同时存在多条历史入住而当时无活动入住，仍需操作者显式选择。
- **R4** 药房多明细发药单只扣第一条明细（020 期遗留，不属本期）。
- **R5** 逾期护理执行无自动收敛、全站无提醒/通知（027 明确非目标，需单独立项）。
- **R6** 主体目录接口需要 `identity.admin` 且只取前 100 条；非管理员登录时姓名解析静默回退为 ULID，属既有口径，本期不新增非管理员目录端点。
- **R7** 数量去尾零后，依赖「定长 6 位小数文本」的外部消费者（报表/导出）若存在会受影响；已在 Aceso 客户端与共享类型内确认无此依赖（未检查仓库外消费者）。
- **R8** 真库/E2E 未执行（§6.2）。
- **R9** 并发窗口已按 D1–D3 关闭：三条写路径均在同一事务内先取 `pg_advisory_xact_lock`（床位键 → 患者键固定顺序）**再**发起冲突 SELECT，并有 SQL 顺序断言测试（`AdmissionConflictTest`「床位冲突检查在取得咨询锁之后才发起」「同长者区间重叠检查在取得咨询锁之后才发起」）。该锁为 PostgreSQL 专用原生 SQL（`$1` 占位符、无迁移），若评审认为超出仓内先例可整块回退，回退后并发窗口重新成为残余。

### 8.1 评审（评审角色独立复跑）后确认的残余

- **R15** 主体 ID 渲染点在评审前仍有 3 处同类遗漏；评审后已补齐 `CheckupPage`（转随访计划责任人）、`ChronicDiseasePage`（随访记录人）、`DiningPage`（配餐登记人），全部复用同一个 `useSubjectDirectory`。评审列出的其它同类渲染点若再出现，仍属同一类缺陷。
- **R16** 前端照护计划门禁按**已加载的评估列表**（`period_id` 维度）计数，服务端口径是 `period_id OR encounter_id`；对「评估只带 `encounter_id`」的历史数据，界面可能先给出提示而服务端本会放行（应用内新增评估同时写两者，暴露面有限）。
- **R17** 同一场景的冲突文案跨入口不完全统一：`POST /encounters`（`ELDERLY_CARE`）不调用 `ensureNoActiveElderlyAdmission`，另有「`status=ACTIVE` 但已填 `discharge_date`」的既有异常行只能靠 V501 兜底，故存在第三种文本；决定一致（都是 409），仅排障时可见差异。
