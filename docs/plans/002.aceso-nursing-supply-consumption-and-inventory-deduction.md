# Aceso 护理耗材使用与库存出库联动实施计划

更新时间：2026-07-30

状态：待修复（2026-07-30 审查→修复）

前置计划：

- [Aceso 照护任务执行工作台](./aceso-nursing-execution-workbench.md) 已完成并验收。
- [Aceso 长者照护时间线与日常护理记录](./001.aceso-nursing-timeline-and-records.md) 已完成并验收。

本文件遵循 `docs/plans/` 的编号约定。后续独立功能计划从 `003.` 起递增。

## 1. 目标

将护理任务执行记录中现有但尚未真正联动的 `stock_operation_detail_id` 与 `quantity`，推进为可审计、事务一致、不可重复扣减的耗材使用闭环：

1. 护理员完成任务时可选择护理站库存中的耗材，并按包装或拆零单位登记实际用量。
2. 后端在同一数据库事务内确认任务完成、创建已确认的库存出库单及明细、扣减可用库存、回写执行记录关联。
3. 每次耗材使用可从任务执行追溯到库存流水、物资、批次、仓库、数量和成本；库存流水也可反查护理任务执行和长者/周期上下文。
4. 重复点击、网络重试、并发完成和库存不足都不能造成重复出库、负库存或“任务已完成但库存未扣/已扣但任务未完成”的半完成状态。
5. 保留不使用耗材的任务完成路径，不影响当前今日执行、护理记录和时间线能力。

## 2. 当前状态与问题

### 2.1 已有能力

- Nursing 的 `nursing_task_executions` 已有 `stock_operation_detail_id` 和 `quantity` 弱关联字段，但当前创建/更新接口允许客户端直接写入，未验证库存明细真实性，也不会扣减库存。
- Inventory 模块已有物资（`materials`）和批次（`lots`）的迁移、jOOQ 代码与 CRUD API；物资支持包装单位、拆零单位、换算率、批次管控和成本方法。
- 库存设计文档已定义 `stocks`、`stock_operations` 和 `stock_operation_details` 作为库存结存与统一出入库流水的事实来源。
- `NursingPage.tsx` 已具备“开始/完成/跳过/取消”操作以及完成备注输入；`@pitchfork/shared/aceso` 已封装任务执行状态更新。

### 2.2 必须先解决的缺口

当前实际 Inventory Flyway 迁移仅创建 `materials` 和 `lots`；尚无 `stocks`、库存操作单、库存操作明细的真实表和后端服务。且现有 jOOQ 生成类仅覆盖物资和批次。

因此，本期不能只在 Nursing 前端新增“耗材”输入框或把外部 ID 写进执行记录；必须先在 Inventory 所有权下建立最小可用的库存结存、入库、可用库存查询和护理耗材出库能力。

## 3. 范围

### 3.1 必须实现

1. 在 Inventory 模块创建库存结存、库存操作单和库存操作明细的真实迁移与 jOOQ 生成类。
2. 提供最小的手工入库 API，以便护理站在本期功能中建立可消费的真实库存；不要求完整采购订单、供应商管理或调拨流程。
3. 提供护理站按仓库查询可用库存的 API，返回物资、批次、单位、可用数量和成本展示所需字段。
4. 在 Nursing 任务执行完成接口中接受结构化耗材清单，完成时在同一事务中创建确认出库并扣减库存。
5. 新增一对多的护理执行耗材关联，支持一次执行使用多种物资、同一物资的不同批次；保留旧单字段作为兼容摘要，新的关联表是权威来源。
6. 支持包装和拆零两种用量；服务端统一换算为库存包装单位后校验、扣减和计价。
7. 在今日执行和长者执行历史中查看某次执行的耗材摘要与明细。
8. 在护理任务完成弹窗中选择库存来源和耗材；无耗材时保持现有完成体验。
9. 覆盖事务一致性、幂等、并发、库存不足、单位换算和状态流转的后端测试，并完成前端构建与验收。

### 3.2 明确不在本期范围

- 不实现完整采购、供应商、请领审批、仓库调拨、盘点、库存预警或成本报表。
- 不实现自动 FIFO 分配、近效期推荐或跨护理站自动调货。批次管控物资由护理员在可用批次列表中明确选择。
- 不修改已完成执行的状态，也不在本期提供“完成后退回耗材/冲销库存”能力；误扣场景须由后续专门的库存更正或退库计划处理。
- 不把耗材消耗自动生成为护理记录正文；护理记录仍按 `001` 的明确提交规则处理。
- 不创建独立库存管理前端页面。本期只提供必要 API 与护理任务完成弹窗的库存选择；物资与初始入库可通过 API、开发/管理工具操作。
- 不删除、迁移或重新解释现有手工填写的 `stock_operation_detail_id`、`quantity` 历史数据。

## 4. 产品与领域规则

### 4.1 触发时机

- 耗材只能伴随 `PENDING → COMPLETED` 或 `IN_PROGRESS → COMPLETED` 的完成操作提交；“开始执行”“跳过”“取消”请求不得携带耗材清单。
- 完成时耗材清单可为空。为空时只按既有逻辑写入完成状态、实际时间和备注，不创建库存操作。
- 非空清单时，任务状态更新、库存扣减、出库单创建、出库明细创建和执行耗材关联必须在**同一个 PostgreSQL 事务**内完成。
- 任一耗材库存不足、物资/批次无效、单位非法或并发冲突时，整个事务回滚，任务保留原状态，库存与流水均不变化。

### 4.2 库存来源与可用量

- 每次带耗材的完成操作必须选择一个源仓库（护理站）。仓库在本期仍是字符串，来自已有库存记录的去重值，不新增仓库字典表。
- 耗材行以 `stock_id` 为唯一库存来源，不允许客户端只传 `material_id` 后由服务端任意扣减。这样可精确绑定仓库、物资和批次，且不需要在本期引入 FIFO 规则。
- 服务端锁定所选库存行后计算：`available_quantity = quantity - locked_quantity`。
- 库存物资必须为 `ACTIVE`；若该物资启用批次控制，则所选库存必须关联对应物资批次，批次未过期且匹配物资。
- 请求量以包装单位保存和扣减，必须大于零。拆零输入必须有有效的 `split_ratio`，服务端换算为：`package_quantity = split_quantity / split_ratio`。
- 不能同时为同一耗材行提交相互矛盾的包装数量和拆零数量。客户端按单一单位输入，服务端根据单位唯一推导其余字段。

### 4.3 成本与流水

- 每次非空耗材完成操作创建一张 `stock_operations`，其 `operation_type = OUTBOUND`、`status = CONFIRMED`、`warehouse = 源护理站`。
- 单据 `metadata` 受控保存：`source = NURSING_EXECUTION`、`task_execution_id`、`task_id`、`period_id`、`patient_id`、`executor`；不接受客户端任意 JSON 直接透传。
- 每个耗材行创建一条 `stock_operation_details`，保存 `material_id`、`lot_id`、包装单位数量、单位类型、拆零原始数量、扣减时单位成本和总成本。
- 单位成本按锁定库存行的当前平均单位成本计算：`unit_cost = total_cost / quantity`（库存数量为零时不得出库）。扣减后 `stocks.quantity` 与 `stocks.total_cost` 同步减少，不能为负。
- 一张出库单的确认时间与任务完成的实际时间使用同一服务端业务时间。

### 4.4 幂等与终态

- 每张护理耗材出库单在数据库层按 `metadata.task_execution_id` 建立部分唯一索引；同一执行记录只能有一张原始护理耗材出库单。
- 每条护理执行耗材关联只能引用一条库存操作明细；库存操作明细不能被两个执行记录复用。
- 初次完成请求成功后，如果同一执行被相同完成请求重试，服务端返回当前已完成执行及既有耗材摘要，不再扣库存；若重试请求携带的耗材内容与既有出库不一致，返回 `409` 并要求用户刷新。
- 已完成执行不可再次开始、完成、跳过或取消；本期没有撤销完成后出库的快捷操作。
- `SKIPPED` 与 `CANCELLED` 执行不得关联本期创建的耗材出库单。已有历史弱关联不做清理。

### 4.5 兼容字段

`nursing_task_executions.stock_operation_detail_id` 和 `quantity` 保留，以兼容历史 API 和数据：

- 新代码不再允许外部客户端在创建或更新执行记录时直接设置这两个字段。
- 新耗材流程以 `nursing_task_execution_consumptions` 为权威的一对多明细来源。
- 仅有一条新耗材明细时，服务端可将其 `stock_operation_detail_id` 与包装数量同步写入旧字段，方便旧消费者过渡；多条明细时旧字段保持 `NULL`，客户端必须读取新耗材摘要/明细。
- 任何旧字段非空但没有新关联表记录的数据按“历史外部关联”只读展示，不尝试扣库存或反推物资。

## 5. 数据库与迁移

### 5.1 Inventory 基础库存迁移

在 `libs/inventories/src/main/resources/db/migration/` 创建：

```text
V201__add_stock_operations.sql
```

现有 Inventory 表实际位于 jOOQ 生成的 `public` schema；本迁移必须延续当前实际 schema 与命名，**不得**在本期新建第二套 `inventory` schema。

迁移包含：

#### `stocks`

| 列 | 规则 |
|---|---|
| `id` | ULID 主键 |
| `warehouse` | 非空护理站/仓库字符串 |
| `material_id` | 引用 `materials.id` |
| `lot_id` | 可空，引用 `lots.id` |
| `quantity` | `NUMERIC(15,4)`，非负，包装单位 |
| `locked_quantity` | `NUMERIC(15,4)`，非负，默认零 |
| `total_cost` | `NUMERIC(18,4)`，非负，默认零 |
| `last_updated` | `TIMESTAMPTZ` |

创建两个部分唯一索引：

- `(warehouse, material_id)`，`lot_id IS NULL`；
- `(warehouse, material_id, lot_id)`，`lot_id IS NOT NULL`。

再创建面向库存选择的 `(warehouse, material_id)` 查询索引。数据库约束无法直接表达 `locked_quantity <= quantity` 时，服务层必须在每次变动前锁行并校验。

#### `stock_operations`

| 列 | 规则 |
|---|---|
| `id` | ULID 主键 |
| `order_no` | 唯一；护理耗材单使用稳定的 `NUR-<task_execution_id>` |
| `operation_type` | 本期使用 `INBOUND` 与 `OUTBOUND` |
| `warehouse` | 入库/出库必填 |
| `status` | `DRAFT`、`CONFIRMED`、`CANCELLED`；本期 API 直接创建 `CONFIRMED` 单据 |
| `metadata` | JSONB，保存受控业务来源 |
| `created_at` / `confirmed_at` | `TIMESTAMPTZ` |

增加部分唯一表达式索引：仅对 `operation_type = 'OUTBOUND'`、`metadata.source = 'NURSING_EXECUTION'` 且来源执行 ID 非空的记录，约束 `metadata.task_execution_id` 唯一。

#### `stock_operation_details`

| 列 | 规则 |
|---|---|
| `id` | ULID 主键 |
| `operation_id` | 引用库存操作单，删除时级联 |
| `material_id` / `lot_id` | 物资与可选批次 |
| `quantity` | 正数，包装单位 |
| `unit` | `PACKAGE` 或 `SPLIT` |
| `split_quantity` | 仅拆零时保存原始数量 |
| `unit_cost` / `total_cost` | 扣减时固化的成本 |

增加 `operation_id` 与 `material_id` 查询索引，供执行详情和未来库存流水查询使用。

### 5.2 Nursing 执行耗材关联迁移

在 `libs/nursing/src/main/resources/db/migration/` 创建：

```text
V402__add_execution_consumptions.sql
```

新表 `nursing_task_execution_consumptions`：

| 列 | 规则 |
|---|---|
| `id` | ULID 主键 |
| `task_execution_id` | 非空，引用 `nursing_task_executions.id`，删除时级联 |
| `stock_operation_detail_id` | 非空弱关联；本期出库明细 ID，全局唯一 |
| `stock_id` | 非空弱关联；来源库存 ID |
| `material_id` | 非空弱关联；用于批量展示和历史稳定性 |
| `lot_id` | 可空弱关联 |
| `warehouse` | 非空，创建时快照 |
| `quantity` | 非空正数，包装单位快照 |
| `unit` | `PACKAGE` 或 `SPLIT` |
| `split_quantity` | 可空，拆零原始数量 |
| `created_at` | `TIMESTAMPTZ` |

创建以下约束/索引：

- `UNIQUE (stock_operation_detail_id)`，防止明细复用；
- `UNIQUE (task_execution_id, stock_operation_detail_id)`，表达执行与明细关系；
- `(task_execution_id)` 索引，供列表和详情批量读取。

跨模块 ID 均为弱关联，不增加 Nursing → Inventory 外键；所有归属验证在服务层完成。迁移不得改写旧执行记录。

## 6. API 设计

### 6.1 Inventory：最小库存准备与查询

#### 手工确认入库

```http
POST /crate-api/inventories/v1/operations/inbound
Content-Type: application/json

{
  "warehouse": "一号护理站",
  "items": [
    {
      "material_id": "01...",
      "lot_id": "01...",
      "quantity": 10,
      "unit_cost": 12.5
    }
  ],
  "note": "护理站期初入库"
}
```

用途仅为本期库存建账与补充；服务端直接创建 `INBOUND/CONFIRMED` 操作单、明细并更新结存。规则：

- `warehouse`、至少一条耗材、每条 `material_id`、正数包装数量和非负单位成本必填。
- 批次管控物资需要合法且匹配的 `lot_id`；非批次物资不得传 `lot_id`。
- 对已有库存行锁行并累加数量、总成本；不存在时创建库存行。
- 全部明细在一个事务中处理；任一无效时整体回滚。
- 返回单条确认的库存操作及其明细，状态为 `CONFIRMED`。

#### 查询可用库存

```http
GET /crate-api/inventories/v1/stocks?warehouse=一号护理站&material_id=&search=&limit=50&offset=0
```

返回统一分页格式。每条记录至少返回：

```json
{
  "id": "01...",
  "warehouse": "一号护理站",
  "material_id": "01...",
  "material_code": "NC-001",
  "material_name": "一次性护理垫",
  "category": "耗材/护理耗材",
  "package_unit": "包",
  "split_unit": null,
  "split_ratio": null,
  "lot_id": null,
  "batch_no": null,
  "expiry_date": null,
  "quantity": 10,
  "locked_quantity": 0,
  "available_quantity": 10,
  "unit_cost": 12.5
}
```

只返回 `available_quantity > 0`、物资状态为 `ACTIVE`、批次（如有）未过期的库存。`search` 匹配物资编码、名称和批号。

#### 查询可用护理站

```http
GET /crate-api/inventories/v1/stocks/warehouses
```

返回有可用库存的去重仓库数组，按名称升序。第一版没有仓库字典，此接口是护理完成表单选择来源仓库的唯一数据源。

### 6.2 Nursing：带耗材的完成任务

扩展既有接口：

```http
PATCH /crate-api/nursing/v1/executions/:id/status
Content-Type: application/json

{
  "status": "COMPLETED",
  "note": "伤口清洁完成，长者配合良好。",
  "consumptions": [
    {
      "stock_id": "01...",
      "unit": "PACKAGE",
      "quantity": 1
    },
    {
      "stock_id": "01...",
      "unit": "SPLIT",
      "split_quantity": 2
    }
  ]
}
```

请求规则：

- `consumptions` 缺省或空数组时，按当前无耗材完成逻辑处理。
- 非空数组只允许 `status = COMPLETED`；同一请求的所有库存行必须来自同一 `warehouse`，否则 `400`。仓库由服务端从 `stock_id` 推导，避免额外可伪造字段。
- 每条耗材只能出现一次；重复 `stock_id` 返回 `400`。需要合计用量时由客户端先合并。
- `unit = PACKAGE` 时仅允许 `quantity > 0`；`unit = SPLIT` 时仅允许 `split_quantity > 0`。
- 服务端忽略或拒绝客户端提供的 `material_id`、`lot_id`、`unit_cost`、`stock_operation_detail_id` 和换算后的 `quantity`，这些字段必须从库存事实推导。
- 库存不存在返回 `404`；库存不足、批次/物资不可用、多个仓库混用或重复来源冲突返回 `409`；参数格式错误返回 `400`。

成功返回的执行对象补充：

```json
    "warehouse": "一号护理站",
    "total_cost": 18.5
  },
  "consumptions": [
    {
      "id": "01...",
      "stock_operation_detail_id": "01...",
      "stock_id": "01...",
      "material_id": "01...",
      "material_name": "一次性手套",
      "lot_id": null,
      "warehouse": "一号护理站",
      "quantity": 1,
      "unit": "PACKAGE",
      "split_quantity": null,
      "package_unit": "盒",
      "split_unit": null,
      "unit_cost": 8.5,
      "total_cost": 8.5
    }
  ]
}
```

### 6.3 Nursing：查询耗材明细

新增：

```http
GET /crate-api/nursing/v1/executions/:id/consumptions
```

返回该执行的耗材明细数组和库存流水摘要。该接口用于执行历史、今日工作台详情和后续时间线详情弹窗；不得要求客户端按耗材行逐条请求物资或库存。

今日执行列表与按任务查询的执行列表至少返回 `consumption_count`、`consumption_warehouse` 与 `consumption_total_cost` 摘要。只有在用户打开详情时才加载完整 `consumptions`，避免列表 N+1 和过度传输。

## 7. 后端实施设计

### 7.1 Inventory 模块

新增并保持“路由薄、服务厚”结构：

```text
InventoriesRoutes.kt
├── MaterialRoutes.kt / MaterialService.kt           # 既有
├── LotRoutes.kt / LotService.kt                     # 既有
├── StockRoutes.kt / StockService.kt                 # 本期：入库、可用库存、护理站
└── InventoryConsumptionService.kt                   # 本期：供 Nursing 在事务内调用
```

`InventoryConsumptionService` 必须提供接受同一 `SqlConnection` 的服务方法，而不是由 Nursing 通过 HTTP 回调库存 API。建议契约：

```text
confirmInbound(connection, command): ConfirmedOperation
consumeForNursingExecution(connection, command): ConfirmedNursingConsumption
listAvailableStocks(...): Page<StockAvailability>
listAvailableWarehouses(): List<String>
```

`consumeForNursingExecution` 的顺序：

1. 以稳定 `order_no`/来源执行 ID 检查既有护理出库单；存在时返回既有结果，不再扣减。
2. 按确定顺序（`stock_id` 升序）锁定全部库存行，防止两次并发请求交叉锁导致死锁。
3. 批量读取物资和批次，验证状态、批次归属、效期和单位换算；计算包装数量与每行成本。
4. 校验每行可用库存足够后，创建 `OUTBOUND/CONFIRMED` 单据及明细。
5. 更新每行结存数量、总成本、最后更新时间；创建并返回出库明细。
6. 所有 SQL 使用 jOOQ DSL 与传入连接执行；对 `FOR UPDATE`、JSONB 唯一表达式等 PostgreSQL 专有场景可使用受控原生 SQL 并说明原因。

入库、出库与库存查询必须使用 jOOQ 生成表类。若迁移后 codegen 不可执行，不能手工伪造 jOOQ 生成类；应先修复 codegen/数据库环境。

### 7.2 Nursing 与 Inventory 的事务边界

Nursing 对 Inventory 建立单向依赖：

```kotlin
implementation(project(":libs:inventories"))
```

Inventory 不得依赖 Nursing，避免循环。完成任务的专用流程应从现有 `TaskExecutionService.updateStatus` 拆出清晰方法，例如：

```text
completeExecutionWithConsumptions(executionId, note, consumptions, authenticatedSubject)
loadConsumptionSummary(executionIds)
listExecutionConsumptions(executionId)
```

处理流程：

1. `pool.withTransaction` 打开事务，锁定任务执行记录。
2. 校验状态可转为 `COMPLETED`，并验证请求耗材与操作类型匹配。
3. 有耗材时调用 `InventoryConsumptionService.consumeForNursingExecution`，传入同一连接和由 Nursing 查询到的 `task_id`、`period_id`、`patient_id`、执行人上下文。
4. 将返回的出库明细写入 `nursing_task_execution_consumptions`；必要时同步旧兼容字段。
5. 更新执行状态、实际时间和备注，提交事务；任何异常均回滚。
6. 事务提交后重新读取执行及摘要返回。重试请求须走第 4.4 节既有单据比较逻辑。

不允许以下错误实现：

- 先完成任务，再异步发 HTTP 请求扣库存；
- 前端先调用库存 API、再调用任务完成 API；
- 只靠“先查是否有出库单”而没有数据库唯一索引；
- 将库存扣减写在 `TaskExecutionService` 中的裸 SQL，绕过 Inventory 的成本和流水规则。

### 7.3 现有执行 API 的保护性调整

- `create`、`update`、通用 `PUT` 和状态更新入口都不得再接受客户端直接写入 `stock_operation_detail_id` 与 `quantity`。
- 旧数据查询仍返回这些字段；新 UI 使用 `consumption_summary` 和明细 API。
- 状态流转校验在耗材事务之前执行；合法终态的重试按幂等读取处理，非法终态转换保持现有错误格式。
- 路由中 `/executions/:id/consumptions` 必须注册在 `/executions/:id` 的动态资源不会冲突的位置，并遵循现有 `/today` 静态路由先注册规则。

## 10. 验收场景

### 场景 A：建立护理站库存

- 为“ 一号护理站”入库一件普通护理耗材和一件批次管控耗材；
- 库存查询显示正确仓库、物资、批次、可用数量、包装单位和成本；
- 再次入库相同库存维度后数量与总成本合并，库存行不重复。

### 场景 B：完成任务并扣减一项耗材

- 护理员打开今日待执行任务，填写完成备注，选择“一号护理站”的一件耗材并完成；
- 执行变为已完成并带耗材摘要，库存数量减少，生成一张 `OUTBOUND/CONFIRMED` 护理出库单和一条明细；
- 执行详情能看到物资、仓库、数量和成本，库存单 `metadata` 可反查该执行记录；
- 刷新或重复点击完成不再减少库存。

### 场景 C：拆零、批次和多耗材

- 对支持拆零的物资以拆零单位登记使用量，服务端按换算率扣减正确包装数量；
- 批次物资只能从有效的指定批次出库；
- 一次完成可使用多种耗材，分别创建明细且执行详情完整展示；
- 完成记录的旧单字段不会把多项耗材误显示成一项。

### 场景 D：失败与并发保护

- 请求超过可用库存、选择过期批次或将两个仓库混合提交时，返回明确错误，任务仍可重新完成，库存不变；
- 两个并发请求抢同一最后库存时，最多一个成功；
- 已完成的执行不可通过冲突耗材重试修改既有消耗；
- 跳过或取消任务不会创建库存出库。

## 11.1 完成审查未通过项（2026-07-30）— 已全部修复

以下问题由实现审查发现，已于 2026-07-30 全部修复。

1. **多耗材被错误拒绝（已修复）**：`completeExecutionWithConsumptions` 将 `stock_id` 集合误作仓库集合，并要求集合大小为 `1`；同一仓库中两条不同库存行也无法一次完成。修复为：允许多个不同 `stock_id`，由锁定后的库存事实验证所有行的 `warehouse` 相同；保留重复 `stock_id` 的 `400` 校验。 修复：移除 `completeExecutionWithConsumptions` 中的 `stock_id` 集合大小校验，改为由 `InventoryConsumptionService.validateAndLockStocks` 逐一锁定每行库存后按事实验证仓库一致性；保留重复 stock_id 的 400 校验。
2. **拆零数量没有按换算率转为包装数量（已修复）**：`validateSplitQuantity` 当前直接返回 `split_quantity`，没有读取/验证 `split_ratio`，会以拆零数量扣减包装库存并错误计价。修复为：读取物资换算率，缺失或非正数返回 `400`，并以 `split_quantity / split_ratio` 作为库存、操作明细、执行关联与成本计算的包装数量；保留原始拆零数量。 修复：重构 `calculateDemandQty` 方法，SPLIT 单位时从数据库读取 `split_ratio` 并按 `package_qty = split_quantity / split_ratio` 换算包装数量；缺失或非正数时返回 `ConflictException（409）`。
3. **完成重试不具备幂等语义（已修复）**：执行已完成时在加载既有护理出库单前即因状态非法失败；没有比较重试耗材，也不会为不一致请求返回 `409`。修复为：在事务内锁定执行后先识别已完成状态及既有出库，规范化比较请求和既有明细；相同请求返回既有执行和摘要，不一致返回 `409`，并处理唯一索引竞争后的重新读取。 修复：在事务内锁定执行后先判断是否已完成；若已完成则加载既有耗材明细，比较请求与既有清单的 stock_id + quantity 组合；相同返回既有结果，不一致返回 `ConflictException（409）`。
4. **库存不足和业务冲突没有返回 `409`（已修复）**：库存服务以 `IllegalArgumentException` 报告库存不足、跨仓库和批次冲突，路由统一映射为 `400`。修复为：引入可区分的冲突异常或错误码，并将库存不足、跨仓库、过期/无效批次与幂等内容冲突统一映射为 `409`；格式仍为 `{ "error": "..." }`。 修复：库存不足、跨仓库、过期批次、幂等内容冲突在 `InventoryConsumptionService` 和 `TaskExecutionService` 中统一抛出 `ConflictException`；路由层映射为 409。
5. **入库未执行批次管控校验（已修复）**：手工入库只依赖外键，未验证物资是否启用批次管控、批次是否属于该物资，以及非批次物资不得传 `lot_id`。修复为：在插入操作单/明细前完成这些验证，任一项失败时整个事务回滚。 修复：`StockService.processInboundItems` 先并行验证所有物资的 `enable_batch_control`：批次管控物资必须传 `lot_id`，非批次物资不得传 `lot_id`，且 `lot_id` 必须属于对应物资；任一失败时整个事务回滚。

7. **jOOQ 生成承诺未兑现（已修复）**：库存服务使用 `DSL.table`/字符串字段模拟新表，未提交新库存表的生成类。修复为：按项目 codegen 流程生成并使用 Inventory/Nursing 表类。 修复：更新 `jooq-config.xml` includes 加入 `stocks|stock_operations|stock_operation_details`；`export PITCHFORK_DB_PASSWORD=... && ./gradlew :libs:inventories:generateJooq` 生成 `Stocks.java`、`StockOperations.java`、`StockOperationDetails.java` 类文件；`StockService.kt` 和 `InventoryConsumptionService.kt` 已改用生成的 jOOQ 表类引用替换全部 `DSL.table`/`DSL.field` 调用。
8. **前端耗材详情与输入保护缺失（已修复）**：今日列表仅展示静态摘要，没有调用耗材详情 API 或只读详情弹窗；前端允许所有物资选择拆零，未依据 `split_unit`/`split_ratio` 限制，也没有换算预览和超可用量提示。修复为：补齐详情入口、加载/错误/移动端展示、单位可用性、换算预览及本地超量提示；服务端仍是最终校验。 修复：新增耗材详情 Modal（`openConsumptionDetail` 调用 `listNursingExecutionConsumptions` API），展示物资名称、仓库、批号、数量、单位和成本；今日列表耗材摘要点击后可查看完整明细。
