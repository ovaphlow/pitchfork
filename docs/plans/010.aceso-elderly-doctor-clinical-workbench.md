# Aceso 福利院医生诊疗工作台：病程记录、诊断、处方与检查医嘱实施计划

更新时间：2026-08-08

状态：开发候选版本（默认验证通过，待用户手测与后置隔离库/浏览器验收）

## 编号与前置计划

本文件是面向福利院场景的下一项医疗主线计划。它不继续扩展护理领域，而是在既有入住、照护和医嘱能力之上，补齐医生日常诊疗工作台。

前置能力：

- 005 已建立活动 `ELDERLY_CARE` 入住与精确护理周期关系，并支持离院收束；
- 006 已提供离院照护档案归档与交接摘要；
- 008 已实现 `medical_orders` 的基础开立、查询、状态变更，以及用药/治疗医嘱到护理执行任务的现有联动；
- 009 已实现候选版本，用户后续手动验证定期复评与照护计划修订；本计划不修改 009 的护理计划修订生产代码；
- Healthcare 的 V500 已建立 `progress_notes`、`diagnoses`、`medical_orders` 和 `medical_records` 基础表，但普通医生病程记录和诊断尚未形成 API/UI 闭环；
- 当前 Aceso 已有医嘱页面，但药房页面和检查管理页面仍为占位，不在本计划内实现完整药房或检查科室流程。

旧的 `service-vertx-kotlin/libs/healthcare/database.md` 仍保留早期 `orders`/`order_items` 草案；实际运行迁移和当前代码以 V500 的 `medical_orders` 为准。本计划不同时创建第二套 `orders` 表，也不把旧草案直接迁回生产代码。

## 1. 目标与业务主线

福利院医生的第一版工作台需要能够围绕一位活动入住老人完成以下连续工作：

```text
选择活动入住老人
→ 查看当前入住和既往诊疗资料
→ 书写医生病程记录
→ 录入诊断
→ 开立用药医嘱
→ 开立治疗医嘱
→ 开立检查/检验医嘱
→ 刷新后继续查看同一入住的完整诊疗历史
```

本计划的目标不是建设完整 HIS，而是让医生可以在 Aceso 页面上完成每天最主要的记录和开嘱操作，并把数据精确挂在当前 `encounter_id` 下。

## 2. 范围

### 2.1 必须实现

1. 提供福利院医生诊疗页面，能够选择活动 `ELDERLY_CARE` 入住；
2. 提供当前入住范围内的医生病程记录创建、列表和详情读取；
3. 提供当前入住范围内的诊断创建、列表和详情读取；
4. 复用现有 `medical_orders`，在同一页面开立 `MEDICATION`、`THERAPY`、`EXAMINATION` 和 `LAB_TEST` 医嘱；
5. 增加长期/临时医嘱的明确区分；
6. 医嘱类型、医嘱周期和执行频次保持三个独立维度：
   - `order_type` 表示用药、治疗、检查或检验；
   - `order_class` 表示长期或临时；
   - `frequency_code` 表示 QD、BID、PRN、STAT 等执行方式；
7. 服务端验证病程、诊断和医嘱都属于请求中的精确 `encounter_id`，不能按 `patient_id` 猜测其他入住；
8. 活动入住可以新增医生记录、诊断和医嘱；已离院、已去世或其他非活动入住只允许读取历史，不允许新增；
9. 页面刷新后仍能看到病程记录、诊断和医嘱，且不同老人、不同入住之间不串数据；
10. 保留现有 008 医嘱 API 的 `order_type` 稳定代码：`MEDICATION`、`THERAPY`、`EXAMINATION`、`LAB_TEST`。中文“用药医嘱”等仅作为 UI 展示标签，不把中文展示文案写入 `order_type`；
11. 通过默认非数据库测试、Aceso Kotlin 编译、Aceso 前端构建和 `git diff --check`，交付可人工操作的页面候选版本。

### 2.2 明确不在本期范围

- 不新建 `prescriptions`、`medication_orders`、`examination_orders`、`lab_orders` 或 `therapy_orders` 四套独立主表；
- 不把 `order_type` 改成 JSON 数组，例如 `['用药医嘱', '长期']`；
- 不重写 008 已有医嘱状态机、护理任务生成或历史医嘱 API 响应；
- 不在本期完成药房药品档案、采购、入库、审方、发药、退药或药房 UI；
- 不在本期完成检查/检验排班、执行、报告录入和结果回写；
- 不新建药品目录或处方多明细模型；药房接入时再根据实际一张处方是否包含多种药品决定是否引入 `medical_order_items`；
- 不实现正式入院记录、出院小结、电子签名、审批、打印/PDF 或完整电子病历模板；
- 不实现 ICD 大型字典、AI 诊断、自动推荐处方或临床规则引擎；
- 不实现护理异常事件、交班、家庭护理、上门排班、护理员统计或质量报表；
- 不修改 009 的复评、计划版本、护理措施和任务生成语义。

## 3. 领域和数据设计

### 3.1 医生病程记录

日常医生书写使用 V500 已存在的 `progress_notes`，不新建重复的医生记录表。

第一版只复用已经存在的 `note_type = DAILY` 表达医生日常病程记录，不在本计划中新增 `PROGRESS` 等未经当前业务确认的枚举值。正式病程文书类型和模板后续另行规划。

每条记录必须包含：

- `encounter_id`；
- `note_type`；
- `content`；
- `physician`；
- `record_time`。

第一版采用追加写入和只读历史语义，不提供直接覆盖、删除或复杂版本编辑。若医生发现错误，后续可另行设计更正语义，不在本计划内擅自引入“编辑后覆盖原病历”。

正式文书仍使用既有 `medical_records` 作为后续能力。本计划不把日常病程记录和正式入院/出院文书混成一张新表。

### 3.2 诊断

诊断复用 V500 已存在的 `diagnoses`：

- `encounter_id`；
- `diagnosis_type`；
- `icd_code` 可选；
- `diagnosis_text`；
- `diagnosis_date`；
- `physician`；
- `is_major`；
- `metadata`。

福利院第一版至少支持主要诊断和次要诊断展示/录入。服务端不得接收客户端伪造的患者或入住归属；诊断归属由路径 `encounter_id` 推导。

本计划不建立 ICD 字典，不要求医生必须填写 ICD 编码；有编码时保存，没有编码时仍允许保存文本诊断。

### 3.3 医嘱分类

医嘱的三个维度必须分开：

| 维度 | 字段 | 稳定值/示例 | UI 展示 |
|---|---|---|---|
| 业务类型 | `order_type` | `MEDICATION`、`THERAPY`、`EXAMINATION`、`LAB_TEST` | 用药医嘱、治疗医嘱、检查医嘱、检验医嘱 |
| 持续周期 | `order_class` | `LONG_TERM`、`TEMPORARY` | 长期医嘱、临时医嘱 |
| 执行方式 | `frequency_code` | `QD`、`BID`、`PRN`、`STAT` | 每日一次、每日两次、按需、立即 |

`MEDICATION` 和“长期”不能放进同一个数组，因为它们不是同一业务维度。`order_type` 是稳定的既有 API 代码；中文标签由前端映射或服务端只读派生，不参与业务判断。

### 3.4 `order_class` 迁移策略

在现有 `medical_orders` 增加最小列：

```sql
order_class VARCHAR
```

允许值为：

- `LONG_TERM`；
- `TEMPORARY`。

为保留历史 008 医嘱，若数据库中已有没有周期标记的历史记录，迁移阶段允许 `NULL`；新建医嘱请求必须明确传入 `order_class`，不得由服务端根据 `duration_days` 或 `frequency_code` 猜测。

如果实际目标数据库没有历史医嘱数据，开发可以将新列收紧为非空；如果存在历史数据，不能擅自把所有旧记录批量标成长期或临时。

`order_class` 的基本规则：

- `LONG_TERM` 必须有开始时间，可没有结束时间；医生停嘱、入住终局或明确结束时停止生成未来执行；
- `TEMPORARY` 必须有明确结束条件：结束时间、持续天数或一次性 `STAT` 执行；
- `PRN`/`STAT` 仍由 `frequency_code` 表示，不能替代 `order_class`；长期备用医嘱允许 `LONG_TERM + PRN`，临时备用医嘱允许 `TEMPORARY + PRN`；
- `status` 继续表示 `ACTIVE`、`DISCONTINUED`、`CANCELLED`、`COMPLETED` 等生命周期，不与长期/临时混用。

### 3.5 第一版不引入医嘱项目表

当前 008 是一条 `medical_orders` 记录派生一条护理任务。本计划保持该语义，不立即引入 `medical_order_items`，避免破坏既有 `nursing_tasks.order_item_id` 关联。

当后续药房确认一张处方需要包含多种药品时，再单独评估：

```text
medical_orders
└── medical_order_items
    ├── medication_details
    ├── therapy_details
    ├── examination_details
    └── lab_test_details
```

该升级不属于本计划，不提前创建空表或同时维护两套医嘱来源。

## 4. API 契约

所有路径位于 `/crate-api/healthcare/v1`，列表响应保持 `{ "records": [], "meta": { "total": N } }`。

### 4.1 病程记录

```text
POST /encounters/:id/progress-notes
GET  /encounters/:id/progress-notes?note_type=&date_from=&date_to=&limit=&offset=
GET  /progress-notes/:id
```

创建请求示例：

```json
{
  "note_type": "DAILY",
  "content": "今日精神状态稳定，食欲一般，继续观察。",
  "physician": "张医生",
  "record_time": "2026-08-05T09:30:00+08:00"
}
```

规则：

- `content` 去首尾空白后不能为空，限制最大长度；
- `physician` 必填；
- `record_time` 缺省时由服务端使用当前业务时间；
- `encounter_id` 不由请求体覆盖；
- 活动养老入住才能创建；
- 读取按照 `record_time DESC` 返回并支持分页。

### 4.2 诊断

```text
POST /encounters/:id/diagnoses
GET  /encounters/:id/diagnoses?diagnosis_type=&limit=&offset=
GET  /diagnoses/:id
```

创建请求示例：

```json
{
  "diagnosis_type": "PRIMARY",
  "diagnosis_text": "高血压",
  "icd_code": "I10",
  "diagnosis_date": "2026-08-05",
  "physician": "张医生",
  "is_major": true,
  "remark": "继续观察血压变化"
}
```

规则：

- `diagnosis_text`、`diagnosis_date`、`physician` 必填；
- `icd_code` 可选，不在本期校验完整 ICD 字典；
- `diagnosis_type` 使用当前项目约定的稳定值，不创建随意的中文同义 code；
- 同一入住可以有多条历史诊断；
- 第一版不提供覆盖式编辑和删除；
- 活动养老入住才能创建，历史入住只读。

### 4.3 既有医嘱接口扩展

保持现有路径和响应形状：

```text
POST /encounters/:id/orders
GET  /encounters/:id/orders
GET  /orders/:id
PATCH /orders/:id/status
```

创建请求增加：

```json
{
  "order_type": "MEDICATION",
  "order_class": "LONG_TERM",
  "order_content": "降压药每日一次",
  "doctor": "张医生",
  "start_time": "2026-08-05T08:00:00+08:00",
  "order_details": {
    "drug_name": "降压药",
    "dose": "1",
    "unit": "片",
    "route": "口服",
    "frequency_code": "QD",
    "frequency_name": "每日一次"
  }
}
```

响应增加：

```json
{
  "order_type": "MEDICATION",
  "order_type_label": "用药医嘱",
  "order_class": "LONG_TERM",
  "order_class_label": "长期医嘱"
}
```

`order_type_label` 和 `order_class_label` 为只读展示字段，不作为查询、状态机或模块联动依据。

## 5. 医嘱类型校验

### 5.1 用药医嘱 `MEDICATION`

允许的 `order_details` 至少包括：

```text
drug_name
dose
unit
route
frequency_code
frequency_name
duration_days
remark
```

本期暂不要求 `material_id`，因为药品目录和药房药品维护不在范围内。药房计划必须在实际接方前补充精确药品关联，不能长期仅依赖自由文本药名。

### 5.2 治疗医嘱 `THERAPY`

至少要求：

```text
treatment_item
```

可选频次、持续天数、部位和备注。

### 5.3 检查医嘱 `EXAMINATION`

至少要求：

```text
item_name
```

可选检查部位、优先级、临床说明和备注。

### 5.4 检验医嘱 `LAB_TEST`

至少要求：

```text
item_name
```

可选标本类型、优先级、是否空腹、临床说明和备注。

未知字段、错误类型或跨类型字段返回 `400`，业务错误仍保持 `{ "error": "<message>" }`。

## 6. 页面设计

优先复用并扩展现有 `/dashboard/orders`，页面产品名称改为“医生诊疗”，不新建孤立的护理或药房页面。

页面结构：

```text
医生诊疗
├── 活动入住选择
├── 老人/入住摘要
├── 病程记录
│   ├── 新增病程记录
│   └── 历史记录
├── 诊断
│   ├── 新增诊断
│   └── 历史诊断
└── 医嘱
    ├── 用药医嘱
    ├── 治疗医嘱
    ├── 检查医嘱
    └── 检验医嘱
```

交互要求：

- 默认加载活动 `ELDERLY_CARE` 入住；
- 从入住管理或护理档案跳转时，可以通过 `encounter_id` 预选老人；
- 新增记录、诊断或医嘱期间禁用对应提交按钮，防止重复提交；
- 请求失败保留表单输入并显示清晰错误；
- 保存成功只刷新当前入住的对应列表，不重置其他筛选；
- 长期/临时医嘱使用明确单选控件；
- `order_type` 的英文 code 不直接显示给医生，页面显示“用药医嘱”等中文；
- 已离院、已去世入住隐藏新增操作，但允许查看历史；
- 桌面端和窄屏下表单、列表、详情都可操作，长文本不得溢出或重叠。

## 7. 实施顺序

1. 核对 V500 实际生成源、`HealthcareService`、`MedicalOrderService`、现有 `OrdersPage` 和 Shared API 类型；不按旧 `database.md` 创建第二套医嘱表。
2. 新增 V506 `order_class` 最小迁移，并在有历史数据时保留空值兼容；更新受影响的 jOOQ 生成源。
3. 在 Healthcare 增加病程记录的创建、列表、详情服务和路由，复用 `progress_notes`。
4. 在 Healthcare 增加诊断的创建、列表、详情服务和路由，复用 `diagnoses`。
5. 扩展现有 `MedicalOrderService` 的 `order_class` 校验、读写和响应映射，保持既有四类 `order_type` code 及医嘱任务联动。
6. 增加 Shared API 类型和客户端，前端只通过 Shared API 调用 Healthcare。
7. 将 `OrdersPage.tsx` 扩展为医生诊疗工作台，复用现有医嘱表单并新增病程、诊断区块。
8. 增加非数据库输入校验和路由行为测试。
9. 执行默认后端定向测试、Aceso 编译、前端构建和 diff 检查。
10. 交付可人工操作页面，由用户手动走查医生主线；手测反馈后只修复实际复现的问题。

## 8. 验收口径

### 8.1 后端和数据

- 活动福利院入住可以创建 `DAILY` 医生病程记录；
- 活动福利院入住可以创建主要/次要诊断；
- 活动福利院入住可以创建四类既有医嘱；
- 新建医嘱必须明确 `order_class`；
- 长期医嘱和临时医嘱返回不同的周期字段；
- `PRN`/`STAT` 仍作为频次/执行方式，不会覆盖 `order_class`；
- 现有医嘱任务派生和状态联动不回归；
- 不同老人、不同入住的病程、诊断和医嘱严格隔离；
- 已离院/已去世入住新增请求失败且无副作用；
- 读取操作不创建任务、不修改库存、不调用药房；
- 旧的未标注医嘱不会被迁移脚本擅自猜成长期或临时。

### 8.2 页面手测

使用一位活动入住老人完成：

1. 新增一条医生病程记录；
2. 新增一条主要诊断；
3. 新增长期用药医嘱；
4. 新增临时治疗医嘱并填写持续天数；
5. 新增检查和检验医嘱；
6. 刷新页面后确认上述数据仍然存在；
7. 切换另一位老人，确认不显示第一位老人的数据；
8. 访问已离院或已去世入住，确认只能读取、不能新增。

## 9. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 把 `order_type` 改成中文或 JSON 数组 | 破坏 008 现有 API、查询和模块联动 | 保留 `MEDICATION` 等既有稳定 code，中文只做展示标签 |
| 把长期/临时混入 `order_type` | 医嘱类型与持续周期无法独立查询 | 增加独立 `order_class` |
| 通过 duration 推断长期/临时 | 历史数据被错误改写 | 新建请求必填，历史空值不猜测 |
| 现在直接引入 `medical_order_items` | 破坏当前医嘱到 Nursing 任务的关联 | 010 保持一条 medical_order 一条任务，药房计划再评估明细化 |
| 普通病程记录和正式文书混用 | 后续病历归档、签名语义混乱 | 日常记录使用 `progress_notes`，正式文书留待后续 |
| 医生数据按 patient_id 查询 | 多次入住数据串联 | 所有写入和读取以精确 `encounter_id` 为边界 |
| 计划膨胀到药房和检查科室 | 主线交付变慢、角色边界失控 | 药房采购/发药和检查结果另立计划 |
