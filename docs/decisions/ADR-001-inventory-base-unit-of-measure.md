# ADR-001：库存以最小可发放／可消耗单位记账

- 日期：2026-08-02
- 状态：已确认（2026-08-09 由计划 016 收敛为基础数量优先与包装规格辅助）
- 决策范围：Aceso Inventory、Pharmacy、Nursing 的库存余额、库存流水、发药、耗材消耗、退回与成本核算。
- 相关计划：[016. Aceso 库存基础数量优先与包装规格辅助](../plans/016.aceso-inventory-base-unit-only-cutover.md)。

## 采纳记录

- 2026-08-09：[计划 015](../plans/015.aceso-inventory-base-unit-and-packaging-conversion.md) 的包装换算、历史兼容、V202/V407 和 `UnitConversionService` 候选已被替代，不得合并或验收。
- 2026-08-09：[计划 016](../plans/016.aceso-inventory-base-unit-only-cutover.md) 采用本 ADR：库存事实与默认后端请求／响应均为基础数量；`package_unit + package_size` 仅保留为物资展示和盘点辅助。计划中的默认验证已执行；隔离 PostgreSQL、E2E 与浏览器验收按用户指示跳过，尚未构成最终验收。

## 背景

当前库存与护理耗材方案以包装单位保存结存，在拆零使用时通过 `split_ratio` 折算包装数量。这能支持基础耗材扣减，但在以下场景会使库存事实难以阅读或校验：

- 药房按粒、片、支、瓶或毫升进行部分发药；
- 耗材按双、枚、片等实际使用单位消耗；
- 未给药或未使用部分需要退回库存；
- 包装规格变化、盘点、批次追溯与单位成本核算需要复现历史换算；
- 以 `0.5` 盒或 `0.0417` 箱表示余额会产生精度、尾差与操作歧义。

库存模型需要同时满足临床可操作性、账实可核对性和不可变流水审计，而不是只优化采购入库的整包录入体验。

## 决策

### 1. 基础记账单位

库存余额、可用量、锁定量、出入库明细、退回量和单位成本均以物资定义的**基础单位**记账。

基础单位定义为“最小可合法发放或可实际消耗的单位”，不机械等同于物理上可以无限拆分的最小单位：

| 物资类型 | 基础单位示例 | 说明 |
|---|---|---|
| 口服固体药品 | 粒、片、袋 | 按实际可发药单位记账；仅在物资明确允许时才可半片或更小分量。 |
| 注射药品 | 支、瓶、预充针 | 一支或一瓶一旦启封不能退回时，其本身是基础单位。 |
| 口服液、消毒液 | 毫升 | 仅在业务允许按体积分装或消耗时采用。 |
| 护理耗材 | 双、枚、片、支 | 以临床实际领用／消耗单位记账。 |
| 无菌组合包装 | 最小无菌包装 | 若拆包后不能安全回库，不得将内部单件作为基础单位。 |

每个物资只能有一个有效基础单位。存在流水后，基础单位不得直接修改；包装规格或单位策略变更必须通过受控换算或新物资档案处理。

### 2. 包装规格与基础数量优先

物资可选维护包装规格，用于页面展示和盘点辅助，例如“盒、包、箱、瓶”。每种规格定义为到基础单位的正向、精确关系：

```text
1 盒阿莫西林 = 24 粒
1 箱阿莫西林 = 20 盒 = 480 粒
1 盒手套 = 50 双
```

库存事实、默认后端请求和默认后端响应只使用基础数量，绝不以“零点几盒”或“零点几箱”作为库存、锁定、流水或成本的权威值。页面可把基础数量显示为“2 盒 + 5 粒”，或把盘点辅助输入的整包数和余数换算为基础数量；常规 API 只提交和返回该基础数量。

未来若确有专门的整包输入需求，必须使用显式接口并由服务端依据受控的物资包装规格精确换算。客户端不得传换算率、包装成本或伪造的基础数量；服务端返回的基础数量仍是权威值。旧 `PACKAGE` / `SPLIT` 枚举、`split_unit`、`split_ratio`、单位规格 ID 和历史兼容投影不再保留。

### 3. 数量精度与拆分约束

所有库存数量使用 `NUMERIC`，禁止使用二进制浮点数。每个物资还必须定义可接受的基础数量精度：

- 粒、支、枚、片、双等默认只允许正整数；
- 液体可按物资配置小数位，例如 `0.001 mL`；
- 只有物资明确标记为可拆分时，才允许 `0.5` 片等非整数数量；
- 系统必须在换算后按该物资精度校验，不能静默四舍五入。

所有 API 的数量和金额字段以十进制文本传输，例如 `"48"`、`"0.125"` 和 `"12.50"`；不得将 `NUMERIC(20,6)` 或成本先转换为 JSON `number` / `Double`。服务端从该文本构造 `BigDecimal`，按物资的 `quantity_scale` 和数据库成本精度拒绝超精度值。

### 4. 成本、批次和不可变流水

- 库存结存按“仓库 + 物资 + 批次（可空）”保存基础数量与总成本。
- 单位成本是每一个基础单位的成本；常规入库、出库和退回直接提交／保存基础单位成本，出库与退回固化当时的成本快照。
- 批次、效期、物资状态、可用数量和并发锁定均按基础数量校验。
- 发药、耗材消耗、退药、报损和库存更正只能创建新的库存操作与明细；不得修改或删除既有确认流水。
- 退药必须引用原发药／领用明细，并校验未退数量。已给药、已启封、污染或报损的数量不得作为可用库存退回。

### 5. 医嘱、发药与护理执行的边界

药房发药与护理给药是两个独立业务动作：

```text
医嘱有效 → 药房发药／库存出库 → 护理执行给药 → 未使用药品退回或报损
```

- 只有有效的 `MEDICATION` 医嘱可以发药。
- 发药明细必须精确关联医嘱，并记录仓库、批次、基础数量、成本与操作者。
- 发药不得自动将护理任务或护理执行标记为完成；实际给药、拒服、漏服和浪费属于后续护理给药闭环。
- 医嘱停嘱、作废、离院或去世后禁止新的发药；已发未用数量依照退药／报损规则处理。

## 后果

### 正面影响

- 部分发药、部分领用、部分退回和盘点差异使用同一数量语言，账实容易核对。
- 批次追溯、效期控制、可用量判断、并发扣减和成本计算不必依赖小数包装数量。
- 前端可按“2 盒 + 5 粒”展示或辅助盘点，但服务端始终接收、返回并保存一个确定的基础数量。
- 后续 Pharmacy、Nursing 与库存更正可共用同一事实账本。

### 代价与控制措施

- 物资档案需要维护可选包装规格和可拆分精度；页面展示／盘点辅助会更复杂，但不能扩散到库存事实或药房／护理业务单位。
- 基础单位不合理会直接影响临床操作，因此必须由业务人员确认药品和无菌耗材的可拆分规则。
- 包装变更会需要版本化或换算快照；禁止覆盖历史规格。
- 同一物资的不同批次与不同包装规格仍必须换算到同一基础单位后才能合并结存。

## 与现有计划的衔接

### 002：护理耗材与库存扣减

`002` 当前将包装单位数量作为结存与扣减口径，并用 `split_ratio` 支持拆零。该已实现方案不得通过修改旧 Flyway 迁移或重解释历史流水来强行改变语义。

本 ADR 的后续实现由计划 016 完成以下未发布基线重建：

1. 从空库重写 Inventory、Pharmacy 和 Nursing 的未发布基线，使基础数量成为唯一库存事实；
2. 保留物资可选 `package_unit + package_size`，但不建立包装数量、包装成本、换算率或历史兼容投影；
3. 让新入库、出库、发药、退药、申领、收货和护理耗材默认只读写基础数量与每基础单位成本；
4. 在独立、可清理数据库上验证库存余额、成本、批次、幂等、并发和事务回滚；不得用全局 Flyway `outOfOrder` 解决版本问题。

### 后续 Pharmacy 发药与退药计划

建议该计划以本 ADR 为前提，并至少落实以下验收要求：

1. 仅 `MEDICATION`、`ACTIVE` 的医嘱可创建发药；状态或终局收束冲突不产生任何库存写入。
2. 一张发药单可从一个或多个明确库存批次发出基础数量；库存不足、批次失效、重复提交或并发竞争必须全量回滚。
3. 发药单、发药明细、库存出库和医嘱关联共用同一事务；每条发药明细保存基础单位、基础数量和成本快照。
4. 全退与部分退均创建反向库存流水，累计退回不得超过原始可退数量；不修改历史发药明细。
5. 护理执行不会因发药自动完成，已给药数量不能作为可用库存退回。
6. PostgreSQL 集成测试和浏览器验收须在独立、可清理环境中覆盖基础数量入库、包装展示／盘点辅助、多批次、退药、终局阻断、幂等与并发。

## 非目标

- 本 ADR 不直接修改任何数据库、Flyway 迁移、生产服务、Shared API 或前端界面。
- 本 ADR 不决定采购订单、供应商、调拨、盘点、库存预警、收费结算、电子签名或审批流。
- 本 ADR 不授权把医嘱发药与护理实际给药合并为一个状态机。
